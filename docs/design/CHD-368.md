# CHD-368: the sender's `→` row when a steer went as the next turn

CHD-365 steers a message into the recipient's running turn. When the agent
refuses the steer (Claude's `promptRequired` at the turn's end) or starts a turn
of its own with it (Codex's `startedNewTurn`, which chord cancels), the message
goes as the recipient's next turn. It waited, the same as a message queued from
the start. The sender's row still reads as if the message went straight in.

## What reads wrong today

Taken on main with `CHORD_FAKE_STEERING=codex CHORD_FAKE_STEER_LATE=1
CHORD_FAKE_STEP_MS=60 bun run chord:fake`, scenario `agents`
(`evidence/CHD-368/120x40-main-before.txt`):

```
 → @parser
   ⎿  I changed how a string at the end of a line is read. Run the parser tests now and tell me only what fails.

 → @parser
   ⎿  The printer is fixed too; run the whole parser suite once more.
```

Parser got neither message in a running turn. The first one started a turn of
its own, which chord cancelled. The second was refused because that turn was
already over. Parser took both as separate turns, one after the other
(`evidence/CHD-365/120x40-codex-late-parser.txt`). The sender's tab gives no
sign of this. Elsewhere in chord, `· queued` on a `→` row means "it waited"
(CHD-167, CHD-239), and a row without it means "it went straight in". Here that
reading is wrong twice.

The recipient's `started this on its own` line does not cover it. That line
is in the recipient's tab, which the person may never open. Claude's refusal
leaves no line anywhere. In both cases the sender's tab is the only place that
gets it wrong.

## The shape

The row says what happened. Once chord knows the message went as the next turn,
the row gets the same dim `· queued` that a message queued from the start has:

```
 → @parser · queued
   ⎿  I changed how a string at the end of a line is read. Run the parser tests now and tell me only what fails.

 → @parser · queued
   ⎿  The printer is fixed too; run the whole parser suite once more.
```

80×24: the note is on the name row, which is short, so it never gets cut:

```
 → @parser · queued
   ⎿  I changed how a string at the end of a line is read. Run the parser tests…
```

### The rules

- **One word, the one that exists.** `· queued`, with the tone and position it
  already has. No `· refused`, `· missed the turn` or `· next turn`. To the
  person, the message waited and then went as a turn of its own, and
  `· queued` already means exactly that. Why it waited (the race with the turn's
  end) is for the recipient's tab, and only Codex's case gets a line there.
- **The row changes in place.** It is drawn as `→ @parser` while the steer is
  out, and gains `· queued` when the agent answers `promptRequired` or
  `startedNewTurn`, or when chord refuses the steer itself because the turn was
  sealed. A steer the agent took (`injected`) leaves the row as it is. Usually
  the change comes within one round trip, so it reads like a row settling, not a
  row taking back what it said. The `send_message` tool call does not wait for
  it. The CHD-365 decision that it would cost too much to make every
  `send_message` wait still stands.
- **Every place the row is drawn.** That includes the sender's own tab, a task
  block's `⎿` list (`→ main · queued`, CHD-225), and the folded `▶`/`»` forms.
  They all read the same mark.
- **Replay.** The record keeps the change, so a resumed session draws
  `→ @parser · queued` where the live screen ended. A resumed screen that showed
  less than the live one did would be the same imprecision, only later.
- **Nothing else changes.** The agent's own tool result is not rewritten, since
  it was answered already. The recipient's `←` rows, its `started this on its
  own` line, the queue rows and the agent list stay as they are.
- **Held for the person's answer.** This is out of scope here. A steer that waits
  behind a permission (`after your answer`) still goes into the running turn,
  so a row without `· queued` is true for it. Only if that steer then finds the
  turn over does it go as the next turn, and then it gets `· queued` by the
  rule above.

### States

| State                                     | Sender's row         |
| ----------------------------------------- | -------------------- |
| No turn running, or agent does not steer  | `→ @parser` / `· queued`, as today |
| Steer out, not answered yet               | `→ @parser`          |
| Steer `injected`                          | `→ @parser`          |
| Steer `promptRequired`, `startedNewTurn`, or sealed | `→ @parser · queued` |
| Sender's tab narrow (80×24)               | same; the name row is short |
| Resumed session                           | as the live screen ended |

### Keys

None. Chord learns the outcome on its own. The person does nothing.

### Why

The task's other option was to leave the row and rely on the receiver's line.
That was set aside because the person reads the sender's tab, the one they are
in, and the receiver's line exists only for Codex. An in-place mark that matches
what chord already writes for a queued message costs the person nothing new to
learn. It also stays truthful in the rare race, without making `send_message`
wait.
