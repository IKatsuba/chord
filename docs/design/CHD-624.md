# CHD-624 — the upstream catch-up: dependencies, pins, Claude's new defaults

The owner, 2026-11-13, took every recommendation of
[the survey](evidence/CHD-624/survey.md). This task is the first of two PRs
(D5 a): the dependency bumps, the registry refresh with its fallout (D6), the
Claude adapter's bump from 0.99.1 to 0.107.x, and what that bump changes for
a person: sessions start in Manual again (D1 b) and an idle compaction is
said to be one (D2 a). The new protocol features (`/rename`, the account in
`/status`, initial options for model and effort, notices, the `session`

extras are CHD-630. The drafts this merges are in
[`evidence/CHD-624/drafts/`](evidence/CHD-624/drafts/).

No new key, no new command and no new component. Three things change on
screen: the words of an unasked compaction, the mode a Claude session opens
in (back to 0.99.1's), and the rows of the agent list.

## Two rules over everything

- **One general path, Claude named once.** Initial config options go out
  through a path any agent that advertises `sessionCapabilities.options`
  takes; CHD-629's F3 adds model and effort to the same path without
  changing it. Claude's adapter is named in one table only: its mode config
  id and chord's default start mode for it.
- **The wire is read, never guessed.** chord marks a compaction unasked from
  its own state (no turn, no cycle), not from the agent's words; where the
  adapter sends something chord cannot attribute, chord does not invent a
  rule for it (owner question O1).

## D1 — Claude starts in Manual

### On the wire

When `initialize` advertised `sessionCapabilities.options` and chord knows
the config id, `openSession` adds `configOptions` to the setup request:

```json
{
  "method": "session/new",
  "params": {
    "cwd": "/work/project",
    "mcpServers": [],
    "configOptions": [{ "configId": "mode", "value": "default" }],
    "_meta": { "claudeCode": { "options": { "promptSuggestions": false } } }
  }
}
```

- Shape: `InitialSessionConfigOption`, value form, no `type` (chord does not
  declare boolean options). One entry per config id, so Claude's duplicate
  check (-32602) cannot fire. Order model, effort, mode; in this task only
  mode exists.
- Built by a pure `src/session/initial_options.ts`:
  `initialEntries(init, starting, known)` returns nothing unless `options` is
  advertised, and only entries whose id is known.

| Request | A mode named (settings, `--permission-mode`, a member's mode) | chord's default (Manual) |
| --- | --- | --- |
| `session/new` — window, `/clear`, children, team members, `-p`, `chord acp`'s downstream sessions | sent | sent |
| `session/load`, `session/resume` | sent, as `#applyStarting` already asks on resume | not sent: the adapter restores the session's own mode |
| `session/fork` | set after the fork, as today (fork's entries are schema 1.32, unreleased) | not sent: a fork keeps its source's mode |

### Where the config id and the default come from

A table beside `FAST_OPTIONS` in `src/agents.ts`, keyed by the adapter's
`agentInfo.name` (`CLAUDE_ADAPTER`, `src/session/enrich.ts:30`), not by
chord's agent name, so `agents.<name>.command` running the adapter is
covered too: `{ configIds: { mode: 'mode' }, startMode: 'default' }`, the
ids read from claude-agent-acp's source and rechecked when its pin moves.
`openSession` exposes the default as `session.startDefaults` on a session it
made with `session/new`, nothing on load, resume or fork; callers resolve
`starting.mode ?? session.startDefaults.mode`. A named mode always wins; the
default is never `required`.

CHD-629's F3 extends this: model and effort entries in the same
`initialEntries`, their ids in the same table or, for agents chord has no
row for, from `session/options` where a picker already needs it.

Not taken: `session/options` before every `session/new` — Claude answers it
by starting a throwaway Claude Code query that runs the person's
`SessionStart` hooks, so every start would run Claude and the hooks twice.
Not taken: learning ids from an earlier session — the first session of a
process, the one a person sees, would get nothing.

An agent that does not advertise `options` (every agent but Claude 0.106+,
and a person's own older Claude adapter, which starts in Manual anyway) gets
no entries and no default: named modes are set after new, as today.

### Reading back

Claude applies the entries before it answers, and the answer's `modes` and
`configOptions` are folded into state (`session.ts:616`) with any early
`current_mode_update`. `#applyStarting` (`conversation.ts:3341`) and
`-p`'s asks (`oneshot.ts:136`) stay the read-back and the fallback, with two
changes the critic asked for:

- The mode step reads the session's current mode **at that step**, after
  model and effort were set, not from the setup answer: a model change can
  move the mode. Already current → nothing sent. Otherwise
  `set_config_option`, as today.
- After a fallback the step checks the mode the agent then reports. Still
  not the asked one → today's refusal line, and a `required` mode fails the
  start. `askStarting` today treats any resolved ask as success.

| Agent | What happens |
| --- | --- |
| Takes the entry | no further request, nothing in the transcript |
| Ignores the entry (unknown id, value not offered) | set after new; refusal line if that fails or does not hold |
| No `options` | as today |
| Refuses `session/new` because of the entries | a start failure in the agent's words, as any refused `session/new`; no retry without them (Claude cannot refuse one entry per id, no other agent advertises `options`) |
| Start cancelled mid-`session/new` | aborted by the start's signal; no fallback request |

There is no race with the first prompt and no flash of Auto: `#applyStarting`
runs before `#report` and `connected` (`conversation.ts:3234-3318`), and the
status line shows `Starting claude…` alone until then. The record is
unchanged: its first `state` entry is written after the starting values.

## D2 — "compacted while idle"

### What Claude 0.107 sends

The adapter queues `/compact` as its own prompt 54 minutes after the last
request (1-hour cache, context at least 200k). chord sees, with no request of
its own open and no `PromptResponse`:

```json
{"sessionUpdate":"compaction_update","compactionId":"<uuid>","status":"in_progress"}
{"sessionUpdate":"compaction_summary_chunk","compactionId":"<uuid>","content":{"type":"text","text":"…"}}
{"sessionUpdate":"compaction_update","compactionId":"<uuid>","status":"completed","summary":[…]}
{"sessionUpdate":"usage_update","used":41200,"size":1000000}
{"sessionUpdate":"usage_update","used":41200,"size":1000000,"cost":{…}}
```

or `status: "failed"` with `error`. The trigger (`idle`) goes only to
JetBrains AIR. None of these kinds is in `CYCLE_WORK` (`cycles.ts:68`), so
today they open no cycle: no "working", no OSC 7501, no notification. D2
therefore needs no change to cycles.

Two adapter paths may still forward an `agent_message_chunk` around a
compaction (a `local_command_output`, or `<local-command-stdout>` text), with
nothing on it that ties it to the compaction; whether Claude Code emits one
for `/compact` cannot be read from the packages (the CLI is a separate native
binary). Such a chunk after a quiet second would open a Claude cycle that
stays "working" until the next prompt — today's documented behaviour
(`claudecyclebare`). This design adds no window and no suppression for it:
owner question O1.

### The mark

`Conversation` decides it, once, at a compaction's first update: unasked when
no turn of the person's, no turn of chord's own (`#selfTurnId`), no cycle and
no settling is under way, and the update is not part of a replay. Not an
enricher: the enricher chain knows chord's open requests but not cycles, and
would mark a compaction inside Claude's own cycle as idle.

- The `update` action gains `unasked?: true`; `Compaction`
  (`transcript/types.ts`) gains the same, taken from the opening update in
  `mergeCompaction` and kept by later patches.
- The record carries it explicitly: `RecordEntry`, `updateEntry`
  (`record.ts:1030`) and `recordActions` (`:725`) each pick their fields, so
  each gains it. A round-trip test: live, record, resume, the mark drawn.
  Older records have no field and draw as today.
- A replay by the agent (`session/load` with no record of chord's, Claude's
  replay across compactions) carries no trigger, so its compactions are
  drawn plain. chord does not guess from gaps.
- `chord acp` relays the update as it is; the mark is chord's state, not an
  assertion on the wire, and is not relayed upstream.
- Another client of the same Claude session (Remote Control): whether its
  compaction reaches this adapter process is unknown; if it does, it is
  drawn "while idle".
- The cost stays where every late Claude cost goes today: the last turn's
  line (`turn_costs.ts:227`). The session's sum is right; no record change.
