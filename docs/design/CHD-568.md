# CHD-568: an MCP tool for the settings file

`settings`, one chord tool to read every key and to write an allowlist of them, each write
behind chord's box. Split from CHD-565 by the owner's Q329. The owner's decisions are final:

| Question | Decision |
| --- | --- |
| Q330, how a write is confirmed | chord's box on every write, under any runtime mode |
| Q331, which keys it may write | The allowlist below: kinds A and B. Kind C stays a hand edit |
| Q332, which file, and secrets | The user's file only; `env`, `headers`, `command`, `args` and `url` values masked on read (widened by the owner) |
| Q333, a linked project file (answer replaced by the owner) | Read as a start reads it, links followed, and only checked values returned. No raw file reaches an answer |

CHD-565's board records Q331 as choice 1, Every key. That is a relay error by main, corrected
by a comment there. The decision is the allowlist.

**Why kind C is out.** chord's server runs outside any agent's sandbox or permission mode, so
a write to those keys would let a model choose a command chord runs, or turn off the
person's ok, past every limit the runtime has.

**The allowlist is exactly those leaves.** A new key is closed until it is named here. It binds
`remove` as it binds `set`.

**Kind C, read but never written:** `agents.<name>.command`, `agents.<name>.permissionMode`,
`agents.<name>.mcpServers`, `mcpServers` and all under it, `teamSelection.constraints` and all
under it. A person edits them in the file by hand.

`keybindings.json` and `.mcp.json` are not settings keys and stay out.

## What it takes and answers

A `path` is a list of keys, not a dotted string, as an agent's name may hold a dot.

| Input | Means | Answer |
| --- | --- | --- |
| `{ action: "read" }` | Every key | `{ user, project, effective, problems }` |
| `{ action: "read", path }` | One key | The same, each of them at that key; `problems` the whole list, as they name no key |
| `{ action: "set", path, value }` | Set the leaf at `path` | `{ path, before, after, file, saved, takesEffect, shadowedBy? }` |
| `{ action: "remove", path }` | Remove the leaf, and parents it leaves empty | The same, `after` absent |

- **`action` is explicit, not `value: null` for removal,** because `teamSelection.prefer.model` takes `null` as a real value: its row says `null`, an absent key `not set`. Removing `offeredAgents` is how a person gets the whole catalog back.
- **Same value, or `remove` of an absent key:** nothing asked or written, `saved: false`, `unchanged: true`.
- **`shadowedBy`** names `.chord/settings.json`, only where the project's checked layer holds the leaf, on a changed or an unchanged answer alike. A value the file's check dropped does not win, so it does not count. A user-only key is never shadowed.
- **`before`** comes from the checked user layer, masked as a read is.
- **`file` and every path in an answer** are as shown on screen (`~/.config/…`): the model is not told the person's home.

## Reading and masking

**The read loads with the ordinary `loadSettings`,** follows links as a start does, and returns only
values the schema checked. No raw file reaches an answer. `user`, `project` and `effective` are the
layers' checked settings and their merge; a layer with no usable file is null. `mcpServers` go through
`src/mcp.ts`'s entry schemas, so `token` or `Env` on a server no longer reads. A server that fails its
schema is left out, and, as the row's count holds settings problems alone, it adds none.

A linked project file reads as an ordinary file.

**Masking goes by key name.** Any value under a key named `env`, `headers`, `command`, `args` or `url`
reads `"***"`; a list or object keeps its shape with each leaf masked. A boolean
`agents.<name>.mcpServers` is not one of those keys and stays. A server or an agent merely named
`url` is masked whole.

**Mask first, then walk the path.** This holds in all three, in `read` with a path and on the row.
So `mcpServers.x.env.TOKEN` reads `"***"`, and a path below a leaf is not set.

**`problems` are fixed words by `kind` plus a count, per file,** with no name or word from the file:
Bun's parser quotes what it chokes on, and a key's name is the file's own. Each is
`{ file, message }`, `file` as shown on screen.

| `kind` | `message` |
| --- | --- |
| `validation` | `3 keys ignored`, `1 key ignored` |
| `scope` | `1 key only the user's file may set; ignored`, `2 keys only the user's file may set; ignored` |
| `parse`, the JSON did not parse | `not valid JSON; ignored` |
| `parse`, valid JSON but no object | `not a JSON object; ignored` |
| `parse`, any other | `cannot be used; ignored` |
| `read` | `cannot be read; ignored` |

The row's count is how many of these lines the answer holds. The start-up warnings do not change.

### Stated limits

- A planted link gives its values only under real setting names, so a server's or agent's own name, and an `env` key's name, can reach the model.
- A start's own read has no size cap, and neither does the tool's.

## Validation

In this order; the first problem refuses, nothing is asked or written, and the file stays as it
was. Each line is the answer's `error` and the row, and goes through "Drawing a value".

| Check | The line |
| --- | --- |
| Not on the allowlist | `No setting agents.claude.modle` |
| Kind C | `chord does not write agents.claude.command; edit the settings file by hand` |
| A parent of leaves | `agents.codex is not one setting; name agents.codex.model or agents.codex.effort` |
| The same, `teamSelection` | `teamSelection is not one setting; name teamSelection.intent, teamSelection.prefer.agent or teamSelection.prefer.model` |
| The key's own schema, validated alone | `editorMode cannot be "emacs": <zod's message>` |
| A name chord does not know | `chord knows no agent named "nope"; list_agents names every one` |
| No home | `No settings file without a home directory; nothing was saved` |
| A file that is not JSON | `~/.config/chord/settings.json was not saved: it is not valid JSON` |
| A file that is not an object | `~/.config/chord/settings.json was not saved: it is not a JSON object` |
| A parent that is not an object | `~/.config/chord/settings.json was not saved: its agents is not an object; edit it by hand` |
| Another change is waiting on the person, checked last, after the same-value answer | `Another settings change is waiting on the person; nothing was asked or saved. Ask again once they have answered` |

- **The schema is the key's own,** exported per key, not `parseSettings`: its drop loop turns a wrong array item into a whole file ignored.
- **Names are checked against `knownAgents`** (`src/settings.ts:730`): each of `offeredAgents`, `agent`, `teamSelection.prefer.agent`, and `<name>` in `agents.<name>.*`, as the tool cannot define an agent. `remove` skips the check on `<name>`: it defines nothing, and it is how a stale agent's key leaves.
- **Ids stay unchecked:** `model` and `effort` are the agent's own, and only a started agent knows them, as `src/teams.ts:46` says. A wrong one behaves as it does in the file today.
- **A parent that is not an object** (`"agents": 3`) is not the value at the path, so it is not replaced. `remove` is refused on it too, rather than called absent: the person should hear of it.
- `__proto__`, `constructor` and `prototype` are never keys: `No setting …`.
- **One change waits at a time.** A second `set` or `remove` while one waits on the person is refused: two calls for the same key would draw identical questions over rows the person must match by eye. It comes last, so an invalid or unchanged call still gets its own line. Reads are unaffected.
- **A bad value at the path itself reads `not set`,** as `before` is from the checked layer: a `set` replaces it, and a `remove` is `unchanged`, as there is nothing checked to remove, so the bad value stays for the person's hand and the next start's warning. A bad key elsewhere stays and is reported at the next start, as today.

## Writing the file

`src/AGENTS.md:5` allows settings writes only through `saveTheme` and `saveEditorMode`; it gains
the tool's writer in this PR. The MCP configuration stays read only.

`saveSetting` (`src/settings.ts:870`) sets one top-level user-only key. The new writer takes a
path: read the raw JSON at the yes, set or remove at the path, creating parents, and write it
whole by the same atomic rename. So one agent's `model` keeps that agent's `command`, and every
other key stays. The layout becomes two-space JSON, as `/theme` does. A file gone bad between the
box and the yes is refused by the table's lines, not overwritten. Two windows are last write wins.

## Which file

The user's alone. A project's file outranks it for every kind B key (`mergeSettings`,
`src/settings.ts:382`), so where it holds the key, a write changes nothing in this directory.
The tool still writes, as it is the person's setting everywhere else, and the row warns.

## Callers and `-p`

Main alone: `toolsOf`'s `person` case and `toolNames('person')`, with the fork refusal, as
`propose_team`. Long-lived children, leads, members and tasks do not get it. Under `-p` the tool
does not exist, as chord's server starts only for a window (`src/main.tsx:609`).

## The running window

Nothing watches the file, and sessions hold what they were started with. On a yes, once the file
is saved, `theme` and `editorMode` take the same state change their commands make, a removed one
falling to what an absent key gives. `/new`'s list is state set once (`agentItems`,
`src/ui/app/App.tsx:455`), so `offeredAgents` sets `agents` the same way. `teamSelection` needs
nothing. Everything else is the next start, and the answer says so. Other windows and hand edits:
next start, except `teamSelection`.

## The screens

### Drawing a value

Every value and every agent-given word on the row or in the box is JSON-encoded: `"gpt-6.1"`,
`true`, `["claude","codex"]`. So the person sees what will be written, and it is one line that
wraps.

`JSON.stringify` alone is not enough: it leaves DEL, the C1 controls (0x9b is CSI), the line
separators and bidi overrides raw. Any `\p{Cc}`, `\p{Cf}`, `\p{Zl}` or `\p{Zp}` left after it is
written `\uXXXX`.

A path is its keys joined by dots; a key that is not plain `[A-Za-z0-9_-]+` is JSON-encoded in
place: `agents."my.agent".model`.

**A write's `before` is masked as a read is,** by its full path, for the answer and the row alike: an
agent named `url` can make `Now` read `"***"`. `After` stays exact.

**A value wraps at the cell and is never cut or folded:** no `+N lines`, no ctrl+o, continuation
rows under the value's own column. The row carries it, as the box only names the path.

### The row

The headline is the tool row's own, `Settings(path)`, its note named once served, as
`Team(bugfix) · proposal`: `change`, `set`, `remove`, `read`, `unchanged`. A refusal has no note.

Colours, by role of `src/ui/theme/theme.ts`: labels `dim`; values the plain text colour; the
`warning` line `warning`; `Saved to…` `success`; `Not saved…` and `unchanged` lines `dim`;
a refusal `error`, as every chord refusal is.

Set on a key that has a value, the person asked:

```text

   ⎿  Now    "gpt-6.1-sol"
      After  "gpt-6.1"
```

### Other states

- **Empty:** no settings file: a `read` says `not there`, a `set` writes `Now  not set` and makes the file and its directory on the yes.
- **Streaming:** a call not served yet is `Settings(path)` with the row's usual running state. A cut-off one says `cutLine`'s words.
- **Narrow:** only wrapping changes. Nothing is dropped at any width, as a value is never cut.
- **Fork:** the `FORK_REFUSED` line as a refusal, as `propose_team`.

### Keys

None new. The box's are the permission box's: `1`/`2`, ↑/↓ and Enter, Esc for the no. The row's
are the transcript's: pgup/pgdn and the wheel; ctrl+o on a read of every key. The shortcuts panel
already lists all of them, so it does not change.

## Its size

None of them touches CHD-565's list, which this tool edits as one more key.
