# CHD-266: A message's body is set apart from the transcript

CHD-225 gave every message between agents a `←` or `→` header, and CHD-239 put
`@` on the names a message can be sent to. The header reads well. The body
under an incoming message does not: it is drawn three cells in, in the text's
own colour, which is exactly where and how the agent's own replies are drawn.
A long instruction from `main` in a child's view runs straight into the
child's `⏺ I'll read the project guidance…` and its tool calls, and nothing but
the blank line between them says where the message ends.

The outgoing row already stands apart: `→ @main` is a tool call, and its body
sits under `⎿`, dim, as any tool's result. So today the two directions of one
conversation have two shapes, and only the outgoing one reads as quoted.

This document puts three ways to set the body apart side by side, for every
message row, and recommends one. The owner chooses; the build is filed after.
The header stays exactly as CHD-230 and CHD-239 have it: arrow, `@name` or the
bare name, `· runtime`, `· report`, `· failed`, `· monitor`, `· queued`.

**Decided (owner, 2026-10-09): option A.** Every message body goes under `⎿`,
dim, markdown kept, as the A mocks below draw it; a failed report's body in
the error colour; the outgoing row and the queued line unchanged. No bracket
variant, no coloured `⎿`. B and C stay below as the record of what was weighed.

## Dark and light

- **Dim** is SGR 2 in both: grey on black, grey on white. A and C rest on it,
  as every tool result already does, and read in both (checked against
  today's `⎿` rows, which use the same attribute).
- **B's bar** takes the theme's agent palette, dark `#6cb6ff #c49cff …` and
  light `#0a5bc4 #7a3fd6 …`, both already chosen to read on their background
  for the names; a one-cell bar is thinner than a name and reads at least as
  well. `main` and chord have no palette colour, so their bar is the default
  colour or dim.
- **`NO_COLOR`:** A and C keep their shape (dim is an attribute); B keeps the
  bar and loses the tie to the sender.

## Narrow

All three wrap the body to the width left after their indent: A and C at
width − 6, B at width − 5. Nothing new folds: the fold stays six lines, its
`… +N lines (ctrl+o to expand)` sits where the body's next line would, and a
monitor's closing sentence still never folds.

## Recommendation: A

The owner's own words were "the way tool output does", and A is exactly that:
the shape every tool result has, the shape the outgoing row already has, so
in and out finally read alike and nothing new is learned. B's selling point,
colour, is absent in the very view the problem was seen in, because `main` is
uncoloured. C separates too weakly. The one cost of A, a dim instruction, is
the cost every tool result already pays, and `ctrl+o` and the scroll keep it
readable.

If the owner wants colour as well, the smallest addition to A is the `⎿` in the
sender's colour, the text still dim; it is not drawn here because a coloured
`⎿` would mean something different from every other `⎿` on screen.
