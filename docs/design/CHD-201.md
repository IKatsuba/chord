# CHD-201: the startup header

CHD-198 puts Chorded's mark at the top of each session's transcript, as
pixel art, the way Claude Code shows its own logo. Beside the mark go chord's
name and version, the agent, the model, the directory and a hint. This spec
settles what is drawn: the mark's grid and the coverage threshold that
produces it, the text lines, the colours at each colour level and in each
theme, a resumed session, where the header stands, and how it scrolls and
works with tabs. CHD-202 (the generator) and CHD-203 (the header) build to it.

The whole-window mock-ups are in `evidence/CHD-201/mock/`, at 120×40 and
80×24, plus one at 44×20. The `.txt` files are the
screen as text. The `.ans` files are the same screens with the mark's real
colour escapes: `cat` one in a terminal to see the colours. They were made
from the real path by a throwaway script that supersamples coverage 24×24
per half cell, interpolates the gradient with culori, and picks the nearest
xterm colour in OKLab. That script is not committed, because CHD-202 writes
the real generator. The owner's changes in CHD-203 (the 4-row mark at every
size, the header at the top) were then carried into the mock-ups by hand. Where the mock-ups show `[2 codex]`, the brackets stand
for the front tab's highlight in the strip.

## Reference: Claude Code

`claude` v2.1.292, opened in an empty temporary directory with no prompt sent,
at 120×40 and 80×24:

```
 ▐▛███▛█   Claude Code v2.1.292
▝▜██████▀  Opus 5.5 · Claude Max
 ▝▝   ▝▝   /private/tmp/chord-qa.RMUA · /rc
```

- The logo is 3 rows of quadrant blocks, one colour (`38;5;174` inside tmux),
  and stays the same size at both window sizes.
- There are 2 columns between the logo and the text.
- `Claude Code` is bold. The version and the other two lines are a grey
  (`38;5;246`), which is the same role as chord's dim text.
- The prompt follows directly below.

chord keeps the arrangement (mark on the left, short lines on the right,
bold name, dim rest), stands where Claude Code's logo stands, at the top of
the transcript, and departs from it in two ways, for reasons given below.
The mark uses half blocks rather than quadrants, so that each cell can carry
two colours of the gradient. And it carries a fourth line, the hint the
owner asked for.

## The decisions, in short

| # | Question | Answer |
| --- | --- | --- |
| 1 | Grid | **4 rows × 4 columns at every window size.** A half cell is filled when **coverage ≥ 0.5**. |
| 2 | Text | `chord` **bold**, then ` v<version>` dim. Then `agent · model`, the directory from `~`, and `? for shortcuts · /help`, all dim. The text starts **3 columns** right of the mark. Before the model is known, line 2 is the agent alone. |
| 3 | Colour | chalk's level, which Ink already uses, decides. Level 3 (truecolor): the gradient's hex per half cell. Level 2: the **nearest xterm-256 colour (indices 16–255) in OKLab**, chosen by the generator. Level 1, and the `-ansi` themes: one named colour. NO_COLOR or a non-TTY: plain blocks. |
| 4 | Light | The light themes use their own stops: **#1e9a5e at 0, #147d55 at 0.55, #0a5e57 at 1**, each 3.6:1 or more on white. `#147d55` is Chorded's own light-background mark (`mark-light.svg`). |
| 5 | Resume | The header **stands above the replayed transcript**. It gets a fifth line, `resumed · <when> · <title>`. |
| 6 | Place, scroll and tabs | The header is the transcript's first entry. **On a fresh session it stands at the top: with one session open it is the window's first row, with nothing above it; with two or more, it is right under the tab strip**, and the transcript grows down from it until it fills the area; then it scrolls away with the transcript and comes back on `home`. **Each tab's transcript starts with its own header**, and `/clear` draws a fresh one. |

## 1. The mark's grid

### How the SVG maps to cells

- The source is `mark.svg`'s path, with viewBox 54.367 × 100.
- A terminal cell is about twice as tall as it is wide, so a **half cell is
  taken as square**. The path is scaled uniformly so that its 100 units of
  height span exactly `2R` half cells, where `R` is the mark's rows.
  One half cell is therefore `unit = 100 / (2R)` viewBox units on both
  axes, with the origin at the viewBox's top-left.
- Columns: `ceil(54.367 / unit)`. Columns that end up empty at the right
  are then trimmed. At 4 rows, `ceil(4.35) = 5`, and the fifth column never
  reaches the threshold, so the mark is 4 columns wide.
- **Coverage** is the share of a half cell's area inside the path: the mean
  alpha of the rendered pixels in it, from resvg or any other renderer. A
  half cell is filled when **coverage ≥ 0.5**.
- The threshold is safe. Every half cell is either below 0.29 or above
  0.88. So any threshold from 0.29 to 0.88 gives the same grid, and small
  differences in a renderer's antialiasing cannot change it. The value
  closest to the threshold is the notch's edge (0.28 out).
- Cell glyphs: top and bottom filled is `█`, top only is `▀`, bottom only is
  `▄`, neither is a space. For colour on a `█` cell, see 3.

### 4 rows × 4 columns

```
█▄
▀██▄
▄██▀
█▀
```

- It matches the 4 text lines, so the header is 4 rows high, about as small
  as Claude Code's 3.
- The notch survives as the `▀`/`▄` pair in column 1, and the tip as the
  `▄`/`▀` in column 4.
- 5 rows was tried (`█▄ / ███▄ / ████ / ███▀ / █▀`). It shows the notch as a
  whole empty cell, but it loses the point of the tip, and it leaves an odd
  row beside 4 lines of text. 3 rows (`█▄ / ███ / █▀`) loses the notch
  altogether, so the mark would just be a triangle.

### One size

The mark is 4 × 4 at every window size, and the text always stands beside
it. The owner chose this after seeing CHD-203's build: an 8 × 9 mark at 100
× 30 and over, the 4 × 4 at 50 × 16 and over, and no mark below that, was
specified here first and dropped. One size keeps the header as small as
Claude Code's at every width, and leaves nothing to read from the window.
At 44 columns the mark and its gap leave the text 35 columns, which the
four lines fit.

Mock-ups: `120-fresh.txt`, `80-fresh.txt`, `44-fresh.txt`.

## 2. The text beside the mark

```
 █▄     chord v0.0.0                 ← "chord" bold, " v0.0.0" dim
 ▀██▄   claude · Sonnet 4.5          ← dim
 ▄██▀   ~/src/app                    ← dim
 █▀     ? for shortcuts · /help      ← dim
```

- **Columns:** the mark starts at column 1, the transcript's left margin
  (where `⏺` and `›` stand). The text starts 3 columns after the mark's last
  column, at column 8. Claude Code uses 2 columns with no left margin. With
  chord's margin, 3 gives the same weight.
- **Rows:** the four lines stand beside the mark's four rows, from its first.
  A resumed session's fifth line goes below the other four (see 5).
- **Lines:**
  1. `chord v<version>`, with the version from `deno.json`, as `--version`
     prints it.
  2. `<agent> · <model>`, with the agent as the tab strip names it and the
     model as the status line names it (`models.ts`).
  3. The session's directory, from `~` as the window shows paths
     (`settings.ts`), the same text as the tab strip's right end.
  4. `? for shortcuts · /help`, with the key the keybindings file binds to
     the shortcuts, as the status line's hint names it; `/help` alone where
     the file unbinds it.
- **Bold and dim only, no colour.** As in Claude Code, the name is the only
  bold text and the rest is dim. chord paints neither plain nor dim text, so
  the text keeps the terminal's own foreground in every theme and under
  NO_COLOR, and the mark is the only colour in the header.
- **Cut to the window:** each line is cut at the window's right margin with
  `…`, after a whole character. Line 3 is cut the same way the tab strip cuts
  the directory, so the two never differ.
- **Before the model is known** (`Starting claude…` on the status line),
  line 2 is the agent alone: `claude`. ` · Sonnet 4.5` is added once the
  agent reports a model. Nothing stands in for it, so nothing is replaced:
  only the end of one line grows. An agent that never reports a model keeps
  `claude` for good. Mock-ups: `120-connecting.txt`, `80-connecting.txt`.
- **A model change later** (`/model`, shift+tab) does not rewrite the
  header. The header says what the session started with, the status line
  says what it uses now, and the change is already a note in the
  transcript.

## 3. Colour

### The gradient

- **Stops:** #89f5b3 at 0, #47e7a5 at 0.55, #15c7a2 at 1 (dark). The light
  stops are in 4.
- **Direction:** from the viewBox's top-left (0, 0) to its bottom-right
  (54.367, 100), in viewBox units. Lines of equal colour run perpendicular
  to that diagonal. For a half cell at column `c` and half-row `r`, sample at
  its centre `(x, y) = ((c + 0.5)·unit, (r + 0.5)·unit)`:

  ```
  t = clamp((x·54.367 + y·100) / (54.367² + 100²), 0, 1)
  ```

- **Interpolation** is linear in sRGB between the two stops around `t`, as an
  SVG `linearGradient` does by default.
- The landing page's vector, (7,7)→(32,45) on its own 40×52 box, comes to
  the same diagonal within a few percent. The corner-to-corner form is used
  because it is simpler to reproduce.
- The result: the top-left arm is the palest, the tip sits at about 0.57,
  and the bottom-left arm is the deepest (up to 0.75). The far end of the
  gradient falls outside the shape, as it does on the landing page.

### Two colours per cell

- Both halves filled: if both get the same colour at the level in use, the
  cell is `█` in that colour. Otherwise it is `▀`, with the top half's colour
  as the foreground and the bottom half's as the background.
- One half filled: `▀` or `▄` in that half's colour, on the terminal's own
  background.

### The colour level

The level is **chalk's level**, from the supports-color copy that chalk 6
carries. That is what Ink's own `chalk` and `src/ui/highlight.ts`'s `PAINT`
already use. Colour as a whole is `highlighting()` (`App.tsx`'s `COLOUR`):
off under NO_COLOR (`Deno.noColor`) or when stdout is not a TTY.

| Level | When (supports-color's rules) | The mark |
| --- | --- | --- |
| 3, truecolor | `COLORTERM=truecolor`, `TERM=xterm-kitty`, `xterm-ghostty` or `wezterm`, iTerm 3 or later | the gradient's hex per half cell |
| 2, 256 colours | `TERM` ending `-256color` or `-256`, Apple Terminal | the generator's nearest 256 index per half cell (below) |
| 1, 16 colours | any other colour terminal | the theme's 16-colour tone (below) |
| colour off | NO_COLOR, or stdout not a TTY | plain `█ ▀ ▄`, in the terminal's foreground |

tmux sets no `COLORTERM` by default, so chord inside tmux runs at level 2.
CHD-203's truecolor capture has to start chord with `COLORTERM=truecolor` in
its environment, or it will be capturing the 256 fallback.

### The 256-colour rule: nearest in OKLab, per half cell

- chalk's own downsampling, ansi-styles' `rgbToAnsi256`, rounds each channel
  to a sixth. The xterm cube's levels are not evenly spaced (0, 95, 135, 175,
  215, 255), so this rounding misses: it maps `#147d55`, the brand's
  light-background green, to `#008787` (teal), where the nearest colour is
  `#00875f`.
- So every filled half cell gets **its own 256 index**, found when the mark
  is drawn (`src/ui/header/mark_rows.ts`) from its place on the gradient; the
  generator stores only that place (CHD-202). The index is the nearest of
  xterm colours **16–255** (the 6×6×6 cube and the grey ramp) by Euclidean
  distance in **OKLab**. Indices 0–15 are left out because terminal themes
  redefine them.
- culori (`nearest` with `differenceEuclidean('oklab')`) does this in one
  call, and it also interpolates the gradient. Try it before writing either.
- Ink paints the index as `ansi256(n)`.

The dark ramp at 256 colours comes to five steps: **121 → 85 → 49 → 78 →
43** (#87ffaf, #5fffaf, #00ffaf, #5fd787, #00d7af). The stops alone map to
121, 78 and 43; the 4 × 4 mark takes four of the five, 49 falling between
its half cells. Each filled half cell (`.` is empty):

```
dark
121  .   .   .
 85  85  .   .
 85  85  85  .
 .   78  78  78
 .   78  78  78
 78  78  43  .
 78  43  .   .
 43  .   .   .
```

Mock-ups: `120-fresh.dark-true.ans`, `120-fresh.dark-256.ans`, and the same
at 80.

### 16 colours: the `-ansi` themes, and level 1

The mark is **one colour**. A two-tone split in 16 colours draws a hard line
across a mark only 4 cells wide, which reads as a rendering fault rather
than a gradient. The 16-colour themes exist so that the terminal's own
palette decides. The tone follows `sixteen(bright)` in `theme.ts`:

| Theme | Tone |
| --- | --- |
| `dark-ansi` | `greenBright` |
| `light-ansi` | `green` |
| `dark`, `dark-daltonized` at level 1 | `greenBright` |
| `light`, `light-daltonized` at level 1 | `green` |

With one colour, every two-half cell is `█`, so no background colour is used.

### NO_COLOR

The plain blocks in the terminal's foreground, the same shape: exactly the
`.txt` mock-ups. Bold and dim on the text stay, as they do everywhere else
in chord under NO_COLOR.

### Where the colour belongs

The header takes its colours through the palette context, the same way
`/theme`'s preview reaches every component. A `mark` role, holding the
three stops (or the 16-colour tone), goes into each `Palette`, and `PLAIN`
has none. `/theme`'s preview then repaints the mark as it moves through the
themes.

## 4. The light themes

On white, the dark gradient almost disappears: 1.33:1 at #89f5b3, 1.59:1 at
#47e7a5, 2.16:1 at #15c7a2. `light` and `light-daltonized` get their own
stops, with the same rise in hue from green to teal:

| Stop | Dark | on black | Light | on white | 256 (light) |
| --- | --- | --- | --- | --- | --- |
| 0 | #89f5b3 | 15.8:1 | **#1e9a5e** | 3.6:1 | 29 #00875f |
| 0.55 | #47e7a5 | 13.2:1 | **#147d55** | 5.1:1 | 29 #00875f |
| 1 | #15c7a2 | 9.7:1 | **#0a5e57** | 7.6:1 | 23 #005f5f |

- **#147d55 is Chorded's own colour for the mark on a light background**
  (`mark-light.svg`, `lockup-light.svg`), so the middle of the light ramp
  is the brand's colour. The other two stops sit either side of it.
- **Every light stop is 3.6:1 or more on white**, above the 3:1 that WCAG
  1.4.11 asks of graphics. The pale stop cannot go lighter: #22a063 is
  3.35:1, and the next xterm step up, 35 #00af5f, is 2.8:1.
- **At 256 colours, the light ramp is two steps: 29, with 23 at the
  bottom-left.** The range is narrow because it has to stay dark enough on
  white. A two-step mark is still recognisably the mark, so that is
  accepted.

```
light
29  .  .  .
29 29  .  .
29 29 29  .
 . 29 29 29
 . 29 29 29
29 29 29  .
29 29  .  .
23  .  .  .
```

- **`light-daltonized` uses the light stops, and `dark-daltonized` uses the
  dark ones.** The mark carries no meaning in its colours, so there is
  nothing for a red–green deficiency to confuse. As in `theme.ts`, the
  daltonized themes change only the diff.
- **`light-ansi` uses `green`**, as in 3.
- **`auto`** takes the stops of whichever theme it comes to.

Mock-ups: `120-fresh.light-true.ans`, `120-fresh.light-256.ans`, and the same
at 80.

## 5. Resume

`--continue`, `--resume <id>`, and `/resume` all draw the header **above the
replayed transcript**, with a **fifth line**:

```
 █▄     chord v0.0.0
 ▀██▄   claude · Sonnet 4.5
 ▄██▀   ~/src/app
 █▀     ? for shortcuts · /help
        resumed · 2 hours ago · fix the failing date test in the parser

 › fix the failing date test in the parser

 ⏺ Read(src/date.ts)
   ⎿  Read 84 lines
```

- **The header stands first.** A resumed session's transcript is drawn as its
  turns were drawn live, and live it began with a header, so it begins with
  one now. Without it, a resumed session would be the only kind with no
  header.
- **`resumed · <when> · <title>`, dim**, under the hint, in the text column.
  The text column keeps the same rows as a fresh session's. The fifth line
  falls below the mark, and the mark's column there stays blank.
  - `<when>` is the session's last use, in the same words `/resume`'s picker
    uses (`picker.ts`: `5 minutes ago`, `yesterday`, `3 weeks ago`).
  - `<title>` is the title the agent gave the session, if it gave one.
    Otherwise it is the first prompt, as the picker lists it.
  - The title goes last because it is the part that gets cut at the margin.
- **The header shows today's facts.** The version is this chord's, and the
  model is the one the resumed session is on now. The replayed turns below
  are the past; the header is not.
- **`/resume` in a running tab** replaces the tab's transcript, so the new
  transcript starts with the resumed header. **`/clear`** starts a new
  session, so it draws a fresh header, without the fifth line.

Mock-ups: `120-resume.txt`, `80-resume.txt`.

## 6. Scrolling away, and tabs

- **The header is the first entry of the transcript, not a fixed part of the
  window.** On a fresh session it stands at the top of the transcript area,
  on the window's first row when one session is open (CHD-224 dropped the
  row of `chord` and `<agent> · <directory>` that stood above it and only
  repeated the header), and under the tab strip with two or more, with the
  empty rows below it and the prompt at the bottom, as in Claude Code. The transcript hangs from the top while
  it fits: each turn lands below the last, and nothing moves up. Once it
  fills the area it sits on the bottom, the newest row above the prompt, and
  the header scrolls off the top with no special case
  (`120-first-turn.txt`, `120-scrolled.txt`, and the same at 80).
- **Back to it:** `home`, or pgup and shift+↑ as far as they go, show it at
  the top again, with the scroll rule at the bottom
  (`120-scrolled-home.txt`, `80-scrolled-home.txt`).
- **This spec first put the header just above the prompt,** with the
  transcript anchored to the bottom from the first row, and rejected the top
  for the blank rows it leaves between the header and the prompt. The owner
  chose the top after seeing CHD-203's build: the blank rows are Claude
  Code's too, and the transcript reads downwards from its first line.
- **Tabs:** each tab's transcript starts with **its own** header, with its
  agent, its model and its directory. Switching tabs switches the header
  along with everything else, because it is part of that tab's transcript
  (`120-tabs.txt`, `80-tabs.txt`: tab 2, codex, in front).
- The header's lines have **no keys**. They are text in the transcript, and
  the hint names keys that already exist (`?`, `/help`).

## For the generator (CHD-202)

| Number | Value |
| --- | --- |
| Source | `mark.svg`'s path (copy committed), viewBox 54.367 × 100 |
| Half cell | square, `unit = 100 / (2R)` viewBox units on both axes, origin at the top-left |
| Size | R = 4 → 8 half rows × 4 columns (5 before the empty right column is trimmed) |
| Coverage threshold | filled at ≥ 0.5 of the half cell's area (stable from 0.29 to 0.88) |
| Gradient | `t = clamp((x·54.367 + y·100) / (54.367² + 100²), 0, 1)` at the half cell's centre, linear sRGB |
| Dark stops | #89f5b3 0, #47e7a5 0.55, #15c7a2 1 |
| Light stops | #1e9a5e 0, #147d55 0.55, #0a5e57 1 |
| 256 | nearest of xterm 16–255 by Euclidean distance in OKLab, per half cell, at draw time |
| 16 | one tone: `greenBright` for dark themes, `green` for light |
| Plain | `█ ▀ ▄` with no colour |

The generator's output can be checked against the shape in 1 and the 256
maps in 3 and 4: those came from a supersampled rasterisation of the same
path. If resvg produces a different grid, compare it against the coverage
values before changing the threshold. The threshold has a margin of ±0.1.
