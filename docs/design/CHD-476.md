# CHD-476: clear a child's context, by the person or by its parent

The owner's answers (Q294–Q297, 2026-10-28): the person's `/clear` with a
child picked clears that child; its parent clears it with a new tool,
`clear_agent`. The child stays the same member, same id and name, with a
fresh agent session. Main and siblings are untouched. Compaction is out of
scope.

This replaces `/clear clears main; pick main first`, and CHD-101's
`A fork cannot be cleared yet · close it with x and /fork again`: `/clear`
on a picked fork clears it as a picked child, with no notice (it has no
parent).

## What clearing does

The same as `/clear` on main, for that one child:

- Its running turn is let go (its cost still counts); its open permission,
  question or form prompts are withdrawn.
- Nothing the old session says afterwards reaches anyone: late tool
  results, its `send_message`, its task agents and monitors, which close
  with it. Agents it opened close with it, as main's do on main's `/clear`.
- Messages queued **to** it are not delivered. The person's own queued
  prompts for it come back into the draft. Other senders' are named as
  not delivered (below).
- The fresh session runs nothing until its next message. That message
  carries what a first message carries: for a team member, the team's and
  its role's instructions in front, as `open_agent` gives them; for a
  plain child, just the message. A cleared team lead keeps its members open;
  its next message carries the team instructions, which name them.
- It keeps its row, name, id, parent, team and position in the agents list.

## The person: `/clear` with a child picked

The child's view becomes empty, as main's after `/clear`: its header line,
then nothing, then the prompt. The record keeps the old turns.

```
 reviewer · claude · Opus · opened by main 12m ago

╭─ reviewer ───────────────────────────────────────────────────────────────────╮
│ ›                                                                            │
╰──────────────────────────────────────────────────────────────────────────────╯
  ? for shortcuts                                     Opus · medium effort
    main      claude · Opus · medium      ◦ idle 4m
    reviewer  claude · Opus · medium      ◦ idle 0s
```

The child stays picked. Its state is the ordinary `◦ idle`; no new state.

Its parent gets one message from chord:

```
<message from="chord">The person cleared reviewer's context (claude · Opus, id a3). It is open with a fresh session and knows nothing of earlier turns; your next message is its first.</message>
```

with, when messages to it were dropped, a sentence after it:
`2 queued messages from main and parser were not delivered.` (one:
`1 queued message from main was not delivered.`). A fork, which has no
parent, gets none.

## The parent: `clear_agent`

Description: `Clears a long-lived agent you opened: its turn stops and it
gets a fresh session that knows nothing of earlier turns, with the same id
and name. Your next message is its first; a team member's carries its
instructions, as open_agent's first message does. The answer comes once
the fresh session is up.` Input `{ to }`, by id or name, as `close_agent`.

It answers once the fresh session is up:

```
reviewer (id a3) has a fresh session; it knows nothing of earlier turns.
```

plus the not-delivered sentence above when messages were dropped. No
notice follows: the parent asked.

In the parent's transcript, as other chord calls:

```
 ⏺ Clear(reviewer)
   ⎿  Fresh session · id a3
```

Refusals, as an error result and a failed chord call:

| Case | Answer |
| --- | --- |
| Not an agent the caller opened (main, a sibling, a grandchild, a fork, an unknown name) | `close_agent`'s own refusal for that name |
| The fresh session fails to start | `Could not clear reviewer: <reason>`; the child shows its failed connection, as a child whose start fails today |

The person's `/clear` on a child whose fresh session fails shows the same
words as the failed line under `/clear`.

## Keys

None new. `/clear` on a picked child or fork is the existing command;
`clear_agent` is a tool. The `/` list entry for `/clear`
(`Start a new session with an empty transcript`) stays: it is now true of
whatever is picked.

## Colour roles

Unchanged: the empty view and the header as today; the parent's notice is
an ordinary chord message; refusals use the failed line's `error`.

## Why

One meaning of `/clear` everywhere: what is on screen starts over, and
nothing old leaks into the new session. The parent is told only when it
did not ask, so it stops citing work the child forgot; the dropped
messages are named so no sender assumes they arrived.
