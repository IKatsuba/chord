# CHD-629 — `/rename`, the account, initial options, notices, subagent links

The second PR of CHD-624 (the owner's D5 a): the protocol features the
survey's D3 a takes up now, on ACP SDK 2.6.0, claude-agent-acp 0.107.x and
codex-acp 2.6.0, which CHD-624 brought in. The drafts this merges, the
brief and the critic's review behind it are in
[`evidence/CHD-629/drafts/`](evidence/CHD-629/drafts/). Where this file and a
draft differ, this file holds.

Five features, no new key, no new component:

- **F1** `/rename <title>` for every agent; `session/set_title` where served.
- **F2** the signed-in account in `/status`; the sign-in failure worded
  from `auth/status`.
- **F3** a session opens on the mode, model and effort chord was asked for,
  through initial `configOptions` where the agent advertises `options`.
- **F4** agent notices drawn as their own line.
- **F5** a tool call names the subagent it refers to.

The owner's answers (Q1–Q8, 2026-11-14) are written in, marked **(owner,
Qn)**, and listed at the end.

## Rules over all five

- **The wire is read, never guessed** (CHD-624). A notice is drawn by its
  `severity` and strings, an account by its fields, a link by its
  `sessionId` against subagents chord already tracks. No word is matched.
- **Every agent string is cleaned** before a report row or a note draws it
  (`strip-ansi`, whitespace runs folded to one space, as CHD-445 folds a
  title), or goes through `theme/Ansi.tsx` (`src/ui/AGENTS.md`).
- **One agent process per chord session** (`openAgent` per `openSession`,
  `src/session/session.ts:463-474`). "Per connection" and "per session" are
  the same in chord; an ACP subagent shares its parent's.
- **No new process of chord's own, no new dependency, no timeout on agent
  requests** beyond the one F2 bound below. Every request goes through
  `connection.ts`'s `ask`, which rejects on the agent's exit or the caller's
  signal.

## F1 — `/rename <title>`

### What the agents do

Claude 0.107 and codex 2.6.0 both advertise `sessionCapabilities.title`.
Both store the title, send `session_info_update {title}`, and **only then**
answer `{title}` with the title as stored (normalised: whitespace folded,
Claude cuts at 256 with `…`). Both then stop generating titles of their own
for that session (Claude's `settledByClient`, codex's `writeAutomaticTitle`).
An empty title is -32602 from both. Claude refuses -32600 on an old CLI that
cannot rename while it runs (the pinned 2.1.323 can). The schema: the
client SHOULD display the answer's title; the agent SHOULD NOT replace it
with a generated one afterwards. codex lists its own `rename` command; chord's
command of the same name wins and the agent's is left out of the `/` list
(`src/ui/prompt/commands.ts:120-124`), as for any clash.

### The command

`/rename` joins `CHORD_COMMANDS` between `new` and `resume`, owner `chord`,
described "Rename this session; the agent's own title may replace it". Its
argument is the rest of the line (`submitted`, `commands.ts:397`), whitespace
runs and newlines folded to one space. It acts on the front session (main,
or the picked child, as `/effort`), renames that session's **title**, never a
child's name (CHD-627), and is accepted during a turn: a title is not a
prompt.

| Target | `/rename` |
| --- | --- |
| main, a long-lived child, a team member | yes, its own `Conversation` and record |
| a task (`spawn_task`) | refused: a task keeps its `spawn_task` title (CHD-445 Q200) |
| a session still starting | refused, not queued: a failed start would leave it nowhere |
| a child that exited | refused |

### On the wire and in the record

```
chord → agent  {"id":7,"method":"session/set_title","params":{"sessionId":"S","title":"Fix the   parser"}}
agent → chord  {"method":"session/update","params":{"sessionId":"S",
                "update":{"sessionUpdate":"session_info_update","title":"Fix the parser"}}}
agent → chord  {"id":7,"result":{"title":"Fix the parser"}}
record         {"type":"update",…session_info_update…}        (the echo, as any update)
record         {"type":"renamed","title":"Fix the parser","at":1763100000000}
```

- **A rename chain per session**, apart from CHD-626's config chain: a hung
  `set_config_option` must not hold a title, nor the other way round, and
  both agents keep the two apart. Renames run one at a time, FIFO; two quick
  ones end on the second on both sides. The chain is reset where `#changes`
  is (`/clear`, resume).
- **One record line per rename, `renamed`, from the answer.** When the
  agent advertises `title`, the link sends `session/set_title` through a new
  `Agent` method that throws without asking where the agent does not offer
  it (as `forkSession`, `connection.ts:512-519`). On the answer, if the
  session is still current (`#current`), `Conversation` emits
  `{type:'renamed', title: response.title}`: the record queues the line and
  `#title` takes it. The answer's title wins over the typed one, silent
  answer or not. Without the capability the link emits `renamed` with the
  folded typed title at once. Record order is then wire order. "Recorded"
  means queued in `FileRecording`'s order (`record.ts:1465-1476`), not a
  disk guarantee, as for every line.
- **A chord-own line, not a synthesised `session_info_update`**: the record
  holds no ACP event the agent did not send (`src/session/AGENTS.md`).
- **Readers.** `recordedTitle` (`src/session/sessions.ts:257-297`) widens its
  fast filter to `{"type":"renamed"` and folds both kinds in line order,
  last wins. `recordActions` (`record.ts:630`) maps it to a past action that
  `Conversation`'s opening loop folds into `#title`; the transcript reducer
  draws nothing for it (CHD-445 draws no line for a title change). Older
  records have no such line; an older chord skips it.
- **Precedence** is "last title wins, whoever set it" (D3 b, CHD-491). The
  echo equals the answer and changes nothing. A later `session_info_update`
  is the agent's title taking over; with Claude and codex that happens only
  for a rename made outside chord.
- **A rename alone keeps no session**: lines held until the first prompt
  (`record.ts:1191-1196`) stay held.
- **Refused or failed `set_title`** (-32602, -32600, -32002, any error, the
  agent exiting): nothing is recorded, the title on screen is unchanged, and
  an error note gives the agent's words (`agentMessageOf`) **(owner,
  Q1 a)**.
- `/clear` mid-rename: the answer is for a retired session and dropped; the
  agent keeps it for that old session.

### `chord acp`

- Advertises `sessionCapabilities.title: {}` for every agent (chord's record
  takes any rename) and serves `session/set_title` through
  `connectAgentApp` with the SDK's handler type.
- **A live session**: the window's path. The answer is `{title}`, the
  agent's stored title or chord's folded one; the agent's echo already
  reaches the client (`session_info_update` is relayed, `upstream.ts:62-73`).
  Empty → -32602. A refusal answers the agent's error (Q1 a).
- **A listed session that is not loaded** **(owner, Q3 d)**:
  chord appends `renamed` to its record, marked not yet taken by the agent;
  when the session is next loaded or resumed, its rename chain sends
  `set_title` first where the agent offers it. Unknown id → -32002.
- `session/list` titles become `title ?? prompt` (`acp_agent.ts:1828-1833`
  sends the first prompt today), so a client sees its rename; a `renamed`
  past action goes up on load as chord's own `session_info_update` (here
  chord is the agent).

## F2 — the account in `/status`, the sign-in failure

### What the agents do

Claude advertises `agentCapabilities.auth.status`. Its identity is per
connection. At `initialize` it starts a `claude auth status --json` probe
(bounded at 5 s) and pushes `auth/status_update` when it lands, after the
`initialize` answer; it probes again at each session creation and each
prompt and pushes only on a change. `auth/status` with nothing known joins
the running probe; otherwise it answers at once. Payloads:
`{state:"authenticated", accounts:[{label:"Claude Max", email, organization,
active:true, …}]}`, an API key as `label:"Anthropic API key",
description:"ANTHROPIC_API_KEY"`, `{state:"unauthenticated"}` with **no
accounts**, `{state:"unknown"}`. factory-droid serves it (payload not read);
codex does not. Account fields are display only: SHOULD NOT be logged.

Signed out, Claude does **not** refuse `session/new` (only `--hide-claude-auth`
or a startup reason such as `org_pin_mismatch` do); its **first prompt**
fails -32000 `authRequired`, which chord today draws as a plain turn error
(`signInOf` is read only at start, `conversation.ts:384`).

### What chord does

- A listener for `auth/status_update` on the SDK client from before
  `initialize` (it is a notification, not a `session/update`, so it is not
  held in `early` and opens no cycle).
- Where `auth.status` is advertised, one `auth/status` right after
  `initialize`, **beside** `session/new`, never awaited by a start that
  succeeds. Claude joins the probe `initialize` began: no second CLI run.
- A pure fold, `src/session/auth_status.ts`, per connection:

  ```ts
  type AccountState =
    | { phase: 'none' }                               // auth.status not advertised
    | { phase: 'pending' }                            // asked, nothing heard
    | { phase: 'heard'; status: AuthStatusResponse }  // answer or push; a push heard after the ask wins (U11 b)
    | { phase: 'failed' };                            // the request erred, nothing heard
  ```

  Answers and pushes fold in arrival order (ACP carries no revision, the
  CHD-626 rule), but for one case: once a push is heard after the
  `auth/status` request went out, the request's answer, folded later, does
  not replace it, since the SDK does not keep the two in wire order
  **(owner, U11 b)**. A push after a failed request moves to `heard`; a
  request that fails after a push leaves the push. An unrecognised `state` word reads
  `unknown` (the schema's MUST).
- Never recorded, never in `-p` output, never an MCP tool. `/status` reads
  the fold and sends nothing: Claude re-probes at every prompt already.
- `SessionState` gains `account: AccountState` (and `SESSION_FIELDS` its
  entry), set by an `account` action from the host as models are. A picked
  child's `/status` reads its own process's.
- **The sign-in failure (owner, Q2 c).** The session opens as
  today. A -32000 at start (`asSignIn`, `session.ts:583-611`) **or at a
  prompt** becomes the sign-in block (`SignIn`, `src/session/sign_in.ts`),
  worded from the fold. If the request is still pending when the failure
  comes, chord waits for it up to `AUTH_WAIT_MS` = 1000 (abortable, by
  `node:timers/promises` `delay`), then words it from whatever it has; past
  that, today's words. A start that succeeds never waits. A later
  `unauthenticated` push only changes `/status`.

### `/status`

An `Account` row after `Agent`, a `Title` row after it (F1). The account's
parts, cleaned, joined by ` · `, each only when sent: `label`,
`description`, `name`, `email`, `organization`.

| --- | --- |
| `none` | no row |
| `pending` | `checking…` |
| `heard`, `authenticated` with accounts | every `active` account, or every account if none is marked, inside the one `Account` row, an empty line between accounts **(owner, U12)** |
| `heard`, `authenticated`, no accounts | `signed in` |
| `heard`, `unauthenticated` | `not signed in` |
| `heard`, `not_required` | `none needed` |

### `chord acp`

It answers `initialize` before any agent runs, so it advertises
`agentCapabilities.auth.status: {}` always and serves from **one source**:
the connection of its oldest live main session of the startup agent. Its
`auth/status` is that connection's fold (`unknown` when the fold is not
`heard`, or there is no such session), and only that connection's pushes
are relayed, deduplicated by payload. When the source closes or exits, the
next oldest becomes the source and chord pushes its status (or `unknown`)
once. Children, other agents and other connections are never mixed in (the
method has no session id). `logout` is not served (F8).

## F3 — sessions open on the chosen mode, model and effort

### What Claude does

`newSession` creates the session, then applies each `configOptions` entry
in list order through the same path as `session/set_config_option`; a model
entry decides which efforts and modes a later entry can pick. An entry that
fails (unknown id, value not offered) is skipped silently; two entries with
one id fail the whole request. The answer carries modes and options as they
stand after, with no `config_option_update`. Auto on a model without it
becomes `acceptEdits`, the warning deferred to the first prompt during
setup. Load and resume take entries too; fork takes none (nor does SDK 2.6's
`ForkSessionRequest`).

### The table and the request

A pure module, `src/session/initial_options.ts`:

```ts
/**
 * The config ids an adapter takes as initial `configOptions` (CHD-629), read
 * from its source and rechecked when its pin moves: asking `session/options`
 * first makes Claude run a throwaway Claude Code and the person's
 * SessionStart hooks (CHD-624).
 */
const INITIAL_CONFIG_IDS = {
  '@agentclientprotocol/claude-agent-acp': { model: 'model', effort: 'effort', mode: 'mode' },
};
```

Keyed by `init.agentInfo.name`, known after `initialize` and before
`session/new`, so it also covers a command that runs the adapter under
another id (`--agent-command`). `FAST_OPTIONS` stays keyed by registry id as
CHD-626 chose it; moving it is not this task.

`initialEntries(init, starting)` returns entries only when
`sessionCapabilities.options` is advertised and the table has the adapter:
value form, one per id, in the order **model, effort, mode**, for the values
that are **named** (`--model`, `--permission-mode`, settings, a team
member's or child's values). chord adds no default of its own (CHD-624 D1 a),
and `fast` is not a starting value. They go on **`session/new` only** (the
window, `/clear`, children, team members, `-p`, `chord acp`'s sessions);
load and resume keep set-after-open, fork takes none. `session/options` is
never sent, and a test asserts it.

### The read-back: `#applyStarting` as the chain's first link

`#session` is set before the async `#setUp` runs and `setMode` checks only
`#session` and `#closing` (`conversation.ts:817-837`, `:2751-2769`), so a
change could today run beside the start asks. `#applyStarting` becomes the
**first link of CHD-626's one chain** (`#changes`): a change asked while the
start runs queues behind it.

Inside, each named value is checked **against the session's current state at
its own turn**, in the order model, effort, mode, not against a list worked
out once (a model the agent moved could change an effort or mode that
matched at first):

1. Already current: nothing is sent.
2. Not listed: today's refusal, no request (`starting.ts:84-87`).
3. Otherwise ask through `setModel`/`setEffort`/`setMode`, as today; a
   refusal reads as today.
4. After a successful ask, read the current value again. If it is still not
   the asked one, the agent chose otherwise:
   - **an optional value** (settings, `--model`, `--permission-mode`): no
     chord line; the status line shows what the session is on, and the
     agent's notice (F4) says why where it sends one;
   - **a required value** (a team member's or child's mode or model): the
     start fails as a refusal, as a refused ask does today
     (`conversation.ts:3390-3392`), worded `the agent is in <current>`.

   chord does not ask again and does not read why: each value is asked at
   most twice (entry, then set-after-new).

So a value the agent took at setup costs nothing; a skipped entry or a stale
table id falls back to today's path using the id the session itself reports
(`modelConfigId`, `effortsOf`, `modeConfigId`, `session.ts:780-858`). The
record gains nothing: its first `state` line is written after the start.

### What the person sees

Nothing new. The status line's first mode, model and effort are the asked
ones, as after today's `#applyStarting`. A refused value reads as today:

```
 ⏺ Could not start in nope mode, set by --permission-mode: the agent offers
   default, acceptEdits, plan
```

A start whose `session/new` fails reads as today's start failure; chord does
not retry without the entries.

### `chord acp`

chord does not advertise `options` (advertising it means serving
`session/options`, which for Claude costs a throwaway Claude Code per call).
**(owner, Q4 b)**: a client's `configOptions` on `session/new`
are passed down **verbatim** where the downstream agent advertises
`options`, and read back by the same ids after the answer: an entry whose
id the session lists and whose value is not current is set by
`set_config_option` with that id and value, as sent; an id the session does
not list is dropped. Nothing is mapped or interpreted. A client's entries
beat chord's settings for the same id; a team member's values stay chord's.

## F4 — notices

### The declaration, per open

`CLIENT_CAPABILITIES` (`connection.ts:228-234`) becomes a parameter of
`openAgent`, and `session.notices: {}` is declared:

| Consumer | Declares `notices` | Why |
| --- | --- | --- |
| the window | yes | F4 |
| `-p` | yes, notices to stderr **(owner, Q5 a)** | stdout keeps the reply only |
| `chord acp` | only when its own client declared it | its clients get what they get today: the bold text if they did not declare, `notice` relayed if they did; chord rewrites nothing |

Declaring it changes what the agents send. Claude moves MCP server failures,
`warning`-level hook and system messages, model fallback, Fast on/off, Auto
unavailable, a task stopped by the person and missing subagent history to
`notice`, and **drops its `info`-level informational messages altogether**
**(owner, Q6 a: accepted)**. API retries stay AIR-only on v1: not
notices. codex 2.6.0 moves config warnings, deprecations, warnings, model
rerouted and the legacy context-compacted line to `notice`.

### State, record, cycles

- A new `src/session/transcript/notices.ts`, the reducer's `case 'notice'`
  (`reducer.ts` drops it in `default` today): an entry
  `{kind:'notice', turnId, severity, title, description?}`, never merged
  (notices have no id); an unknown severity is drawn as `info`. A subagent's
  notice goes into that subagent's entries.
- The record keeps the update whole, as it keeps every update, so a resume
  draws it where it was. Older records have none.
- `notice` is not in `CYCLE_WORK` (`cycles.ts:67-73`): outside a turn it opens
  no cycle, no spinner, no OSC 7501, no bell. Today the same advice arrives as
  an `agent_message_chunk`, which can open a Claude cycle; declaring removes
  that. Like every update it moves `#heardAt`, so a queued message may wait
