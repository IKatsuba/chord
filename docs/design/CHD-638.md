# CHD-638: a website that is a terminal

The site is one chord_tui program compiled with `dart compile wasm` and drawn
full-window by wterm (`@wterm/dom`). Everything a visitor sees is drawn by
chord_tui; the page is a host for the terminal and nothing else. It covers
chord (the app) and chord_tui (the framework), lives in `site/`, and builds
to a static folder that any static host can serve, as long as the host sends
every unknown path to `index.html` (SPA fallback). There is no server process
per visitor.

The owner approved this design on 2026-11-26, changing only question 1
(real paths through the History API, not the URL hash). Every question at the
end carries the owner's answer. Deploy stays out of the slice.

## What the probes found

Spike CHD-637 (commit 9cd77b053) left six items open. Each was probed against
wterm 0.6.0 (the current npm release) in headless Chrome 157, on a probe app
built from the spike's framework tree. The probe page served wterm from its
npm tarballs, not a CDN. The captures are in
[`evidence/CHD-638/`](evidence/CHD-638/).

| Item | Result | Evidence |

Any failure runApp tries to print would be lost the same way. | `build-error-120x40.png` |

Four more facts the design rests on:

- **Size.** The probe (six framework examples plus the probe app) is
  2,197,475 bytes of Wasm: 624,699 gzip -9 and 493,032 brotli -q 11.
  wterm's core is 55 KB of Wasm, also shipped inlined as a 74 KB JS chunk.
  Start (compile and instantiate) took 23 ms.
- **Resize.** With `autoResize` on, a 1400x900 viewport gives 163x51 cells;
  resizing to 700x500 gives 80x28, and chord_tui redraws at the new size.
- **Phone.** An iPhone 15 viewport (390x844) gives 43x37 cells
  (`phone-390x844.png`). A tap focuses wterm's textarea, which opens the soft
  keyboard. Tap-as-mouse-report with tracking on was not probed.
- **The chord app does not compile to Wasm yet.** `bin/chord.dart`,
  `tool/start.dart` and `tool/steering.dart` all stop at `dart:ffi` in
  `lib/platform/process.dart`, `lib/platform/group_exec.dart` and
  `lib/platform/resource_executable.dart`. Any page that runs chord's own
  widgets needs those three behind conditional imports, as the spike did for
  the framework. What fails at runtime after that (processes, records,
  settings files) is unknown until it is tried.

**wterm carries everything the site needs.** Nothing here forces xterm.js.

(question 8). xterm.js stays an option for the owner, not a recommendation:

browser find and screen readers do not read.


## The slice and its units

In build order. Framework units come before the site units that use them.
"Screen" marks a unit that changes what is drawn; designer looks at those
in a browser at 120x40 and 80x24 before review. P1 (the `dart:ffi` split in
`lib/platform/`) and the live chord fixtures (question 2, B) are a follow-up
task, not this slice.

### Framework

**F1. Wasm-safe terminal and runApp.** Not on screen.
`packages/chord_tui/lib/`:

- Take the spike's split: `settle_input_ffi.dart` and
  `settle_input_stub.dart` behind `if (dart.library.ffi)`.
- runApp's exit path stops touching `stderr`, `exit`, `Process.killPid` and
  `Platform.environment` where they do not exist. One small
  conditionally-imported module (`process_io.dart` / `process_web.dart`)
  holds `reportFailure(Object)`, `exitWith(int)` and the environment. On the
  web, `reportFailure` goes to `console.error` and exiting is a no-op. On
  native, behaviour is byte-for-byte as today.
- Under Wasm, a clean quit returns from runApp and a failure completes its
  future with the error. It no longer throws `Unsupported operation`.

Tests: the existing run_app and signal suites unchanged; one VM test that the
failure report goes through the seam; one `compile`-tagged test that
`dart compile wasm example/main.dart` succeeds, so a new `dart:ffi` import
fails CI.

**F2. The web terminal**, public in `package:chord_tui/web.dart`
(question 3, A). Not on screen by itself. In two layers, so that most of it
is testable on the VM:

- `HostTerminal`, plain Dart: a `Terminal` over a host given as Dart
  functions (`write`, an input stream, a size and a resize stream). It owns
  the escape sequences that `StdioTerminal._acquire` writes today (alt
  screen, hidden cursor, bracketed paste, and with `mouse: true` the
  1000/1002/1006 modes), and undoes them on `leave`. It refuses `suspend`
  and `runEditor` with a clear error, because there is no process to lend
  the terminal to.
- `WebTerminal`, over `dart:js_interop`: binds a page object with `cols`,
  `rows`, `write`, `onData` and `onResize` (the spike's `_Host`) to a
  `HostTerminal`. It overrides `copyToClipboard`
  (`navigator.clipboard.writeText`), `openUrl` (`window.open` with
  `noopener`), `setTitle` (`document.title`) and `bell` (ignored). The page
  object is not wterm-specific, so the same binding drives xterm.js.

The call site reads like any chord_tui app:

```dart
import 'package:chord_tui/chord_tui.dart';
import 'package:chord_tui/web.dart';

void main() => runApp(
  const Site(),
  terminal: WebTerminal(mouse: true), // reads globalThis.chordTerminal
  exitProcess: false,
  handleSignals: false,
);
```

`chord_tui.dart` stays free of `js_interop`; `web.dart` carries `///` docs,
a README section and a pana check for web support.

Tests: `HostTerminal` on the VM through a fake host (modes written on enter
and undone on leave, input and resizes delivered, suspend refused).
`WebTerminal` in headless Chrome (see "How done is checked").

**F3. Playback.** Screen, public widget. Plays a recorded terminal: frames
of ANSI rows captured from a real program, with play, pause and step keys.
The site's chord pages use it (question 2, A). Its API is in "Playback"
below.

**F4. KeyHelpBoundary.** Screen, public widget. Lets an app embed another
widget tree, keys and all, and keep each help row honest: help drawn inside
the boundary lists only the embedded tree's keys, and keys the host takes
first are listed nowhere. Built before S3 closes; the gallery's frame uses
it. Its API is in "KeyHelpBoundary" below.

### The site

**S1. The site's Dart package.** Not on screen. `site/pubspec.yaml`
(`chord_site`, `publish_to: none`, chord_tui by path), `site/lib/`,
`site/test/`, `site/web/main.dart` as above. Its own `analysis_options.yaml`
includes the root one. It is not part of the shared version.

**S2. Pages, routes and the History API.** Screen. Described in "Routes"
below. A pure router reducer (`site/lib/router.dart`) and the shell widget:
a header with the name and the links, the page in the middle, and a
`KeyHelp` row at the bottom. Every action has a key bound through `Actions`,
and the shortcuts panel lists it.

**S3. Framework pages and the gallery.** Screen. Pages about chord_tui, built
on live widgets: `/chord_tui` (what it is, README's example running, a link
to the gallery) and `/chord_tui/gallery` (the examples as a list). The
gallery runs the framework's examples in place: `demo`, `markdown`,
`picker`, `form`, `text_area`, `diff`, `dialog`, `layers` and `mouse`. They
are imported from `packages/chord_tui/example/` with a prefix
(`import '.../example/markdown.dart' as markdown;`), not copied.

**The examples need no change to be imported.** Every one of them already
exposes its widget as a public class, apart from `main()`: `Demo`,
`MarkdownExample`, `PickerExample`, `FormExample`, `TextAreaExample`,
`DiffExample`, `DialogExample`, `Layers` and `MouseExample`. A library with
a `main()` can be imported; its `main` is simply not called. None of these
nine imports `dart:io`. Two things the gallery handles itself, in `site/`:

- `form.dart` reads `--narrow` and `--long-list` from `main`'s arguments. The
  gallery passes the same choices through `FormExample(maxRows:,
  longList:)`, which already takes them.
- Every example binds Ctrl+Q to `exitApp(context)`, and the host turns an
  unhandled Ctrl+C into an exit. Question 4 says quit means home. The
  gallery frame holds a `Focus(onKeyCapture:)` above the example that takes
  Ctrl+Q and Ctrl+C first and goes to the home route, so the example never
  sees them. As a backstop, if runApp ever returns, `main` starts it again
  at the home route. Taking the keys needs no framework API. Listing
  them honestly does: the frame wraps the example in
  `KeyHelpBoundary(taken: {ctrl+q, ctrl+c, f1})` (F4; F1 per "The keys
  panel, `?` and F1"), so the example's own
  help row lists only its keys and never offers its Quit.

The S3 tests check that every gallery entry builds and draws at 120x40 and
80x24 through the tester, so an example whose constructor changes breaks
the site's tests, not the site.

**S4a. Recordings from tool/screenshots.dart.** Not on screen by itself.
Next to each shot's PNG, `tool/screenshots.dart` writes the shot as a
recording. Each shot is recorded twice, at 120x36 and at 80x20 (the room the
site gives a recording at 120x40 and 80x24), into two files,
`docs/images/<name>.120x36.rec.json` and `docs/images/<name>.80x20.rec.json`.
Each file is one version-1 recording (format below) with its own `cols` and
`rows`, so `TerminalRecording.fromJson` reads either unchanged; S4 picks the
largest that fits. It captures a frame with `capture-pane -p -e` after every
step, and while it waits keeps at most one unlabelled frame per 250 ms;
labelled step frames are always kept. It drops frames identical to the one
before. (At 100 ms the recordings came to 2.1 MB, `codeblocks` alone 1.55 MB
in 190 frames; the lead set 250 ms.) Each frame carries the time since the shot started and, for a step,
a label a visitor reads in the bar:

| Step | Label |
| ---- | ----- |
| typed text | `typed <text>`, cut to 40 cells with `…` |
| a key | the key in chord_tui's spelling, as help rows write it: `enter`, `ctrl+o`, `escape`, not tmux's `Enter`, `C-o` |
| a respawn | `started again` |
| leaving by `/exit` | `left` |
| a wait or a pause | none: its frames carry no label |

The PNGs do not change.

Tests: beside the existing `test/tool/screenshots*_test.dart`, the
recording writer (dedup, labels, both sizes) on canned panes, with no tmux.

**S4. chord pages.** Screen. What chord is, its screens as recordings in
`Playback`, and install. The site reads `docs/images/*.<cols>x<rows>.rec.json` at build
time and ships them as files under `recordings/`; a page fetches its
recording when it opens, so the Wasm does not carry them.

**S5. The page and the build.** Screen (fonts, colours, full-window
geometry). `site/web/index.html`: wterm full-window with the WebGL renderer
and one bundled OFL monospace font (question 8; named below), the host object, the Wasm
loader, a `<noscript>` line, and an `aria-label` on the terminal. Then
`site/tool/build.dart`:

- `build [--base=/]`: `dart compile wasm -O4` into `site/build/` with
  `index.html`, `main.wasm`, `main.mjs`, wterm's files (fetched from npm,
  pinned by version and sha512, question 7), the font and `recordings/`.
  `--base` defaults to `/`, must start and end with `/`, and is written into
  `index.html` as `<base href="...">`. Every asset URL in `index.html` and
  every URL the loader builds is relative, so it resolves against that base
  from any deep path.
- `serve [--base=/] [--port=8080]`: serves `site/build/` on loopback with
  the SPA fallback a host must give: a path under the base that names an
  existing file gets the file; any other path without a file extension gets
  `index.html`; a missing path with an extension (`/x/main.wasm`) gets 404,
  so a broken asset URL fails loudly instead of loading HTML as Wasm.
  `.wasm` is served as `application/wasm`. The smoke tests use the same
  server.
- `build` measures and prints no sizes: there is no size budget
  (question 9).

The output has no host-specific files. A host needs only two things: the SPA
fallback, and `.wasm` as `application/wasm`.

**The font: JetBrains Mono** (OFL 1.1), Regular and Bold. Checked
against every glyph the site draws (`❯ ▸ ▾ › ⌄ ❚ ■ ▶ ↑ ↓ ← → – ─ │ ┌ ┐ └ ┘
╭ ╮ ╰ ╯ · …`):

| Candidate | Glyphs missing | Size |
| --------- | -------------- | ---- |
| JetBrains Mono, full font | `❚` only | 92 KB (Regular woff2, v2.304) |
| `@fontsource/jetbrains-mono` latin | `❯ ▸ ▾ ⌄ ❚ ■ ▶ ← →` and all box drawing | 21 KB |
| `@fontsource/fira-mono` latin | `❯ ▸ ▾ ⌄ ❚ ■ ▶ ← →` and all box drawing | 16 KB |
| `@fontsource/iosevka` latin | `⌄` only | 961 KB |

Fontsource's subsets drop box drawing, which is the reason for bundling a
font at all, and Iosevka alone would weigh more than the Wasm. So the
build takes the full font from JetBrains' own release,
`github.com/JetBrains/JetBrainsMono` v2.304 (`JetBrainsMono-2.304.zip`),
pinned by version and checksum and cached like the SDK and wterm. Not from
npm: the `jetbrains-mono` npm package is a third party's unmaintained
repackage of an older version. From the zip it keeps
`fonts/webfonts/JetBrainsMono-Regular.woff2` and `-Bold.woff2` (chord_tui
draws bold for keys and headings; italic is synthesised), and `OFL.txt`,
which ships beside them in `site/build/`.

Ligatures: the release ships the no-ligature (NL) cut only as ttf (about
210 KB each), so the site uses the regular cut and turns ligatures off in
CSS instead. wterm's `terminal.css` already sets
`font-variant-ligatures: none` (which includes `no-contextual`, where
JetBrains Mono keeps its code ligatures) and `font-kerning: none`; the
page adds `font-feature-settings: "calt" 0, "liga" 0` on the host as well.
S5 checks it in the browser, in both renderers: `-> => != <= ===` in the
diff example must draw as one glyph per cell.

**Fallback is acceptable.** A glyph the font lacks (`❚` in the paused bar,
CJK and emoji in the examples) falls back to the system's fonts. wterm sizes
cells from the bundled font's advance, so a fallback glyph cannot move a
column. The CSS font stack is `"JetBrains Mono", ui-monospace, Menlo,
Consolas, monospace`. S5 checks the box-line seam again with this font
(question 8).

**S6. CI.** Not on screen. A required `site` job (question 6): `dart
analyze` and the format check for `site/`, `dart test` on the VM, `build`,
and the `browser`-tagged tests in Chrome. F1's Wasm
compile test goes in the existing `compile` job.

## Routes

Real paths through the History API (question 1).

| Path (under the base)    | Page | `document.title` | Esc goes to |
| ------------------------ | ---- | ---------------- | ----------- |
| `/`                      | home: the menu | `chord and chord_tui` | nothing (home) |
| `/chord`                 | chord: what it is, a list of its screens | `chord` | `/` |
| `/chord/<recording>`     | one screen, in `Playback` (`/chord/permission`) | `permission · chord` | `/chord` |
| `/chord_tui`             | chord_tui: what it is, README's example, a link to the gallery | `chord_tui` | `/` |
| `/chord_tui/gallery`     | the gallery: the examples as a list | `gallery · chord_tui` | `/chord_tui` |
| `/chord_tui/<example>`   | one example (`/chord_tui/markdown`) | `markdown · chord_tui` | `/chord_tui/gallery` |
| `/install`               | install | `install · chord` | `/` |
| anything else            | not found | `not found · chord` | `/` |

- **Names.** `<recording>` is the shot's name in `tool/screenshots.dart`
  (`permission`, `team`); `<example>` is the example's file name in
  `packages/chord_tui/example/` (`markdown`, `text_area`). `gallery` is
  reserved: a router test fails if an example is ever named that. The title
  uses the same name, lower case, then ` · ` and the section.
- **Home menu item 3, Gallery,** opens `/chord_tui/gallery`. Esc from an
  example goes back to the gallery, where it was picked, not to
  `/chord_tui`: the parent of an example is the gallery, and the paths
  stay short and owner-approved (`/chord_tui/markdown`). The router
  defines the parent per route, as the table says, rather than by cutting
  the last path segment.

- **The router** is a pure reducer in `site/lib/router.dart`: a path in, a
  route out, and back. Paths are read relative to the base: the page's
  `document.baseURI` path is stripped from `location.pathname`, so under
  `--base=/chord/` the path `/chord/chord_tui/markdown` is the route
  `/chord_tui/markdown`. A trailing slash is ignored; a path with a
  different case or an unknown segment is not found.
- **Opening a page** (Enter on a menu row, a digit, a link) calls
  `history.pushState` with the page's full path and sets `document.title`
  ("markdown · chord_tui").
- **Esc** goes to the parent route in the table (`/chord_tui/markdown` →
  `/chord_tui/gallery` → `/chord_tui` → `/`), also by `pushState`, so it is predictable whatever the visitor's
  history is. **The browser's Back and Forward** arrive as `popstate`; the
  router takes the path and the shell draws that page, without pushing.
- **Deep links** work because the host serves `index.html` for every path:
  the app reads the starting path once, at startup, and opens that page.
- **Not found** draws the path that was asked for and one choice, with a
  key: `enter  home`, also Esc. Its title is "not found · chord". It does
  not redirect by itself, so a mistyped link stays visible.
- The binding to `history` and `popstate` is a few lines of `js_interop` in
  `site/lib/web/`; the reducer and every page are tested on the VM.

## Playback

`Playback` draws a recorded terminal; a `PlaybackController` plays it. The
shape follows Flutter's video_player package, which Flutter developers
know: a controller with `play`, `pause` and `seekTo`, and a widget that
draws what the controller is on.

```dart
final recording = TerminalRecording.fromJson(jsonDecode(text)); // or TerminalRecording(...)
final controller = PlaybackController(recording, looping: true)..play();

Column(children: [
  Expanded(child: Playback(controller, autofocus: true)),
  PlaybackBar(controller),
])
```

**`TerminalRecording`**: `cols`, `rows`, and a list of
`TerminalRecordingFrame(at: Duration, rows: List<String>, label: String?)`,
where each row carries its own SGR sequences, as `capture-pane -e` writes
them. `TerminalRecording.fromJson` reads the file S4a writes. The names
carry `Terminal` because the port already has its own `Recording`
(`lib/session/record.dart`), and an export of the same name from
`chord_tui.dart` would make the port's imports ambiguous.

```json
{"version": 1, "cols": 120, "rows": 36,
 "frames": [{"at": 0, "rows": ["\u001b[1mchord\u001b[0m ..."], "label": null},
            {"at": 1300, "rows": ["..."], "label": "typed the prompt"}]}
```

One `Playback` shows one recording; choosing between sizes is the page's job (below).

**`PlaybackController`** (a `ChangeNotifier`): `play()`, `pause()`,
`seekTo(Duration)`, `nextStep()`, `previousStep()`, `restart()`, and
`value` (`position`, `isPlaying`, `isEnded`, the frame index, the current
step and its label). `looping` defaults to false. Its state is a pure
reducer (`PlaybackState` and `reducePlayback`) with no timer in it, tested
without time; the controller only adds the timer that advances it. Steps
are the frames with a label; with no labels, every frame is a step.

**`Playback(controller, {autofocus = false, focusNode})`** draws the current
frame's rows with `parseAnsi`, at the recording's size, from the top left.
It is focusable and binds, through `Actions`, with descriptions the
shortcuts panel lists:

| Key | Action | Description (as help lists it) |
| --- | ------ | ----------------------------- |
| `space` | Play or pause | `Play/pause` |
| `right`, `l` | Next step | `Next` |
| `left`, `h` | Previous step | `Previous` |
| `r` | Restart | `Restart` |
| `shift+right` / `shift+left` / `shift+up` / `shift+down` | Pan a clipped recording | `Pan` |

The descriptions are short so that Playback's keys and a host's own fit one
help row at 80 columns: `space Play/pause  right/l Next  left/h Previous  r
Restart  escape up  ? keys` (S4, 80x24).

**`PlaybackBar(controller)`** is one row: `▶ 0:04 / 0:12 · step 3 of 7 ·
typed the prompt`, `❚❚` while paused, `■ ended · r restart` at the end. It
is a separate widget, as Flutter's `VideoProgressIndicator` is, so a page can
put it where it wants or leave it out.

States:

- **Empty** (no frames): `Playback` draws nothing; the bar says
  `no frames`.
- **Playing / paused / ended**: as the bar says; at the end the last frame
  stays (unless `looping`).
- **Focused / unfocused**: the keys work only when focused. Playback draws
  no focus mark of its own; the page's frame does, as other chord_tui
  widgets leave that to their container.
- **Clipped** (room smaller than the recording): rows and columns are cut at
  the bottom and right, a dim `›` fills the last column and `⌄` the last row
  on the edges that are cut, and Shift+arrows pan. Nothing is scaled or
  reflowed; a recording is a picture of a fixed-size terminal.
- **Larger room**: the frame sits at the top left, and the rest is empty.

The site gives a recording a room of `cols x (rows - 4)` (header two rows,
bar and help one each) and picks, per page, the largest of the 120x36 and
80x20 recordings that fits. Below 80 columns (phones), the 80x20 recording
is shown clipped, with panning. So that the header is two rows at every
width, a recording page (`/chord/<recording>`) never folds the GitHub link
under the name: below 100 columns it drops the link, as phones do, and the
link stays in the `?` panel (`g open GitHub`).

The recording page: `loading <name>…` until its fetch returns, then the
largest recording that fits plays from the start, not looping, with
`Playback` focused and `PlaybackBar` under it. A failed fetch shows
`couldn't load <name>` and `escape up`. `/chord` is two README lines and a
numbered menu of the screens, each with the caption of its README image.
`/install` is README's install section as text.

## KeyHelpBoundary

The gallery frames an example that draws its own `KeyHelp`. `KeyHelp` lists
`FocusManager.activeBindings`, every enabled binding on the focus path,
ancestors included. So the example's row listed the site's keys too, and
said `ctrl+q Quit` while the frame's `onKeyCapture` takes Ctrl+Q home.

```dart
KeyHelpBoundary(
  taken: {KeyCombo.parse('ctrl+q'), KeyCombo.parse('ctrl+c')},
  child: Focus(
    onKeyCapture: goHomeOnQuit, // the host takes these keys first
    child: const markdown.MarkdownExample(),
  ),
)
```

**`KeyHelpBoundary({Key? key, Set<KeyCombo> taken = const {}, required
Widget child})`.** It changes only what help lists. Key dispatch, focus and
traversal are untouched: every binding fires exactly as without it. It marks
a point on the focus path. A binding is *inside* when its focus node is below
that point; the rest are *outside*.

What help lists, for `KeyHelp` and `KeyHelp.builder` alike (the builder gets
the filtered list):

- **Help built inside a boundary** (its `BuildContext` is below the
  boundary) lists only the active bindings that are inside the nearest
  enclosing boundary, less those on `taken` keys. Outer keys still work;
  they are just not this row's to list.
- **Help built outside** lists all active bindings, as today, less the
  bindings inside a boundary whose first key is one of that boundary's
  `taken` keys.
- **`taken`** matches a binding by its chord's first key: `ctrl+q` hides
  `ctrl+q` and any chord starting with it. A taken binding never fires,
  because the host's capture handler sees its key first, so no help
  anywhere lists it. `taken` is only a statement about listing; taking the
  key is the host's own `onKeyCapture`, as before.
- **Nested boundaries.** The nearest enclosing boundary decides inside or
  outside for a help row. `taken` keys add up: a binding is hidden if any
  boundary it sits inside takes its key.
- **A pending chord** (`ctrl+x …`) shows in a help row as today, filtered
  the same way: the chords offered to finish it are the listed ones that
  start with it.
- **Empty.** Help inside a boundary whose tree has no bindings of its own
  draws nothing, not the outer keys.

**The `?` keys panel follows the same rule, by where it is built.** The
rule depends on where a help widget sits, not on what kind of widget it is.
The site's `?` panel is drawn by the shell, outside the boundary, so it
lists the site's keys and the example's together, less the taken ones. It
is the one place that shows every key the visitor can press. A shortcuts
panel built inside a boundary would list only the inside keys, like a
`KeyHelp` there. The site's own help row is also outside, and S3 filters it
further to the site's keys alone (finding 1 of S3), with its own builder.

Why `taken` lives on the boundary and not on a binding: the embedded tree
is someone else's code (an example, a plugin) whose bindings the host
cannot rename. The host knows which keys it takes, so it says so where it
embeds.

There is no Flutter counterpart, since Flutter has no key help. The name
and shape follow Flutter's boundary and exclusion widgets
(`RepaintBoundary`, `ExcludeSemantics`): a wrapper with a child that
changes one aspect of what is below it.

### Framework widgets

Four public widgets, all in `packages/chord_tui/lib/`, each with `///` docs,
tests through the tester, and a gallery-sized example where one helps.

**Buttons: checked first.** `Form`'s submit and decline buttons are drawn
inside `_FormState` as rows of the form. They are not a widget, take no key
of their own, and cannot stand outside a form. So they do not cover
`Button`, and `Form` keeps them as they are in this slice.

#### `DisplayText`

Display type built from block cells, for a hero or a big number. Flutter has
no counterpart; it reads like `Text`.

```dart
DisplayText(
  'CHORD.',
  size: DisplaySize.huge,
  gradient: [mint, violet],                  // left to right
)

DisplayText.rich(
  TextSpan('CHORD', children: [
    TextSpan('.', style: Style(fg: amber)),  // a run's own colour wins
  ]),
  size: DisplaySize.large,
  gradient: [mint, violet],
)
```

- `size`: `DisplaySize.small` (half blocks, 4 rows, 6 columns a glyph),
  `medium` (half blocks doubled across, 4 rows, 12 columns), `large` (full
  blocks, 7 rows, 12 columns) and `huge` (full blocks, 14 rows, 24
  columns). One column of each glyph's advance is the gap.
- `style`: the colour when there is no `gradient`, taken from
  `DefaultTextStyle` when null. `gradient`: two or more colours spread
  evenly across the text's whole width. `TextAlign align` as `Text`.
- The glyphs are a 5x7 bitmap: `A–Z` (lower case draws as capitals), `0–9`,
  space and `. , : ! ? - _ / ' +`. Any other character draws a hollow box.
  It does not wrap. Wider than its constraints, it clips at the right, as
  `Text` with `softWrap: false` does. `DisplayText.measure(text, size)`
  returns the cell size, for a page to choose a size by width.
- The font is about the terminal, but developer first looks on pub.dev for
  a maintained 5x7 or FIGlet font package that works under `dart compile
  wasm` and says what was tried. If none fits, that finding goes to
  `docs/decisions.md` and the bitmap stays in the framework.

#### `Scrollbar`

```dart
Scrollbar(
  controller: scroll,
  child: ListView.builder(controller: scroll, itemCount: n, itemBuilder: build),
)
```

- It takes one column on the right of `child`, always, so the page does
  not shift when content starts to overflow. The thumb is `┃` in
  `thumbStyle` (the theme's border by default). The track is blank in
  `trackStyle`. The thumb's length is `track × view / content` rows,
  rounded and at least 1, where `track` is the scrollbar's own height.
  Its top is `(track − thumb) × offset / (content − view)`, rounded. When everything fits there is
  no thumb.
- Pointer: a press on the track above or below the thumb pages up or down.
  A drag on the thumb moves the view (`jumpTo`). The wheel is the list's,
  as now.
- It has no keys of its own: the list's scroll keys move it.
  `thumbVisibility` (Flutter's name) defaults to `true`; `false` draws the
  thumb only while the view moves, and hides it 600 ms (Flutter's
  `timeToFade`) after the last move, without a fade.
- `controller` is required. Unlike Flutter, chord_tui has no primary scroll
  controller to find.

#### `FilledButton` and `OutlinedButton`

Flutter's names and shape, plus one thing a terminal needs: a key.

```dart
Actions(
  bindings: [
    Binding('i', 'install chord', install, id: 'site:install'),
    Binding('w', 'watch it run', watch, id: 'site:watch'),
  ],
  child: Row(
    spacing: 3,
    children: [
      FilledButton(action: 'site:install', child: Text('Install chord')),
      OutlinedButton(action: 'site:watch', child: Text('Watch it run')),
    ],
  ),
)

FilledButton(onPressed: save, child: Text('Save'))   // no key: focus, Enter, tap
```

- **Exactly one of `onPressed` and `action`.** `onPressed: null` disables
  the button, as in Flutter. `action` names a `Binding.id` in an ancestor
  `Actions`. The button presses by invoking that binding, is disabled while
  it is disabled, and draws its current key under the face (`press i`), as
  the `Keymap` has moved it. The key lives in one place, the panel lists it
  once, and rebinding moves the hint too. This needs one new lookup,
  `Actions.maybeBindingOf(context, id)`, with the keymap applied. A missing
  id asserts in debug and draws disabled in release.
- Both buttons are focusable (`focusNode`, `autofocus`), take Enter and
  space when focused through `Actions` bindings (`enter press`), so the
  help row and the panel list them while a button has focus, and press on a pointer press and release inside them.
- `FilledButton`: 3 rows, `theme.accent` bold and inverse, so the face is
  the accent colour and the label the terminal's background, in every
  theme and under NO_COLOR. 4 columns of padding each side. Focused it is
  `theme.focus` inverse, disabled `theme.dim` inverse. ThemeData gets no
  new role. `OutlinedButton`: 3 rows, a rounded frame in `theme.border`
  around the bold label, 3 columns of padding. Focused, the frame turns
  `theme.focus`. Disabled, frame and label are `theme.dim`.
- Focus must show without colour (NO_COLOR, or two accents of one hue):
  a focused button also underlines its label.
- `showShortcut` (default `true` with `action`) draws the key row, centred
  under the face: `press` in `theme.dim`, then the key in bold
  `theme.text`, spelt as KeyHelp spells it (`ctrl+q`). Without it the
  button is 3 rows only.
- A keymap that unbinds the action's id leaves the button disabled with no
  key row, and that is not an error. Only an id that no ancestor `Actions`
  declares asserts.

#### `Link`

```dart
Link('GitHub', action: 'site:github', external: true)
Link('Read about chord_tui', onPressed: () => open(const ChordTuiRoute()))
Link('JetBrains Mono', uri: Uri.parse('https://www.jetbrains.com/lp/mono/'))
```

- **Exactly one of `uri`, `onPressed` and `action`** decides what Enter or
  a click does. A `uri` opens through the app's terminal
  (`TerminalScope.of(context).openUrl`), which is `window.open` with
  `noopener` on the web. `onPressed` is for routes inside the app.
  `action` invokes the binding with that id, as on the buttons, and the
  binding's own `onInvoke` opens whatever it opens.
- `external` draws ` ↗` after the text. It defaults to `true` with a
  `uri` and `false` otherwise, so a keyed link to another site says so:
  `GitHub ↗ g`.
- One line: the text and the arrow in `theme.link`, underlined. With
  `action`, the key follows as ` g` in `theme.dim`, moved by the keymap.
  A link whose action is unbound draws in `theme.dim` with no key.
- Focusable, with Enter bound through `Actions` (`enter open`), so the help
  row lists it while the link has focus. Focused, the text and the arrow
  take `theme.focus`
  **inverse**: the underline is already there, so inverse is the cue that
  survives NO_COLOR. It does not wrap. An inline link inside a paragraph
  is a later span-level piece, not this widget.

**`TerminalScope`.** `TerminalScope.of(context)` returns the app's
`Terminal`, and `maybeOf` returns null outside runApp. runApp hands its
terminal to the host's `BuildOwner`, which the lookup falls back to, so the
widget tree is unchanged. A `TerminalScope` widget gives a subtree another
terminal. The tester supplies its recording
terminal the same way, so a test sees the URL a link opened. `Link` is its
first user; Markdown links and the services example can move to it later.
It lives in `widgets/`: `Terminal` itself does not learn about widgets.

#### Frame titles

`Box` and `DecoratedBox` take `titleStyle`. When it is null the title draws
as it does now, bold in the border's style, so nothing else changes. The
site passes `theme.dim`, or `theme.accent` on an entered live frame,
because its border colour (`#2b2e38`) is meant for lines and is too dark
for text. Flutter's nearest name is `InputDecoration.labelStyle`; a title
style beside a border is what a reader of `Box` looks for.
