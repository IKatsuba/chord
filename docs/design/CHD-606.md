# CHD-606: riff's credential store

CHD-485's "Sign-in: where it lives", "G. No credential store",
"Credentials" and "Failures" settle C1 and L2. This is part 4: use the
existing start-failure row and status-notice line. The sign-in box,
`/login`, `/logout` and their recovery actions belong to part 5.
No new widget, colour role or key is needed.

## No store: riff does not start

Keep the existing `<agent> did not start: it refused session/new: <cause>`
failure surface. The refusal prefix is shared by every agent; part 5's
sign-in box replaces this surface for riff. The platform module supplies
the store's name; the window does not guess it from an error string. The
cause names the store and the next step:

| Store | Cause after `riff did not start: it refused session/new: ` |
| --- | --- |
| macOS Keychain | `chord keeps your sign-in in the system's credential store, and none answered: no macOS Keychain. Unlock the login keychain in Keychain Access and try again.` |
| Secret Service | `chord keeps your sign-in in the system's credential store, and none answered: no Secret Service (gnome-keyring or KeePassXC). Start one and try again.` |
| Windows Credential Manager | `chord keeps your sign-in in the system's credential store, and none answered: no Windows Credential Manager. Enable the Credential Manager service and try again.` |

These retain G's explanation and Secret Service sentence. The instruction
is a recovery step, not a claim that a locked keychain is the only possible
cause. A store failure never offers a file, environment variable or
memory-only sign-in.

For a timeout, the cause is `The macOS Keychain did not answer in 20 s.`;
substitute `Secret Service` or `Windows Credential Manager` from the
platform module for the other platforms. Keep that sentence intact. The
ordinary starting status remains while the operation is pending. Part 4
does not add G's sign-in-box working line or its Try the store again action.

## Credential notices

Draw `_chord/credentials {provider, state}` on the existing status-notice
surface below the prompt. Use provider display names `ChatGPT` and `Grok`.
These are status facts, not assistant replies, tool results or modal asks.
Keep the transcript, draft and ongoing tool output in place.

| State | Words (`ChatGPT` shown) |
| --- | --- |
| `unsaved` | `ChatGPT sign-in refreshed but not saved; will retry.` |
| `saved` | `ChatGPT sign-in saved.` |
| `signed_out` | `ChatGPT sign-in removed. This session is signed out.` |
| `account_changed` | `ChatGPT account changed. This session is signed out.` |

The first two distinguish a refreshed credential held for retry from one
actually saved. The last two distinguish removal from account replacement
and make clear that this session cannot continue using its old account.
They do not claim which application changed the store. A missed notice
still becomes the L2 refusal at the next prompt. Do not advertise `/login`
before part 5 supplies it.

At 120 columns the ordinary model/effort may remain to the right as the
existing status layout permits; at 80 columns the notice takes precedence.
Each notice fits at 80 columns without losing its outcome. For example:

```text

│ ›                                                                            │

  ChatGPT sign-in refreshed but not saved; will retry.
```

## L2: the next prompt fails through today's path

At each prompt the child rereads the store. Missing credentials or another
account cause `-32000` (`authRequired`) before provider work. In part 4 this
follows the existing failed-turn path: retain the person's submitted row,
append the error-coloured `⏺` row with the request error's readable message,
end Working and restore the rounded prompt. Previous transcript and tool
results remain. No sign-in box opens and no prompt is silently retried.
The numeric protocol code does not need a new visual treatment.

A refresh failure also fails the prompt `-32000` (`authRequired`) through
this existing path. libfx raises the same refresh-failure code for 429 and
500 as for a rejected token, so chord never clears the stored entry on a
refresh failure: the entry stays until a new sign-in, a logout or an
account change (owner, through main as delegate). A refresh failure alone
must not produce the `signed_out` or `account_changed` notice.

The shape below records that existing path; the message is illustrative,
not a new credential-specific error prefix:

```text
 › hello

 ⏺ Authentication required

╭──────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                            │
╰──────────────────────────────────────────────────────────────────────────────╯
  ? for shortcuts
```

Unit 4's captures must record the actual request-error words for both a
removed credential and a replaced account, rather than redesigning this
shared failure surface. Part 5 replaces this interim recovery with its box.

## States, colour roles and keys

- **Empty:** existing riff header and rounded prompt, no credential notice.
- **Starting:** existing Starting riff status until store success, failure
  or the 20 s bound; no false ready state.
- **Streaming:** existing working line and streamed transcript; credential
  notices use only the existing bottom status notice.
- **Waiting on the person:** no new waiting state or credential action in
  this part. A missing store is a start failure, not a permission request.
- **Error:** start failure or failed-turn row uses existing `error`;
  notices keep the status surface's existing plain/dim treatment. No
  credential-specific warning or success colours are introduced.
- **Narrow:** failure text wraps under its own gutter; notices fit on one
  line; prompt and permanent rows remain usable at 80x24.

No new keys. Enter submits the draft; Esc interrupts a running turn;
ctrl+c and `/exit` retain their existing exit behavior; `?` on an empty
prompt lists shortcuts. No retry, provider choice or sign-in action is
added here, so there is no new shortcuts-panel entry.
