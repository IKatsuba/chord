# CHD-532: choose the agent before a new unnamed start

## Implementation authority and working defaults — 2026-10-28

The owner explicitly authorized implementation using the reviewed recommended
defaults. This supersedes the proposal-only and approval-gate wording below;
the earlier proposal remains as design and research history. Offer the picker
on every new unnamed interactive start, using existing listing order and
configured/default highlight, with no saved choice. Preserve explicit,
headless, resume and non-TTY routes. Cancel starts nothing; a refused selected
agent follows existing refusal behavior without fallback. Reuse the existing
startup and picker components, with selection before agent/server/resources/
copier startup. Verification uses isolated fake commands only, with no live
registry, provider or clipboard effects. A new library mismatch still returns
to the owner with concrete options.

**Proposal only; owner choices below must be approved before code.** The
owner wants an agent choice when no agent is named. Recommend a picker on
every new, unnamed, interactive start, using the same candidates and order
as `chord agents`, highlighting the configured/default agent, remembering
nothing. This is a proposed package, not an approved change to startup.

## Owner decisions

| Question | Recommended package | Alternative and cost |
| --- | --- | --- |
| When to offer the picker | Every new interactive start with no named agent and no explicit command override | Only when settings contain no agent; a configured default keeps starting directly and the choice is less discoverable |
| Candidate source | Existing `listedAgents(agentCommands)`, the source of `chord agents` | Registry only omits CLI/settings-only agents; installed only requires a new agreed availability definition |
| Order | Existing registry order with public aliases, nonduplicate CLI entries, then settings-only names in settings order | Alphabetical or installed-first changes the familiar listing order |
| Initial highlight | Configured agent, else built-in default; first candidate if that name is absent | Always first candidate ignores the user's default |
| Remember the choice | No write; it selects this invocation only | Save user or project settings; owner must choose destination and precedence, and approve the persistent effect |
| Explicit/headless/resume/non-TTY starts | Skip this picker and retain the exact current route | Add choices to some routes; must define input, record-agent and automation behavior separately |
| Cancellation | Existing picker cancel or Ctrl+C exits cleanly with zero agent starts | Fall back to default; starts work after the person cancelled |
| Selected unavailable/refused agent | Existing startup refusal, no automatic retry or substitution | Return to picker with feedback; adds a new recovery flow |

No new flag, filter, availability probe, install command, remember checkbox
or persistence prompt. If a candidate source returns no entries, show the
empty state below and allow cancellation only. The current built-in catalog
makes this an exceptional fixture state, not an observed production case.

## Trigger and preserved routes

Offer the new picker only if this is a **new interactive** start and all of
these are absent: named agent, `--agent-command`, `-p`, `--continue`, and
any `--resume` form. Both stdin and stdout must be terminals for the new
picker. This is an owner proposal, including the terminal definition.

| Invocation/context | Proposed behavior |
| --- | --- |
| `chord` in a terminal | Offer the picker, including with `agent` set in settings |
| `chord <agent>` | Existing explicit-agent route |
| `chord --agent-command <command>` | Existing override route; do not discard the override |
| `chord -p <prompt>` | Existing headless route, no new picker |
| `chord --continue` | Existing resolved-agent-and-cwd-scoped latest-session lookup, no cross-agent discovery |
| `chord --resume <id>` | Existing recorded agent/directory and explicit override/mismatch rules |
| `chord --resume` without id | Existing startup resume picker exactly once, no additional agent picker |
| New unnamed start without both TTYs | Existing deterministic resolution and behavior; no newly invented refusal or interactive read |

Skipping the new picker does not guarantee that an existing route starts
successfully: preserve its validation and errors as well. In particular,
there is no general current plain-start non-TTY refusal to claim preserved.

## Screen and startup boundary

Reuse the existing startup composition in
[Start.tsx](../../src/ui/app/Start.tsx) and the numbered list in
[Pickers.tsx](../../src/ui/pickers/Pickers.tsx), with the existing
[picker.ts](../../src/ui/pickers/picker.ts) scrolling/layout/key behavior.
Promoting the existing private `PickerList` for reuse is preferable to a
new list implementation. These are source-fit candidates, not a completed
integration or measured widget trial.

Before selection, show `chord` at upper left and the working directory dim
at upper right. Do not name an agent as if it were already running. At the
bottom, show `Select agent`, the existing numbered choices, overflow
indicator where needed, and a dim key hint. No prompt box, session status,
model, working line, startup splash or agent-specific startup header yet.
This follows the existing resume startup screen's header/list boundary.

A choice row is `name · title` when the public title adds information,
otherwise the name alone. Append ` · not found` only for the existing
`found === false` CLI fact. Do not display inferred “installed” or “ready”
labels for registry or custom commands. Keep the existing one-line picker
truncation and scrolling, not a new multiline label layout. The configured
agent sets the initial highlight, not list order and not an active-session
check mark. No agent is in use yet.

Settings and candidate metadata may be read before choice. Do not create an
agent/session, Chord server, resource collector or clipboard copier before
the pick. Defer agent-specific command validation and startup settings to
the selected agent. An unknown, unselected default must not prevent choosing
a known candidate. If the configured/default name is missing, open on the
first candidate without injecting or silently starting an unknown name.

Selecting starts that agent exactly once through the existing resolution,
validation and startup path, respecting settings command/model precedence.
Then the existing splash/header/status behavior belongs to that selected
agent. Reuse the renderer handoff as startup resume does; do not exit and
reopen the screen solely to transfer into the conversation. Cancellation
starts nothing and restores the terminal through the existing cleanup.
An unavailable or refused selected command follows existing startup refusal
and exit behavior; no other agent starts and no automatic installation is
added. Existing registry runners may fetch their packages after selection;
the picker itself does not promise local installation or authentication.

## States and keys

| State | Concrete display/behavior |
| --- | --- |
| Short list | As above; initial highlight is visible, no empty placeholder rows inside the list |
| Long list | Same bottom list within `menuRowLimit`: 10 rows at 40 high, 6 at 24 high; existing scrolling keeps highlight visible, existing `… +N more` indicator; no list rotation or new paging controls |
| Very long custom name/title | Existing single-line truncation; selection still uses its unchanged full candidate id |
| Empty candidates | Title `Select agent`, dim `No agents available`, hint `Esc to cancel`; Enter and digits start nothing |
| Known missing CLI | Existing row plus dim ` · not found`; still selectable, then existing missing-command refusal exits without a process |
| Unknown availability | Ordinary selectable row; do not infer missing or installed from absent `found` |
| Startup refused after pick | Existing selected-agent diagnostic/cleanup, no return-to-picker or fallback invented |
| Cancel | Screen closes through startup cleanup; zero agent/server/resources started |
| Waiting for pick | List remains interactive; no agent streaming or working state exists yet |

The exact row budget and long-label visibility must be verified after
integration; this source-fit proposal does not establish a running layout.
No special authentication/error dialog is added before choice.

| Key/action | Behavior |
| --- | --- |
| Existing picker previous/next (`↑ ↓`, `k j`) | Move highlight using existing picker semantics |
| Existing picker select (`Enter`) | Start the highlighted candidate once |

| Existing `select:cancel` (default `Esc`) | Cancel startup |
| `Ctrl+C` | Cancel startup as the existing Start screen does |

Respect existing rebindings for picker actions and do not add command
bindings. The startup hint displays their resolved names where existing
helpers provide them. The `?` shortcuts panel must list these startup-picker
uses through the existing picker entries and their tests, including cancel
and absolute numbered selection. The startup screen itself adds no help
mode or new `?` handler; its visible hint supplies the applicable keys.
Do not copy the resume screen's scope-toggle action into the agent list.

Colors come from `src/ui/theme/theme.ts`: terminal foreground for names and
plain text, `permission` for the highlighted choice and marker, dim for
directory, title details, availability qualifier and hint. No agent-specific
palette identity before selection, new role, nested frame or status row.

## Baseline evidence and integration limits

Developer's read-only source report and this proposal refer to `6629f815`:

- [main.tsx](../../src/main.tsx) resolves the command-line agent, then
  settings agent, then `DEFAULT_AGENT` (`claude`). Its existing validation
  can reject an unknown resolved agent before a picker; the new path must
  delay that selected-agent decision until the choice.
- [agents.ts](../../src/agents.ts) supplies `listedAgents`: registry public
  aliases, nonduplicate CLI entries and settings-only entries in their
  existing order, with settings commands overriding catalog commands.
  `found` is a CLI PATH check using the existing `@david/which`; registry
  runner availability and custom-command executability are not proven.
- Current plain startup creates copier, server and resources before App;
  insert the choice boundary before all three. Existing startup resume
  already picks before server/resources and hands its renderer to App.
- Existing picker state supports initial `current` highlight, scrolling,
  resize and numbered selection. Use `current` for opening position only;
  do not add an in-use mark to the proposed candidate labels.

No runtime/widget trial, real agent, authentication, native clipboard,
installation, startup capture, test or compile run accompanies this design.
Choice-before-start ordering, settings/model precedence after choice,
pre-choice terminal restoration and compiled integration are **untried**.
If reuse does not fit, return to the owner with concrete options rather than
writing a custom list or changing library input/behavior.
