# CHD-387: a sent message reads like a received one

A message an agent sent draws today as its `→ to @name` headline with the
text under `⎿` on one row, cut by OpenTUI in the middle (`...`), even in
ctrl+o's view. The message that answers it, `← from @name`, is drawn as
markdown, wrapped to the window and folded after six lines. The owner
decided (2026-10-15) that a sent message's text is drawn the way a received
one's is: the whole text, as markdown, folded after the same six lines with
the same `… +N lines (ctrl+o to expand)` hint, expanded in ctrl+o's view,
under its `→` headline. The headline (`→ to @name`, `· queued`, its arrow's
tone) is drawn as today.

## After

### Where the body sits

Under the headline, exactly where it is today and where a received body
sits: the first row behind `⎿` in the five-column gutter, every row after
it indented to the same column, no `⎿`. The `→` row itself does not move.

```
 → to @parser · queued
   ⎿  CHD-1 unit 4: points 1 and 2 are good. Four things before I look again:

      1. The fold counts the blank line after the list; drop it, as foldMessage already does for a received message.
      2. foldMessage runs on every render; keep its lines in the same useMemo as the markdown.
      3. The hint names ctrl+o even when the person has rebound it; take the key from useHintKey.
      4. The refusal goes after the body, in the error colour, never folded.
     … +2 lines (ctrl+o to expand)
```

### One layout for both arrows

The body is the received message's body, not a copy of it: the same steps
in the same order, so the two can never drift apart.

1. The text, its escapes stripped (`stripAnsi`), as an agent's text is
   for a received message.
2. Laid out as markdown by `markdown()` at the body's width, `width - 5`,
   blocks joined by one blank row. A numbered list, bold, inline code and
   a fenced block read as they do in a received message; a list item's
   continuation hangs under its text.
3. Folded by `foldMessage`: `MESSAGE_LINES` (six) rows, a last blank row
   dropped before counting, a fold that would end on a blank row ending on
   the row before it.
4. Drawn as `Under` rows, `FILL` (wrapped, never `CUT`), selectable, dim,
   then `Folded` with the hidden count.

How it is shared is the developer's call; the screen only needs both
arrows to go through the same function and component, with the headline
the one thing that differs. Monitors keep their own verbatim layout; a
sent message is never a monitor.

### The fold and its hint

Six rows, counted after wrapping, as a received message counts them, not
the three a tool's output gets: a message is words meant to be read. The
hint is `Folded`'s, the same line under both arrows:

```
     … +6 lines (ctrl+o to expand)
```

`ctrl+o` is read from the binding (`app:toggleTranscript`), so a rebound
key shows its own name. In ctrl+o's view the whole body is drawn and the
hint goes. No new key: ctrl+o already expands every fold in the
transcript, received messages included.

### The states of a send

The headline says the state; the body is the same text in every state.

| State | Headline | Under it |
|---|---|---|
| Pending or running | `→ to @parser`, arrow dim | the text, dim, folded |
| Queued | `→ to @parser · queued`, arrow dim | the text, dim, folded |
| Delivered | `→ to @parser`, arrow in the recipient's colour | the text, dim, folded |
| Refused by chord | `→ to @parser`, arrow `error` | the text, dim, folded; then chord's refusal in `error` |
| Failed with no refusal | `→ to @parser`, arrow `error` | the text, dim, folded; then `Failed` in `error` |

**Pending and running** draw the text at once, as they do today: the
agent has said what it sends the moment the call starts, and a `Waiting…`
line would only stand where the words are. Nothing marks the wait but the
dim arrow, as now.

**Refused and failed** keep the text and add chord's sentence after it.
The owner's ask is to read what was sent; a refused message is the one the
person most needs to read, since the agent will often send it again or do
the work itself. The refusal goes last, after the fold hint, in the error
colour and never folded, the way a monitor's ending sentence follows its
folded lines (`Folded.sentence` in `message.ts`). The red arrow at the top
says it failed before the eye reaches the body; the sentence says why.

```
 → to @parser
   ⎿  Are you still there?
      No agent parser is open in this session; list_sessions names them
```

Folded, the refusal still shows:

```
 → to @parser
   ⎿  CHD-1 unit 4: points 1 and 2 are good. Four things before I look again:
      …four more rows…
     … +2 lines (ctrl+o to expand)
      No agent parser is open in this session; list_sessions names them
```

A message whose text is empty draws no body; then the row falls back to
what it says today (`Waiting…`, `Running…`, `Failed`, or chord's refusal
alone).

### A resumed session

A resumed session replays its record through the same reducer, and the
call carries the text it sent in its input, so its sent messages draw
exactly as live ones: wrapped, folded, the refusal after the body. There
is nothing of its own to draw.

## Colour roles

From `theme/theme.ts`, all already in use on these rows:

- The arrow: dim until delivered, the recipient's colour (`agents`) once
  delivered, `error` when refused or failed, as today.
- The body: dim, like a received body, so what agents said to each other
  reads as quoted beside the agent's own bright replies. Markdown's own
  styling (bold, code) sits on top of the dim, as in a received message.
- The fold hint: dim.
- The refusal or `Failed`: `error`.
