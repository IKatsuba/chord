# CHD-568: an MCP tool for the settings file

The owner corrected Q322 on CHD-565: the tool is for all of settings, not `offeredAgents`
alone. Q329 made it this task of its own, which starts after CHD-565 merges. Decided on the
CHD-565 board:

| Question | Decision |
| --- | --- |
| Q330, how a write is confirmed | chord's box on every write |
| Q331, which keys it may write | The allowlist below: kinds A and B. Kind C stays a hand edit |
| Q332, which file, and secrets | The user's file only; `env` and `headers` values masked on read |

**A note on Q331.** CHD-565's board records Q331 as choice 1, Every key. That is a relay error by
main, who gave the owner the options in a different order, and the correction is a comment
on CHD-565. The decision is the allowlist.

**Why kind C is out.** chord's server runs outside any agent's sandbox or permission mode, so
a write to those keys would let a model choose a command chord runs, or turn off the
person's ok, past every limit the runtime has.

## Every key, by kind

The keys of `SettingsFile` (`src/settings.ts:63`), with `AgentSettings` (`:19`) and
`TeamSelection` (`src/session/budgets.ts:10`).

| Key | Kind | What a write means | Takes effect |
| --- | --- | --- | --- |
| `theme` | A, user-only | Colours | At once, as `/theme` |
| `editorMode` | A, user-only | The prompt's editing | At once, as `/vim` |
| `mouse` | A, user-only | Mouse reporting; read as the terminal opens (`src/main.tsx:146`) | Next start |
| `copyOnSelect` | A, user-only | Copy on release; a prop (`src/main.tsx:660`) | Next start |
| `offeredAgents` | A, user-only | The menu; names checked against the catalog | `/new` at once, start screen next start |
| `preferredNotifChannel` | B, either file | How the terminal is told | Next start |
| `agent` | B, either file | The default agent. The picker's highlight, but under `-p` it is what runs | Next start |
| `agents.<name>.model` | B, either file | That agent's model. Spends the person's account | Next start |
| `agents.<name>.effort` | B, either file | That agent's effort. Spends too | Next start |
| `teamSelection.intent`, `.prefer.agent`, `.prefer.model` | B, either file | A preference for optional team selection | At once, read at each selection (`src/main.tsx:522`) |

**The allowlist is exactly those keys.** A new key is closed until it is named here.

**Kind C, read but never written:** `agents.<name>.command`, `mcpServers.<name>`,
`agents.<name>.permissionMode`, `agents.<name>.mcpServers` and
`teamSelection.constraints.*`. A person edits them in the file by hand.

`keybindings.json` and `.mcp.json` are not settings keys and stay out.

## Which file

The user's file alone. A project's file outranks the user's for every kind B key
(`mergeSettings`, `src/settings.ts:362`), so where it holds the key, a write changes nothing
in this directory. The tool still writes, as it is the person's setting everywhere else; the
answer's `shadowedBy` names the project's file, and the call's row says so in `warning`:
`.chord/settings.json sets this too, and wins here`.

## What it takes and answers

`settings`, one tool. A `path` is a list of keys, not a dotted string, as an agent's name
may hold a dot.

| Input | Means | Answer |
| --- | --- | --- |
| `{ action: "read" }` | Every key | `{ user, project, effective, problems }` |
| `{ action: "read", path }` | One key | The same, of that key |
| `{ action: "set", path, value }` | Set the value at `path` | `{ path, before, after, file, saved, takesEffect, shadowedBy? }` |
| `{ action: "remove", path }` | Remove the key, and parents it leaves empty | the same, `after` absent |

- **`action` is explicit, not `value: null` for removal,** because `teamSelection.prefer.model` takes `null` as a real value. Removing `offeredAgents` is how a person gets the whole catalog back.
- **Reading masks secrets.** `mcpServers.*.env` and `.headers` values read as `"***"` and are not sent to the model. The same on the call's row.
- **Same value as now:** nothing asked or written, `saved: false`, `unchanged: true`.
- **`takesEffect`** is `now` or `next start`, from the table above.

## Writing and keeping the file

`src/AGENTS.md:5` allows settings writes only through `saveTheme` and `saveEditorMode`; it
gains the tool's writer. The MCP configuration stays read only.

`saveSetting` (`src/settings.ts:869`) sets one top-level user-only key. The new writer
takes a path: read the raw JSON, set or remove at the path, creating parents, and write it
whole by the same atomic rename. So one agent's `model` keeps that agent's `command`, and
every other key stays, unknown or wrong ones too. It rewrites the layout to two-space
JSON, as `/theme` does. A leaf is replaced whole, as `offeredAgents` is one list.

A file that is not valid JSON or not an object is refused and left alone, as today:
`~/.config/chord/settings.json was not saved: it is not valid JSON`. No home: refused. Two
windows are last write wins.

## Validation

First problem refused, nothing written:

1. **The path must be on the allowlist:** `No setting agents.claude.modle`, or, for kind C, `chord does not write agents.claude.command; edit the settings file by hand`. `__proto__` and the like are never keys.
2. **The value goes through the key's own schema,** validated alone, not through `parseSettings`: its drop loop turns a wrong array item into a whole file ignored. So `SettingsFile`'s shape is exported per key.
3. **Beyond the schema:** `offeredAgents` names against the catalog; `agents.<name>.*` for a name chord knows, as the tool cannot define one.
4. **Ids stay unchecked:** `model` and `effort` are the agent's own, and only a started agent knows them, as `src/teams.ts:46` says. A wrong one behaves as it does in the file today.

**An existing bad key elsewhere stays as it was** and is reported at the next start as
today. The tool was not asked about it. A bad value at the path itself is replaced.

## Callers and `-p`

Main alone: `toolsOf`'s `person` case and `toolNames('person')`, with the fork refusal, as
`propose_team`. Long-lived children, leads, members and tasks do not get it. Under `-p` the
tool does not exist, as chord's server starts only for a window (`src/main.tsx:609`).

## The running window

Nothing watches the file, and sessions hold what they were started with. A write takes
effect at once only where a path already exists: `theme` and `editorMode` by the same
state change their commands make, `offeredAgents` in `/new`, and `teamSelection` because
it is read at each selection. Everything else is the next start, and the answer says so.
Open sessions never change. Other windows and hand edits: next start, except
`teamSelection`.

## The box

On every write, under a runtime's auto or bypass mode too: `Conversation.ask`
(`src/session/conversation.ts:2454`) reads no mode. A read never asks. As `propose_team`, the
call is served `pending` with its change drawn on it, above an unchanged `SaveBox`.

- A value wraps and is never cut.
- Answered: `Saved to …`, or `Not saved; the person will say what to change`. Withdrawn: refused, nothing saved. The keys are the permission box's; there is no new action.
- A box for kind C, with `No` first and the value in `warning`, is out, as those keys are not writable.

## Its size

About six units: the path writer and its rule; per-key validation; the read with masking;
the write with its box, row and headline; the live pick-up; and a fake scenario, tests and
the guide. None of them touches CHD-565's list, which this tool edits as one more key.
