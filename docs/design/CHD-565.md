# CHD-565: the list of agents chord offers

The build's specification, on the owner's answers (Q322–Q326, 2026-10-30). With
the setting absent, chord behaves as it does now. The MCP tool is redrafted below for
the whole settings file, on the owner's correction of Q322; nobody builds it before the
owner has answered.

## Decisions

```json
{ "offeredAgents": ["claude", "codex", "my-agent"] }
```

| Question | Decision |
| --- | --- |
| Where it is set | The user's settings file, and an MCP tool for the whole file (redrafted below). No screen and no key |
| Shape | `offeredAgents`, an array of names; its order is the order on screen |
| Files | The user's file only. In a project's file it is reported and left out, as `theme` is |
| What it governs | The start screen and `/new`'s completion. Nothing is refused |
| A listed CLI PATH lacks | Shown as `cursor · Cursor · not on PATH`; picking it gives today's refusal |
| An unknown name | Dropped, and named on the page |
| `[]` | Invalid: reported, and counts as absent, so the whole catalog shows |
| Only unknown names | No fall back: `No agents available` and a sentence naming the setting |

Rejected, one line each:

- A screen inside chord (`/agents`, `e` on the page): a new tick-and-reorder widget for a list set once.
- A later file replacing the list, joining lists, or a flag on each agent: the list is about a person, not a project.
- Governing `list_agents` too, or an allowlist refusing names: a saved team on another runtime would break, for a setting meant to shorten a menu.
- The PATH filter on a listed agent, or a dim row that cannot be picked: a name the person wrote would vanish, or `PickerList` would need disabled rows.
- A settings problem alone for an unknown name, an unknown row, or ignoring the whole key: the page would say nothing, or a typo could be picked, or one typo would cost the list.

### What does not change

- `chord agents` stays whole: it is where the names come from.
- `list_agents`, `open_agent`, team files and `propose_team` read `runtimes`, which stays whole.
- `chord <agent>`, `/new <agent>`, `--agent-command` and `--resume` work for a name outside the list. `@@` lists open recipients, never the catalog.
- `agent` only sets the opening highlight; outside the list, the first row is highlighted, as today. A route that skips the picker (a named agent, `--resume`, `--agent-command`) is not offered the list, but its window still reports unknown names, as `/new` in that window reads the list. `-p` reads nothing.
- A list of one still asks: the page never picks for the person.

## The setting

**`src/settings.ts`.** `offeredAgents` joins `USER_ONLY` (`:54`), so `loadSettings`
reports it in a project's file and `saveSetting` takes it. `mergeSettings` (`:362`)
copies key by key, so it needs its own line.

**`[]` is invalid:** one problem line, and the key counts as absent (Q326).

**A wrong element: open on Q327, the owner's.** `parseSettings` drops the path of each
issue, and deleting an array's element leaves a hole that fails again: after eight rounds
the whole file is ignored, `theme` with it. (Seen with `[1, "x"]` in
`teamSelection.constraints.agents`, today's behaviour there.) Checking the array as one
value would make `[1]` and `""` cost the key alone, with its issue at `offeredAgents`,
but it works around the library's per-item check, so it waits for the answer. Whatever
the answer, this section and the checks below follow it.

**A repeated name is dropped silently, its first place kept.** The screen is right
either way, and a problem line would be noise. It is not an unknown name.

**`offeredAgents` in `src/agents.ts`,** with its tests in `tests/agents_test.ts`:

```ts
function offeredAgents(
  catalog: readonly ListedAgent[],
  offered: readonly string[] | undefined,
): { agents: readonly ListedAgent[]; unknown: readonly string[] };
```

- Absent: `agents` is the catalog less an own CLI PATH lacks, as the start screen has it today.
- Set: the names in the array's order, repeats dropped, each its catalog row, a missing CLI's too; `unknown` holds the names the catalog lacks, in order.

The catalog is `listedAgents(agentCommands(layers))`, so a name a settings file gives a
command is known, a project's too. Such a name is unknown in a directory without that
project's file; the note says so there, and the owner's user-only choice accepts this.

**Unknown names are settings problems too,** one each, in the user's file:
`"offeredAgents": no agent named cdex, left out`. They go through `report` to stderr
and into the window's `warnings`, which hold every name; the page's note is the short form.

**The note is one row, never wrapped.** A page's rows should not grow with a typo, and
the problem lines hold every name. A pure `unknownNote(names, width)` fits whole names
at `column − 2`, in order, and counts the rest as `+N more`, reserving that word's room;
at least one name always shows, and `CUT` cuts what is still too wide. The sentence in
the only-unknown state does not list names, so it does not repeat the note: no note there.

### Rows, against `startLayout`

`startLayout` takes a new `noteRows`, 0 or 2 (the gap and the row). The step is still
decided without it, so **a note never moves a window to another step**, and a list stays
the last thing to give way:

```ts

// pageRows gains noteRows only where `note` holds.
```

A note that would cost a list row is not drawn; the problem lines still say it. In the
only-unknown state `lines` is 2, and the sentence counts as the list's second row.

## The MCP tool: redrafted for the whole settings file, not to be built yet

The owner corrected Q322: the tool is for all of settings, not `offeredAgents` alone. The
`offered_agents` draft and Q328 are withdrawn. Everything here waits on the owner's
answers below.

**The point to weigh hardest.** chord's server runs in chord's own process, outside any
agent's sandbox or permission mode. So a tool that writes `agents.<name>.command` lets a
model, or text a model read, choose a command chord will run on this machine at the next
start, outside every permission the runtime has, and go on running it at each start
after. `agents.<name>.permissionMode` lets an agent turn off the person's ok for its own
later sessions. `mcpServers` also starts commands. A runtime kept to its project by a
sandbox cannot reach the user's file today; this tool would hand it that reach. Where an
agent can already edit that file with its own tools, the tool adds no new power, and no
box of chord's stops that route.

**Kind A** can only be in the user's file, so what the tool writes is what applies.
**Kind B** can also be in a project's file, which wins: see below. **Kind C** is the
weighing above.

### Which file

The user's file alone is the draft; the alternative is question 3. A project's file
outranks the user's for every kind B and C key (`mergeSettings`, `src/settings.ts:362`).
So where the project's file holds the key, a write to the user's file changes nothing in
this directory. The tool still writes, as it is the person's setting everywhere else; the
answer's `shadowedBy` names the project's file, and the call's row says so in `warning`:
`.chord/settings.json sets this too, and wins here`.

### What it takes and answers

`settings`, one tool. A `path` is a list of keys, not a dotted string, as an agent's name
may hold a dot.

| Input | Means | Answer |
| --- | --- | --- |
| `{ action: "read" }` | Every key | `{ user, project, effective, problems }` |
| `{ action: "read", path }` | One key | The same, of that key |
| `{ action: "set", path, value }` | Set the value at `path` | `{ path, before, after, file, saved, takesEffect, shadowedBy? }` |
| `{ action: "remove", path }` | Remove the key, and parents it leaves empty | the same, `after` absent |

- **`action` is explicit, not `value: null` for removal,** because `teamSelection.prefer.model` takes `null` as a real value. Removing `offeredAgents` is how a person gets the whole catalog back.
- **Reading masks secrets.** `mcpServers.*.env` and `.headers` values read as `"***"` and are not sent to the model. The same on the call's row. See question 4.
- **Same value as now:** nothing asked or written, `saved: false`, `unchanged: true`.
- **`takesEffect`** is `now` or `next start`, from the table above.

### Writing and keeping the file

`src/AGENTS.md:5` allows settings writes only through `saveTheme` and `saveEditorMode`; it
gains the tool's writer. If `mcpServers` stays writable, `src/AGENTS.md:6` and the
top of `src/mcp.ts`, which say the MCP configuration is read only, change too.

`saveSetting` (`src/settings.ts:869`) sets one top-level user-only key. The new writer
takes a path: read the raw JSON, set or remove at the path, creating parents, and write it
whole by the same atomic rename. So one agent's `model` keeps that agent's `command`, and
every other key stays, unknown or wrong ones too. It rewrites the layout to two-space
JSON, as `/theme` does. A leaf is replaced whole: `mcpServers.<name>` is one entry, and
`offeredAgents` one list.

A file that is not valid JSON or not an object is refused and left alone, as today:
`~/.config/chord/settings.json was not saved: it is not valid JSON`. No home: refused. Two
windows are last write wins.

### Validation

First problem refused, nothing written:

1. **The path must be a key in the table above,** and within what question 2 allows: `No setting agents.claude.modle`, or `chord does not write agents.claude.command`. `__proto__` and the like are never keys.
2. **The value goes through the key's own schema,** validated alone, not through `parseSettings`: its drop loop turns a wrong array item into a whole file ignored, as this document's array section says. So `SettingsFile`'s shape is exported per key.
3. **Beyond the schema:** `mcpServers.<name>` through `src/mcp.ts`'s check, as its schema is `unknown`; `offeredAgents` names against the catalog; `agents.<name>.*` for a name chord knows, or, where `command` is allowed, one this call defines.
4. **Ids stay unchecked:** `model`, `effort` and `permissionMode` are the agent's own, and only a started agent knows them, as `src/teams.ts:46` says. A wrong one behaves as it does in the file today.

**An existing bad key elsewhere stays as it was** and is reported at the next start as
today. The tool was not asked about it. A bad value at the path itself is replaced.

### Callers and `-p`

Main alone: `toolsOf`'s `person` case and `toolNames('person')`, with the fork refusal, as
`propose_team`. Long-lived children, leads, members and tasks do not get it: a member
should not reconfigure the person's chord, least of all a team's limits. Under `-p` the
tool does not exist, as chord's server starts only for a window (`src/main.tsx:609`).

### The running window

Nothing watches the file, and sessions hold what they were started with. A write takes
effect at once only where a path already exists: `theme` and `editorMode` by the same
state change their commands make, `offeredAgents` in `/new`, and `teamSelection` because
it is read at each selection. Everything else is the next start, and the answer says so.
Open sessions never change. Other windows and hand edits: next start, except
`teamSelection`.

### The owner's choices

**1. How a write is confirmed.** A read never asks.

| Option | Under a runtime's auto or bypass | Under `-p` | Trade-off |
| --- | --- | --- | --- |
| **chord's box, every write, every kind** | Still asks: `Conversation.ask` (`src/session/conversation.ts:2454`) reads no mode | No tool | One rule. A key press on a rare action, two questions where the runtime also asks for MCP tools |
| **By kind: A and B written with a row, C the box** | A and B unasked; C asks | No tool | Fewer questions. A table to keep right for each new key, and the agent can quietly spend more through `model` |
| **The runtime's permission alone** | Nothing asks, kind C included: a command is set with nobody asked | No tool | Fewest questions, differs per runtime. Not acceptable for kind C |

**Recommendation: the box on every write.** It is `propose_team`'s rule: chord writes a
person's config on their yes. The answer does differ by kind in what the box says: a kind
C box puts `No` first and highlighted, and draws the value and what it does in `warning`.

**2. Which keys it may write.**

| Option | Means | Trade-off |
| --- | --- | --- |
| **Every key** | What the owner asked for | Kind C through a box only. The box is the one defence, and a person reading fast in a long run is the weak point |
| **Every key but kind C, as a rule** | C is refused; a person edits the file by hand | Closes the hard cases. A new key is writable unless someone remembers to exclude it |
| **An allowlist: kinds A and B** | The same today, written as names | A new key is closed until named, one line each. `settings` still reads every key, secrets masked |

**Recommendation: the allowlist.** Kinds A and B are what a person would ask an agent to
change, and the five kind C keys are where one wrong yes runs a command or removes the
person's ok, for good, outside the runtime's limits. This narrows what the owner asked,
which is the owner's to accept. If the answer is every key, the kind C box below is the
minimum: `No` first, the value whole and never cut.

**3. Which file it writes.** User's file alone (**recommended**: it is the person's own,
and a project's file is shared through git, so a write there changes what teammates run),
or also the project's, with the box asking which, as `propose_team` does. Writing a
project's file would be the only way to change a key a project shadows; the person can
still edit it by hand.

**4. Whether a read may show secrets.** Masked (**recommended**: a read goes to the model's
provider and into the transcript), or whole, which is simpler and lets an agent report a
wrong token. The agent's own file tools may read the file anyway, where they reach it.
