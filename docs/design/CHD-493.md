# CHD-493 — one main session per chord process: tabs go

The owner's call (2026-10-21): chord drops tabs. A chord process runs one
main session, with its children (long-lived agents, team members, task
agents, subagents, monitors) as today. Several sessions side by side are
the terminal's: panes, Chorded. This design settles what goes, what each
feature that names a tab becomes, how old window records are answered,
what is left of CHD-445, and the units the ship team builds it in.

The architects' drafts, read against origin/main `3f6f6656` (v0.57.0), are
the record: `evidence/CHD-493/drafts/` (`brief.md`, `protocol.md`,
`interface.md`, `runtime.md`). They carry the line references and the full
test inventories; this file is what was decided.

**The short of it: the window becomes what chord with one tab already
is.** Every screen a single-tab chord draws today stays as it is. What
goes is what only exists with a second tab, the keys and commands that
open, reach or count tabs, the window records, and `--resume` of several
ids. Nothing chord sends the agent over ACP changes, and the session
record's format does not change.

recommended option while it is open, and marked where the design depends
on it:

## What stays

The header, the transcript, the prompt, the status line, the permission
prompt and forms, the agents list under the prompt and its keys (↓ from an
empty prompt, ↑ ↓ / j k, Enter, Esc, `x`), the background summary and view,
`/team`, monitors, `/clear`, `/model`, `/config`, `/mcp`, `/theme`, `/vim`,
the crash screen, the splash, `-p`, `--continue`, `--resume <id>` and
`--resume` with no id. A picked child keeps its own draft, queue, scroll and
dialogs through the same per-key state tabs used: `SessionState` is still
kept by key in `WindowedState.sessions`; only the level above children goes.

## Each feature that named a tab

- **`ctrl+x a`** (`session:attention`) stays, same name, `Global`,
  rebindable, and does exactly what it does with one tab today: the main
  session's own request between turns first, then the agent of this
  session (main or a child) that has waited longest, round on each press;
  from the background view it closes the view first. With nothing waiting:
  `Nothing waits on you` (was `No session waits`). `ctrl+x` stays a leader:
  `ctrl+x a` keeps its key and a person's own `ctrl+x …` chords keep a
  leader line. Freed keys are bound to nothing.
- **The agents list** is unchanged on screen and in keys. Its main row may
  later show the session's title (CHD-445, below).
- **The background view** (CHD-487): `Background · 3 in this session` (was
  `in this tab`); the guide's "the front tab's items" reads "the session's".
- **The waits notice** reads only the session's own agents: one named
  (`● docs needs your permission`, `● docs asks for input`, a task by its
  box's name), more counted as `● N agents wait`; failures `✗ parser
  exited`, `✗ parser's turn failed`, counted by kind. The `replied` branch
  goes (it fired only for a tab; a child's reply is the list's `✓ new
  reply`). `TabBehind` becomes `AgentWaiting { name, wait, task? }`.
- **Terminal notifications** (OSC 9/777/BEL) name the main session by its
  agent alone, as one tab reads today, a child by its name, a member with
  its run (`tester (bugfix)`). `fake (2)` never appears.
- **OSC 7501** (CHD-382) folds the main session and its children: the same
  rule, the same tie-break, main first then children in opening order,
  which is what "further left" meant inside one tab. With one session the
  record is byte for byte today's one-tab record. Its `title` (CHD-491) is
  the main session's `Conversation.title ?? openSessionLabel(firstPrompt)`;
  Q111 (which tab's name) has nothing left to choose, Q119 holds as it is.
- **`chord_session`** (CHD-492): the main session's id; the table row "until
  CHD-493 removes tabs: the front tab changes" goes, nothing else. Under
  `/clear`'s row (empty at once, the new id once its first prompt is
  flushed) covers it; `/new` leaves main's session as it is (U6).
- **`/resume`** lists sessions only, newest first; subtitle `fake's earlier
  sessions in this directory.` (no "and saved windows"); with ctrl+a the
  directory column is the session's own. `open in N` becomes `open now`,
  which marks a session open as a child of this one; Enter on it picks the
  child and loads nothing twice. Enter on any other row replaces the main
  session in place, as it does inside a tab today (`pickSession` calls
  `Conversation.clear()` with the chosen id): the transcript empties, the
  chosen past plays in, the old main's long-lived children close with it as
  on `/clear`, the refusals stay. Empty: `No earlier fake session to resume,
  here or in any other directory.` A window's sessions were always listed
  one row each, so nothing becomes unreachable; a codex session that lived
  in a window started as `chord claude` is now reached from `chord codex`'s
  `/resume` or by its command.
- **The start picker** (`chord --resume` with no id): the same rows,
  `Pick one of fake's earlier sessions to open.`; nothing anywhere: `No
  earlier <agent> session to resume.` (drops "or window").
- **`/status`** reads as one session reads today, with no `Sessions` row.
- **Closing and quitting.** ctrl+d and `/exit` quit at once, children and
  teams closing with it, as one tab does today. ctrl+c twice stays, its
  line `Press ctrl+c again to quit` without a count. `x` on a busy child or
  team lead keeps its arming. `closePicked` on `main` says `main is the
  session · ctrl+d quits` (was `· ctrl+x k closes it`). The quit prints
  `Resume this session with:` and the main session's one command, when a
  prompt or message went to it; children are never printed.
- **`/cost`** has no tab level: top-level rows are `main` (and each main
  session `/clear` or a pick let go), each child, each team run with its
  members, each task under whoever started it; the total reads `Total` (was
  `This window`).
- **The shortcuts panel**: the leader entry becomes one plain entry,
  `ctrl + x a for what waits on you` (`actions: ['session:attention']`,
  `commands: ['key_pending', 'attend_session']`); `SESSION_ACTIONS`,
  `sessionDoes`, `LEADER`, `leaderLines` go. The panel keeps its 40 lines.
- **A keybindings file binding a removed action** keeps working: that one
  binding is left out with its own words, `keybindings.json: session:new
  went with tabs: chord runs one session, ignored`, wherever keybinding
  problems are said today. `bindings.ts` keeps a `REMOVED` list of the
  eleven names, read before `isAction`; `null` on a key one of them held is
  no problem. Nothing in the file is rewritten.
- **`list_sessions`** stays and answers one row: the caller's main session,
  its id, runtime, model and long-lived agents (how an agent finds its
  children again after a compaction, and what chord's refusals point to).
  `tab` goes from the answer and from `SessionRow`/`OpenSessionView`. Its
  transcript row (`transcript/tools/chord.ts`) draws the runtime alone with
  `(you)` and the agents counted, and ignores `tab` in an answer a 0.57.0
  record kept, so old records still draw. Description: "The session chord
  runs: its id, runtime and model, and the long-lived agents open in it, by
  id and name; yours marked `you`."
- **`Caller.key`** stays the main session's key, fixed for the process, as
  a tab's key was fixed across its `/clear`s and picks (see **[G]** below).

### `/new` opens an agent beside main (U6) **[N]**

The owner answered Q153 with neither option: `/new` creates a new agent and
moves the view to it, as if the main session had asked chord's MCP
`open_agent` for one. It is a child agent of this process and shows in the
agents list. `/new <agent>` does the same with that agent. This replaces
U2's `/new` as `/clear`'s alias (99f08db7); `/clear` keeps its own name
and loses the alias.

What the code and the owner's words settle, each with its reason:

- **Who owns it: main.** "As if the main session had asked `open_agent`"
  and "a child agent of this process": `/new` runs `openAgent(main.key,
  args)`, the path `open_agent` takes, so the child is main's, as a child
  main opened is. This holds with the view on a child too: chord has one
  main, and only main opens long-lived agents of its own (a lead opens its
  team's members by file, not by `/new`). `/team run` is the precedent: the
  person's command runs `run_team`'s path for main (`runTyped`).
- **Its name: `open_agent`'s default.** `/new` gives no name, so
  `childName` names it after its runtime, numbered past the first and never
  `main` or `chord`: `fake`, then `fake 2`; `codex`. The owner gave `/new`
  no name argument, so none is added.
- **The cap and the refusals: `open_agent`'s.** `startRefusal` (a runtime
  chord does not know, one not installed, a model or mode refused) and
  `fullRefusal` (`MAX_CHILDREN`, 8) answer as they answer `open_agent`, shown
  as a failed note under `/new`, as `/team run` shows them. Nothing opens
  and the view stays.
- **What the path gives it, the same as main's own child:** an MCP token as
  a child (`Caller` role `child`, main's key, its id); `send_message` from
  main reaches it and its own reach main (its parent is main's
  conversation); main's `close_agent` and the person's `x` in the agents
  list close it; `/clear` closes it with the session it lets go, as any
  child; a start that fails tells main `… did not start: …` and shows in
  its view, as for `open_agent`. A person-opened child lacks nothing a
  main-opened one has, but a first prompt from main (below).
- **Main is told, and the call is drawn as main's.** Main did not ask, so,
  as for `/team run`, the call is drawn in main's transcript as its
  `open_agent` call (`ranTyped`), and a note goes ahead of main's next
  prompt (`aside`), not a turn of its own: `The person opened @fake 2
  (fake) with /new; it reports to you, and send_message reaches it.` Without
  it main would not know an agent of its own exists, which "as if main had
  asked" rules out.
- **The view moves to it** at once, as `ctrl+x a` or Enter in the agents
  list moves it: the prompt box is titled with its name (`╭─ fake 2 ─`), the
  status line is its own, and the agents list under the prompt gains its
  row. Main's turn, if one is running, goes on.

The owner's answers to what they did not settle:

- **[N1] No first prompt** (Q187, option 1). The child starts idle; its
  first turn is the first prompt the person sends in its view, the
  person's, not a message from main. Main's `Open(…)` row says `opened
  with /new` where a first prompt would be, and the note ahead of main's
  next prompt says it has none yet.
- **[N2] A bare `/new` opens main's runtime** (Q188, option 1), whichever
  agent is in view.
- **[N3] Model, effort and mode as `open_agent` gives them with none
  named** (Q189, option 1): the runtime's own model and effort, and the
  settings' mode (`startup.starting.mode`), as `childConversation` sets
  them. Not main's: a `/new` on main's runtime may start on another model
  than main is on.

### `↓` sets a draft aside (U10, Q183)

The owner answered Q183 with a third way: `↓` in a prompt with text moves
the draft aside, as if the history's last entry were always an empty
prompt. The field empties, the draft is kept, and `↑` brings it back. One
more `↓` from the empty prompt goes into the agents list, as today. So
`↓ ↓` leaves an agent with a draft, and the draft is there on return. This
replaces the paragraph above that keeps a non-empty draft from the list.

The walk, oldest at the top:

```
  … older prompts
  the newest prompt
  the oldest kept draft        kept drafts, a stack: ↑ reaches the newest
  …                            first, then older ones, then history (Q191)
  the newest kept draft
  the field                    what the person is typing, or empty
  the agents list              ↓ from the empty field, as today
```

`↓` from a field with text pushes it onto the stack as the newest kept
draft and leaves the field empty.

What the code and the owner's words settle, each with its reason:

- **The key is `history:next`**, `↓` and whatever a person binds to it:
  the owner put the draft in the history's walk, so it is the walk's own
  step, `newerSteps` in `src/ui/app/keys.ts`. No new action, no new key.
- **When `↓` sets a draft aside:** the draft is not empty, the box is not
  walking history (`history.index` undefined), and no command menu or file
  list is on screen, whose `↓` is theirs, as `newerSteps` gates today. In
  history search, `↓` is the search's, as today.
- **While walking history**, `↓` steps to a newer prompt as today and, past
  the newest, to the draft (`newer`). Only a `↓` from the draft itself sets
  it aside, so from a recalled prompt it takes one `↓` per entry and then one
  more, never a jump past the draft.
- **A draft of several lines:** `↓` moves the cursor down first; only `↓` on
  the last line reaches `newerSteps` (the textarea gives it `onNewer` there),
  and that one sets the draft aside. A recalled prompt left untouched still
  walks from any line, as `walking` says today.
- **What is kept** is the whole draft as it stands: its text, its pasted
  images (`state.images`, whose placeholders are in the text), bash mode
  (`!`), and the cursor where it was. `↑` from the empty prompt puts all of
  it back, the cursor where it was left, so `one X|two` comes back with the
  cursor after `X` (U2's per-agent guarantee, below). History's own recall
  keeps putting the cursor at the end of a recalled prompt.
- **Where it is kept: with the agent**, beside its field in that agent's
  state, not in the window's history, which all agents share
  (`useState(emptyHistory)` in `App.tsx`). So `↑` in another agent never
  brings this agent's draft, and each agent keeps its own.
- **`↑` from the field** (its first line, as for history) shows the newest
  kept draft, then older ones, then history, with what the field held kept
  as the walk's draft and given back by `↓` at the bottom, as history keeps
  it today. With nothing kept, `↑` walks history at once, as today.
- **Back at the agent** (Q190, the owner's option 1): the field is as it
  was left, empty after `↓ ↓`, and the draft is one `↑` away.
- **Sending and `/clear` leave the stack** (Q191): a prompt sent from the
  field, or `/clear`, does not touch the kept drafts; they belong to the
  agent's prompt, not to its session. Sending a kept draft shown by `↑`
  takes it off the stack, as it leaves the field. A kept draft emptied by
  hand (`ctrl+c` while it is shown) goes too.
- **`↓` from the empty prompt** goes into the agents list when there is
  one, as today; with no children open, it does nothing, as today, and the
  draft stays aside.
- **Vim insert mode** is the textarea's: `↓` as above. **Normal mode:**
  `j` (and `↓`) on the last line sets the draft aside as `↓` does, since it
  shares `newerSteps` with it (D3, settled by the lead), and `k` from the
  empty prompt brings it back as `↑` does.

On screen nothing new is drawn: the field empties as `ctrl+c` empties it,
and the draft's return redraws it as it was. The status line keeps its
words; nothing says a draft is kept (see [D1]).
