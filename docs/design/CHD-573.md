# CHD-573: `chord acp`, chord as an ACP agent over stdio

`chord acp` runs chord with no interface as an ACP agent on stdin and stdout. An
ACP client starts it as a child process and drives, through it, the agents and
teams chord runs. Toward those agents chord stays the ACP client it already is.
Transport for this work is stdio only.

The owner's answers are the comments on CHD-573, 2026-11-02, and each has its
entry in `docs/decisions.md`. The record of how they were reached is in
`docs/design/evidence/CHD-573/`: the brief, three drafts with their `file:line`
evidence and the options the owner did not take, and the SDK trial. Where a
draft and this file differ, this file holds. Line numbers are at the head of
`next` when this was written. CHD-574/576, CHD-579/580, CHD-581 and CHD-575 are built;
CHD-582 remains planned. Adapter behaviour is read from
`docs/agent-capabilities.md`, not run.

## Two rules over everything

**The target.** The design targets a client that declares `subagents` and
chord's extensions. Private extensions on top of ACP are the normal way. No tool
or command gate or text fallback is built for a client that declares less: it
gets what plain ACP carries. Child traffic is dropped and child asks are refused
with a stderr line, per place, so none waits unseen. The guide says so.

**One agent surface.** chord absorbs every agent's specifics, and `chord acp` shows
no differences between agents. "This agent lacks X" is decided inside chord,
reusing what the window already does. What cannot be absorbed is listed below with
the reason.

## The package

- One process: one client connection, one main runtime, any number of upstream
  sessions, each its own `Conversation` and its own agent process.
- ACP v1 from the SDK's `/unstable` entrypoint, on `agent({ name })`, both ways.
- Everything is forwarded as it comes, a late update and a turn nobody prompted
  too, less one drop-only check for what a client has not declared.
- The client answers permissions and forms. Agents keep their own files and
  terminals.
- Recorded as the window's sessions are; `session/list`, `load` and `resume` read
  those records.
- Teams by chord's own commands in the agent's list; children by `subagent_update`;
  six extension methods for the rest in CHD-575, at 1.0.0-next.2.

## What a person sees

`chord acp` draws nothing and has no keys: no window, alternate screen or raw mode,
so `keys.ts`, `bindings.ts` and the shortcuts panel gain nothing. Its `--help` line
describes it. A client's stdin is a pipe and sees no note.

### Run by hand, stdin a terminal

Only `process.stdin.isTTY` decides the note, in a pure function beside the command.
It goes to stderr, plain, with no escape bytes or theme role. The longest line is
77 columns, so 120x40 and 80x24 are the same screen.

```text
$ chord acp
chord: acp serves ACP on stdin and stdout, for a client that starts it.
chord: nothing to press here. Ctrl-D or Ctrl-C leaves; `chord` opens a window.
█
```

A line that is not JSON gets the SDK's answer, on stdout. A request gets an answer;
the terminal wraps a long one, at 80 sooner than at 120.

```text
hello
{"jsonrpc":"2.0","id":null,"error":{"code":-32700,"message":"Parse error"}}
{"jsonrpc":"2.0","id":1,"method":"initialize","params":{"protocolVersion":1}}
{"jsonrpc":"2.0","id":1,"result":{"protocolVersion":1,"agentInfo":{"name":"chord",…
█
```

| stdin | stdout | Result |
| --- | --- | --- |
| pipe | pipe | A client: no note |
| terminal | terminal | The screens above |
| terminal | pipe or file | The note on stderr; ACP goes to the file |
| pipe | terminal | No note; ACP lines on screen, ending at the pipe's EOF |

Ctrl-D is EOF: exit 0, nothing further said. Ctrl-C is SIGINT: the way out, then
death by the signal. Both are the terminal's, and cannot be rebound. The note's
wording and chord's own start were not run this way; a throwaway SDK agent gave the
rest in tmux at both sizes.

`chord acp` is a subcommand as `agents` and `upgrade` are, so it takes the word from
any agent configured under the name `acp`, as those do. `chord --agent-command … acp`
was not tried; CHD-574 tests what it does. A Cliffy usage error prints the help to
stdout (`@cliffy/command/command.js:1365`), so the command uses Cliffy's own
`.throwErrors()` and writes the message to stderr.

## Methods

### The client calls chord

| Method | Answer | Reaches the agent as |
| --- | --- | --- |
| `initialize` | yes; no agent is started | nothing |
| `session/new` | when the agent is up | spawn, `initialize`, `session/new` |
| `session/load` | replays the record, then answers | `session/resume` when recorded, else `session/load` (`session.ts:841`) |
| `session/resume` | no replay | the same |
| `session/list` | chord's records, all in one answer, no cursor | nothing |
| `session/close` | yes | `Conversation.close()`; the record stays |
| `session/prompt` | at its own turn's end | `Conversation.send`, bound as below; chord commands except `/team new` never reach it |
| `session/cancel` | notification | `Conversation.interrupt` for main or a long-lived child; `TaskAgent.cancel` for a chord task; `stopSubagent` for an adapter subagent |
| `$/cancel_request` | a prompt's cancels that prompt alone; no cancellation of a chord command in flight | `Conversation.cancelPrompt` |
| `session/set_config_option` | the whole `configOptions`; `type: "boolean"` is -32602 | `setMode`, `setModel` or `setOption` by the option, each on its queue |
| `session/set_mode` | `{}`, for a client that calls it | `Conversation.setMode` |
| `authenticate` | -32601; `authMethods: []` | nothing |
| `_chord/*` | extension results below | the same session and host operations |

Not advertised: `logout`, `session/delete`, `session/fork`, `providers/*`, `mcp/message`,
`_session/steering`. `session/set_model` is not in the schema: `Session.setModel` uses
it behind the one `model` option.

### chord calls the client

| Method | When |
| --- | --- |
| `session/update` | every update, under "What is not sent" |
| `session/request_permission` | every ask and plan ask |
| `elicitation/create`, `elicitation/complete` | as asked, raw, whatever the client declared. An error answer is `cancel`. One scoped to a request and not a session is cancelled: no request here is the client's |

### `initialize`

```json
{
  "protocolVersion": 1,
  "agentInfo": { "name": "chord", "version": "<manifest>" },
  "authMethods": [],
  "agentCapabilities": {
    "loadSession": true,
    "promptCapabilities": { "image": true, "audio": false, "embeddedContext": false },
    "mcpCapabilities": { "http": true, "sse": true },
    "sessionCapabilities": { "list": {}, "resume": {}, "close": {} }
  },
  "_meta": { "chord/acp": { "version": 1, "extensions": { "session/state": 1, "session/steer": 1, "agents": 1, "monitors": 1 }, "agent": { "name": "<agent>" } } }
}
```

`extensions` advertises the four keys above. `initialize` fails for no reason below chord, and
chord keeps the first `clientCapabilities` it hears. **Images:** `image` is static
`true`. An image to an agent that takes none is -32602 in the window's words, "<agent>
does not take images" (`src/ui/app/terminal.ts:281`), and the true value is on the
session's answer as `_meta["chord/acp"].image`, which is what the window's
`prompt_capabilities` is. `resource` and `audio` blocks are -32602.

**Toward the agent:** `CLIENT_CAPABILITIES` stays the constant it is
(`connection.ts:228`), chord's full set always, and `fs` and `terminal` stay
undeclared. So a record is the window's whichever client wrote it. A client that
declares less loses what comes only by those kinds: a Codex plan as `plan_update`
does not reach it as text.

## Traffic

Everything is read after the enricher chain. `chord acp` adds a pure mapper beside
the reducer, in `src/session/upstream.ts`, tested by table; no new reducer action.

| Event from `Conversation` | Upstream |
| --- | --- |
| `update` | `session/update` under the upstream id, whole, `_meta` included |
| `update` with `subagentId` | the same, under the child's composite id |
| `prompt`, `queued`, `result`, `queue_withdrawn`, `cycle_started`, `self_started`, `disconnected` | "Turn ownership" |
| `permission_requested`, `elicitation_requested` | forwarded, with the raw request kept beside `PendingPermission` and `waitOf`, or `chord/questions` is lost |
| `permission_settled` or `plan_settled` withdrawn | `$/cancel_request` for the pending request |
| `plan_requested` | "A plan ask" |
| `connected`, `connect_failed` | answers or fails `session/new`, `load`, `resume` |
| `warned`, `failed` outside a turn | stderr always, and `notice`; held-back servers also on the answer as `_meta["chord/held_back"]`. A `failed` for a set the client asked is that request's error |
| `modes`, `model`, `options` | "One shape for configuration" |
| `monitors` | `_chord/monitors/changed` |
| `commands`, `mode_asked`, `mode_answered`, `noted`, `closing`, `resumed`, `prompt_capabilities` | nothing: forwarded already, or the window's |

`_meta` goes as it is: `chord/filled` is how a client tells chord's estimate from the
agent's figure. The guide says those keys are informational and unversioned.

### What is not sent

One drop-only check, the same live and on `session/load`, because the schema says
an agent MUST NOT send some kinds to a client that has not declared them. It lands
in CHD-574. No refusal, translation or text fallback.

| Kind | Needs |
| --- | --- |
| `subagent_update`, `session_message`, `session_message_chunk`, a child's traffic | `subagents` |
| `plan_update`, `plan_removed` | `plan` |
| `compaction_update`, `compaction_summary_chunk` | `session.compaction` |
| `notice` | `session.notices` |
| a kind the v1 schema lacks | never goes |

The record keeps what was dropped. A window record loaded by a client with no
capabilities loses those kinds upstream, as a live session would. Updates after a
prompt's answer go at once, and a turn may start with no prompt pending, asks in it:
the guide says so. A client that declares less may read a late chunk as the next reply,
or not show such a turn, and an ask between turns then holds the queue
(`conversation.ts:3233-3250`) until `session/cancel`. Those losses are accepted.

### Session ids

Main's upstream id is the agent's (`Session.id`), so `session/list`, `load` and
`--resume` name one thing and the record format does not change. `session/load` or
`resume` of an id live here is -32602.

A second `session/new` answered with a live id takes an **alias**, `s1~2`: upstream only,
in the table, never recorded. An agent with per-process counter ids gets as many live
sessions as any other. An alias is not listed and does not reload, and such an agent's
records already collide (`sessions.ts:424-425`), in the window too.

A child gets `<main>/<child>`, with chord's child id or the adapter's subagent id; a
child's own subagent is `<main>/<child>/<id>`. It is looked up exactly in the table and
never parsed. The mapper rewrites every id leaving, and the record holds downstream
ids, composed the same way on replay.

### Prompts

| Block | Goes as |
| --- | --- |
| `text` | joined, in order |
| `image` | an `Attachment`, if the agent takes images |
| `resource_link` | a new `links` argument, as given; `Recording.sent` takes it already |

A second `session/prompt` while one runs is queued, as the window's is, and answered
when its own turn ends. `_chord/session/steer` puts words into the running turn.

### Turn ownership

This is the contract `src/acp/upstream_turns.ts` implements, a pure reducer. `send`
mints its turn id inside and emits before it returns (`conversation.ts:1054-1077`,
`:2019-2050`), so a request cannot learn its turn: with a monitor's turn running and
prompts A and B queued, guessing by arrival answers the wrong one. So the handler binds
first, with no `await` before it, or a cancel can pass it.

```ts
const turnId = crypto.randomUUID();

turns.bind(requestId, turnId); // before send: send emits synchronously
if (!conversation.send(text, text, images, [], { turnId, links })) {
  turns.unbind(requestId); // not up, or closing: sessionNotFound
}
```

**Additive changes to `Conversation`:** `send` takes an optional `turnId` and `links`;
`queue_withdrawn` gains `turnIds`; `cancelPrompt(turnId)` is new; `setMode`, `setModel`
and `setOption` return a promise that rejects on refusal, keeping today's events.

| Client sends | Target | What happens |
| --- | --- | --- |
| `$/cancel_request` | a queued prompt | out of `#queued`, nothing goes to the agent; answered `cancelled`; others untouched |
| `$/cancel_request` | the running prompt | `interrupt`'s running half: seal, cancel plans, withdraw asks, `turn.cancel()`. The queue stays and runs next. Answered on its `result` |
| `session/cancel` | the session | `interrupt`, as Esc: every client prompt queued withdrawn, the running turn cancelled whoever began it, a cycle ended. Agents' messages stay queued |
| either | a request already answered | nothing |

| Event | Condition | Binding, state | Sends |
| --- | --- | --- | --- |
| `queued` | any | none | nothing; a row may repeat for a turn |
| `prompt` | bound | running: client | state |
| `prompt` | unbound, no `into` | running: message | `user_message_chunk` with `_meta["chord/from"]`, state |
| `prompt` | `into` set: steered into a running turn | no change; it gets no `result` | `user_message_chunk` with `_meta["chord/from"]` |
| `prompt` | while a cycle runs | replaces it, with no `result` for the cycle (`:3491-3493`) | as above |
| `result` | bound | unbind; running: none if it was this turn | the answer: `stopReason` and `usage`, or the error for `failed`; state idle |
| `result` | unbound | running: none if it was this turn | state idle |
| `queue_withdrawn` | `turnIds` | unbind each bound | each answered `cancelled` |
| `cycle_started` | | running: agent | state |
| `self_started` | a steer the agent took as its own turn, cancelled at once | running: agent; no `result`: the held message's `prompt` replaces it | state |
| `cancel` | | none | nothing; the `result` says it |
| `disconnected` | | running: none. Bound and running: its `result` is `failed`. Bound and queued: answered `sessionNotFound` | state idle |
| close, `session/close`, leaving | | every binding answered `cancelled` | |

"State" is `_chord/session/state`; nothing follows a close. A `result`
waits out `#quieten` while anything is queued, up to 5 s (`:3565-3567`), so an answer
can lag its turn. No other holding of an answer is added.

## What chord absorbs

**One shape for configuration.** Modes, models and efforts reach a client as
`configOptions`, built by one pure function from `AgentState`: the agent's select
options as `optionsFromConfigOptions` reads them; a `mode` option, the agent's own or
made from `modesFrom`; a `model` option likewise from `modelsFrom`, so an agent with only
`session/set_model` shows the same choice as any other. `modes` is never sent, and
`current_mode_update` becomes `config_option_update`. A thing an agent lacks is absent,
not differently shaped. Boolean options never appear, as the window shows none.

The answer to `session/new`, `load` or `resume` is built at `connected`, not from the
agent's raw answer, as `#applyStarting` (`:2813`) may have moved things. The mapper keeps
what it last sent per session and, on `modes`, `model`, `options` or any such update,
sends the whole `config_option_update` only if it differs, marked `chord/filled` and not
recorded. So an agent that changes config only in responses, one that answers `set_mode`
with nothing, and one that sends updates all look alike. `Conversation`'s existing queues
serialise; a handler never calls `Session.setMode` or its kin.

**A plan ask.** `plan_requested` goes up as an ordinary permission, one small function for
every agent. The record is the window's `plan_asked` and `plan_answered`.

```json
{"method":"session/request_permission","params":{"sessionId":"…","toolCall":{"toolCallId":"<wait.toolCallId>","title":"<name, or Plan>","content":[{"type":"content","content":{"type":"text","text":"<overview, plan, todos and phases as markdown>"}}]},"options":[{"optionId":"accepted","name":"Yes, accept the plan","kind":"allow_once"},{"optionId":"kept","name":"No, keep planning","kind":"reject_once"}]}}
```

| Client answers | `answerPlan` |
| --- | --- |
| `accepted` | `accepted` |
| `kept` | `kept` |
| `left`, grok's third, also `reject_once` | `left` |
| `cancelled`, an error, an unknown id | `cancelled`, **never a yes** |

**Also the same for every agent:** cost and window size by the enrichers, marked
`chord/filled`; tool titles, kinds and output; forms' questions in `chord/questions`; a
command list even from an agent that sends none; sign-in errors as -32000 with
`signInLines`, the agent's words its own; subagent shape, and a draft's `completed`,
`failed`, `cancelled`, `disconnected` mapped to ACP's `idle` or `unknown` with the detail in
`_meta["chord/agent"]`; `session/load` and `resume` both offered; MCP transports held back
by `serversFor` with reasons; dimcode's notice once as `notice` and on stderr, from the
existing `dimcodeAtRisk`, since it warns of approvals bypassed.

**What cannot be absorbed, and why:**

| Difference | Why | What a client sees |
| --- | --- | --- |
| A model without images | a model's sight | the refusal above, and the `_meta` |
| Steering's timing | an agent with no steering cannot take words mid-turn | `delivery: "queued"` |
| Usage on cursor and droid | the data does not exist | no `usage_update`, as the window |
| Subagents on gemini, droid, dirac, goose | the agent runs them as one call | one tool call. chord's own tasks and children are the same on every runtime |
| An agent with neither load nor resume | it alone holds the conversation | the window's "cannot resume" words |
| An agent with no HTTP MCP | chord's server is HTTP, and a stdio bridge is new code | no chord tools; chord's commands still run |
| Names and values of modes and models, which permission options exist, what cancel stops | the agent's own | the same shape |
| The window's note on "keep planning" | a permission's answer has no place for it | the person's next prompt says it |

**Left by an earlier choice:** pi's terminal output shows as its last chunk and droid's as
text at the end (CHD-456), as in the window.

## Who answers

- **Permissions** go to the client, with no timer and no chord policy to bypass. An
  error answer is a refusal. An unknown `optionId` is validated against the retained
  options **before** `choose`, then goes to `reject(id)`: `choose` removes the ask and
  emits chosen before `resolve` throws (`conversation.ts:2437`, `permissions.ts:135`),
  so catching would leave the ask gone, the agent waiting and a false answer recorded.
- **`--permission-mode`** is a starting value only. There is no
  `--dangerously-skip-permissions`.
- **A child's ask** goes under its composite id. Without `subagents`, each place
  refuses a permission, form or plan with a stderr line: it can name no session
  that client knows and must never wait unseen. No tool or command is refused.
- **A client that never answers** holds that one ask. `session/cancel` still ends the
  turn: chord answers the agent itself (`connection.ts:292-300,545`), as the SDK settles
  nothing on cancel, and a late answer changes nothing.
- **Filesystem and terminal** are chord's: neither is declared, as today, and agents use
  their own tools on the same machine. A client can put unsaved buffers in a prompt.
- **Sign-in** is not forwarded: the error says what to run on the machine.

## Choosing the agent and the team

One main agent per process, from `chord acp [agent]`, `--agent-command` or the settings
default; `--model`, `--effort` and `--permission-mode` as `chord` has them. Children may
run on other runtimes: `/new codex` under a Claude main, and any team file naming others.
Each `session/new`'s `cwd` decides that session's settings and `.mcp.json`.

`mcpServers` from a client are the nearest layer in `mergeServers`, through `serversFor`:
chord's own goes last and is renamed `chord-2` if taken; `mcpServers: false` holds the
client's back too; an `acp` transport is -32602. Children take the settings' servers only:
a client's server goes to the session it named. This one is the lead's call, as it is one
argument and adds nothing.

### chord's commands (CHD-581)

chord adds `team` and `new` to the agent's list, takes such a prompt and runs it itself.
Asking in words still works. Only these two names are chord's: everything else goes to the
agent as typed, unlike in the window.

| Form | Does |
| --- | --- |
| `/team list`, `/team` | names from `listTeams`, as text |
| `/team show <name>` | the file, description, agents; a running one's job, lead and which are open. No state, headline or receipt: those read window state |
| `/team run <name> <job>` | as `run_team`; answers once started. `/team run` with no job is refused |
| `/team stop <run>` | closes the lead and members; the run's name is in `run`'s reply |
| `/team new <words>` | a normal turn, with `newTeamPrompt` as its preamble |
| `/new [agent]` | an idle child, main's runtime if omitted; the reply says so. Main's `send_message` or `_chord/agents/send` starts it |

```json
{"name":"team","description":"Show and run teams of agents","input":{"hint":"list | run <name> <job> | show <name> | stop <run> | new <words>"}}
{"name":"new","description":"Open a new agent beside main","input":{"hint":"<agent>"}}
```

**A name both offer:** chord's wins and the agent's leaves the list, as in the window
(`src/ui/prompt/commands.ts:112-117`). A person cannot reach an agent's own `/new` through
chord. The merge is in the mapper, not in state, because `foldUpdate` replaces the list
whole (`agent_state.ts:55-58`): each root `available_commands_update` is rewritten on the
way out, an agent that sends none gets chord's once the session's answer is written, a
child's is not merged, and replay goes through the same rewrite. `AgentState.commands` and
the record stay the agent's own.

**A result or a refusal** is one chunk, then the answer. A refusal is not a JSON-RPC error,
as nothing failed at the protocol's level, nor `stopReason: "refusal"`, which is the
agent's. No usage or `user_message_chunk`; the reply itself adds no transcript entry.
File-sourced text stays on one line per field. A client treats it as untrusted, as
it does agent text.

```json
{"sessionUpdate":"agent_message_chunk","content":{"type":"text","text":"Team bugfix started. Its lead is bugfix; /team stop bugfix ends it."},"_meta":{"chord/command":{"name":"team","failed":false}}}
{"id":7,"result":{"stopReason":"end_turn"}}
```

**Parsing:** the window's `^/(\S+)(?:\s+([\s\S]*))?$` (`prompt/commands.ts:377`), on the first
text block. A prompt with other blocks beside it gets a refused line, not a silent drop.
**During a turn** it runs at once and never queues, as in the window, so it overtakes queued
prompts, and its `aside` reaches the next `send`. `session/cancel` aborts a run still starting
and does not stop a running one; use `/team stop`.

**A run leaves no prompt pending.** Its work, asks and reports follow with none
open, and a lead's report starts a main turn that costs money. A client
declaring `subagents` follows it by `subagent_update`; `_chord/session/state`
reports main's state. A run has no defined end, so a prompt cannot be held open
for it.

**The record:** as the window. `session/load` shows nothing of a command, with
no format change. A session whose only act is `/team run` writes no record and
stays unlisted. Leading chord asides no longer read as the person's words in
`-r`, `/resume`'s list or `session/load`. A task's aside stays to avoid hiding
arbitrary personal text. A person's exact leading
`<message from="chord">\n...\n</message>\n\n` is indistinguishable from chord's
aside and is omitted from resumed display and titles too; the raw record retains
it.

## Extensions (CHD-575)

CHD-575 serves six methods under four versioned keys. The public parameters,
results and errors are in [the guide](../guide.md#extensions). The
`chord/agent` metadata below remains informational and unversioned.

**Form.** Names are `_chord/<noun>/<verb>`, matching the `chord/` `_meta` keys. One integer
per extension; a new integer only for a break, not for a new optional field. chord advertises
in `initialize`'s `_meta["chord/acp"]`. A client declares in
`clientCapabilities._meta["chord/acp"]`, `{ "extensions": { "session/state": 1, "session/steer": 1,
"agents": 1, "monitors": 1 } }`. chord branches on none of these versions yet:
beyond the drop-only check, it sends notifications to every client, and the SDK
ignores what a client does not handle. The declaration is what a future break selects
on, and is what the guide means by "a client that declares them".

```json
{"method":"_chord/session/state","params":{"sessionId":"…","state":"running","origin":"message"}}
{"method":"_chord/monitors/changed","params":{"sessionId":"…","running":[{"id":"m1","description":"…","command":"…","startedAt":0,"timeoutMs":0,"events":2}],"ended":[{"id":"m2","description":"…","command":"…","startedAt":0,"timeoutMs":0,"events":1,"lastEvent":{"lines":["done"],"at":0},"end":{"kind":"exit","code":0},"endedAt":0}]}}
{"id":1,"method":"_chord/agents/send","params":{"sessionId":"<main>/<child>","prompt":[{"type":"text","text":"…"}]}}
{"id":1,"result":{"delivery":"sent"}}
{"id":2,"method":"_chord/agents/close","params":{"sessionId":"<main>/<child>"}}
{"id":2,"result":{"closed":["lead-1","tester"]}}
{"id":3,"method":"_chord/monitors/stop","params":{"sessionId":"…","id":"m1"}}
{"id":3,"result":{"id":"m1","description":"…","events":2,"ran_ms":0}}
{"id":4,"method":"_chord/session/steer","params":{"sessionId":"…","prompt":[{"type":"text","text":"…"}]}}
{"id":4,"result":{"delivery":"queued"}}
```

- **`session/state`:** `running`, `idle` or `requires_action` for main; a child's
  state stays on `subagent_update`. `origin` is `client`, `message` or `agent`
  while a turn runs; idle has none. Main's asks, including a task's ask that
  its turn waits on, make it `requires_action`. Nothing follows a close.
- **`agents/send`:** the person's prompt to a long-lived child, answered `sent`
  when idle or `queued` when busy; the turn is seen by `subagent_update`.
  Unknown, closed or failed-start children, tasks and adapter subagents are
  -32002. Starting or clearing children are -32603; send again after idle.
- **`agents/close`:** answers the names closed, a lead's members with it; works
  on a failed-start child too. Unknown or closed children are -32002.
- **`monitors/changed`, `monitors/stop`:** whole running and ended objects,
  including `lastEvent` when present; children's use composite session ids.
  Stop returns `id`, `description`, `events` and `ran_ms`; unknown session or
  monitor ids are -32002. No notifications after a close.
- **`session/steer`:** text, links and supported images, steering its own entry
  rather than the oldest queued. `sent` means into a running turn; otherwise
  `queued` starts its own turn with no request waiting, `origin: client` and
  no echo. A refused steer returns to the queue; a refused send or gone session
  is -32002. Unsupported blocks or images and malformed params are -32602.
  All extension requests during shutdown are -32603.

`_meta["chord/agent"]` goes on `subagent_update`, which already carries title, description,
nesting by parent, `state` and `capabilities.cancel`:

```json
{"sessionUpdate":"subagent_update","sessionId":"<main>/<child>","title":"tester","state":{"state":"running"},"capabilities":{"cancel":{}},"_meta":{"chord/agent":{"runtime":"codex","model":"…","effort":"…","mode":"…","team":"bugfix","role":"member"}}}
```

CHD-581 synthesises a long-lived child's update on its immediate parent, not
recorded. `mode` reports its current mode, with no policy; `gone` and `failed`
explain exit or startup failure, and `closed: true` comes without cancel
capability. Order, picking, folding, attention, unseen marks and elapsed time
are the client's layout. There is no agent list, as one connection has seen
every announcement; no clear, which stays `clear_agent` in words; either can be
added later.

**The record: nothing new.** On load or resume, children and monitors are not
restarted. A task's work replays on load; a long-lived child's does not, as its
updates are not recorded. Both answers name children left open in the record
as `_meta["chord/left_open"]`: `name`, `runtime` and optional `team` and `agents`
(the run's agent count).

## Sessions and records

Recorded as the window's. `session/list` is `earlierSessions(records, { agent, cwd })`, `title`
from `sessionLabel`, `updatedAt` from `lastUsedAt`, with every directory when `cwd` is omitted.
`session/load` maps the past to updates: `prompt` to `user_message_chunk`, `update` as live under
"What is not sent", the rest dropped, before the answer. `resume` replays nothing. A session opens
either way between `chord acp` and `chord <agent> -r <id>`. Sessions chord never recorded are not
listed, but load by id still reaches them.

| Case | Answer |
| --- | --- |
| `load` with another `cwd` than the record's | -32602 naming the record's (`sessions.ts:382`) |
| An id of another agent's record | -32602, `ResumeError`'s words (`sessions.ts:434`) |
| A record that cannot be written | stderr and `notice`; the session goes on (`record.ts:1206`) |

## Processes and concurrency

`src/acp_agent.ts` has `runAcp(options)`, as `headless.ts` is to `-p`: it takes `input`, `output`,
`stderr` and `open`, so tests run it in-process, and `main.tsx` only wires it. No lazy import: all
of `src/main.tsx`'s graph loads with 0 bytes on stdout, no patched `console.log`, cooked stdin and
no signal listeners, on both targets.

```text
src/acp_agent.ts            runAcp
src/acp/agent_app.ts        agent({ name }) and its handlers; no logic of its own
src/acp/stdio.ts            the stream on stdout's callback; the wrapper that sees each write
src/acp/upstream_turns.ts   pure: the turn table
src/session/upstream.ts     pure: the mapper
src/session/leaving.ts      ACP way out and window forced-exit closes; separate leave paths
src/platform/process.ts     gains the registry of spawned groups
src/session/place.ts        moved (CHD-579): a directory's settings and MCP servers
src/session/agents_host.ts  moved (CHD-580): main, children, teams, the tools' port
```

| Situation | Outcome |
| --- | --- |
| Sessions | Any number, no cap. One `AgentsHost` each, sharing one `ChordServer`, resource readers and `settingsBoxClaim`. This is not tabs: the window keeps one main |
| Two sessions' turns | Independent: own process, own queue. Updates interleave, each whole |
| Several asks | Each its own request, each settled alone |
| A child opened while closing | Refused: `launchSignal` and `stale(caller)` hold |
| A second `chord acp` in one directory | No lock and nothing to clash on: port 0, a UUID record, atomic settings writes. Two on one session id append to one record, as two windows do today |

**stdout** is one `WritableStream` over `process.stdout.write(chunk, callback)`, as
`src/acp/process.ts:240-255` wraps an agent's stdin. `Writable.toWeb(process.stdout)` loses data
under Bun: 65,536 of 16 MiB arrived before `process.exit`. `Bun.write(Bun.stdout)` blocks the loop.
A test fails if anyone goes back. Any `console.log` reaches stdout as a non-JSON line, so a lint
rule holds `src/session/`, `src/acp/` and `src/server/`, and a spawned test asserts every line
parses.

## The way out

If main's agent dies, close all children (owner option a): nothing may run that
its client can no longer name. The window keeps children, since its person can
still reach them. This difference is intentional.

One `leave(reason)`, once, whatever starts it.

```text
1. Arm the deadline, LEAVE_MS = 15000, before anything else and before any await.
2. Refuse new work: -32603 "chord is closing".
3. If the connection lives (a signal; not EOF or EPIPE): send the answers the turn
   table gives for closing. Withdraw each ask.
4. At once, none behind another, each settled on its own:
   a. drain: await those answers' writes, at most DRAIN_MS = 500, then connection.close();
   b. each host's closeAll: stdin, SIGTERM, SIGKILL to each group, record flush;
   c. chord's MCP server, the probes, the resource readers.
5. All settled: each failure to stderr, SIGKILL what the registry still holds, exit.
6. Deadline first: stderr names what had not settled and each group by pid. SIGKILL
   every group in the registry at once, without waiting. Exit.
```

15 s: one agent takes at most 6 s (`process.ts:18-22`), and `Conversation.close` awaits tasks
before its own session, so a hung task and a hung main take 12 s. The SDK's `close()` has no drain
and drops what is queued behind it, so step 4a waits on the wrapper's view of each write. **The
drain is best effort:** what is at the head or queued when it passes is abandoned by
`process.exit`, so a client gets its `cancelled` answers only if it is reading. `process.exit` is
called, not left to the loop.

**Exit:** EOF, 0 if cleanup was clean, else 1. A signal: dies by it after leaving, expiry too. An
oversized line or stdout gone: 1.

**The registry** is new, in `spawnGroup` (`src/platform/process.ts:61`), whose callers are all of
chord's groups: every group from spawn until nothing is left in it. `Session.agentPids` will not
do: it holds the live main's pid only. A group is added at spawn; at its leader's exit it is dropped
if `alive()` says it is empty, else kept and rechecked at each spawn and at the sweep. The risk left
is a kept group's pgid reused before a check.

**What holds:** on every way out that runs, every group chord spawned has been stopped or has had
SIGKILL. **What does not:** chord itself SIGKILLed, or its loop blocked synchronously; a process
that left its group; a reused pgid.

### Known limits, for the guide

- A task's agent can name another announced subagent of the same session or
  claim a sibling's id. An agent announcing a subagent under a child's id can
  mislead about state only; it gains no control of that child.
- The synchronous transcript fold per session and child adds memory use that
  has not been measured.
- **A client that stops reading stdout.** There is no rule, and chord files no SDK issue. A client
  that hangs while still connected holds chord's memory and running agents until it is killed. The
  SDK offers no public place to count every class of output before its write queue (`Connection`
  and its kin are not exported; `dist/core/jsonrpc.js:743-764`), and its limits cover HTTP and
  WebSocket only. Measured on the callback stream with nobody reading: 256 MiB of notifications
  held 345-353 MiB RSS; 500k of the SDK's -32601s held 1.6-1.8 GiB.
- **A malformed line while stdout is full stops chord reading its input,** because `ndJsonStream`
  awaits its own error write in the read loop (`core/stream.js:48,78`). Later requests and EOF go
  unseen until the client reads, goes, or chord gets a signal. Trial, both targets: SIGTERM reaches
  the way out in 55 ms; the client killed, 11-12 ms by EPIPE; its stdout reader gone, 11 ms; stdin
  closed with stdout still held, not seen in 5 s. Valid input alone does not stop it: then EOF is
  seen in 12-66 ms. A second observer of `process.stdin`'s `end` ended the trial in 11-12 ms; it
  is not built, and is the owner's call.
- **A half-closed stdin means the client is gone.** The SDK closes the connection on EOF, so a
  running prompt gets no answer.
- **One line over 32 MiB closes the connection,** the SDK's default, kept.
- **Updates may follow an answer,** and a turn may start with no prompt pending.

## The SDK trial

`@agentclientprotocol/sdk` 2.2.0, `agent({ name })`, Bun 1.4.4 and `bun build --compile`, darwin
arm64, 24 scenarios over real pipes, the two targets equal. Scripts and output are in
`docs/design/evidence/CHD-573/sdk-trial/`. It needs no protocol helper. What binds this design:

- Outgoing messages are not validated, so an unknown kind goes as sent: hence "What is not sent".
- Incoming params are parsed: `_meta` survives, unknown top-level fields do not.
- A cancelled outgoing request settles nothing.
- `close()` does not flush. EOF closes the whole connection.
- A plain v1 `agent()` answers 1 to any number. A v2-shaped client gets 1 and decides for itself. v2
  is another lifecycle, not a superset: a prompt answers at insertion, and `session/load` is -32601.

## Not measured

- Any real ACP client: its timeouts, a slow `session/new`, how soon it kills chord after closing
  stdin, whether it reads stderr, how it treats updates after an answer.
- Real agents through `chord acp`. Each adapter's behaviour is read, not run.
- Linux and Windows. The trial ran on one Mac; `process.kill(-pid)` is not on Windows; the stdout
  numbers may differ on Linux, and the stdio test runs on CI's Linux shards. Whether stderr stays
  non-blocking off macOS, as a blocking one would hold the deadline.
- Long runs, memory of many sessions, throughput with many agents on one stdout. `bun dev memory`
  has no acp mode.
- Whether any agent chord runs issues per-process counter ids.
- `readRecords` cost on a large store, for `session/list`; it reads every file.
- Two processes on one agent session.
- Whether `Conversation` holds any update `#updated` should pass, and whether `#advance` plays what
  is queued on a dead session.
- What `runTeamAt` returns when `session/cancel` aborts a run still starting, and how a replayed
  `prompt` shows `aside`'s text.
- Whether the hook's closures hold anything a render refreshes, beyond its 2 `all.` reads.
- Where `settingsBoxClaim` goes if a person is asked in two sessions at once.
- The `exit` listener the compiled load adds, not traced.
