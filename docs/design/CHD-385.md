# CHD-385: `from` and `to` after a message's arrow

The owner could not tell, at a glance, whether a message row came in or went
out: `← @parser · codex` and `→ main · queued` both put the arrow straight
before the name. The owner decided (2026-10-14) that the arrows stay and a
word follows each, and that every name keeps its `@`:

```
← from @parser · codex
→ to @main · queued
```

Everything else on each row (the runtime, the note, the state, the folded
text) keeps its order. This document says how every row that draws a
message reads afterwards, how it is coloured, and what gives way at 80
columns.

The captures of today are in `evidence/CHD-385/today/`, taken with
`bun run chord:fake` in a `/tmp` directory with the fake teams copied into
`.chord/teams/`. The mocks in `evidence/CHD-385/mock/` are those captures
with only the message rows changed. The long name is a copy of `bugfix`
saved as `sssssssssssssss.md` and run with
`/team run sssssssssssssss Fix the parser bug`: a lead takes its team's
name, so the lead's messages to main and the members' messages to it carry
the long name.

## The rows

### Incoming, `←`

The word is `from`, between the arrow and the name, for every sender: an
agent, chord, and a monitor. The name keeps exactly the form `senderName`
gives it today: `@` for a name `send_message` reaches, bare for a task,
chord and a monitor's description.

## Colour

The word is **dim**, like the rest of the header around the name. The name
stays the one bold, coloured thing on the row, so the eye still lands on
who it is. The arrow keeps its tone.

```
←  from  @parser  · fake
│  │     │        └ dim
│  │     └ bold, the agent's colour (theme `agents` role)
│  └ dim
└ as today: the agent's colour, dim for chord, `error` for a failed
  report, a monitor's end by how it ended (`warning` for a timeout)

→  to  @main  · queued
│  │   │      └ dim
│  │   └ bold, the recipient's colour
│  └ dim, in every state, refused included
└ as today: dim until delivered, the recipient's colour once delivered,
  `error` when refused
```

A queue row is dim from end to end today, and `from` is dim with it. In
`/team show` the headline is plain text as today, and the word goes with
it.

## What gives way at 80 columns

The new word adds five cells to an incoming row and three to an outgoing
one. A member's name is at most 16 characters (`teams.ts` `MEMBER_NAME`)
and a team's 24, so `← from @sssssssssssssss · codex · failed` is about
40 cells. The transcript's header, the outgoing headline and a subagent's
latest call all still fit in 80 columns with room left over. For those rows
nothing gives way, and their cut at the edge stays what it is today.

**The queue row is the one row that changes.** It is the header followed by
the message's first line, cut by OpenTUI in the middle (`...`). That keeps
about the first half of the row and the last half. Today, at 80 columns,
the first half holds the whole header:

```
 ← @main · after your answer: When the ...add the new flag to docs/FEATURES.md.
```

With a long name and the new word, a middle cut lands inside the header and
takes `your answer` with it (`mock/long-queue-80x24-uncut-header-rejected.txt`):

```
 ← from @sssssssssssssss · fake · after ...dd the new flag to docs/FEATURES.md.
```

That changes what the row says. The row would no longer say why the
message waits.

**The rule: the message's text gives way first, and the header never.** The
header is drawn whole. The text takes the rest of the row and is cut in its
middle the way it is today, `...` included. `queuedMessage`'s own comment
already says the cut never reaches the header. This rule keeps that
promise for long names:

```
 ← from @main · after your answer: When the README secti...to docs/FEATURES.md.
 ← from @sssssssssssssss · fake · after your answer: When the REA...EATURES.md.
```

(`mock/agentsheld-steer-80x24.txt`, `mock/long-queue-80x24.txt`. The second
row is drawn in docs' view for comparison. In a run, it is the row a member
sees when its lead's message waits on the member's permission.)

Only the text's share of the row changes. Every word of the header stays,
so this is not a choice for the owner. If a window is too narrow for even
the header (under about 55 columns with the longest name), the header is
cut at its end like any one-row line. The `from` and the name come first
and survive the longest.

In `/team show`, the headline is the last column and is already given up
below 12 cells. A longer headline changes nothing: at 80 columns it was
given up before this task (`today/long-teamshow-80x24.txt`), and at 120 it
is cut at its end like any headline.
