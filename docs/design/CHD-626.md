# CHD-626 — model parameters in `/model`; `/effort` and fast

The owner, 2026-11-13, after a live run of `cursor-cloud`: choosing a
model's effort and other parameters in chord is bad UX for every agent.
`/model` lists models only; effort, fast and context sit in `/config`, one
list per option; on cursor-cloud's "Cursor's default" there is nothing at
all. The owner's direction: effort changed in place in `/model` as Claude
Code does it, a separate `/effort`, a separate way to toggle fast, and the
context window reachable (`/config`).

This design answers the task's four questions with options and a
recommendation each. Seven choices in it are the owner's (O1–O7, at the
end); the parts that depend on them say so. Nothing here is built until the
owner has answered.

The drafts behind it, and the critic's review they answered, are in
`evidence/CHD-626/drafts/` (`brief.md`, `protocol.md`, `interface.md`,
`runtime.md`). Where this file and a draft differ, this file holds.

## Two rules over everything

1. **chord recognises a parameter by what ACP says, never by its words.**
   Effort is the first select of category `thought_level` (as
   `src/session/efforts.ts` reads it today). A model's other parameters are
   the options of category `model_config`, which ACP defines as "context
   size or speed/quality trade-off" and asks clients to show near the model
   selector. ACP has nothing that tells fast from context from Claude's
   `ultracode`: all three are `model_config`. So chord shows them under the
   agent's own names and does not know which is which (see Q3, O3).
2. **No new widget.** Every screen below is the picker chord has
   (`PickerList`), its hint line, and one line of text under the list. A
   horizontal effort scale like Claude Code's is not in this design: OpenTUI
   has no labelled slider, and drawing our own is the owner's to allow (O2).

## What agents send

From `protocol.md` §2 (Claude's adapter 0.106.0 and Codex's 2.6.0 read from
their npm tarballs; the rest from `docs/agent-capabilities.md`). chord
declares no boolean config options, so on/off parameters arrive as selects.

| agent | effort (`thought_level`) | `model_config` | other |
| --- | --- | --- | --- |
| claude-acp | `effort`, per model | `fast`, `ultracode` (on/off), per model | `agent` (no category) |
| codex-acp | `reasoning_effort`, per model | `fast-mode` (on/off), where the model has it | `collaboration_mode` |
| cursor-cloud (ours) | none today | none today | one uncategorised select per Cursor parameter of the model in use; none on Cursor's default |
| fx | `effort` (`auto` first) | none: `fast`, `ultrafast` are category `model` | `provider` is the first `model` select |
| most others | `thought_level` or nothing | not recorded | |

Every agent sends a model's parameters only while the session is on that
model, and resends the set after a change (in the answer, by
`config_option_update`, or both, as recorded per agent). ACP has no call
that reads another model's parameters without switching to it.

## Q1. `/model`: layout and keys

The list stays as it is. Under it, one line for the model in use (the
**settings line**), always one row, so moving the highlight never shifts
the frame:

- effort, by the agent's name for it: `Medium effort  ←/→ to adjust`;
- then each `model_config` option as `Name  Value`, ` · ` between, in the
  agent's order;
- then `/config for all settings` when the agent has options beyond these.

It is cut with `…` from the right; effort is the last to go. No glyph and no
"Faster ↔ Smarter": ACP's order is priority, not a scale (fx lists `auto`
first), so a "more or less" mark would be read into the order.

| Key | Does | In the panel |
| --- | --- | --- |
| ↑ ↓ j k | move, as today | the existing "move between choices" line |
| ← → | effort down or up one in the agent's order, stopping at either end; nothing is sent until Enter | the same line becomes `↑ ↓ j k ← →  to move or change a value`; ← → are actions `modelPicker:decreaseEffort` / `increaseEffort` in a new `ModelPicker` context of `bindings.ts` (Claude Code's names), rebindable |
| Enter | on the model in use: send the changed effort, if any, and close; on another model: switch, then the effort (O1) | as today |
| 1–9 | as Enter on that row (they pick at once today), with the same pending effort | as today |
| Esc | close; nothing pending is sent | as today |

← → are free in a picker today (only the background view reads ←).
A changed effort waits marked `•`, and the hint says `Enter to set`.
Every other parameter is changed in `/config`: no Tab and no second level in
`/model`. This is the drafts' "Tab for all settings" left out (critic 5,
10): it bound edits to the model in use while another was highlighted, and
needed a panel line the panel does not have.

**Another model highlighted (O1).** Its parameters are unknown until the
session is on it. Options:

- **A. Switch first.** The line says `Haiku 5.5's settings show once it is
  in use`; ←/→ do nothing. Enter switches and the picker stays open,
  `switching…`, until the agent's new set comes; then the line is live for
  it. One more Enter than Claude Code, never a value the model did not offer.
- **B. Carry over (recommended).** The line keeps the model in use's
  efforts. ←/→ move it; the line then says `asked for once Haiku 5.5 is in
  use, if it offers High` (M3). Enter closes and switches; after the
  agent's answer chord asks for the same value id of the new set's
  `thought_level` option, **only if the person moved it** and the new set
  lists that id; otherwise the transcript says `Haiku 5.5 offers no High
  effort; it is on Medium.` It matches ids the agent sent, not meanings.
  Claude's and Codex's adapters carry an effort across models themselves
  where the new one has it, so an unmoved effort is left to them.
- **C. Codex's way.** Enter switches and closes; `/effort` opens by itself on
  the new model's efforts when it has some.

The drafts also proposed remembering, per session, each model's option set
the last time the session was on it, to show a visited model's own efforts.
Rejected: B covers the case with nothing stored, and a stale memory adds
states for little (critic 2).

Agents with no options besides their models (gemini, M5) see today's
picker, no settings line.

## Q2. `/effort` and fast

**`/effort`** is a chord command, "Change the agent's effort for this
session". It opens the picker chord has, titled `Effort`, over the efforts
of the model in use, in the agent's order, `✔` on the one in use (E1, N4);
Enter sets and closes, Esc closes. The horizontal scale of Claude Code is
O2. On an agent or model with no efforts it opens nothing and notes
`claude-acp offers no effort for Haiku 5.5.` (no pointer to a model that
has one: other models' efforts are unknown). `/effort <value>` takes a value id, exactly; anything else notes
the ids. Names are not matched: two values may share a name (critic 11).

**Fast** has no ACP signal (rule 1), so a `/fast` that toggles "the fast
option" needs chord to know which option that is. Options (O3):

- **A. A recorded table, per agent entry.** chord's agent list names, for
  an agent, the id of its fast option as read from the adapter's source
  (`claude-acp`: `fast`; `codex-acp`: `fast-mode`; cursor-cloud: once its
  ids are recorded, O5). `/fast` toggles that option's other value; for an
  agent without an entry, or a model without the option, it notes
  `codex-acp offers no fast mode for GPT-5.5.` Not a guess from words: a
  fact recorded per adapter, rechecked when its version moves. It is the
  kind of list the effort decision refused, so it is the owner's.
- **B. An ACP extension.** chord and our cursor-cloud package agree a
  `_meta` key (or a `_`-category) marking an option as fast; chord files an
  ACP proposal for reserved speed and context categories. Works for
  cursor-cloud at once; for Claude and Codex only when their adapters adopt
  it.
- **C. No `/fast`.** Fast is reached on `/model`'s settings line (as an
  ordinary `model_config` value) and `/config`.

Recommended: **A and B together** — A gives `/fast` for Claude and Codex
now; B is how it stops being a table. Without A or B, C is all that can be
built: showing `model_config` options on the settings line does not by
itself give the owner the separate fast toggle asked for.

Global keys (Claude Code's `meta+p`, `meta+o`, `ctrl+x =`/`-`): none in
this task. The shortcuts panel is full at 40 lines; the commands are
typed. If the owner wants them, they need two panel lines freed (O6).

## Q3. What stays in `/config`, and how options are recognised

`/config` stays as it is (two levels: the list of options, Enter, the
option's values) and lists **every** settable option but the mode and the
model, effort and `model_config` ones included: nothing becomes reachable
only through a new screen, and the context window is there for every agent
that sends one (Claude puts context lanes in its model ids, `opus[1m]`, so
for it context is a model). The drafts' one-level `/config` with `‹ Value ›`
rows was a new widget and is left out (critic 3).

Recognition: effort by `thought_level`; the settings line by `model_config`;
fast by O3; context by nothing (no agent marks it, and none is needed: it is
a `model_config` option on the line and a row in `/config`). Never by id or
name otherwise.

- `optionsFromConfigOptions` keeps its whole list: the record's `state`
  line and `options` entries are written from it (`record.ts`), and
  narrowing it would silently stop recording effort and fast (critic 4).
  New readers beside it select the settings line's options from the same
  set.
- Boolean options (O4): ACP sends them only to a client that declares
  `session.configOptions.boolean`. Declaring it makes Claude's and Codex's
  on/off parameters real booleans, and makes cline's auto-approve and
  dirac's `yolo` settable from `/config` — options that skip every
  permission prompt. If the owner takes it, options become a select/boolean
  union through the reducer, the request (`type: 'boolean'`), the record
  and `/config` (On/Off as its two values), each with a test of true and
  false as booleans, not strings. Recommended: not in this task; the on/off
  selects already work.
- fx (O7): its `fast` and `ultrafast` are category `model`, and its first
  `model` select is the provider, so chord's `/model` sets fx's provider.
  Recommended: ask fx upstream to use `model_config` and a `_`-category for
  the provider, and record it; preferring an option whose id is `model` is
  an id rule, the owner's.
- cursor-cloud (ours, O5): its parameters go out with no category because
  Cursor's parameter ids are not recorded. One authorised
  `Cursor.models.list()` on the owner's account records them in
  `docs/agent-capabilities.md`; then the package marks the recorded effort
  id `thought_level` and the rest `model_config`. Until then they are
  `/config` rows only, and cursor-cloud's `/model` shows no settings line
  but `/config for all settings`.

## Q4. A model with no parameters (Cursor's default)

The settings line says `Cursor's default has no effort or settings to
change`, dim; ←/→ do nothing and leave the hint (M4, N3). `/effort` and
`/fast` note that the agent offers none for it, `/config` keeps today's
"has no settings other than its model and mode" note. Rejected: no line
(the frame jumps when the highlight moves) and a mark on the row (possible
only for the model in use).

## Order of calls, concurrency, failure

A choice is one Enter. Its steps run one after another, each one ACP call:

1. the model, if it changed (`set_config_option` on the model option, or
   `session/set_model`); wait for the answer;
2. the effort, if moved, looked up in the option set as it is **after**
   that answer: the first `thought_level` select's values, by value id.
   Sent only if listed there; else skipped with a note. This is
   `askStarting`'s rule (`src/session/starting.ts`, listed only, read at ask
   time), reused.

- **One chain.** `Conversation`'s two chains, `#modelChanges` and
  `#optionChanges`, become one per session, which the mode joins: today an
  effort set can overtake a model set, which the picker would hit. A
  replaced session (`/clear`, resume) gets a new chain; each step checks
  that its session is still current before it sends and after it awaits.
- **Resent sets.** Folded in arrival order, as today; the answer to a step
  is what the next step reads. The drafts' rule to drop an answer when an
  update arrived meanwhile is rejected: ACP gives no revision, so arrival
  order cannot prove which is newer (critic 1). Tests cover an update
  before and after the answer, with sets that differ.
- **Mid-turn.** Sent at once, as `/model` and `/config` are today.
- **In flight.** The command's transcript row shows the step pending
  (`⎿ Switching to Haiku 5.5…`) until its answer replaces it with the
  outcome; nothing is added to the status line. A hung agent holds the
  chain; `/clear`, close and quit work as today. No timeout.
- **Failure.** The model refused: stop, `Could not switch to Haiku 5.5:
  <reason>`. Model set, effort refused or not offered: the model stays and
  one note says both (`Switched to Haiku 5.5; it offers no High effort, it
  is on Medium.`). No undo: it is another call that may fail, and the person
  asked for the model.
- **Pending values the agent takes away.** A moved effort is kept as asked
  (option id and value id) until Enter; if the set has changed by then, the
  note says it was not sent and why. Nothing is dropped silently.
- **Legacy `session/set_model`** answers with no options: the effort step
  reads whatever `config_option_update` has come, else skips with its note.
- `-p --effort` is unchanged; `--fast` and a `fast` setting wait on O3.
