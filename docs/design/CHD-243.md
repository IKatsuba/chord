# CHD-243 — The monitor, on screen and as tools

CHD-242 gives chord's MCP server a monitor. An agent starts a command, and each
batch of lines the command prints reaches that agent later as a message: a new
turn, drawn with CHD-170's message rows. The model to follow is Claude Code's
own Monitor tool. claude-acp hides that tool's events from the client, and no
other agent has anything like it.

This page settles the event row, where running monitors show and the key that
stops them, the tools, the permission question, and the numbers. The engineer
builds CHD-244 (the engine) and CHD-245 (the screen) from it.

The mocks are in `evidence/CHD-243/mock/`, one file per state at 120×40 and
80×24. I laid them out from the real rows of `deno task chord:fake`: the box,
the status line, the permission box, the shortcuts panel, and CHD-170's agent
list and message rows. Then I printed each one in tmux at its size and
compared the capture with the file. All sixteen fit with nothing wrapped or
cut. Text cannot show colour, so the colours are given in words beside each
mock.

| State | Files |
| --- | --- |
| One running monitor, an event delivered | `120-1-event.txt`, `80-1-event.txt` |
| Two running monitors under the prompt, an event queued | `120-2-two-monitors.txt`, `80-2-…` |
| A monitor picked in the list (the stop key) | `120-3-monitor-picked.txt`, `80-3-…` |
| A monitor ended by its exit code | `120-4-ended-exit.txt`, `80-4-…` |
| A flood stop | `120-5-flood.txt`, `80-5-…` |
| Monitors and a long-lived child in one list | `120-6-with-child.txt`, `80-6-…` |
| The permission box for a `monitor` call | `120-7-permission.txt`, `80-7-…` |
| The shortcuts panel | `120-8-shortcuts.txt`, `80-8-…` |

## The decisions, in short

| Question | Answer |
| --- | --- |
| An event's row | `← <description> · monitor`, the lines under it verbatim. It is a CHD-170 message row: same arrow, indent and fold (6 lines). No `@`, because a monitor cannot be written to (CHD-239). |
| A monitor's end | One more row of the same kind, with the end in its header: `· exit code 1`, `· killed by SIGKILL`, `· timed out`, `· stopped`, `· flooded`. Any lines not yet delivered come first, then chord's one dim sentence. The arrow carries the state's colour. |
| Where running monitors show | **Rows in the agent list under the status line** (CHD-167 part 4), after the agents: `description  $ command  running 6m · 3 events`. The list shows while the session has a child **or** a running monitor. |
| Stopping one | `↓` into the list (on an empty draft, as today), `↑ ↓` to the monitor, `x`. It stops at once with no arming. The key is `agents:close`, which stops a monitor on a monitor's row. |
| Shortcuts panel | `↑ ↓ for prompts, agents and monitors` and a new line, `x to close an agent or stop a monitor`. It still fits 80×24 (`80-8-shortcuts.txt`). |
| Tools | `monitor {command, description, timeout_ms?}` answers at once with an id (`m1`). `stop_monitor {id}`. **`list_monitors {}`**, not a field in `list_sessions`. |
| `timeout_ms` | Default 600000 (10 min), cap 3600000 (1 h). A value outside 1000…3600000 is refused, not clamped. |
| Who gets them | The person's sessions and long-lived children. Not task agents: a task ends with its first turn, so later events would have nobody to go to. |
| Permission | **chord adds no prompt of its own.** But the agent's ask does **not** show the command in chord today, so the permission box must show the request's raw input (part 4). That is part of CHD-245. |
| Batching | A fixed 200 ms window from a batch's first line. One event holds at most 100 lines and 16 KiB. A line is cut at 1,000 characters. ANSI escapes are stripped. |
| Flood | More than 1,000 lines or 256 KiB within any 10 s stops the monitor, with a `· flooded` row. |
| Queued events | While the agent is in a turn, a monitor has at most **one** queued message. New batches add to it, up to the same 100 lines. |

## 1. The event row

An event is a message to the agent that started the monitor, so it is a turn,
and its row stands where that turn starts (CHD-167 part 2). `120-1-event.txt`:

```
 ⏺ Monitor(dev server errors)
   ⎿  $ tail -f dev.log | grep --line-buffered -E "ERROR|WARN"
      m1 · times out after 10m

 ⏺ Now the login form.

 ⏺ Update(src/routes/login.tsx)
   ⎿  Updated src/routes/login.tsx with 6 additions and 2 removals

 ← dev server errors · monitor
   ERROR [router] POST /login 500: Cannot read properties of undefined (reading 'trim')
       at validate (src/routes/login.tsx:41:22)
       at handler (src/routes/login.tsx:58:9)

 ⏺ My change broke the handler: validate() gets undefined when the field is missing. I'll guard it.

 ✻ Working… (8s · esc to interrupt)

╭──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                                                                    │
╰──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╯
  ? for shortcuts                                                                              Opus · 91% context left
    dev server errors  $ tail -f dev.log | grep --line-buffered -E "ERROR|WARN"  running 2m · 1 event
```

- **The glyph is `←`.** An event came in to the agent, and CHD-225 gave every
  message that came in `←`. A glyph of its own would make the person learn a
  second sign for "this started a turn and was not you".
- **The header is `<description> · monitor`.** The description is bold and
  plain. `· monitor` is dim, in the place where a message's runtime goes
  (`← @parser · codex`), so the row reads "who · what kind". There is no `@`:
  CHD-239's test is "could `send_message` reach this name", and nothing can
  write to a monitor. The arrow is plain, as for a task's report.
- **The id is not on the row.** The person stops a monitor from the list, by
  its description, so `m1` would be noise on every event. The agent gets it in
  the wrapper (below), and the `Monitor(…)` call that started it shows it.
- **The lines are verbatim.** They are drawn as plain text, never as
  markdown, because a log's `*` and `_` are not emphasis. They are not dim:
  they are why the row exists. Lines are indented three columns, and a long
  one wraps at the same indent, as tool output does. Blank lines are kept.
- **Folding: 6 lines**, then `… +N lines (ctrl+o to expand)`, which is the
  same fold as every `←` row. One rule for the row type is worth more than
  tool output's 3, and 6 still leaves room for the agent's answer at 24 rows.
  The first lines are kept, because a batch's first line is usually the error
  and the rest is its trace. ctrl+o shows the whole event, as for a message.
- **What the agent reads** is CHD-167's wrapper, with the header as `from`
  word for word, plus the id:
  `<message from="dev server errors · monitor" monitor="m1">…lines…</message>`.
  The person reads what the agent read.

### Queued behind a turn

`120-2-two-monitors.txt`. While the agent works, an event waits in the queue
as CHD-167's dim row, `← <description> · monitor: <first line>`, cut with `…`:

```
 ✻ Working… (21s · esc to interrupt)
 ← dev server errors · monitor: WARN [db] slow query 1.4s: SELECT * FROM sessions WHERE user_id = $1
```

- **One queued message per monitor.** A batch that comes while that monitor
  already has a message in the queue is added to it, and the row keeps
  showing the first line. Otherwise a busy log would fill the queue with rows
  and give the agent ten turns in a row about one log. The merged message
  holds at most 100 lines, the event cap. Lines past that are counted, and
  its last line says `… 240 more lines not delivered (an event carries at most
  100)`.
- Esc never takes a queued event into the draft, as for every message
  (CHD-167). An event still queued when Esc interrupts waits for the next
  turn.

### How a monitor ends

`120-4-ended-exit.txt`:

```
 ← CI run 4812 · monitor · exit code 1
   ✓ lint in 41s
   X test (ubuntu-latest) in 3m 12s
     X login rejects an empty email: expected 400, got 500
   ✓ build in 2m 5s
   Run 4812 (ci.yml) failed: 1 of 3 jobs failed
   Exited with code 1 after 6m 3s.

 ⏺ CI still runs the old handler: the push went before the guard. I'll push the guard and watch the new run.
```

The end is one more message, so the agent learns of it in a turn of its own,
as Claude Code's Monitor tells its model. Lines that were batched or queued
but not yet delivered go into the end message, ahead of chord's sentence, so
the end never costs a second turn. The sentence is dim, never folded, and
always last.

| End | Header word | Arrow | chord's sentence |
| --- | --- | --- | --- |
| the command exited 0 | `· exit code 0` | plain | `Exited with code 0 after 6m 3s.` |
| exited non-zero | `· exit code 1` | `error` | `Exited with code 1 after 6m 3s.` For 126 and 127: `Exited with code 127 (command not found) after 0s.` / `(not executable)` |
| killed by a signal chord did not send | `· killed by SIGKILL` | `error` | `Killed by SIGKILL after 6m 3s.` |
| its `timeout_ms` passed | `· timed out` | `warning` | `Timed out after 10m (timeout_ms 600000); chord stopped it.` |
| the person pressed `x` | `· stopped` | dim | `The person stopped it after 4m 12s.` |
| it flooded | `· flooded` | `error` | `chord stopped it: 1,000 lines in 10s is more than a monitor may print. Filter its output (grep --line-buffered) and start it again.` (or `256 KiB in 10s`) |

- **The agent's own `stop_monitor` sends no end message.** The agent asked,
  and the call's answer tells it, as `close_agent` does (CHD-167 part 5).
- **The session closing or chord quitting sends none either.** Nobody is
  left to read it.
- 126 and 127 get their meaning in the sentence because stderr goes nowhere
  (CHD-242). Without it, a mistyped command would end with a bare code.
- The end wording is the wrapper's `from` too:
  `<message from="CI run 4812 · monitor · exit code 1" monitor="m2">`.

### The flood stop

`80-5-flood.txt`:

```
 ← request log · monitor · flooded
   127.0.0.1 - - [08/Oct/2026:14:02:11 +0000] "GET /health HTTP/1.1" 200 2
   127.0.0.1 - - [08/Oct/2026:14:02:11 +0000] "GET /health HTTP/1.1" 200 2
   127.0.0.1 - - [08/Oct/2026:14:02:11 +0000] "GET /health HTTP/1.1" 200 2
   127.0.0.1 - - [08/Oct/2026:14:02:11 +0000] "GET /health HTTP/1.1" 200 2
   127.0.0.1 - - [08/Oct/2026:14:02:11 +0000] "GET /health HTTP/1.1" 200 2
   … +95 lines (ctrl+o to expand)
   chord stopped it: 1,000 lines in 10s is more than a monitor may print.
   Filter its output (grep --line-buffered) and start it again.

 ⏺ The access log is too busy to watch whole. I'll watch only the 5xx lines.

 ⏺ Monitor(5xx responses)
   ⎿  $ tail -n 0 -f access.log | grep --line-buffered '" 5[0-9][0-9] '
      m4 · times out after 10m
```

The flood row carries a sample of what flooded, the undelivered lines up to
the 100-line cap, so the agent can see what to filter. The sentence tells it
how. In the mock the agent does just that, and that is the reason the
sentence names `grep --line-buffered`.

## 2. Running monitors: rows in the agent list

**They go in the list under the status line (CHD-167 part 4), not on a line
above the box.** The list already has everything a monitor needs: ↓ reaches
it, ↑ ↓ move, `x` acts on the row, and the status line says what the keys do.
A line above the box would compete with the queue and the plan for the same
rows (CHD-167 kept those three apart on purpose) and would need a way in of
its own.

`120-2-two-monitors.txt`, the bottom:

```
╭──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                                                                    │
╰──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╯
  ? for shortcuts                                                                              Opus · 91% context left
    dev server errors  $ tail -f dev.log | grep --line-buffered -E "ERROR|WARN"  running 6m · 3 events
    CI run 4812        $ gh run watch 4812 --exit-status --compact               running 1m · no events
```

`80-2-two-monitors.txt`:

```
  ? for shortcuts                                      Opus · 91% context left
    dev server errors  $ tail -f dev.log | grep --lin…  running 6m · 3 events
    CI run 4812        $ gh run watch 4812 --exit-sta…  running 1m · no events
```

- **When the list shows.** While the session has a long-lived child **or** a
  running monitor, whichever agent started it. The `main` row is drawn only
  when there is a child, as today, so a session with monitors and no child
  shows only its monitors. A session with neither looks exactly as it does
  today.
- **Order.** Agents first (`main`, then children, as today), then monitors in
  the order they started. A monitor that ends leaves the list at once: its
  end row in the transcript says what happened.
- **A monitor's row.** It uses the same three columns as an agent's, in one
  table:
  - the **description**, cut to 24 cells. It is plain for main's monitor, and
    in the child's colour for a child's. It is bold while focused.
  - the **command**, dim, after `$ `. The `$` is what says "this row is a
    command, not an agent" at a glance, in every font and under `NO_COLOR`,
    so the row needs no glyph of its own.
  - the **state**, dim: `running 6m · 3 events`, or `no events`. For a
    child's monitor it ends `· parser`, in parser's colour, so the colour is
    never the only sign of whose it is (`120-6-with-child.txt`).
- **Narrow.** The command is cut with `…` first, down to `$` and 12
  characters. Then `running 6m · ` is dropped, leaving `3 events`. The
  description is never cut below 12 cells. At 80 columns the commands are cut
  and nothing else is (`80-2`, `80-6`).
- **Height.** CHD-167's limit applies to the whole list, agents and monitors
  together: `max(2, ⌊rows / 6⌋)` rows (4 at 24 rows, 6 at 40), then
  `… +N more`. While the list has the focus, it scrolls so the focused row
  stays in view. `80-6-with-child.txt` is the full 24-row case:
  `main`, `parser` and two monitors.
- A session runs at most **8 monitors**, counting all its agents. That is the
  children's own limit, and it keeps the list's longest case known.

### Picking and stopping one

`120-3-monitor-picked.txt`:

```
╭──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                                                                    │
╰──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╯
  ↑ ↓ to pick · x to stop it · enter esc to go back                                            Opus · 91% context left
    dev server errors  $ tail -f dev.log | grep --line-buffered -E "ERROR|WARN"  running 7m · 3 events
  ❯ CI run 4812        $ gh run watch 4812 --exit-status --compact               running 2m · no events
```

- **↓ moves the focus into the list** on an empty draft that is not walking
  history, exactly as for agents today. `↑ ↓` or `j k` move. ↑ from the top
  row returns to the box.
- **Moving onto a monitor picks nothing.** Moving onto an agent picks it, as
  today. A monitor is not something the person writes to, so the box keeps the
  agent it had, with its colour and name, and the transcript does not change.
  `❯` marks the focused row either way.
- **`x` stops the focused monitor at once.** There is no arming. A monitor is
  cheap to start again and holds nothing of the person's, unlike a working
  child. The row leaves, and the focus moves to the row above, or back to the
  box if the list is gone. The owner gets the `· stopped` message.
- **Enter and Esc** return to the box, as on an agent's row.
- **The status line's hint** on a monitor's row is
  `↑ ↓ to pick · x to stop it · enter esc to go back`, and at 80 columns
  `↑ ↓ pick · x stop · esc back`. On an agent's row it stays as built.
- **No key sequence.** Each press is an action of its own that shows its
  result: ↓ shows the focused list with its hint, ↑ ↓ move a visible `❯`, and
  `x` acts. There is no leader and no chord of keys, so nothing has to be
  remembered between presses. This is the path CHD-167 already uses to close
  a child.
- **Esc in the prompt does not stop monitors.** A monitor is meant to outlive
  the turn that started it. Esc interrupts the turn, as today.

### Shortcuts panel

`80-8-shortcuts.txt`. The prompt group's `↑ ↓` line becomes
`↑ ↓ for prompts, agents and monitors`, and one line is added under it:
`x to close an agent or stop a monitor`. The panel grows from 19 rows to 20 at
80 columns and still fits 24 rows with the box. At 120 it is 13 rows in three
columns.

```
  ↑ ↓ for prompts, agents and monitors    ctrl + c to clear input
  x to close an agent or stop a monitor   ctrl + d or ctrl + c twice to quit
```

`x` is `agents:close` (context `Agents`, default `x`, bindable), which today
closes the focused child. On a monitor's row the same action stops the
monitor. "Act on the focused row" is one action, and two bindings for one key
in one list would only let a person split them by mistake. `keys_test.tsx`
presses it on both kinds of row.

## 3. The tools

Three tools, added to chord's MCP server for the person's sessions and for
long-lived children. A task agent gets none of them. Each answers with text
for the model plus `structuredContent`, as the server's other tools do.

### `monitor`

| Argument | Type | |
| --- | --- | --- |
| `command` | string, required | Run through the person's shell (`$SHELL -c`) in the session's directory, in a process group of its own as `src/shell.ts` does. stdin is `/dev/null`. stderr is dropped unless the command merges it. |
| `description` | string, required, 1–60 characters, one line | Shown on every event and in the list. |
| `timeout_ms` | integer, optional, 1000…3600000, default 600000 | When it passes, the monitor is stopped with `· timed out`. |

It answers at once:

```
Started monitor m1 (dev server errors); it times out in 10m. Its output does not come in this answer:
each batch of lines (up to 100, gathered over 200 ms) reaches you later as a message from
"dev server errors · monitor", and so does its end. Keep working. stop_monitor with id "m1" stops it.
```

`structuredContent`: `{ id, description, timeout_ms }`.

Refusals are a failed call, and the `⎿` line shows them in the error colour
(CHD-167 part 3):

- `This session has 8 monitors running; stop_monitor one first`
- `description is at most 60 characters on one line; it is shown on every event`
- `timeout_ms is between 1000 and 3600000 (1h)`, which is refused rather than
  clamped, so the agent never thinks it has a timeout it does not have
- `Could not start the command: <the error>`, when the shell itself does not
  start

**Ids** are `m1`, `m2`, … for each session, in start order. The count carries
on from the session's record, so a resumed session never reuses an id. They
are short so that the person can read them on the call row and the agent can
type them.

The description the model reads (the tool's `description`), as a draft for
the engineer:

> Run a shell command in the background and hear from it later. Each line it
> prints to stdout is an event; lines within 200 ms come together, up to 100,
> as one message from "<description> · monitor", which starts a new turn
> after the current one. This answer only gives the monitor's id. Use it to
> wait on something without polling: a log (`tail -n 0 -f app.log | grep
> --line-buffered ERROR`), a poll loop, a CI run. Print only what you need to
> hear: a monitor printing more than 1,000 lines or 256 KiB within 10 s is
> stopped. stderr is dropped unless you merge it (`2>&1`). It ends when the
> command exits, when timeout_ms passes, or with stop_monitor; you get a
> message when it ends on its own.

### `stop_monitor`

`{ id: string }`. It stops the caller's own running monitor: SIGTERM to the
group, then SIGKILL within `process.ts`'s bound. It answers
`Stopped m1 (dev server errors) after 4m 12s and 3 events.` with
`{ id, description, events, ran_ms }`. It refuses with:

- `No running monitor m9 of yours; list_monitors names them`, for an unknown
  id or another agent's monitor. An agent sees and stops only its own.
- `m1 already ended: exit code 0`
- `m1 was running when this session was left and was not restarted; monitor starts another`,
  after `--resume`

### `list_monitors`

`{}`. It answers the caller's own **running** monitors:
`2 running: m1 dev server errors (6m, 3 events), m2 CI run 4812 (1m, no events)`,
or `No monitors running`. `structuredContent`:
`{ monitors: [{ id, description, command, started_at, events, timeout_ms }] }`.

**Why a tool of its own and not a field in `list_sessions`:** `list_sessions`
answers "which sessions and agents are in this window", which is a different
question from "what am I waiting on", and children do not get
`list_sessions`. A child that starts monitors needs to list them too. The
answer is also scoped differently: sessions are the window's, and monitors are
the caller's own.

### The calls on screen

The calls are named in CHD-167 part 3's style. chord knows each call is its
own by the request it served:

| Tool | Headline | Under `⎿` |
| --- | --- | --- |
| `monitor` | `Monitor(dev server errors)` | `$ <command>`, then `m1 · times out after 10m` |
| `stop_monitor` | `Stop monitor(dev server errors)` | `Stopped after 4m 12s · 3 events` |
| `list_monitors` | `List monitors` | `2 running · dev server errors, CI run 4812` / `None running` |

The command goes on its own line under `⎿`, not in the headline. The headline
names the monitor the way its events will, so the person can match a
`← dev server errors · monitor` row to the call that started it.

`/mcp`'s line for chord's server gains the three names:
`chord's server gives claude list_agents, list_sessions, spawn_task, open_agent, send_message, close_agent, monitor, stop_monitor and list_monitors.`
With a child picked it reads `… send_message, to main only, and monitor, stop_monitor and list_monitors.`

## 4. Permission

**Yes to the lead's recommendation: chord adds no prompt of its own.** The
`monitor` call goes through the agent's own permission rules, like any MCP
tool:

- In the agent's default mode, the agent already asks, and a second chord
  prompt would ask the person the same thing twice in a row.
- In the modes where the agent does not ask (accept-all, bypass), the person
  chose not to be asked about shell commands. A chord prompt would overrule
  that choice for this one tool, while `Bash` runs freely beside it.
- The person can still see and stop every monitor in the list the moment it
  starts. That is more than a background `Bash` call gets.

**But the premise is false in chord today, and CHD-245 must fix it.** The
lead's reason was that the agent's ask already shows the command. It does not
in chord. I read claude-agent-acp 0.87.0: its permission request for an MCP
tool carries the call's `rawInput` (`{command, description, timeout_ms}`) and a
title that is only the tool's name (`mcp__chord__monitor`, as CHD-167 read in
0.86.0). chord's box (`src/ui/dialogs/Permission.tsx`) draws the title and
the locations, never `rawInput`. So the person would be asked to allow
`mcp__chord__monitor` without seeing what it runs.

The fix is general, and it does not guess which server a call belongs to.
**A permission request with no `content` of its own shows its `rawInput`
under the title, one `key: value` per line**, with strings unquoted, long
values wrapped at the key's indent, and nested values as compact JSON. Claude
Code's own MCP prompt does the same, showing a tool's arguments beside its
name. `120-7-permission.txt`, at 80 (the options are the agent's, and these
are illustrative):

```
╭──────────────────────────────────────────────────────────────────────────────╮
│ mcp__chord__monitor                                                          │
│   command: tail -f dev.log | grep --line-buffered -E "ERROR|WARN"            │
│   description: dev server errors                                             │
│   timeout_ms: 600000                                                         │
│                                                                              │
│ Do you want to proceed?                                                      │
│ ❯ 1. Yes                                                                     │
│   2. Yes, and don't ask again for chord - monitor commands in ~/src/app      │
│   3. No, and tell Claude what to do differently                              │
│                                                                              │
│ Esc to reject                                                                │
╰──────────────────────────────────────────────────────────────────────────────╯
```

This helps every MCP tool of the person's own servers too. A request that has
`content` (a diff, a command an agent already rendered) is drawn as today.

## 5. The numbers

| | Number | Why |
| --- | --- | --- |
| Batch window | **200 ms, fixed**, from the first line after the last batch went | Claude Code's figure. Fixed, not a debounce: a steady stream would push a debounce back forever and never deliver. |
| Lines per event | **100** | Enough for a stack trace or a test run's failures. Past it the agent is reading a log, not hearing an event. |
| Bytes per event | **16 KiB** | It stops 100 long lines from becoming one huge turn. About 4k tokens at most. |
| Line length | **1,000 characters**, then `… (+N characters)` | One minified line must not take the whole event. |
| Overflow in a window | Counted, not sent: the last line is `… 240 more lines not delivered (an event carries at most 100)` | The agent knows something was cut. Overflow alone is not a flood. |
| Flood | **More than 1,000 lines or 256 KiB within any 10 s** (sliding) | A sustained 100 lines a second is a log the agent forgot to filter. A start-up burst (`tail` printing its last lines, a test run's summary) stays well under it. |
| On a flood | SIGTERM to the group, SIGKILL after `process.ts`'s bound, then the `· flooded` message with the undelivered lines up to 100 | The sample shows what flooded. |
| Running per session | **8** | The children's limit, so the list's longest case stays known. |
| `timeout_ms` | default **600000** (10 min), range **1000…3600000** (1 h) | 10 min covers a dev-server watch or a short CI run without leaving a forgotten `tail -f` running all day. 1 h covers a long CI run. Past that, the agent starts another. |

Lines are split on `\n`, with a trailing `\r` dropped, and decoded as UTF-8
with replacement. ANSI escapes are stripped before anything is batched, for
the agent and the screen alike. A line still open when the command exits goes
with the end message.

## 6. Everything else a monitor touches

- **Turn notifications.** A turn that an event started does not notify the
  terminal when it ends. A busy log would ring the bell all afternoon. A turn
  that an end message started notifies, as any turn's end does. A permission
  or form inside either one notifies as always.
- **Busy, closing, quitting.** A running monitor does not make a session busy.
  Closing it or quitting stops every monitor silently, with no arming. A
  monitor holds nothing that is lost, and with it counted, a window with a
  `tail -f` running could never be quit with one ctrl+d. Tabs, the strip, the
  sessions picker and the status line's notices do not change.
- **A long-lived child's monitors** deliver into the child's transcript (seen
  with the child picked). They show in the parent's list with the child's
  colour and `· parser`. `x` on one stops it, and the child gets the
  `· stopped` message. Closing a child stops its monitors.
- **`--resume`.** Event and end rows come back as they were recorded. Monitors
  are not restarted, because restarting commands the person may not want is
  the children's reasoning again. A closing note, chord's own `⏺` after the
  past, names the ones that were running:
  `dev server errors and CI run 4812 were running when this session was left and are not restarted`.
  The agent is not told at resume, since that would start a turn nobody asked
  for. Its `stop_monitor` on one gets the refusal in part 3.
- **`-p`.** There is no MCP server in `-p`, so there is no monitor. Nothing
  changes there.
- **Light and dark.** The rows use only existing roles: plain, dim, bold,
  `error`, `warning`, and the agents' colours. Nothing new is added to the
  theme.

## Rejected

- **A line above the box** (`◉ 2 monitors · dev server errors, CI run 4812`).
  It would compete with the queue and the plan for the rows above the box,
  and it would need its own way in. The list already has one.
- **A glyph for monitor rows** (`◉`, `↻`, `⧖`). `$` before the command already
  marks the row in every font. `⧖` is in none of the default fonts (CHD-225's
  lesson about `✉`), and `◉` reads as a radio button.
- **`@monitor` or `← monitor` as the sender.** `@` promises the name can be
  written to (CHD-239). A bare `monitor` would hide which of several sent the
  event, and the description is what the person and the agent both chose to
  recognise it by.
- **Folding events at 3 lines, as tool output.** The row is a message row,
  and one fold for every `←` keeps the rule simple. 6 lines still fit at 24
  rows.
- **Arming `x` for a monitor.** It is cheap to restart and nothing is lost.
  The child's arming exists because a working child's turn is lost.
- **Monitors in `list_sessions`.** Covered in part 3.
- **A permission prompt of chord's own.** Covered in part 4.

## For the engineers

- **CHD-244 (the engine).** Covers parts 3 and 5, the end messages and
  wrappers in part 1, part 6's resume record, and the closing and quitting.
  The one rule: before writing a line splitter, try `@std/streams`'
  `TextLineStream` on the child's stdout. For ANSI, try `@std/fmt/colors`'
  `stripAnsiCode`. For the process, reuse `src/shell.ts`'s process group, not
  a new spawner. The batch window and the flood count are timers chord owns,
  so let tests pass the clock in (`@std/testing/time`'s `FakeTime` is the
  library to try). No test runs a real agent: a monitor's command in tests is
  `printf` or a `deno eval` loop.
- **CHD-245 (the screen).** Covers part 1's rows, part 2 entirely, part 3's
  headlines and `/mcp` line, part 4's raw input in the permission box, the
  shortcuts panel, and the end rows' colours. Its acceptance is the eight
  states above, captured at 120×40 and 80×24 from `deno task chord:fake`. The
  fake agent will need a prompt that calls `monitor` with a `printf` command,
  and one that floods. The captures go under `evidence/CHD-245/`.
- The mocks show the bottom of each screen as Ink anchors it. Where a mock's
  transcript is short, the header shows above it, as in the running app.
