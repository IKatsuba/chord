# CHD-524: cursor moves in the question dialog's Note

**Proposal only; owner decision required before implementation.** Recommend
option A below. Neither arrow remap is approved by this document. This task
changes only the focused, non-secret `Note` beside a question's choices.
It keeps the question box designed in [CHD-1](CHD-1.md) and the word/line
vocabulary in [CHD-386](CHD-386.md).

## The choice the owner must make

The conflict is present in the unchanged baseline `6629f815`:
[`askKey`](../../src/ui/dialogs/questions.ts) handles `leftArrow` and
`rightArrow` before dispatching to a text row. Neither branch checks a
modifier. Bare arrows and modified arrows therefore move between question
steps today, including while the Note is focused. CHD-1 assigns arrows and
Tab to question navigation. The requested modified arrows take that action
away in one context; this needs the owner's choice.

| Key while the Note is focused | A: recommended | B: alternative |
| --- | --- | --- |
| `alt + ← →` (option) | Move by word | Move by word |
| `cmd + ← →` | Move to displayed-line start/end | Move to displayed-line start/end |
| Bare `← →` | Previous/next question, unchanged | Move one character within the Note |
| `Tab`, `Shift+Tab` | Next/previous question, unchanged | Next/previous question |
| `↑ ↓` | Existing row navigation | Existing row navigation |
| `Enter` | Next step, unchanged | Next step, unchanged |
| `Esc` | Cancel the question request, unchanged | Cancel the question request, unchanged |

**Why A:** it restores the requested editing moves while preserving bare
arrows as question navigation, including the existing on-screen hint.
**Cost of A:** moving one character requires a word/line move followed by
editing, or another already supported editing key; bare arrows still leave
the Note. **Why choose B:** character moves feel familiar in a text field.
**Cost of B:** bare arrows stop navigating questions from the Note, and its
hint must say Tab for questions. Outside this Note, both options retain all
existing question navigation and option-selection behavior.

## The resulting field

Use the existing public OpenTUI textarea, with its own edit buffer, cursor,
word boundaries and visual-line actions. Keep the current `Note` label,
`❯`, indentation, wrapping and bounded question layout. No extra border,
mode switch, nested editor, save action or pointer dependency.

Typing and Backspace edit at the cursor. In `Please use teh parser`, move
to the typo, remove `teh`, and insert `the`; the existing choice stays
selected and the answer sends both that choice and the corrected note.
Cursor moves alone do not select an option, change steps or answer the
request. Cmd moves target the displayed wrapped line, not the whole note.
The editor shows the cursor's line within the existing available space.

- **Empty:** keep the current dim optional-note placeholder; focus shows
  the editor cursor. An empty note still sends no additional answer.
- **Editing:** terminal foreground for text and the native editor cursor;
  `permission` for the existing border, title, focused marker and Note
  label; dim descriptions and hints, `success` for completed step marks,
  `warning` for required markers. Roles are from `src/ui/theme/theme.ts`.
- **Leaving and returning:** retain text and cursor by the current request,
  question and agent. Do not reset the cursor merely because another row,
  step or agent owns focus. An answered, withdrawn or replaced request
  releases its editor state; nothing carries into a different request.
- **Paste:** retain the existing Note paste meaning and answer content;
  insert at the cursor. Existing newline/control handling must be tried
  with the public widget before integration is accepted. Do not rewrite
  input or patch the library to obtain compatibility on our own call.
- **Waiting/streaming:** keep the existing waiting line and transcript;
  background updates do not move the Note cursor or focus. A focused Note
  owns its editing keys only while that request owns the dialog.
- **Validation/error:** preserve existing blockers, required markers and
  submit feedback. Moving the cursor introduces no error or toast.
- **Narrow/overflow:** retain the question's bounded height and existing
  options/step visibility. The focused Note must remain editable at 80 by
  24; existing navigation and overflow keys must not become editor keys.
  If the public widget cannot preserve this layout, return to the owner.

## Inventory and finite scope

| Existing field | Baseline behavior | This proposal |
| --- | --- | --- |
| Non-secret question Note beside choices | Shared `edited()` appends/deletes at end; `Typed` draws end cursor | Only field changed, after owner approval |
| Question own-answer/instead option | Same `edited()`/`Typed` path; selection semantics differ | Unchanged, deferred |
| Plain text question and secret text fields | Shared end-editing path; secret masking must hold | Unchanged, deferred |
| Plan approval Note | Shares `edited()`; wrapped/pageable Note under CHD-437 | Unchanged, deferred |
| Generic form text/number fields | Separate `form.ts` cursor, character arrows, Home/End and mid-text edits already exist | Unchanged, deferred |
| Form choices/lists/buttons | Arrows open/close lists or switch buttons | Unchanged |

A shared helper is not a reason to broaden the slice. No new text editor,
parser, dependency, clipboard behavior, answer schema or dialog navigation
outside the focused Note. No generic form migration, Plan Note migration,
new multiline-answer semantics or secret-field migration. If integration
proves a wider change inseparable, bring the concrete dependency and options
to the owner before proceeding.

## Public-widget trial and its limits

Developer reported a read-only `bun -e` harness trial on OpenTUI 0.6.6,
using React `createElement`, the existing `TextArea` wrapper and
`tests/ui/harness`'s `draw`. No files, agents or native clipboard were used;
the trial took 0.175 seconds. A width-10, height-3, character-wrapped editor
started with `alpha beta gamma` at public `cursorOffset` 16:

| Input | Observed result |
| --- | --- |
| Option-left, `CSI 1;3D` | Cursor offset 11 |
| Insert `X` | `alpha beta Xgamma`, cursor offset 12 |
| Cmd-left, `CSI 1;9D` | Cursor offset 10, current visual-line start |
| Cmd-right, `CSI 1;9C` | Cursor offset 17, current visual-line end |

The inherited public bindings provide `word-backward`, `word-forward`,
`visual-line-home` and `visual-line-end`. This supports trying the existing
widget before any custom editing logic. The public `Input` contract instead
fixes height to one, disables wrapping and strips newlines; using it for the
wrapped Note would change the required displayed-line behavior. It was
inspected, not run as a replacement.

**Untried:** actual question Note embedding, event routing and key conflict
resolution, focus transfer, paste compatibility, request/agent cursor
persistence, overflow integration, Unicode editing, source-terminal QA and
compiled-binary integration. The isolated widget result establishes none of
these. No production implementation, dependency change, compile trial or
terminal capture accompanies this proposal.
