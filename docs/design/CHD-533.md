# CHD-533 — resource facts for choosing a team run

**Implementation approved: Q251 and Q252, option 1, on 2026-10-27.** The owner
approved package `6461ce56`, based on `origin/main` `a0c61ab5` (0.60.0). This
document specifies the implementation; it does not claim it has shipped. Native
lint/canary work belongs to CHD-538.

The owner-approved direction is simple: Chord collects resource facts; the agent
launching a team chooses its composition. Preserve capacity until reset with
reserve rather than equalizing tasks or exhausting subscriptions. Saved teams
and running work stay in place. There is no scheduler, executor registry,
background coordination service, reservation system or worker migration.

### Approved lifecycle and cache defaults

These approved defaults are implementation choices still to test, not provider
guarantees or measurements:

1. Collect only Codex/Claude providers referenced by the current session or a
   resolved team run/choose request, using existing
   configuration/authentication. No installed-runtime discovery, startup of
   unrelated runtimes or new auth settings. `get_budgets` reads the current
   cache immediately, without spawning a collector or waiting for refresh.
2. First eligible use schedules one background read. While that provider remains
   relevant, refresh at most once per 120 seconds; close each collector after
   its read. One in-flight read per configured provider/path per process;
   concurrent consumers share it. No cross-process scheduling or quota lock.
3. Bound acquisition to 20 seconds total, initialization to 8 seconds and each
   subsequent request to 3 seconds within that total. Cancelling one consumer
   detaches it and revokes its generation's publication/launch authority; other
   live consumers may still publish the shared result. Last-consumer cancel,
   deadline or shutdown invalidates the read, rejects late publication and
   requests library close. Clearing/replacing the caller revokes pending choose
   authority; no late result can act in its replacement.
4. Under the approved group ownership, allow 500ms for close/stdin end, then
   group TERM with 500ms grace, group KILL with 500ms verification. Stop waiting
   after that bound and report cleanup failure; never claim exit from request
   rejection. Check the owned group on every success/error/cancel/exit. On Chord
   shutdown cancel all reads and perform those bounded group steps.
5. Failures negative-cache for 120 seconds, then back off to 240, 480 and 900
   seconds maximum; success resets cadence. A usable provider Retry-After can
   extend the next attempt. No immediate automatic retry or auth repair. Missing
   executable/version/scope and unsupported-source errors wait until their
   existing configuration/session changes, rather than polling a permanent
   failure. No retry changes authentication or starts a model turn.
6. Track acquisition recency separately: a receipt within 180 seconds is a
   recent read, not fresh provider data. Apply the per-window 60-second provider
   observation rule below only when that timestamp exists. Both measured
   official sources currently remain `unknown` without it. Failed refresh keeps
   the original utilization/reset/receipt/observation time plus failure reason;
   partial replies cannot redate omitted windows.
7. At 15 minutes from original receipt, or after a known reset passes, retain
   the old value only as stale historical context, excluded from usable capacity
   advice. With no usable observation report unavailable and its reason. Persist
   only allowlisted normalized facts in the bounded cache below; no raw provider
   stdout/stderr, account identifiers or credentials. Disk retention is not a
   freshness grant. Unknown identity remains source-scoped and unmerged.

## Resource snapshot contract

Proposed `get_budgets {}` reads observations already available to Chord,
effective preferences and active work. It sends no model prompt and does not
start every installed runtime. Eligible collectors refresh on the bounded
lifecycle above and may consume supported updates; missing collectors remain
explicitly unavailable. A read does not redate cached facts. Expose the tool to
person and long-lived-agent callers eligible for `list_agents`; task-agent tool
eligibility stays unchanged. Use a finite internal retry classification,
stripped from public unavailable reasons. Do not parse reason prose, add login
or loop retries for configuration failures.

The response is a versioned object:

```ts
{
  schemaVersion: 1,
  observedAt: string, // UTC ISO time of this read, not of every fact
  preferences: TeamSelection,
  pools: PoolSnapshot[],
  unbound: UnboundObservation[],
  unavailable: { agent: string; reason: string }[],
  warnings: string[],
  activeRuns: ActiveRun[]
}
```

Top-level `warnings` is a bounded list of sanitized incomplete-cache coverage
warnings for limits, malformed or unreadable data; no raw errors or paths.
Nonempty means incomplete collected coverage. Empty does not establish whole
account/provider completeness. Per-source coverage and unavailable reasons
remain separate. Process cache files need not persist derived reader warnings.

Each pool identifies one provider account, billing source and resource pool:
`poolRef`, `accountRef`, `provider`, `billing: 'subscription' | 'api'`,
`source`, `sourceVersion`, `identityObservedAt`,
`coverage: 'account' | 'chord'`, `externalActivity: 'visible' | 'unknown'`, and
`identity: 'verified'`. References are opaque local identifiers, not keys,
emails or raw provider account IDs. Only an authoritative provider identity can
make two observations the same pool. Runtime names, login-file presence,
matching percentages and plan names cannot. Unknown identity is an unbound
observation scoped to its source/session and never merged with a verified pool.
`UnboundObservation` retains
`{observationRef, sourceRef, sessionRef, agent, source, sourceVersion, observedAt, billingKind: 'subscription' | 'api' | 'unknown', windows: WindowSnapshot[], reason}`.
It carries any known per-window facts in the same window shape below, without
account/pool identity. `observationRef` is stable only within the emitting
source/session; it does not link an account across processes. Include
observation coverage and external activity as known/unknown fields,
independently from identity. It is advisory evidence scoped to that
source/session, never deduplicated across sources or counted as another
available pool. `unavailable` is reserved for sources with no usable observation
at all.

Each subscription window is independent:

```ts
{
  windowRef: string,
  models: string[] | null, // null means model scope unknown
  usedPercent: number | null, // inclusive 0..100; null is unknown
  windowSeconds: number | null,
  resetsAt: string | null,
  observedAt: string | null, // provider observation time, not local receipt
  receivedAt: string | null, // local receipt only; does not establish freshness
  state: 'fresh' | 'stale' | 'unknown' | 'unsupported',
  reason: string | null
}
```

Absent windows are not zero usage. A partial event updates only its named
window; it does not erase or refresh the others. An adapter must distinguish an
account-wide window from a model-scoped one; unknown applicability is reported,
never widened to all models. Preserve source utilization precision.

Proposed freshness is at most 60 seconds from each window's actual observation,
and never past its reset. Future timestamps over five seconds ahead are unknown
due to clock skew; slightly future timestamps use age zero without extending the
60-second deadline. Within a process use monotonic elapsed time; if wall time
moves backwards or cached time is implausible, mark stale/unknown until
refreshed, never manufacture freshness. Older/out-of-order observations cannot
replace newer ones. A reset passing marks the old observation stale until
refreshed; it never synthesizes a full pool. Failed refresh retains original
time/value with stale/error reason. A missing reset can leave utilization fresh,
but balance-until-reset advice is unavailable. Without duration/start, do not
calculate a remaining-time fraction. A source without a provider observation
timestamp keeps `observedAt: null` and `state: unknown`, even with a new local
`receivedAt`. Retain its utilization/reset and source; missing observation time
does not make the whole read unavailable. Acquisition recency may inform the
agent with uncertainty. Receipt alone cannot pass the 60-second freshness check.
These thresholds are proposals to test, not provider guarantees.

API monetary observations remain separate from subscription windows. When
available, report currency, reported/estimated spending, period, coverage and
unknown costs. A future optional monetary ceiling is advisory context, not a
payment-source grant, strict enforcement or subscription conversion. No API
budget schema or fallback authorization is part of the first slice. Never infer
authentication or payment source from cost being present.

`ActiveRun` carries opaque process/run/session refs, safe team/member names,
effective agent/model and any known resource refs, state and `lastSeenAt`. It
includes unopened members as planned, not spending. A live process publishes its
own work with a 15-second heartbeat; after 45 seconds, show it as stale/possibly
active, not ended. External applications and crashed processes may be missing.
There is no reservation or deduction of predicted usage.

## Settings proposal

Add `teamSelection` to existing settings, checked by the existing strict Zod
schema. These examples are proposed schema shapes, not runnable settings today.

```json
{
  "teamSelection": {
    "intent": "balanced",
    "prefer": { "agent": "codex", "model": null },
    "constraints": {
      "agents": ["claude", "codex"],
      "models": { "claude": ["sonnet"], "codex": ["gpt-5"] },
      "modes": { "claude": ["acceptEdits"], "codex": ["auto"] }
    }
  }
}
```

`intent` is `balanced | prefer | economy | fixed`; default `fixed` preserves
saved selection. `prefer` is soft, used only for `intent: prefer`. `balanced`
asks the launching agent to consider every applicable window and time to reset,
keeping reserve for later work; it prescribes no fixed provider split or
unmeasured numerical reserve. `economy` asks it to prefer lower monetary spend
among supported choices using existing authentication. `fixed` asks it to keep
the saved composition.

`constraints.agents`, `models` and `modes` are exact allowlists, with omission
meaning no additional restriction and an empty list meaning no allowed choice.
They are hard constraints, not rankings. Mode IDs are runtime-specific:
`acceptEdits` and `auto` in this illustrative policy are separately allowed, not
asserted equivalent. Switching runtime requires an explicit allowed mode for the
destination and preserved role requirements; when those cannot be proved, reject
and ask for policy correction. Never infer a permission order from names or
silently broaden permissions.

Use the existing user/project settings merge for preferences and supported
runtime/model/mode constraints. Merge `intent` by latest value and `prefer`
keywise. Replace `constraints.agents`; merge `models` and `modes` maps keywise,
replacing each named runtime list. Empty lists deny. Invalid or unknown fields
fail visibly. No new project payment authority or narrowing-only monetary policy
is proposed.

## Choosing and launching one run

Proposed tool arguments extend the current call without rewriting team files:

```ts

  team: string,
  job: string,
  selection?: {
    reason: string, // required, nonempty, at most 500 characters
    lead?: RunChoice,
    members?: Record<string, RunChoice>
  }
}

// {agent?, model?, effort?, mode?}
```

Omitted `selection` retains today's saved-team behavior. With `selection`,
unknown fields/member names fail. Omitted role fields inherit saved values only
on the same runtime. Changing `agent` drops incompatible saved model/effort/mode
values: the caller must supply destination `model` and `mode`, plus `effort`
when requested by that role. An instruction requiring exact effort cannot be
satisfied by a soft request: refuse that substitution pending an owner-approved
exact-effort contract. No old-runtime default leaks into the new one. A model
the provider cannot confirm is not a successful exact override. Omitting effort
requests the destination's default and records the actual value when known. An
explicitly requested effort remains soft after startup. No null/reset shorthand.
Reject known unsupported explicit effort in preflight; a later runtime refusal
remains visible as actual effort plus note under CHD-353/354. Do not claim exact
effort was guaranteed.

Before starting any lead job, resolve the saved team and effective policy once,
validate the complete proposed composition against known capabilities and
permission requirements, and freeze it in the existing in-memory run. Copy only
selectable configuration fields; retain body, roles, instructions, permissions,
project handoffs and QA requirements byte for byte. The launching agent attests
in its reason that the choice preserves those prose requirements; Chord checks
structured allowlists and exact target mode. It cannot validate arbitrary prose
requirements. With ambiguous or conflicting prose, the agent must refuse
substitution and ask. This attestation is not proof of cross-runtime permission
equivalence: Chord checks the configured exact target mode. Explicitly fixed
harness/role requirements remain hard caller obligations; ambiguous mappings
refuse. There is no new per-role settings subsystem or manual configuration
requirement for every team member.

Validate the lead's actual configuration after startup and before its first job.
Unknown capabilities may require supported initialization, never a paid prompt
merely to discover them. Members open later from the frozen run, not the current
saved file; each is revalidated against current policy and capabilities before
receiving its first job. A changed policy may refuse an unopened member but
cannot mutate it into another selection.

Static composition errors start nobody. A lead initialization failure closes
that attempted lead without a job. A later member failure leaves existing work
running and reports that member refused; it does not silently restart the team,
substitute a provider or duplicate jobs. Refused startup is visible to caller
and person. Record actual values/refusals as they arrive. No success claim for
an unopened member: its status is planned/unconfirmed.

The answer includes run ID, saved team source, effective choices and per-role
validation state, reason, snapshot observation references and warnings. Persist
the same selection receipt in the existing run/session record so replay and
`/team show <run>` distinguish the saved team, planned choices and actual live
configuration. Do not persist credentials or raw provider payloads.

A caller interrupted, cleared, replaced or disconnected before launch loses its
pending launch authority; a late result cannot act in the replacement session.
U4 must add and test the caller-generation launch guard; current behavior does
not guarantee this protection. A transport timeout is not proof that a run
failed: inspect `list_teams`/the existing run ID before retry. Do not retry
launch automatically.

The launching agent's compact instruction is: read `get_budgets` and
team/runtime capabilities; preserve instructions and hard constraints; choose
supported new-run settings within the existing permissions; explain the choice
and uncertainties; call `run_team` once with overrides and reason. Unknown
capacity is not unlimited. A rejected choice requires a visible revised choice,
not hidden fallback. No nested selection turn or model-authored scheduler is
added.

## Storage, concurrency and separate API accounting

Use the existing state directory for replaceable telemetry cache files, one
writer-owned file per live Chord process, atomically replaced with private file
permissions. Readers fold observations by verified pool/window/source identity
and choose the newest valid observation; they do not sum percentages or whole
pool balances across processes/projects. Cache observations expire by their
original times. No shared mutable balance, database, lock service or daemon.
Concurrent launches see imperfect snapshots; either may consume the same pool.
Neither the UI nor tool promises quota or dollar enforcement. On startup, each
process reads at most 256 cache files of at most 256 KiB each;
additional/malformed data is skipped with explicit incomplete-coverage warnings.
Keep only the latest observation per source/window in each process file. Files
older than 24 hours are ignored; each writer may remove only its own expired
file on close. As a separate startup exception, best-effort cleanup may remove
at most 32 expired files from any process whose embedded write time and file
modification time are both over 24 hours old, rechecking metadata before
removal; failure only warns. A living process recreates its replaceable file if
necessary. Never infer liveness from PID existence/reuse. Skipped/unreadable
sources mean incomplete active-work/usage coverage, not zero. Future long-run
fixtures must verify bounded reads and cleanup without a daemon.

The separate advisory API goal would derive Chord API spending only from turns
authoritatively bound to the verified API billing pool. Existing records lack
that billing binding: their dollar costs may belong to subscription work, so
historical costs remain unassigned and cannot establish API spend. Add verified
billing provenance for future turns before counting them. Upsert the latest
usage by `(sessionId, turnId)`; repeated/replayed revisions replace, never add.
Late costs may revise a completed turn. Provider-reported cost replaces an
estimate for that same usage; retain provenance and known coverage. Assign a
turn to the period containing its recorded start; a later revision stays with
that period. Unknown start time is uncounted. Split-boundary provider aggregates
cannot be assigned without authoritative interval detail.

Do not add parent/subagent totals when one includes the other. An adapter must
identify inclusion/coverage; absent that contract, expose overlap as uncounted
rather than claiming a complete sum. Likewise use either authoritative
account-period cumulative spending or Chord turn totals for a given scope, never
both. A cumulative observation without matching period/currency/account cannot
replace or extend Chord totals. Show Chord-only coverage and unknown external
activity unless the provider establishes account-wide coverage. Active work and
estimates remain separate from settled reported spending. Do not scan all
historical records on each `get_budgets` call. Maintain a process-local derived
index from the existing record reader, updated for changed records; first read
is bounded to the current API period and at most 10,000 turn records or two
seconds, including record discovery/header reads (at most 256 files and 64 MiB).
On truncation return incomplete/unknown coverage rather than a misleading
remaining budget. The derived index is disposable, not a new shared ledger.
Future checks must measure cold/warm reads, revision repair and memory on
representative large records; these bounds/performance are unmeasured.
