# CHD-531: npm login during release preparation

**Proposal only. Owner policy decisions are required before implementation.**
The owner has decided that a release should run npm login interactively when
its npm identity check fails, then continue. This proposal makes the failure,
terminal, dry-run and ordering choices concrete. It does not authorize a
login, credential/configuration inspection, release or production edit now.

## Recommended package

Keep the existing npm wrapper and invoke plain `npm login` once, with the
owner's terminal inherited, only after a failed `npm whoami` and a successful
TTY check. After login exits successfully, run the same `npm whoami` again.
Continue only when that recheck succeeds. A failed check is the trigger;
do not claim that its cause must be missing credentials.

Use `npm(release, ['whoami'])`, then when needed
`npm(release, ['login'], { stdio: 'inherit' })`, then
`npm(release, ['whoami'])`. These are proposed calls, not commands executed
for this investigation. Do not add registry, scope or auth-type flags,
change the environment, parse npm's prompts/errors, collect credentials or
retry in a loop. npm owns browser interaction, prompts, authentication and
configuration writes. Wait for its process as the publish stage does.

## Policy decisions for the owner

Each recommendation below is pending, including its application to runs
that do not publish. Review does not approve the policy.

| Condition | Recommended policy | Owner alternative and cost |
| --- | --- | --- |
| Initial whoami succeeds | Continue without login, with or without TTY | Requiring a TTY here would reject otherwise usable checks; publish retains its own terminal requirement |
| Initial whoami fails, stdin and stdout are TTYs | Explain the handoff; run one unchanged npm login | Stop for manual login; does not fulfill the requested automatic recovery |
| Login exits nonzero | Stop before build, version commit, push or publish; let npm's inherited output explain its failure | Retry login; adds another credential/browser interaction and a retry policy |
| Login is cancelled or ends without an exit status | Stop, never proceed to release work | Offer another attempt; adds an interruption/retry flow |
| Login exits zero, whoami recheck fails | Stop; report the failed recheck without guessing the cause | Retry login or continue on login status alone; respectively repeats side effects or loses the identity gate |
| Initial whoami fails without TTY | Stop with terminal-required guidance; do not start login | Attempt inherited noninteractive login; can fail or wait without an interactive owner |
| Dry run, including `--skip notarise` | Apply the same auth recovery; explicitly disclose npm credential/configuration and possible browser effects | Require manual login and stop on failure, or skip authentication; both diverge from the task's dry-run acceptance and current always-auth check |
| Selected stages exclude publish | Apply the same auth gate, as today | Authenticate only publishing runs; reduces unnecessary login but changes current release prerequisites |

The recommended failure policy is one attempt per release invocation, no
release-level retry prompt. A later invocation may try again. Do not infer
cancel from error text: nonzero status, signal termination or a null status
all prevent continuation. npm output remains its own; Chord must not capture
or copy authentication prompts into its release diagnostics. Existing
captured whoami failure diagnostics can identify which check failed without
claiming a particular authentication cause.

Before handing over the terminal, proposed Chord wording is:

```text
npm whoami failed; npm login will use this terminal and may open a browser.
npm may save credentials and registry settings, including during a dry run.
```

For no TTY after a failed check:

```text
npm login needs stdin and stdout on a terminal; rerun this release in a terminal.
```

For a failed login: `npm login did not complete; release stopped`.
For a failed recheck: `npm whoami still failed after login; release stopped`.
These are proposed messages, not terminal captures. npm supplies its own
keys and prompts; no Chord dialog, new keyboard binding or TUI is added.

## Phase placement

**Recommend a separate mandatory authentication phase immediately after all
read-only preflight guards**, before the resume-publish branch, Apple
credential checks, builds and version hold/commit/push. It is preparation,
not a selectable stage: `--skip`, `--only`, `--from` and `--to` cannot bypass
it. It runs for fresh and resumed releases under the approved dry-run and
nonpublishing policy. Successful preflight must no longer claim to have
validated npm identity; authentication preparation does that separately.

The concrete order is platform/stage/version eligibility, read-only tree
and registry-version checks, publishing branch/origin/tag checks when
applicable, authentication preparation, then the existing resume or fresh
release path. A publishing preflight already uses `git fetch origin`; the
existing comment's read-only distinction is about avoiding credential,
version and publication mutations, not a promise of zero Git metadata or
network effects. This proposal adds no fetch or other guard.

**Alternative: keep recovery inside preflight step 3.** This is the smaller
edit and preserves current check ordering, but preflight's “only read”
contract must change. npm may save credentials before a publishing run is
rejected for its branch or tag. The separate phase avoids that unnecessary
login, at the cost of moving the existing identity check later and changing
the preflight/orchestrator boundary. This placement is an owner choice,
not an approved refactor. No new stage name, CLI option or skip flag.

## Official-source research and unknowns

Developer researched the following official public sources; they were also
opened during proposal preparation. These are moving documentation/source
URLs, not proof of the installed npm version or the owner's configuration:

- [npm login documentation](https://docs.npmjs.com/cli/v11/commands/npm-login/)
  documents credential saving and configurable registry/scope/auth strategy.
  Its default auth type is web; OTP configuration can select legacy.
- [npm login source](https://github.com/npm/cli/blob/latest/lib/commands/login.js)
  selects a configured scope registry when present without a CLI registry
  override, then saves user configuration after successful login.
- [npm auth source](https://raw.githubusercontent.com/npm/cli/latest/lib/utils/auth.js)
  includes upstream fallback from unsupported web authentication to legacy.
  Plain login delegates this to npm; even forcing web would not justify a
  promise of no upstream fallback.
- [npm whoami documentation](https://docs.npmjs.com/cli/v11/commands/npm-whoami/)
  describes token-registry identity lookup and Basic Auth username behavior.
  An identity result is not proof of permission to publish these packages.

The actual npm version, effective registry, scoped registry, auth settings
and owner's manual login command are **unknown and were not inspected**.
The wrapper does not pin npmjs. A configured scope may make login target a
different registry from whoami. The mandatory recheck prevents proceeding
when the existing identity check still fails; it does not establish registry
consistency or publish rights. Do not guess flags or resolve that mismatch
by reading/changing credentials. If implementation exposes a concrete
mismatch, return it to the owner with options before altering the command.

No live whoami/login, logout, npm configuration/credential/log access,
release, test or compile run was performed. Browser behavior, cancellation,
installed-runtime compatibility and successful account recovery remain
**unmeasured**. The proposal is not a completed fix or acceptance proof.
