# CHD-394: a code block's buttons, copy and put into the prompt

The owner decided (2026-10-15, revised 2026-10-25): every code block in a
reply gets a `[copy]` button; a block labelled `sh` or `bash` also gets
`[run]`, which puts its command into the prompt box in bash mode (`!`) and
runs nothing; a `console` block and an unlabelled one get `[copy]` only. A
copy gives the selection copy's feedback (CHD-172). The owner approved this
design pass with the bracketed words, the keys as below, and the answers in
§5.

Captures are in `evidence/CHD-394/`: `today-*` is chord at fdc2df86 on the
fake agent's `markdown` scenario at 120×40 and 80×24. Every `words-*`
picture is that capture with only this design's changes edited in. Each is
a whole-window colour PNG with its text beside it.

## 1. The buttons

On the right end of the box's top border (U2 as built: `u2-markdown-*`,
`u2-markdowncode-*`; `u2-streaming-*` while a fence is still open):

```
   ┌─ ts ──────────────────────────────────────────────────[copy]─┐
   │ const session = await openSession({ agent: 'claude', cwd }); │

      ┌─ sh ─[copy]─[run]─┐
      │ deno task check   │
      └───────────────────┘
```

- **The words** say what each does, and every terminal draws them, being
  ASCII. `[run]` suggests running, though it only fills the prompt; the
  shortcuts panel and the pick line say "put in the prompt" (§3).
- **Place.** Right-aligned, with the border's `─` running up to each
  button, one `─` between them and one after, then `┐`: no blank cell around
  a button (owner), because OpenTUI blends a space without a background, so
  the border would show through it. The language label keeps its place on
  the left, as today, and the code's rows are untouched, so a copy over the
  code reads as it does now.
- **How they are drawn** (owner): each button is a `<text>` placed
  absolutely on the box's top row, over the border, so the box itself, its
  label and its code are drawn as today.
- **Which boxes.** `[copy]` on every code box, in a list too. `[run]` only
  on `sh` and `bash`. An unlabelled box: `┌──────────[copy]─┐`. A table
  is not a code block and gets nothing.
- **A code block inside a quote gets no buttons** (owner): it is drawn as
  characters in the quote's text, not as an OpenTUI box, so there is no box
  row to place them on. The keys still reach it: `ctrl+x b` and ↑ ↓ pick
  it, `c` copies it, `r` fills the prompt for an `sh` or `bash` one, and
  while picked its border characters are drawn in the accent colour.
- **Look.** The buttons are in the text's own colour on the dim border, so
  they read as something to press. No hover look: chord reads the mouse
  without motion reports (CHD-172 turned 1003 off). A picked box is drawn
  in the accent colour, buttons bold (§3).
- **Streaming.** A box whose fence is still open gets no buttons until it
  closes: its text is not final.

### A narrow block

A box is at least wide enough for its label, one `─`, and its buttons, as
it already grows for a label wider than its code (`markdowncode`). The
least widths, corners included:

| Box | Least width |
| --- | --- |
| `sh` or `bash`, both buttons | `┌─ sh ─[copy]─[run]─┐`, 21; `bash` 23 |
| `ts`, `console` or any other label, copy only | `┌─ ts ─[copy]─┐`, 15; `console` 20 |
| unlabelled | `┌─[copy]─┐`, 10 |

`deno task check` needs a box of 19; its box grows to 21, the least it can
be, with one `─` between label and buttons (`u2-markdown-*`, the box under
"Run the checks").

**One cell narrower:** a box is never drawn narrower than its least width;
it grows by that cell instead, its code padded on the right, as for a wide
label. Only when the transcript itself has fewer columns than the least
width (a window under about 25 columns) do the buttons give way: `[run]`
first, then `[copy]`, then the label is cut as today. Their keys (§3) still
work then. At 24 columns (`u2-narrow-24x30`) the `typescript` box
has no room for `[copy]` and the long `sh` box keeps only `[copy]`; at 30
(`u2-narrow-30x30`) all fit.

### Clicks

A press and a release on the same button is a click. The whole bracketed
word answers, brackets included: `[copy]` six cells, `[run]` five. A click
copies or puts into the prompt, as the keys do.

- **The wheel** is unchanged: it is its own button, and a button never
  answers it.
- **The selection.** The border is chord's furniture and starts no
  selection (CHD-172); the buttons are part of it, so a press on one starts
  none either. A press there clears a shown selection, as any press
  elsewhere does. A drag that starts in the code and ends on a button is a
  selection, not a click.
- **The terminal's own selection** (shift-drag) is untouched: a shift-held
  press goes to the terminal, never to chord.

## 2. The copy feedback

The selection copy's note, word for word, alone on the status line for 3 s
(`COPIED_NOTE_MS`, `u3-copied-*`, a click on `[copy]`):

```
╭──────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                            │
╰──────────────────────────────────────────────────────────────────────────────╯
  copied 75 chars to clipboard
```

and `sent N chars to the terminal's clipboard` when only OSC 52 went, as
CHD-172. N counts the block's graphemes. What is copied is the block's text
as the agent wrote it, its lines joined with newlines: no border, no label,
no wrapping of chord's, no trailing newline. The copy goes through the
selection copy's clipboard path (`createClipboard`).

A failed copy says `could not copy: <reason>`, in the error colour as a
failed selection copy's note is, and lapses after 3 s like the success
note. It has no retry hint: the selection's `ctrl + c to try again` would
clear the draft or arm quit here, as there is no selection, and the button
or `ctrl+x b c` is right in front of the person.

## 3. The keys

A leader, then a picking mode, so nothing takes a key the prompt, the
selection or the wheel already uses.

- **`ctrl+x b`** picks a code block. `ctrl+x` is chord's leader (`ctrl+x a`
  for what waits on the person), and the leader line names it
  (`u4a-leader-*`, as built):

  ```
    ctrl+x …  b a code block · a the one that waits · esc never mind
  ```

- **Picking.** The newest code box on screen is picked; if none is on
  screen, the newest in the transcript, and the view scrolls to show it
  whole. The picked box's border, label and buttons turn to the accent
  colour, the buttons bold, and the status line names the keys
  (`words-picked-*`, `words-picked-up-*`):

  ```
    ↑ ↓ another block · c copy · r put in the prompt · esc done
  ```

  - **↑ ↓** move to the block above or below, across replies, scrolling
    the transcript so it is whole in view.
  - **c** copies it (§2) and ends picking.
  - **r** puts it into the prompt (§4) and ends picking. On a block without
    `[run]` it does nothing, and the status line leaves it out
    (`words-picked-ts-120x40`).
  - **esc** ends picking with nothing done.
  - Any other key ends picking and then does what it does today; the wheel
    and pgup/pgdn scroll as usual and keep the pick.
- **Why not plain keys.** Tab is `chat:steer` during a turn and the lists'
  completion; ↑ ↓ are history; letters are text. A mode reached through the
  leader owns its keys only while it lasts, as the agents list does.
- **A block still streaming** (its fence open) cannot be picked, by
  `ctrl+x b` or by ↑ ↓, as it has no buttons (§1); it becomes pickable once
  its fence closes.
- **No code block in the transcript:** `ctrl+x b` leaves the note `No code
  block to pick` for 3 s.
- **Rebindable**, in `bindings.ts`, in a `CodeBlock` context:
  `codeBlock:pick` (`ctrl+x b`, Global), `codeBlock:copy` (`c`),
  `codeBlock:prompt` (`r`), `codeBlock:previous` (`up`), `codeBlock:next`
  (`down`), `codeBlock:cancel` (`escape`).
- **The shortcuts panel**, two lines, after `ctrl + x a for what waits on
  you`:

  ```
    ctrl + x b to pick a code block
    c r to copy or put in the prompt
  ```

  The second line reads on from the first; a longer one (43 characters)
  would be the panel's widest and drop it to one column at 80×24 and two
  at 120×40.
  The panel scrolls at 80×24 since CHD-378, so two more lines cost a row of
  scroll.

## 4. After "put into the prompt"

The prompt box in bash mode holding the command, the cursor at its end,
nothing run (`u3-run-80x24`, a click on `[run]`; `u3-run-later-80x24` once
the copy note has gone; `u3-draft-80x24` with a draft in the box):

```
╭──────────────────────────────────────────────────────────────────────────────╮
│ ! deno task check                                                            │
╰──────────────────────────────────────────────────────────────────────────────╯
  ! for bash mode
```

It is today's bash mode exactly, as if the person had typed `!` and the
command: Enter runs it in the session's directory, its output held for the
agent ahead of the next prompt; backspace on an empty draft leaves bash
mode; esc and ctrl+c behave as in bash mode today.

- **A draft already in the box** is never replaced: nothing is put in, the
  draft stays, and the status line says `The prompt holds a draft · ctrl+c
  clears it` for 3 s, in the warning tone of a notice whose ask did not
  happen.
- **During a turn** it goes in all the same; bash mode during a turn works
  as today.

## 5. What `[run]` puts in (owner, 2026-10-25)

- **A block of several lines goes whole, as its lines.** The box holds
  every line; Enter runs them as one script, in order
  (`u3-run-120x40`, as built; mock `words-q-multi-a-whole-*`):

  ```sh
  deno task compile --all
  for bin in dist/*/chord; do echo "built $bin"; done
  ```

  ```
  │ ! deno task compile --all                                    │
  │   for bin in dist/*/chord; do echo "built $bin"; done        │
  ```

- **A leading `$ ` is taken off** each line that starts with it; other
  lines stay as written (`words-q-dollar-a-stripped-*`):

  ```sh
  $ bun install
  $ bun test tests/parse
  ```

  ```
  │ ! bun install                                                │
  │   bun test tests/parse                                       │
  ```

- **A `console` block gets `[copy]` only**, no `[run]`: it mixes commands
  with their output, and `r` does nothing on it, as on any block without
  `[run]`.

## Colour roles

- Buttons: the text's own colour; border and label dim, as today.
- A picked box: `accent` for its border, label and buttons, the buttons
  bold.
- The copy note: as CHD-172's. The draft notice: `warning` (the `failed`
  tone).
- The prompt after `[run]`: bash mode's `bash` colour, as today.

## Why

The owner wants a block one press from the clipboard or the shell. The
buttons sit on the border so the code a person reads and copies is
unchanged, as bracketed words that read as buttons in any font. A key path
through chord's leader and a short picking mode reaches every block
without taking a key the prompt already owns, and it reads on screen as the
box lighting up with its keys under the prompt. Putting the command into
bash mode rather than running it keeps the person's Enter between an
agent's text and their shell.
