# CHD-623 — `bun dev` for several packages

`bun dev` (`scripts/dev.ts`, on Cliffy) grew around one package. CHD-622
adds a second, `@chorded/cursor-cloud-acp` in `packages/cursor-cloud-acp/`.
This design reviews `bun dev` as a whole: which commands take a package,
the file in which each package defines its steps, how a release runs a
package's stages, and what replaces today's `--package`. It writes no code.

The owner's decisions (CHD-623's body, from CHD-622's questions) are fixed
here: everything goes through `bun dev`; a package is named by its npm name
without the scope (`chord`, `cursor-cloud-acp`); a package is an explicit
positional argument, neither a subcommand nor a flag, with no default
(chord's release is named too); a bare `bun dev release` releases nothing
and says it is not clear which package to release; the version or bump is
`--bump`; every package defines its checks and its build, publish and
other steps, in their order, in a file at its root, and a command run for a
package runs only that package's steps; `bun quality` becomes the checks
command for chord, `bun lint --fix` a `bun dev` command for a package,
`bun dev test` stays chord's suite runner, CI calls the checks command per
package; no GitHub release for a package other than chord. The questions
still the owner's are at the end.

The draft and the critic's review behind it are in
`evidence/CHD-623/drafts/` (`brief.md`, `runtime.md`); where they differ
from this file, this file holds.

## The principle: a word means one thing

- **`<package>`** is a positional argument and only ever a package of the
  repository by its npm name without the scope.
- **A command that takes `<package>`** runs that package's steps from its
  `steps.ts` and nothing else: `quality`, `lint`, `release`.
- **chord's own tools**, with no counterpart in another package, keep their
  names and take no package: `chord`, `test`, `compile`, `npm`, `selftest`,
  `memory`. Their help starts with "chord's".
- **The repository's tools** take nothing: `registry`, `mark`,
  `screenshots`, `social`.
- **The checks command is `quality`** (the owner allowed either name):
  `check` stays Bun's own `bun check`, which is one step inside it. The
  release stage that runs it is renamed `quality` too.
- **Stage names are each package's own**: `compile` is only chord's
  `bun build --compile`, `selftest` only chord's binary self-test;
  cursor-cloud-acp's are `build` and its smoke.
- **`--package` goes**; publishing one of chord's five npm packages takes
  `--npm <full npm name>` (O2).

## The command tree

`bun dev --help` (Cliffy's layout; `<package>`'s values come from the
packages found):

```
Usage:   bun dev
Description:

  chord's build, release and maintenance tools. A command that takes
  <package> runs that package's steps from its steps.ts and nothing else:
  chord or cursor-cloud-acp, its npm name without the scope.

Commands:

  quality      <package>              - A package's checks in its steps.ts's order, stopping at the first that fails.
  lint         <package> [args...]    - ESLint with a package's config over its files; the rest of the arguments are ESLint's.
  release      [package]              - Release one package by its steps.ts. With none, releases nothing.
  chord        [args...]              - chord's: run it from source with React's production build.
  test         [args...]              - chord's suite with bun test, a worker per core.
  compile                             - chord's binary with bun build --compile into dist/<target>/chord.
  npm                                 - chord's five npm packages laid out in npm/ from dist/.
  selftest     <binary>               - chord's release self-test of one binary.
  memory                              - chord's long-run memory check.
  registry                            - Refetch the ACP Registry into src/registry.ts.
  mark                                - Rasterise scripts/mark.svg into src/ui/header/mark.ts.
  screenshots  [names...]             - Retake docs/images/ from chord on the fake agent.
  social                              - GitHub's social preview from docs/images into dist/.
```

`riff-models` leaves with CHD-621.

- **`quality <package> [--static]`.** A missing or unknown package is
  Cliffy's own refusal, which lists the packages (`Argument "package" must
  be of type "package", but got "x". Expected values: "chord",
  "cursor-cloud-acp"`). `--static` runs the steps marked `static`.
- **`lint <package> [args...]`**, `.stopEarly()` as today's `bun lint`:
  `bun dev lint chord --fix` passes `--fix` on; an empty argument needs
  `--`.
- **`release [package]`.** The package is a positional of `release`
  itself, declared optional so that a bare run reaches the release's own
  words: it releases nothing, does no preflight, git, network or npm
  authentication, writes `release: not clear which package to release:
  bun dev release <package> (chord, cursor-cloud-acp)` on stderr and exits
  1, whatever else was given. Its options:

```
Usage:   bun dev release [package]

Options:

  --bump     <version>    - An exact version above the package's package.json, or major, minor, patch or fix.
  --channel  <name>       - A pre-release on this channel, from the branch of that name.
  --dry-run               - Every stage but publish.
  --skip     <stages>     - Leave these of the package's stages out (comma-separated).
  --only     <stages>     - Run only these of the package's stages.
  --from     <stage>      - Start at this stage.
  --to       <stage>      - Stop after this stage.
  --npm      <name>       - chord only: publish only this npm package, @chorded/chord-darwin-arm64, … or @chorded/chord.

Stages:

  chord             install, quality, natives, compile, sign, selftest, notarise, pack, publish
  cursor-cloud-acp  install, quality, build, pack, publish
```

Stage options are typed by one `EnumType` over every package's stage
names; after parsing, the release refuses a stage the named package does
not have with a Cliffy `ValidationError`, which prints the help and names
the package's stages (`cursor-cloud-acp has no stage "compile"; its stages
are install, quality, build, pack, publish`). That is semantic validation
of parsed values, as `select.ts` already does for `--dry-run --only
publish`; no argv is read by hand. `--npm` with any package but chord is
refused the same way.

## `steps.ts`: a package's steps

Each package has a `steps.ts` at its root, named for what it holds: chord's
at the repository's root (its package is the root),
`packages/cursor-cloud-acp/steps.ts` for the other. It is a TypeScript
module whose default export `satisfies PackageSteps`, a type
`scripts/dev/steps.ts` exports; a steps file imports that type only.
A step is data where it can be (an argv) and a function where the work is
code (chord's sign, notarise, pack), imported lazily when the step runs, so
parsing any `bun dev` command loads no release module.

```ts
/** One check: an argv run from the repository's root, or a function answering a status. */
export interface Check {
  readonly name: string;
  /** Run by `--static` too; the suite, a build and a smoke are not. */
  readonly static?: boolean;
  readonly run: readonly string[] | ((context: StepContext) => Promise<number>);
}

/** One release stage, in the package's order. */
export interface Stage {
  readonly name: string;
  /** The line `bun dev release --help` lists it with. */
  readonly about: string;
  /** Refused elsewhere, before preflight, when selected (chord's natives, sign, notarise). */
  readonly machine?: { readonly platform: string; readonly arch: string };
  /** Found ready before any stage runs (a signing identity, notary credentials). */
  readonly ready?: (release: Release) => Promise<void>;
  /** Puts the version into what is published: a new version needs it selected. */
  readonly versioned?: boolean;
  readonly run: (release: Release, version: string) => Promise<void>;
}

/** The publish stage: data the release's one publish implementation runs. */
export interface Publish {
  readonly name: 'publish';
  /** Full npm names in publish order; the last is the package's main one. */
  readonly npm: readonly string[];
  /** The git tag, `{version}` standing for the version. */
  readonly tag: string;
  /** chord only: recheck the source archives, then a draft GitHub release with them. */
  readonly githubRelease?: true;
}

export interface PackageSteps {
  readonly checks: readonly Check[];
  /** ESLint's argv for this package, before `bun dev lint`'s own arguments. */
  readonly lint: readonly string[];
  /** In order; exactly one `publish`, and it is last. */
  readonly release: readonly (Stage | Publish)[];
  /** A package's own preflight (chord: its agent pins on npm, CHD-622). */
  readonly preflight?: (release: Release, version: string) => Promise<void>;
}
```

Publishing is listed in the package's order as a stage of its own, and is
data: what to publish, in what order, how to tag, whether a GitHub release
follows. The npm wait, the skip of what npm has, the checksums, the
terminal hand-over and the GitHub release are one implementation in
`scripts/dev/release/publish.ts`, as today; the archives `fetchedSource`
returns pass to `draftRelease` inside it, as today. Discovery refuses a
release list with no `publish`, two, one not last, or two stages of one
name.

### Where each steps file is checked

A package's `steps.ts` and its `scripts/` are its own Bun tooling and are
checked by its own checks, never by chord's. For cursor-cloud-acp that is a
second project, `tsconfig.tools.json` (Bun's types, `steps.ts` and
`scripts/`), beside its Node project for `src/`; its covered step counts
both. chord's root `tsconfig.json` does not include `packages/`, so
TypeScript never follows a package's dynamic imports from chord's check. A
steps file reaches chord's code only through the type-only import of
`scripts/dev/steps.ts`, which imports nothing but types. A test puts a
deliberate type error in a fixture package's tooling and checks
`bun dev quality chord` still passes and the package's quality fails.

### What `bun dev` reads, and how

At start, `scripts/dev/steps.ts`'s `packages(root)` reads the root
`package.json`'s name and `workspaces` (expanded by globby, already a
dependency), names each package by its npm name without `@chorded/`, and
imports each `steps.ts`. A name outside the scope, a duplicate, a missing
`steps.ts` or a release list that breaks the rules above stops `bun dev`
naming the folder. The names feed `<package>`'s `EnumType`, the stage
names the stage `EnumType`.

A broken steps file stops every `bun dev` command, `bun dev chord` too,
since the tree is built from all of them; the error names the file, and
the file's own package's checks catch it in CI before it reaches main.
Building the tree lazily would need argv read by hand, which the one rule
refuses.

A steps file is never shipped: chord's `npm.ts` writes named files only
(its test gains "no `steps.ts`"); cursor-cloud-acp's `files` holds `dist`,
`README.md` and `LICENSE`, and its pack stage checks the tarball's list.
ESLint forbids `src/**` and `packages/*/src/**` to import a `steps.ts` or
`scripts/`.

## Running steps

One runner, `run(steps, context)`, serves `bun dev quality` and the
release's quality stage. Its context is explicit: the root, the
environment, the spawn and the output a step uses. `bun dev quality`
passes the real ones; the release passes its `Release`'s, so a release test
in a scratch root runs the scratch package's steps there and no real tool
runs. Steps run in order from the root; the first that fails stops the run
with `quality <package>: <step> failed with status <n>` on stderr (CHD-467's
line with the package), and its status is the command's.

| Case | Outcome |
| --- | --- |
| a step dies by a signal | status 128 + its number, as `spawn` answers today |
| Ctrl+C in `quality` | the step's child ends; `bun dev` ends 130 |
| the smoke | its own scratch directory from `mkdtemp`, removed when it ends, so two runs never share one |
| no Node 22.13+ for the smoke | the step fails naming the `node` found past Bun's (CHD-395's finder, moved to a module both use) and the floor |
| a broken steps file | every command stops at start, naming it |

## The release

The release (`scripts/dev/release/`, one implementation) runs the named
package's `release` list, parametrised by its name, folder and its
`publish` stage. Order of a run, unchanged for chord: parse and validate →
the lock → `machine` of selected stages → version → preflight (the
release's, then the package's) → npm authentication → `ready` of selected
stages → version commit (pushed when publishing) → stages in order.

| Guard or duty | Whose | Per package |
| --- | --- | --- |
| one release per checkout at a time | release: a lock with `proper-lockfile` (already a dependency) on a file in git's directory, taken before preflight, held to the end | any; a second run is refused naming the first's pid |
| a selected stage's `machine` | release, over selected stages only | chord's natives, sign, notarise |
| a clean tree | release | the whole tree |
| version, `--bump`, `--channel` (CHD-577) | release | the package's `package.json`; channel bumps count from npm's latest stable of its main npm name |
| a new version needs a `versioned` stage | release | chord: compile; cursor-cloud-acp: build |
| CHD-547 | release | against the package's main npm name |
| the package's own preflight | the package | chord: its agent pins on npm (CHD-622) |
| branch level with origin and no tag, when publishing | release | `tag` with the version |
| `gh` signed in | release, when `githubRelease` | chord only |
| npm authentication, every run | release | both |
| the version commit, pushed or dropped, signals | release | `chore: <package> v<version>`, chord's message unchanged; the package's `package.json` and `bun.lock` where Bun records it (ship checks with Bun's own commands; a hand edit of the lock comes back as a question) |
| sums, npm publish, the wait, the main package last, the tag | release | the `publish` stage's data |
| a draft GitHub release | release, when `githubRelease` | chord only |

`--npm <full name>` keeps `--package`'s rules: chord only, needs `publish`
among the stages, conflicts with `--dry-run`, and a single platform package
leaves the tag to the run that publishes the last.

**A run stopped after npm published.** Today, chord's publish prints the
`git tag` command when tagging fails, and a rerun with the main package on
npm is refused. For a one-tarball package nothing else is left to resume.
Proposed (O4): a run without `--bump` whose package's main npm name is at
`package.json`'s version and whose tag is missing on origin finishes by
tagging alone (creating the tag if it is not here, pushing it, and for
chord drafting the GitHub release if none exists), after the same guards
(clean tree, branch level with origin, HEAD the version commit). Tests
cover each boundary: tag not created, created but not pushed, pushed but
no GitHub release.

## Landing

job and the docs. The several-package paths are tested on fixture packages.

## Why

- **Only commands with a choice take a package**: a positional with one
  possible value says nothing; `bun dev chord`'s name is taken by running
  chord, so a namespace per package was rejected.
- **`quality`, not `check`**: `bun check` is Bun's, and is one step of it.
- **A typed TS module**: chord's stages are code; argv where it can be,
  functions where it must, all checked by `bun check`.
- **Publish as data in the list**: the package's order says where it runs;
  the guards around a version reaching npm stay one implementation.
- **A lock**: two releases in one checkout would move each other's version
  commits; nothing in the tree or branch state catches the second.

## Questions for the owner

- **O1. Publishing.** (a) A stage of the release, listed last in each
  package's steps (recommended: the version rules, the version commit, the
  branch and tag guards and resume all surround it, and a separate command
  would repeat them or leave a commit for another command to drop); (b)
  its own command, `bun dev publish <package>`, the release ending at pack;
  (c) both, `publish` naming `release <package> --only publish`.
- **O2. What replaces `--package`.** (a) `--npm <full npm name>` on chord's
  release only (recommended: the tool stays, under a word that cannot mean
  a package of the repository); (b) the same with unscoped names, where
  `--npm chord` would mean the shim while `release chord` means the whole
  package; (c) dropped: a rerun already publishes only what npm lacks.
- **O3. Stages.** (a) Each package's own, named and ordered in its
  `steps.ts` (recommended); (b) one stage list for every package, a
  package filling the ones it has, `compile` and `selftest` bent to mean
  cursor-cloud-acp's build and smoke.
- **O4. A run stopped after npm published.** (a) A rerun finishes it by
  tagging alone, for both packages, after the guards (recommended: a
  one-tarball package has no other way back but by hand); (b) as chord
  today: refused, the failed publish having printed the `git tag` command
  to run by hand.
- **O5. The command set.** As laid out: only `quality`, `lint` and
  `release` take a package; `compile`, `npm`, `selftest`, `test`, `memory`
  stay chord's tools; `registry`, `mark`, `screenshots`, `social` the
  repository's (recommended); or every command takes a package, chord's
  tools with `chord` as their only value.
