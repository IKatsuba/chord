# CHD-479: an adapter's subagents named by their parent, and gone when they end

The owner read `background  ✓ 1 agent done` under an agents list of `main`
and `ship` as a listed agent counted twice. It was a subagent main's Claude
adapter had run and finished (an Agent tool call): CHD-2 makes every
subagent an adapter announces with `capabilities.cancel` an `agent` item,
and nothing on the summary line said whose it was.

The owner's answers set the frame:

| Question | The owner's answer |
| --- | --- |
| Q83 (CHD-479) | Adapter subagents stay background `agent` items; the summary line and the view name the parent agent, and the summary counts only running ones: ended ones leave the line. |
| Q86 (CHD-482) | Every ended item leaves the background list at once, with a transcript line saying it ended and why, not an error unless it failed. |

Everything [CHD-424](CHD-424.md) and [CHD-2](CHD-2.md) settle holds but
what this page changes: an `agent` item's kind phrase on the summary line,
and what happens when an item ends. The rule for an end is written for every
item kind; CHD-479 applies it to `agent` items and monitors, CHD-482 to
tasks.

## The parent

An `agent` item's parent is its owner as CHD-2 has it: the tab's agent
whose transcript announced it, `main`, a long-lived child, a team's lead or
a member. It is named as the view's owner column names it, which is the
name on that agent's row in the agents list (`main`, `parser`, `tester`).
A subagent of a subagent has the same parent as the subagent it came under.

## The summary line

Only the groups an `agent` item can still be in carry one: asking
(`● … asking`), running (`… running`, with `■ stopping` counted there as
CHD-2 says) and, pending the owner, untracked (below). An ended agent is no
longer an item, so `✓ done`, `✗ failed` and `■ stopped` never count agents.

**An `agent` kind phrase names its parent in the possessive**, in place of
CHD-424's bare `N agents`:

| Agents in the group | Phrase |
| --- | --- |
| one, main's | `main's agent` |
| two, main's | `main's 2 agents` |
| two of main's, one of tester's | `main's 2 agents and tester's agent` |

- **The count:** one is the parent's `agent`, with no `1`; two and more are
  `N agents`. **Why no `1`:** `main's 1 agent` reads as main having one
  agent at all; `main's agent` reads as the one in question.
- **Several parents** are listed in the agents list's order (`main` first,
  then the rows under it), each with its own count, joined by `and` as
  CHD-424 joins kinds.
- **Among other kinds,** the agent phrases come where `agents` came, after
  monitors and tasks, joined the same way:

```
    background  ● main's agent asking · 1 monitor and 1 task and main's 2 agents running
```

One parent, running, at 120 columns:

```
    background  main's 2 agents running
```

Several parents, a task asking, at 80 columns: it wraps between groups as
CHD-424 says, and a group longer than the width breaks between words, never
inside a name:

```
  ? for shortcuts             Fake Large with a 1M context window · 1% used
    main       fake                    ✻ working 15s
    bugfix     team · fake · 3 agents  ● tester: permission 1m 56s
    background  ● 1 task asking · 1 monitor and main's 2 agents and
                tester's agent running
```

**What gives way at 80 columns:** nothing is shortened or dropped; the line
wraps and is never cut (CHD-424, Q17). A parent's name is never cut or
abbreviated, as the agents list's names are not.

**Colour:** as CHD-424: the group's colour for the whole phrase, the
parent's name too. **Why not the agent colour for the name:** the group's
colour is what the line is read by (`●` warning first); a second colour per
name would compete with it.

**Why the possessive:** it says in the line's own words that these agents
belong to `main`, not that they are `main`; that was the misreading. `·
main` after the group (Q83's example) would sit beside `·`-joined groups and
read as one more group.

## The view

**Unchanged in its columns:** the owner column already names the parent
(CHD-424, CHD-2). Only running, asking, stopping and (pending) untracked
`agent` rows are in it; an ended one leaves at once (next section). The
title's count counts the rows left.

## When an item ends (every kind)

**An item that ends leaves the summary line and the view at once**, and its
owner's transcript says it ended and why. This replaces CHD-424's Q21 rule
(an ended item stays until the next prompt) for the kinds it is applied to:
`agent` items and monitors here, tasks in CHD-482.

### The transcript line

One line in the owner's transcript, appended at its end as a message is:

```
 ✓ Run the test suite · agent · done in 4s
 ✗ Find the session layer · agent · failed after 22s: tsc exited 2
 ■ Run the whole test suite · agent · stopped with x after 43s
 ■ Review the diff · agent · stopped after 30s
 ■ Explore the parser · agent · ended after 1m 2s
 ✗ Read the transport tests · agent · disconnected after 4m
```

- **The words** are `<marker> <name> · <kind> · <end>`: the item's name and
  kind as the view's row had them, and its end in the view's state words
  (CHD-424, CHD-2), which already say why: done, failed, stopped, ended,
  disconnected.
- **A failure's reason** follows a colon: the first line of the error the
  agent gave (`error.message`), through `theme/Ansi.tsx`, cut to the width
  with `…`. With none, the line ends at the time.
- **Stopped:** `stopped with x after …` when the person's `x` in the view
  sent the stop; `stopped after …` when the agent or its adapter cancelled
  it. **Why:** Q86 asks for why it ended, and chord knows only whether it
  sent the stop itself.
- **Colour:** the marker and the end words in the state's colour, success
  for done, error for failed and disconnected, dim for stopped and ended;
  the name in the transcript's text colour; ` · agent · ` dim. Only a
  failure is red (Q86).
- **The gutter:** the marker stands where `⏺` stands, so the line lines up
  with the transcript's other entries.

### Not twice

The line is written only where nothing in sight already says the end:

- **An `agent` item that ends while the turn that announced it is still
  running gets no line.** Its block, which is the turn's live output in
  front of the person, already ends `Done`, `Failed`, `Cancelled` or
  `Ended` (CHD-432 U1), and the turn's answer follows it. **One that ends
  after that turn has ended gets the line**: its block, now above the
  turn's answer, still updates in place, but out of the person's way.
- **An item whose end already writes a line of its own gets no second
  one:** a monitor's end is a message to its agent, drawn as
  `← CI run 4812 · monitor · exit code 1` (CHD-266); that line is its end
  line. CHD-482 settles a task's the same way against its report.

### In the view

- **The `❯` on a row that leaves** moves to the row that takes its place,
  or the row above when it was the last.
- **The last row leaving** closes the view, as Esc does, and the summary
  line goes with the last item; the keys go back to the prompt box.
- **`x`** turns a row to `■ stopping …` as CHD-2 says; when its `idle`
  comes, the row leaves and the transcript says `stopped with x after …`.

## Untracked: open, with the owner

CHD-2 makes `unknown` (`? untracked`) neither running nor ended: the
adapter lost sight of the subagent, which may still be at work, and a later
state takes it back. Q83 counts only running ones and Q86 removes ended
ones; neither says which this is. Built meanwhile as (a):

- **(a) It stays, and counts.** It keeps its row (`? untracked 3m 2s`) and
  its group on the line, `? main's agent untracked`. Q86 does not apply: it
  has not ended. Recommended: CHD-2 settled it as not ended, and dropping a
  subagent that may still be working would hide it.
- **(b) It stays in the view, but not on the line.** The line counts only
  what runs or asks; a tab with only an untracked item shows no summary
  line, so the view is reached only while something else is listed.
- **(c) It leaves as an ended one,** with a transcript line
  `? Explore the parser · agent · untracked after 3m 2s`; a later state
  brings it back as a new item, in its start order.
