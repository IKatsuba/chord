# CHD-536: restore image paste from the terminal

This is the restoration and investigation contract; the reported regression
has not yet been independently reproduced. If the existing path passes,
record that evidence without inventing a production fix. The specification
is the 2026-10-08
empty-bracketed-paste decision and the 2026-10-11 OpenTUI part 5 decision in
[decisions.md](../decisions.md). The prompt, transcript, status line and
shortcuts panel keep their existing layout and words.

## Behavior and states

- **Empty prompt or existing draft:** an empty OpenTUI paste event requests
  the clipboard image quietly. Insert the existing `[Image #N]` placeholder
  at the cursor; retain surrounding text, existing attachments and numbering.
  Enter sends the draft and its images through the existing send behavior.
- **Ordinary text:** nonempty paste stays on the existing text-paste path in
  insert mode, including multiline text. Never treat it as image paste.
  Vim normal mode drops pasted text, as the owner decided in CHD-308;
  pasted characters must not become normal-mode commands.
- **Vim normal mode:** an empty paste still requests the image and retains
  the existing mode and cursor behavior. No new mode transition.
- **No image:** empty paste changes nothing and says nothing. Explicit
  Ctrl+V keeps its existing feedback. Do not introduce a success toast.
- **Waiting or error:** retain existing startup, unsupported-image and
  clipboard-failure status notices, their lifetimes and colors:
  `X has not started yet`, `X does not take images`, and the reader
  failure text (for example `No image in the clipboard` for explicit
  Ctrl+V). Preserve the draft on failure. No new error wording or retry
  action.
- **Streaming:** retain the running transcript, working line and current
  draft behavior. Pasting adds no new working indicator or layout state.
- **Focus:** paste belongs to the focused input. A form, history search,
  permission prompt or picker must not lose its paste to the chat prompt.
  Keep the existing search, bash-mode and keyboard-owned-list gates and
  the pending-key-chord gate; an empty paste partway through
  a chord does not insert an image. Preserve the current front-agent and
  late-read ownership rules.
- **Narrow:** the same placeholder wraps with the existing prompt content;
  neither the status line nor a neighboring focused widget moves or gains
  a row for this fix.

## Colors and keys

Use the existing roles in `src/ui/theme/theme.ts`: terminal foreground for
plain draft and placeholder text, existing dim prompt border and secondary
status text, `accent` for the working line, `permission` for the waiting
widget, and the existing `error`/`warning` roles where current notices use
them. This fix adds no role, tint, highlight or border change.

Ctrl+V remains `chat:imagePaste`, rebindable as today and listed in `?`.
Cmd+V is the terminal's paste action: chord receives its paste event rather
than the macOS key. Enter sends; existing atomic image-placeholder deletion
and editing keys remain. No new chord action or binding is introduced.

## Acceptance and evidence boundary

After developer hands over the screen commit, inspect the whole running
fake-agent TUI in a dedicated tmux session at 120 by 40 and 80 by 24. Save
full-window plain text, ANSI and color PNG evidence under
`evidence/CHD-536/`, naming the source commit, dimensions, input and fixture
source. Check insertion, ordinary text, quiet no-image, existing failure
feedback, normal mode and focused-widget isolation wherever safely
reachable. Use fixture clipboard access only; do not modify the native
clipboard or installed data. Run the privacy test before committing captures.

Injected bracketed-paste bytes establish terminal-input behavior only.
Injected fixture images establish fixture image insertion only. Neither
proves a physical Cmd+V gesture, native clipboard access or a particular
terminal's behavior. Native Cmd+V and native Ctrl+V with an image remain
separate acceptance evidence unless explicitly performed and recorded.

The historical terminal findings in decisions.md are source research, not
fresh manual verification: Ghostty sent empty bracketed paste; kitty and
WezTerm sent nothing for image-only clipboard contents; iTerm2 offered
non-text paste options; Terminal.app was unknown. Document limitations with
that provenance. A terminal that emits no paste event gives chord nothing
to act on; Ctrl+V remains the explicit image action.

## Implementation boundary

Use existing maintained OpenTUI paste events and the existing image action
and clipboard service. No new parser, marker rewriting, input guessing,
clipboard provider or library patch is authorized. A library mismatch goes
to the lead and owner with options before implementation proceeds.
