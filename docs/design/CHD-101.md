# CHD-101: /fork opens a session that goes on from the conversation so far

The owner's answers (Q298–Q303, 2026-10-28; task body and comments):
`/fork` opens another agent in the same chord process, a top-level agent
beside `main` and child of no one, that starts from the whole current
conversation through ACP `session/fork` and then goes on by itself. The
person picks it and writes to it as to a child. No Esc Esc, no fork point.

## The command

`/fork` forks the agent on screen: `main`, or a fork that is picked.
`/fork <name>` names the fork; without a name it is `fork`, numbered past
the first (`fork 2`), with the name rules of `open_agent`'s `name` (`main`
and `chord` are taken, a taken name is numbered).

It answers by **picking the fork at once**. On the agent it was forked
from, the command's line says where it went:

```
 › /fork
   ⎿  Forked into fork
```

The fork's view opens with the header line a picked child has, where
`opened by main 4m ago` becomes `forked from <name> 2m ago`
(`fork · claude · Opus · forked from main 2m ago`): it was opened by no
one. Below it is the conversation as it stood, chord's copy of what was
on screen (the agent's fork replays nothing), then a dim divider, then the
fork's own turns:

```
 › Make the parser handle trailing commas

 ⏺ Done: the parser now accepts trailing commas in arrays and objects.

 ── forked from main · 22:10 ──

╭──────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                            │
╰──────────────────────────────────────────────────────────────────────────────╯
  ? for shortcuts                Opus · medium effort · 1% context used
    main  claude · Opus · medium         ◦ idle
    fork  fork · claude · Opus · medium  ◦ idle
```

- **The divider** is dim, one line, the full width at 120 and at 80 as
  `── forked from <name> · HH:MM ──`; the name is what was forked (`main`,
  `fork`). It stays in the fork's view and its record.
- **The agents list.** The fork's row says `fork ·` first in the runtime
  column, as a team lead's says `team ·`. Forks come after `main` and all
  its children, in the order they were made: top level, under no one. Its
  state is the ordinary `◦ idle` / `✻ working`.

At 120×40 the same lines, wider; nothing wraps.

## Refusals

Each is the failed line under the typed command, as `/clear`'s refusal is
today, in the `error` role of a failed `noted` line. Nothing is opened.

| Case | Line |
| --- | --- |
| The agent does not offer `session/fork` | `This agent does not fork sessions` |
| The agent on screen is working, has a permission or question open, or has queued prompts | `<name> is working · /fork once its turn ends` |
| The name breaks the name rules | the rule's own words, as `open_agent` gives them |
| The agent's `session/fork` fails | `Could not fork: <reason>` |
| `/clear` with a fork picked | `A fork cannot be cleared yet · close it with x and /fork again` |
| `/fork` with an ordinary child picked (Q303) | `/fork forks main or a fork` |

The `/clear` refusal stands until CHD-476 decides what clearing a picked
child does; then a fork clears as a picked child does.

## Lifecycle

- **A fork can be forked:** pick it, `/fork`; the new one is top level too,
  its divider says `forked from fork`.
- **Closing:** `x` on its row in the agents list, as a child. No notice to
  anyone: it has no parent. Its task agents and monitors close with it.
- **main's `/clear`** leaves forks open; it closes only main's children.
- **chord quits:** forks close with the process. Each is in the session
  record, so `/resume` and `chord -r <id>` open it later as a session of
  its own; chord does not reopen forks on the next start.

## Tools

A fork has main's tool set but for `open_agent`, `run_team`,
`propose_team` and `close_agent` (Q304): a fork opens no agents and no team
runs. Called from a fork, each is refused with the answer

```
This tool works only from main and its agents, not from a fork.
```

as an error result its agent reads; the fork's transcript shows the call
failed, as any refused chord tool call. `spawn_task`, `send_message`,
monitors and the rest work as on main. `main` and a fork cannot address each other:
`send_message` to `main` from a fork, or to a fork from main, is refused as
any unknown name is.

## Keys

None new. `/fork` is a slash command, listed in the `/` list with
`Fork the conversation into a new agent`; picking is the agents list's
↑ ↓ and Enter; `x` closes, as for a child.

## Colour roles

Divider: dim (the transcript's dim text). Refusals: the failed `noted`
line's `error`. The `fork ·` tag: the runtime column's own dim. Nothing new
in `theme.ts`.

## Why

A fork is a second road from the same point, not a helper: so it stands
beside `main`, not under it, and the person lands in it, since that is
where they forked to go. The copied transcript and the divider say exactly
what it knows and where it parted. Refusing while the agent works keeps
the fork point the one the person sees; adapters' mid-turn forks differ
(glm cancels the source's turn).
