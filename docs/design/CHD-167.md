# CHD-167 — Agents that start agents, on screen

M4 lets a session start agents on any runtime chord knows, through chord's own
MCP server ("M4: agents start agents through an MCP server chord serves" in
`decisions.md`). There are two kinds of child. A **task agent**
(`spawn_task`) does one job and reports back. A **long-lived agent**
(`open_agent`) stays open, and the parent and the person both talk to it. This
page shows how each one looks on screen.

The owner changed the long-lived half on 2026-10-07, so this page draws the
new version. **A long-lived agent gets no tab.** It lives inside its parent's
session, in a list of the session's agents under the prompt, the way Claude
Code lists its background agents. The tab strip (`ctrl+x`) is still only for
the person's own sessions. Task agents are as the decision describes them:
nested blocks in the parent's turn, drawn the way CHD-149 draws a subagent.

The mocks are in `evidence/CHD-167/mock/`, at 120×40 and 80×24, one file per
state. They were laid out to exact widths from the real rows of
`deno task chord:fake` (`evidence/CHD-167/today/`: tool calls, the queue, a
plan, `/mcp` with the user's servers, two tabs and the sessions picker), with
the directory shown as `~/src/app`. Each state below is drawn at one width.
The file at the other width is in the folder. Text captures cannot show
colour or inverse video, so the colours are described in words beside each
mock.

Claude Code is the reference for the look. I did not capture its background
agents, because that takes a prompt and a spent turn. The list copies the
idea the owner described (agents under the prompt, the one picked takes the
prompt), and its rows are drawn the way chord's own lists already are.

## The decisions, in short

| Question | Answer |
| --- | --- |
| A task agent's block | `⏺ Agent(<name>) · <runtime> · <model>`, otherwise exactly CHD-149's block: its latest three calls, then `Done (6 tool uses · 41s)`, `Failed`, `Cancelled` or `Disconnected`, and ctrl+o opens it. The dim `· codex · gpt-5.3-codex` after the title is the **only** thing that tells it apart from the agent's own subagent. |
| Where the block stands | **In the place of the `spawn_task` call.** chord serves the call, so unlike an ACP subagent it can tie the block to it. |
| A task's report | A **message row** to the parent: `← Fix the tokenizer · codex · report`, with the report text under it. A failed task: `· failed`, with the error and a red `←`. |
| A message from another agent | A row of its own: `← <sender> · <runtime>`, with the text under it, folded after 6 lines to `… +N lines (ctrl+o to expand)`. Never the person's `›`. |
| Queued behind a turn | One dim row among the queue's `›` rows: `← parser · codex: <first line>…`. |
| chord's tools as calls | `Agent(…)` for `spawn_task`, `Open(name) · runtime · model`, `Close(name)`, `List agents` / `List agents(codex)`, `List sessions`. What was said goes under `⎿`. A message sent is not a call but `→ name`, its text under `⎿` too (CHD-225). |
| Naming a child | `spawn_task` and `open_agent` take an optional `name`. A task falls back to its prompt's first line. A long-lived agent falls back to its runtime (`codex`, then `codex 2`). |
| The session's agents | A list **under the status line**: `main`, then each long-lived child, one row each. It is shown only while there is a child. At most `max(2, ⌊rows / 6⌋)` rows (4 at 24 rows, 6 at 40), then `… +N more`. |
| Each agent's colour | `main` has none, so the box keeps today's border. Children take the next of six colours in the order they opened: blue, purple, cyan, green, yellow, pink. The colour is on the child's name in the list and on the prompt box's border while it is picked. |
| Who the prompt goes to | The picked agent. While a child is picked, the box's top border names it (`╭─ parser ───╮`) in its colour, so colour is never the only signal. |
| ↓ | On an empty draft that is not walking history, ↓ moves the focus into the list. Anywhere else ↓ does what it does today. In the list, ↑ ↓ (or j k) move, and moving picks. ↑ from `main` returns to the box. Enter and Esc return to the box with the pick kept. |
| Closing a child | `x` while the list has the focus (`agents:close`). If the child is busy, the first press arms. chord then tells the parent: `← chord`, `The person closed parser (…). It takes no more messages; open_agent starts another.` |
| A child that waits on the person | `● permission 12s` on its row, and the status line notice `● docs needs your permission · ctrl+x a`. `ctrl+x a` picks it. Its permission box opens when it is picked, and the box names it on top. |
| Tabs and the sessions picker | Children never get a tab. A parent's tab takes the most urgent glyph among its agents. The picker's row says `claude · 2 agents` and names the child that waits. |
| Busy | A running task agent, or a long-lived child that is working or waiting, makes its session busy: `1 claude has 2 task agents running`, or `has 3 agents working` once a long-lived child is counted. Closing the parent stops its tasks and closes its children. |
| `/mcp` | Lists chord's own server first (`chord · http · http://127.0.0.1:52817/mcp · chord itself`), then the line of tools it gave the picked agent, or why it was not passed. |
| `--resume` of a parent | Task blocks and message rows come back as they were. Long-lived children are not reopened, and a closing note says so: `parser (codex) and docs (claude) were open when this session was left and are not reopened · /resume lists them`. No list is drawn. |
| New keys | `↓` into the list (on an empty prompt) and `x` to close the picked agent. Both go in `keys.ts` and the shortcuts panel. `agents:close` can be rebound. |

## 1. A task agent, nested in the parent's turn

`spawn_task(agent, model, prompt, name?)` draws CHD-149's block in the place of
its own call. CHD-149's blocks stand beside the parent's calls only because no
adapter ties a subagent to a call. chord serves `spawn_task` itself, and the
call's answer carries the task's id, so the block replaces the call. Until
that answer comes, which takes milliseconds, the call draws as the block's
`Initializing…`.

`120-1-task-running.txt`:

```
 › Fix the tokenizer bug in src/parse, and keep codex on the parser tests while you do.

 ⏺ I'll send a task agent on codex for the fix.

 ⏺ Agent(Fix the tokenizer) · codex · gpt-5.3-codex
   ⎿  Search(pattern: "tokenize", path: "src/parse")
      Read(src/parse/tokenize.ts)
      Edit(src/parse/tokenize.ts)
      +2 more tool uses (ctrl+o to expand)

 ✻ Working… (34s · esc to interrupt)
```

- **The title.** It is `Agent(<name>)`, then the runtime and the model,
  dim, in the same `·` style as CHD-149's counts. `<name>` is the call's
  `name`, or failing that its prompt's first line, cut to the width with
  `…`. The runtime goes after the brackets and not inside them
  (`Agent(codex · gpt-5.3-codex: fix…)`), because inside, the title is the
  first thing cut and the runtime would go with it. When a row does not fit,
  the model is dropped first, then the counts, and then the title is cut.
  The runtime is never dropped, because it is what makes a task agent
  different.
- **How it differs from a subagent: only that suffix.** Everything else is
  the same: the marker's tones, the three latest calls, the endings, ctrl+o's
  view of the task and the work, the permission box's
  `Agent(Fix the tokenizer) · codex asks` row
  (`120-1-task-permission.txt`), and the `· waiting for permission` on the
  call. A person needs to know that another runtime is doing the job, and
  the suffix says so. Two shapes for the same idea would be one too many.
- **Grouping.** Task agents spawned back to back form one
  `Running N agents…` tree, as subagents do. Each row carries its runtime
  (and its model when it fits): `├─ Agent(Fix the tokenizer) · codex ·
  6 tool uses · 41s`. A task agent and a subagent never share a group,
  because they come from different places (a call the parent made, against
  an update the agent's runtime sent).
- **Esc.** It interrupts the parent's turn and stops every task agent still
  running in the session, as Esc ends a turn's subagents today. A task
  stopped this way sends no report: a new turn right after the person
  pressed Esc would undo the Esc. Instead, the note that it was cancelled
  goes ahead of the person's next prompt, as held bash output does.

### The report

A task ends with its first turn, and its report reaches the parent as a
message (decisions.md). On screen that message is a row of its own, where the
parent's next turn starts. If the parent is still in a turn, the row waits in
the queue first (part 2).

`120-1-task-report.txt`:

```
 ⏺ Agent(Fix the tokenizer) · codex · gpt-5.3-codex
   ⎿  Done (6 tool uses · 41s)

 ⏺ It is running; I will check its report when it lands.

 ← Fix the tokenizer · codex · report
   The tokenizer dropped a closing quote when a string ended the line. Fixed in src/parse/tokenize.ts (+12 −3), with two
   cases added to tests/parse/tokenize_test.ts. deno task test passes: 214 passed, 0 failed.

 ⏺ codex fixed it: a string at the end of a line lost its closing quote. Two tests cover it and the suite passes.
```

- The header is the task's name, its runtime and `report`, or `failed` for a
  turn that failed, with the error as the text (`120-1-task-group.txt`). The
  block's own ending line still says `Done` or `Failed`. The block is what
  the child did, and the row is what the parent was told.
- The report is not repeated in the block. CHD-149 left a subagent's final
  message to ctrl+o because the parent's answer already said it. Here the
  report is a message the parent *received*, so it is drawn where the parent
  received it, like every other message.
- What the agent gets is the decision's wrapper:
  `<message from="Fix the tokenizer · codex · report">…</message>`. Its `from`
  is the row's header word for word, so the person reads what the agent read.

## 2. Messages between agents

A message is a turn for its recipient, so its row stands where a prompt would:
at the start of the turn it begins.

`80-2-messages.txt`:

```
 → parser
   ⎿  I changed how a string at the end of a line is read. Run the parser
      tests now and tell me only what fails.

 ⏺ Waiting on parser.

 ← parser · codex
   Ran deno task test tests/parse: 2 failures, both in
   tests/parse/printer_test.ts. The printer still expects the old token for a
   trailing quote: "prints a quoted string at the end of a line" and
   "round-trips a line ending in a quote". Expected [Str "a"] [Eol], got [Str
   "a\""] [Eol] in both. Nothing else fails. I have not touched any file; say
   if I should update the printer or the tests, and I will run the whole suite
   … +1 line (ctrl+o to expand)

 ⏺ Two printer tests expect the old token. I will update the printer.
```

- **The row.** `←` and the sender's name are in the sender's colour, and the
  name is bold. A task's report, `main` and `chord` have no colour, so their
  `←` is plain (`chord`'s dim); a failed report's is red (CHD-225). The runtime is dim, and the text is plain, indented three
  columns as a reply's is. The sender is `main` for the parent, the child's
  name for a child, and `chord` for chord itself (part 5). The person's own
  prompts keep `›`, so nothing an agent wrote ever looks like the person's
  words.
- **Folding.** After 6 lines the text folds to `… +N lines (ctrl+o to
  expand)`, and ctrl+o shows all of it. That is twice a tool call's three
  lines, because a message is words meant to be read, not output. 6 still
  leaves room for the reply under it at 24 rows. The text is drawn as
  markdown, as a reply is, since agents write markdown.
- **The parent's own `send_message`** is `→ parser`, the arrow and the name
  in the recipient's colour, with the text it sent under `⎿`, folded the
  same way. It shows what it sent, so the two sides of an exchange read
  alike, `←` and `→` (CHD-225). A message that had to wait adds a dim
  `· queued` after the name (`120-3-chord-calls.txt`). The call's states are
  on the arrow: dim while it is delivering, red when chord refuses it.
  Delivery is all the call waits for, so `⎿ Running…` is gone within a
  moment.

### Queued behind a turn

`120-2-queued.txt`. A message to an agent in a turn waits in that session's
queue with the person's prompts, in the order they came, as one dim row:

```
 ✻ Working… (34s · esc to interrupt)
 › and keep the old token name in the changelog
 ← parser · codex: Ran deno task test tests/parse: 2 failures, both in tests/parse/printer_test.ts. The printer st…
```

- The row is `← <sender> · <runtime>: ` and then the first line, cut with
  `…` at the width. It counts toward the queue's row limit as a prompt does.
- Esc takes the person's queued prompts back into the draft, as today. It
  never puts a queued message there, because that text is not the
  person's. A message still queued when Esc interrupts goes as the next
  turn once the interrupted one ends (CHD-360).

## 3. chord's tools as tool calls

The agents name these calls in their own ways: Claude's adapter titles an MCP
call by its tool name (`mcp__chord__spawn_task`, kind `other`, which I read
in claude-agent-acp 0.86.0's `tools.js`), and other adapters use other forms.
chord serves each call itself, so it knows which call is its own by the
request it answered, not by guessing from the title. The headlines are:

| Tool | Headline | Under `⎿` |
| --- | --- | --- |
| `spawn_task` | the `Agent(name) · runtime · model` block (part 1) | its calls, then its ending |
| `open_agent` | `Open(parser) · codex · gpt-5.3-codex` | the opening prompt, folded as a message |
| `send_message` | `→ parser`, `· queued` if it waited | the text sent |
| `close_agent` | `Close(parser)` | `Closed` |
| `list_agents` | `List agents`, or `List agents(codex)` | `22 runtimes · claude, codex, gemini, +19 more`, or `3 models · gpt-5.3-codex, …` |
| `list_sessions` | `List sessions` | `2 open · 1 claude (you), 2 codex` |

`120-3-chord-calls.txt` (the 80 file shows its bottom):

```
 ⏺ List agents
   ⎿  22 runtimes · claude, codex, gemini, opencode, +18 more

 ⏺ List agents(codex)
   ⎿  3 models · gpt-5.3-codex, gpt-5.3-codex-mini, gpt-5.2

 ⏺ List sessions
   ⎿  2 open · 1 claude (you), 2 codex

 ⏺ Open(parser) · codex · gpt-5.3-codex
   ⎿  Run the parser tests after every change to src/parse and tell me what breaks.

 → docs · queued
   ⎿  When you finish the README section, add the new flag to docs/FEATURES.md.

 ⏺ Close(parser)
   ⎿  Closed

 ⏺ Open(review) · codx
   ⎿  No agent named codx · list_agents names them
```

- The names are verbs in the `Read(path)` style. No `mcp__chord__` and no
  JSON: the raw input is ctrl+o's, as for any call.
- A refused call (an unknown runtime, a model the runtime lacks, a ninth
  child, a closed agent) is a failed call. Its `⎿` line is chord's answer, in
  the error colour.
- A child's only tool reads the same from its side: `→ main`, inside a task
  block's `⎿` list too.
- The user's own MCP servers' calls keep today's headlines. Only chord's
  server's calls are renamed.

## 4. Long-lived agents: the list under the prompt

`open_agent(agent, model, prompt, name?)` opens a child inside the parent's
session. Its first prompt is the parent's message. From then on, both the
parent and the person can talk to it.

`120-4-list.txt`: main is picked, the focus is in the box, and the list sits
under the status line.

```
╭──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                                                                    │
╰──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╯
  ? for shortcuts                                                                              Opus · 91% context left
    main    claude · Opus
    parser  codex · gpt-5.3-codex  ✻ working 41s
    docs    claude · Sonnet        ← message from main
```

- **Where.** Under the status line, the last rows of the screen. The status
  line belongs to the box (its mode, the hint, the model the prompt goes to),
  so it stays right under the box. The list goes below both, where ↓ goes.
  The plan list and the queue stay above the box, so the three never compete
  for the same rows (`80-4-crowded.txt`).
- **When.** Only while the session has a long-lived child. A session with no
  children looks exactly as it does today, as one session shows no strip.
- **A row.** Two columns of indent (the `❯` goes there while the list has
  the focus), the name (bold and in its colour when picked, in its colour
  otherwise; `main` in plain text), the runtime and model (dim), and the
  state:

  | State | Colour | Meaning |
  | --- | --- | --- |
  | `● permission 12s` / `● input 12s` | `warning` | waits for the person: a permission, a form or a link |
  | `✗ failed` / `✗ exited` | `error` | its turn failed, or its agent exited |
  | `← message from main` | dim | a message came in since the person last looked at it |
  | `✓ replied 2m ago` | `success` | a turn ended since the person last looked at it |
  | `✻ working 41s` | dim | a turn is running |
  | (nothing) | | idle and seen |

  The glyphs are the strip's and the words are the sessions picker's, in the
  same order of urgency, plus `←`. Picking an agent clears its `✓`, `✗` and
  `←`, as going to a tab does. `main` gets the same marks while a child is
  picked.
- **Height.** At most `max(2, ⌊rows / 6⌋)` rows, the queue's own limit: 4 at
  24 rows (main and three children) and 6 at 40. Past that, the last row is
  `… +N more`. While the list has the focus, it scrolls so the picked row
  stays in view. A session holds at most **eight children**, so with `main`
  the list is never longer than the tabs' nine. `open_agent` past that
  answers `This session has 8 agents open; close_agent one first`.
- **Narrow.** A row that does not fit drops the model first (`codex`), then
  the state's words (leaving the glyph). The name is never cut below 12
  columns.

### Picking an agent

`120-4-child-focused.txt`: ↓ moved the focus into the list, and ↓ again
picked `parser`.

```
 parser · codex · gpt-5.3-codex · opened by main 4m ago

 ← main
   Run the parser tests after every change to src/parse and tell me what breaks.

 ⏺ Bash(deno task test tests/parse)
   ⎿  2 failed, 212 passed
 …
 ✻ Working… (12s · esc to interrupt)

╭─ parser ─────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                                                                    │
╰──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╯
  ↑ ↓ to pick · enter to write to it · x to close · esc to go back                    gpt-5.3-codex · 97% context left
    main    claude · Opus
  ❯ parser  codex · gpt-5.3-codex  ✻ working 12s
    docs    claude · Sonnet        ← message from main
```

- **Picking swaps what a tab switch swaps**, but inside one tab. It swaps
  the transcript and its scroll, the plan, the working line and queue, the
  draft, an open permission or form, and the status line's mode, model and
  context. The header and the strip do not change: this is still the same
  session.
- **A child's transcript opens with one line in place of the startup
  header**: `parser · codex · gpt-5.3-codex · opened by main 4m ago`, with
  the name in its colour. The parent's messages to it are `← main` rows, its
  own `send_message` calls are `→ main`, and the person's prompts are
  `›`.
- **The box takes the picked agent's colour and name.** The border is drawn
  in the child's colour, and its top border names the child. With `main`
  picked the box is exactly today's: no name and no new colour. Under
  `NO_COLOR` the name alone says who the prompt goes to.
- **While the list has the focus**, the status line's hint says what the
  keys do, as a picker's last line does. At 80 columns this is shortened to
  `↑ ↓ pick · enter write · x close · esc back`.
- **What the person types goes to the picked agent** as their own prompt,
  with no wrapper (`120-4-child-typing.txt`). shift+tab, `/model`,
  `/config`, `/cost`, `/context`, `/mcp` and Esc act on the picked agent,
  and its own slash commands are offered. Window-wide commands (`/new`,
  `/resume`, `/theme`, `/vim`, `/help`, `/exit`) behave as before.
  `/clear` with a child picked is refused:
  `/clear clears main; pick main first`. Clearing a child would leave the
  parent talking to an agent that no longer knows what it was asked.
- `main` is always the top row. The others are in the order they opened.

### ↓, beside prompt history

↑ and ↓ already walk the prompt history. The rule keeps that whole:

- **↓ goes into the list only when the draft is empty and history is not
  being walked.** That is the one place ↓ does nothing today, so no habit
  breaks. While ↑ has brought back an earlier prompt, ↓ walks forward
  through history as before. Once it reaches the empty draft at the bottom,
  the *next* ↓ enters the list. In a draft with lines below the cursor, ↓
  moves the cursor.
- **In the list:** ↑ ↓ or j k move, and moving picks, as the owner asked.
  ↑ on `main` returns the focus to the box. Enter and Esc also return it,
  with the pick kept, so the person can type to the agent at once. `x`
  closes the picked child (part 5). Other letters do nothing while the list
  has the focus, so a stray key never lands in a child's prompt.
- With no list (no children), ↓ is today's ↓.

### A child that needs the person

`120-4-child-waits.txt`. The person is on `main`, and `docs` asks for a
permission:

```
  ● docs needs your permission · ctrl+x a                                                      Opus · 91% context left
    main    claude · Opus
    parser  codex · gpt-5.3-codex  ✓ replied 2m ago
    docs    claude · Sonnet        ● permission 12s
```

- The row says `● permission 12s`, and the status line carries the same
  notice a session behind gets, naming the child. `ctrl+x a` goes to the
  wait: it picks `docs` when it is in this session, or switches to the tab
  and then picks it when it is in another session. The terminal is
  notified as for any wait, with the child named.
- **A child's permission box opens only when that child is picked**,
  because the call it is about is in the child's transcript, not main's. Its
  first row is `docs asks`, with the name in its colour, as CHD-149's
  `Agent(…) asks`. A task agent's box still opens in front of `main` (part
  1): a task's calls are drawn in main's transcript, so its box belongs
  there.
- `←` and `✓` put nothing on the status line. Agents trading messages would
  keep it busy all the time, and the list already shows them.

### The strip and the sessions picker

`120-4-sessions-picker.txt`. Children never get a tab. A parent's tab takes
the most urgent glyph among all its agents, so a session behind whose child
waits shows `●`. A message between agents inside a session marks no tab.
That message starts a turn, and the turn's `✻` and then `✓` already say so.

```
 chord   1 claude ●    2 codex                                                                                ~/src/app
╭──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ Sessions in ~/src/app                                                                                                │
│                                                                                                                      │
│ ❯ 1. claude · 2 agents  ● docs: permission 12s  Fix the tokenizer bug in src/parse, and keep codex on the parser…    │
│   2. codex              here                     Review the diff on main                                             │
```

The picker's row adds `· 2 agents` after the runtime, and a wait that is a
child's names it before its words (`● docs: permission 12s`). Going to that
row picks the child that waits. (Tab 2 is in front here, drawn inverse on
screen.)

### Colours, light and dark

`main` is never coloured, so a person who never opens a child sees no new
colour. The children take, in the order they opened (the seventh wraps
round):

| | blue | purple | cyan | green | yellow | pink |
| --- | --- | --- | --- | --- | --- | --- |
| dark | `#6cb6ff` | `#c49cff` | `#56d4dd` | `#7ccf7f` | `#e8c95a` | `#f59ac6` |
| light | `#0a5bc4` | `#7a3fd6` | `#00727a` | `#2c7a39` | `#8a6100` | `#b0306f` |
| 16 colours | `blueBright`/`blue` | `magentaBright`/`magenta` | `cyan…` | `green…` | `yellow…` | `red…` |

They go in the theme as one new role, `agents`, a list of six. The light set
is 4.5:1 or more on white (the code tones' own hues), and the dark set is
lighter than the dark theme's accent, so a name never sinks into the border.
Each child also has its name, on its row and on the box, and each state has
its word, so neither colour blindness nor `NO_COLOR` loses anything. A
child's colour lasts as long as the child: closing one does not recolour the
rest.

## 5. Busy, closing and quitting

A session is busy when anything in it would be lost: what busy means today,
plus a running task agent, plus a long-lived child that is working or waits on
the person. An idle child loses nothing, because its record stays and
`/resume` opens it.

| Busy because | Words (`closing.ts` order) |
| --- | --- |
| any agent of it waits for a permission | `waits for your permission` |
| a form or link is open | `asks for input` |
| prompts queued | `has 2 prompts queued` |
| task agents running, no long-lived child at work | `has 2 task agents running` |
| task agents and/or long-lived children at work | `has 3 agents working` |
| main's turn | `is working` |

The agents come before `is working` because they say more: a closing tab
would stop them too.

`120-5-close-armed.txt`:

```
  1 claude has 3 agents working · ctrl+x k again to stop them and close
```

`120-5-quit-armed.txt`:

```
  2 sessions are busy: 1 claude has 2 task agents running, 2 codex is working · ctrl+d again to quit
```

(At 80 columns it counts instead: `2 sessions busy · ctrl+d again to quit`, as
today.)

- **Closing a parent closes everything it started.** Its task agents are
  cancelled and its long-lived children are closed, each one recorded. A
  child has no tab to fall back to, so leaving it running would leave it
  invisible. The note in the tab that comes forward is
  `Closed 1 claude and its 2 agents · /resume opens them again`. This
  replaces the decision's "its long-lived children stay open as the person's
  sessions", which assumed children had tabs. **Owner, please confirm.**
- **Quitting** closes every session and every child, as now. The resume
  command printed on quit names the sessions alone, not their children
  (part 7).

### `x`: the person closes a child

`80-5-x-armed.txt`. With the list focused on a child, `x` closes it. If the
child is working or waits, the first press arms, like ctrl+c:

```
╭─ parser ─────────────────────────────────────────────────────────────────────╮
│ ›                                                                            │
╰──────────────────────────────────────────────────────────────────────────────╯
  parser is working · x again to stop it and close
  ❯ parser  codex · gpt-5.3-codex  ✻ working 12s
```

Any other key, or the same two seconds, takes it back. An idle child closes
on the first press. `main` is picked and the focus stays in the list. On
`main`, `x` does nothing and the status line says
`main is the session · ctrl+x k closes it`.

Then chord tells the parent (`80-5-x-closed.txt`). This is a message, so it is
a turn, and the parent is not left waiting on a child that will never answer:

```
 ← chord
   The person closed parser (codex · gpt-5.3-codex, id 7f3a9c2e). It takes no
   more messages; open_agent starts another.

 ⏺ parser is closed, so I will run the parser tests myself.
```

- The wording is `The person closed <name> (<runtime> · <model>, id <id>).
  It takes no more messages; open_agent starts another.` The id is the one
  `open_agent` answered, so the parent can match it whatever it called the
  child. It goes as `<message from="chord">`.
- A later `send_message` to it is refused with
  `parser is closed; open_agent starts another`.
- `close_agent` from the parent sends no such message. The parent asked, and
  its `Close(parser)` call's `⎿ Closed` is the answer.

## 7. `--resume` of a parent

`120-7-resume.txt`. The parent's record keeps each child's start, end and
messages, so the past draws as it did live:

```
 ▀▀     Resumed · last used 2h ago

 › Fix the tokenizer bug in src/parse, and keep codex on the parser tests while you do.

 ⏺ Open(parser) · codex · gpt-5.3-codex
   ⎿  Run the parser tests after every change to src/parse and tell me what breaks.

 ⏺ Agent(Fix the tokenizer) · codex · gpt-5.3-codex
   ⎿  Done (6 tool uses · 41s)

 ⏺ Agent(Check the printer) · gemini · gemini-2.5-pro
   ⎿  Disconnected (1 tool use · 9s)

 ← Fix the tokenizer · codex · report
   Fixed in src/parse/tokenize.ts (+12 −3); deno task test passes.

 ← parser · codex
   All 214 parser tests pass now.

 ⏺ The fix is in and every parser test passes.

 ⏺ parser (codex) and docs (claude) were open when this session was left and are not reopened · /resume lists them
```

- **Task blocks** are drawn from each child's record, folded, with ctrl+o
  opening the work as it was. A task that was still running when the
  session was left ends `Disconnected`, CHD-149's word for a child with no
  ending.
- **Message rows** come back as they were, both ways, and so do the
  `Open`, `Message` and `Close` calls.
- **Long-lived children are not reopened.** Starting every child's runtime
  again would cost the person agents they may not want. A closing note,
  chord's own `⏺` note after the past, names those that were still open.
  Each one is in `/resume`'s list like any session, and one opened there is
  the person's, in a tab, with no parent to message. Children the parent
  closed in its own time get no note. The list under the prompt is not
  drawn, since no child is open.
- The parent is not told at resume, because a message would start a turn
  nobody asked for. Its first `send_message` to a child that is gone is
  refused with `parser was closed when this session was left; open_agent
  starts another`.

## Keys

| --- | --- | --- | --- | --- |
| `↓` | empty prompt, not walking history, with a list | moves the focus into the agents list | `↓ for the session's agents` | no (it is `history:next`'s key at its end) |

| `enter` `esc` | agents list | back to the prompt, pick kept | `enter esc to write to it` | no |
| `x` | agents list | close the picked agent; twice if it is busy | `x to close an agent` | yes: `agents:close`, context `Agents`, default `x` |

The panel puts these four in a group after the prompt's own keys, under
`↓ for the session's agents`. `tests/ui/shortcuts/keys_test.tsx` presses each.
The leader line is unchanged: `ctrl+x k` still closes the session, and
`ctrl+x a` reaches a child's wait as well.

## Rejected

- **A child in a tab of its own**, the decision's first shape. The owner
  dropped it on 2026-10-07: it filled the person's strip with agents they
  did not open, and moved a child's work away from the conversation that
  asked for it.
- **The list between the box and the status line.** The status line
  describes the box (mode, model, `! for bash`), and splitting them would
  make the person read across the list to find the model the prompt goes
  to.
- **`ctrl+x k` on a picked child.** It would mean "close what is in front"
  and need no new key. But a person who means to close the session, with a
  child picked, would close the child instead and have to press again. Two
  keys for two things.
- **The list as a row of names, left and right.** The owner asked for up
  and down. A row would also cut the states, which matter more than the
  names.
- **Colouring `main`.** It would change every session that never opens a
  child.
