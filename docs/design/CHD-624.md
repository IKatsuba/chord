# CHD-624 — the upstream catch-up: dependencies, pins, Claude's new defaults

The owner, 2026-11-13, took the recommendations of
[the survey](evidence/CHD-624/survey.md), then changed D1 on reading the
design: Claude starts in Auto, as its adapter now does. This task is the
first of two PRs (D5 a): the dependency bumps, the registry refresh with its
fallout (D6), the Claude adapter's bump from 0.99.1 to 0.107.x, and the one
thing that bump makes chord draw differently: an idle compaction is said to
be one (D2 a). The new protocol features (`/rename`, the account in
`/status`, initial config options for mode, model and effort, notices, the
`session` tool-call content) are CHD-629, which waits for this one;
cursor-cloud's extras are CHD-630. The drafts this merges are in
[`evidence/CHD-624/drafts/`](evidence/CHD-624/drafts/); their D1 parts
(initial options, a Claude mode table) describe the choice the owner did not
take and are kept as the record for CHD-629.

No new key, no new command and no new component. Three things change on
screen: the mode a Claude session opens in (the adapter's Auto), the words
of an unasked compaction, and the rows of the agent list.

## Two rules over everything

- **The adapter's defaults are the agent's.** chord sends no start mode of
  its own; a mode the person names is set as today.
- **The wire is read, never guessed.** chord marks a compaction unasked from
  its own state (no turn, no cycle), not from the agent's words; where the
  adapter sends something chord cannot attribute, chord invents no rule for
  it (the owner's O1 a).

## D1 — Claude starts in Auto (owner)

Claude settings name `permissions.defaultMode`; 0.99.1 started in Manual.
The owner chose to take the adapter's default (D1 a) and say so in the
release notes. chord changes nothing in its start path:

- No mode is sent by chord's own choice. A mode named by `permissionMode`,

  0.99.1 (the adapter reads it).
- The release note says that Claude sessions now open in Auto, where Claude
  decides permissions, and how to start in another mode: `permissionMode`

  `permissions.defaultMode`.

## D2 — "compacted while idle"

### What Claude 0.107 sends

The adapter queues `/compact` as its own prompt 54 minutes after the last
request (1-hour cache, context at least 200k). chord sees, with no request of
its own open and no `PromptResponse`:

```json
{"sessionUpdate":"compaction_update","compactionId":"<uuid>","status":"in_progress"}
{"sessionUpdate":"compaction_summary_chunk","compactionId":"<uuid>","content":{"type":"text","text":"…"}}
{"sessionUpdate":"compaction_update","compactionId":"<uuid>","status":"completed","summary":[…]}
{"sessionUpdate":"usage_update","used":41200,"size":1000000}
{"sessionUpdate":"usage_update","used":41200,"size":1000000,"cost":{…}}
```

or `status: "failed"` with `error`. The trigger (`idle`) goes only to
JetBrains AIR. None of these kinds is in `CYCLE_WORK` (`cycles.ts:68`), so
today they open no cycle: no "working", no OSC 7501, no notification. D2
therefore needs no change to cycles.

Two adapter paths may still forward an `agent_message_chunk` around a
compaction (a `local_command_output`, or `<local-command-stdout>` text), with
nothing on it that ties it to the compaction; whether Claude Code emits one
for `/compact` cannot be read from the packages (the CLI is a separate native
binary). Such a chunk after a quiet second would open a Claude cycle that
stays "working" until the next prompt — today's documented behaviour
(`claudecyclebare`). The owner accepted that (O1 a): no window, no
suppression, no upstream ask.

### The mark

`Conversation` decides it, once, at a compaction's first update: unasked when
no turn of the person's, no turn of chord's own (`#selfTurnId`), no cycle and
no settling is under way, and the update is not part of a replay. Not an
enricher: the enricher chain knows chord's open requests but not cycles, and
would mark a compaction inside Claude's own cycle as idle.

- The `update` action gains `unasked?: true`; `Compaction`
  (`transcript/types.ts`) gains the same, taken from the opening update in
  `mergeCompaction` and kept by later patches.
- The record carries it explicitly: `RecordEntry`, `updateEntry`
  (`record.ts:1030`) and `recordActions` (`:725`) each pick their fields, so
  each gains it. A round-trip test: live, record, resume, the mark drawn.
  Older records have no field and draw as today.
- A replay by the agent (`session/load` with no record of chord's, Claude's
  replay across compactions) carries no trigger, so its compactions are
  drawn plain. chord does not guess from gaps.
- `chord acp` relays the update as it is; the mark is chord's state, not an
  assertion on the wire, and is not relayed upstream.
- Another client of the same Claude session (Remote Control): whether its
  compaction reaches this adapter process is unknown; if it does, it is
  drawn "while idle".
- The cost stays where every late Claude cost goes today: the last turn's
  line (`turn_costs.ts:227`). The session's sum is right; no record change.

`src/ui/transcript/compaction.ts`); only the words gain "while idle". They
do not depend on the agent.
