# CHD-492 — chord tells its terminal the session id to resume

Chorded, the terminal app chord runs in, wants to reopen chord after its
pane ends, whatever ended it (its resume task is CHRD-412). The owner's
direction (2026-10-21, on the task, and Q124): chord tells the terminal the
main session's agent session id as soon as `--resume` can use it, in a
terminal user variable apart from the OSC 7501 status; Chorded keeps it and
later runs the existing `chord --resume <sessionId>`, which it measured
reliable (12/12). Before the first prompt there is nothing to resume, and
Chorded starts chord again. No launcher-given id, no mapping file, no lock;
OpenTUI's `setProgramStatus` and chord's OSC 7501 record are untouched.

Three earlier designs (a launcher-named window record, a launcher-given
`--id`, the id in OSC 7501) were superseded with their questions Q112–Q117,
Q120–Q123 and Q124. The architects' drafts for the first stay in
`evidence/CHD-492/drafts/` as the record; the critic's findings on the
first two were taken into them before they were superseded.

## The sequence

iTerm2's user variable, which WezTerm also takes:

```
ESC ] 1337 ; SetUserVar=chord_session=<base64 of the session id> BEL
```

- **Name `chord_session`**: letters and an underscore, which every reader
  of user variables takes; `chord_` keeps it apart from other programs'.
- **Value**: standard base64 of the id's UTF-8, as the protocol asks, so an
  agent's id of any shape goes through unchanged
  (`0199f1c2-7c1e-7d43-9a3b-5f0e2c1d4b6a` is
  `MDE5OWYxYzItN2MxZS03ZDQzLTlhM2ItNWYwZTJjMWQ0YjZh`).
- **Empty value** (`SetUserVar=chord_session=`): nothing to resume now.
- **Terminated by BEL**, as chord's OSC 9 and OSC 777 are.

### Where it is written

OpenTUI 0.6.6 has no call for a user variable, nor one for bytes of chord's
own: its renderer offers `setProgramStatus`, `triggerNotification`,
`setTerminalTitle` and `writeToScrollback`, none of which writes an
arbitrary sequence. So it goes as OSC 9 and OSC 777 go today: through
`useStdout` (`src/ui/app/renderer.tsx`), which writes to the stream OpenTUI
draws on once the renderer is idle, so a frame part is never cut, and
nothing once it is destroyed. The bytes are built by a pure function beside
`notificationBytes` in `src/notify.ts`, and a hook beside `useNotify` in
`src/ui/app/terminal.ts` sends them when the value changes.

### tmux, and terminals that do not know it

- **Inside tmux** (`TMUX` set) the sequence is wrapped in tmux's DCS
  passthrough with each ESC doubled, by `notify.ts`'s `throughTmux`, as
  OSC 9 and 777 are. tmux hands it to the terminal outside only with `set -g
  allow-passthrough on` (off by default since 3.3), and drops it otherwise;
  the guide says so. Several chords in panes of one tmux all set the outer
  terminal's one variable, the last write winning; Chorded's resume then
  names the last of them. That is tmux's to have, not chord's to work
  around.
- **A terminal that does not know OSC 1337** ignores it: an operating
  system command it has no handler for is consumed up to its BEL and drawn
  as nothing, as xterm, VTE, kitty, Alacritty, Ghostty and Terminal.app do
  and as chord already relies on for OSC 9, 777 and 7501. iTerm2 and
  WezTerm keep the variable (iTerm2 shows it to badges and scripts as
  `user.chord_session`).
- **Sent in every terminal**, not gated on `TERM_PROGRAM`: Chorded is the
  reader, its identity is not chord's to guess, and a few dozen bytes on a
  change cost nothing where they are ignored. Not tied to
  `preferredNotifChannel` either: it is not a notification.

## When it is sent and cleared

The variable always says the main session's resumable id, or is empty.

| When | Value |
| --- | --- |
| chord starts a new session | empty: a session nobody prompted has no record ("Nothing is written until a prompt is"), and claude-agent-acp 0.93.0 cannot resume one from a new process |
| the first prompt has gone to the agent and its line is flushed to the session record (`resumableSession`, the quit's own test, then `FileRecording`'s `flushed()`) | its id |
| chord starts on a resumed session (`--resume`, `--continue`, the start picker) | its id, once it is open |
| `/clear` | empty at once; the new id after its first prompt is flushed |
| a `/resume` pick | the picked session's id, as it has a record |
| until CHD-493 removes tabs: the front tab changes | the front tab's, by the rules above |
| the agent exits or fails mid-session | unchanged: the session is still resumable |
| chord exits (quit, a signal, a crash), or an editor has the terminal | unchanged: **not cleared** |

- **A failed append** to the session record does not hold the id back:
  `--resume` still reaches the agent, which reopens the session drawn from
  its replay, as for any session chord never recorded.
- **Not cleared on exit.** Reopening after the pane ends is the point, so
  the last value outlives chord, unlike the OSC 7501 record, which chord
  clears as it gives the terminal back. A shell left in the pane keeps a
  variable naming the last chord's session, which is true: that is what a
  resume there would open. The next chord in the pane sets it again at its
  start.
- **Signals and SIGKILL** need nothing: the id went out when the first
  prompt was flushed, before any of them.
- **Children** (task agents, team members, long-lived agents) are not
  reported; reopening the main session draws their work from their records
  and does not restart them ("Teams on resume").
- **Equal values are not resent**: the hook remembers the last value it
  wrote.

## Resuming a session whose record is gone (today)

`--resume <sessionId>` with no record of that id hands it to the agent as it
is (`sessionById`); chord does not refuse it. An agent that still has the
session loads or resumes it, and the transcript is drawn from its replay.
One that does not answers with an error, which chord draws as `it cannot
resume session <id>: <the agent's reason>` (`src/session/session.ts`). The
same happens when the agent can neither load nor resume, or the directory
is gone. Nothing here changes that.

## What CHRD-412 reads and calls

- **Read** OSC 1337 `SetUserVar` with the name `chord_session` from the
  pane, base64-decode the value, and keep the last one per pane. An empty
  value means nothing to resume.
- **When the pane ends**, however it ended, take the last value kept.
- **Call**, to reopen: the command it started chord with plus
  `--resume=<sessionId>`, in the `=` form:
  `chord [agent] [--agent-command …] --resume=<sessionId>`. **Why `=`:**
  given apart, `--resume <sessionId>` reads an id that starts with `-` as
  options (`Unknown option -a`); joined by `=`, such an id reaches
  `session/load` whole. Probed on the fake, from source and compiled
  (f4ab3e48): `--resume=-abc`, `--resume=--x`, `--resume=-0199f1c2-…` and a
  plain UUID each reach `session/load` intact.
- **The limit**, accepted by the owner (`docs/decisions.md`, "`--resume`
  takes an optional value"): an id that spells one of chord's option names
  (`-r`, `-c`, `-m`, `model`, …) is not taken as an id, even with `=`:
  `--resume=-r` does not reach `session/load`. Of the agents whose ids
  are recorded so far, dirac and openclaw, both use UUIDs, which never
  spell one.
- The agent must be the same: `--resume` looks the id up among that agent's
  records and refuses one recorded for another (`Session … belongs to
  another agent (…)`). `--resume` opens the session in its own directory,
  so `-C` does not matter.
- **Nothing kept, or empty:** start chord again as it was started.
- Nothing to read from OSC 7501, from chord's output or from files.

## The screens

Nothing on screen changes: the id goes to the terminal, not to chord's
window. `/status` already shows `Session:`, and the quit already prints
`Resume this session with:`. No key is added; `keys.ts`, `bindings.ts` and
the shortcuts panel are unchanged.
