# CHD-622 — `@chorded/cursor-cloud-acp`: Cursor cloud agents over ACP

A new npm package in this repository, `@chorded/cursor-cloud-acp`, serves
Cursor's cloud agents as an ACP v1 agent on stdin and stdout, on Cursor's
TypeScript SDK `@cursor/sdk`. chord starts it with `npx`, as it starts the
Claude and Codex adapters, and lists it beside them. Cursor's own CLI
(`agent acp`, chord's `cursor`) runs local agents only and stays as it is.

The owner's decisions of 2026-11-12 (CHD-622's comments) frame everything
here: code in this repository, versioned on its own; `@cursor/sdk` a plain
dependency, never bundled; cloud agents only; start from the current branch
when pushed, refuse otherwise and with no remote; a first message naming the
repository, branch and link; no permission requests, `request` events as
text; sign-in by the package's `login` command into the OS keychain as the
SDK's `SdkCredentialStore`, `CURSOR_API_KEY` honoured, no sign-in code in
chord; serve what the SDK supports. The owner answered this design's nine
questions on 2026-11-12 (Q1–Q9, at the end). How `bun dev` checks, builds
and releases a package of this repository is CHD-623's
(`docs/design/CHD-623.md`); this design names only what this package puts
there. It waits for CHD-623.

The drafts behind this design, and the critic's review they answered, are in
`evidence/CHD-622/drafts/` (`brief.md`, `protocol.md`, `interface.md`,
`runtime.md`). Where this file and a draft differ, this file holds.

## Two rules over everything

1. **chord gains no screen, state, component or key for this agent.** Every
   frame below is drawn by what chord has: the picker, CHD-435's sign-in
   block, CHD-454's start-failure block, agent messages, tool rows, the
   status line and `/resume`. chord's code changes are its agent-list entry
   and one generic word fix (see "Changes in chord").
2. **The adapter says only what the SDK tells it.** No parsing of messages,
   no guessed shapes, no answered `request`s. Where the SDK's types and docs
   leave a fact open, the design names it and ship checks it in one
   authorized live run before the part that depends on it lands.

## The protocol

### `initialize`

`agentInfo` `{ name: "@chorded/cursor-cloud-acp", title: "Cursor Cloud
Agents", version }`. One `authMethods` entry, `{ id: "cursor-login", name:
"Cursor login", description: "Run `npx -y @chorded/cursor-cloud-acp@<own
version> login` in a terminal, or set CURSOR_API_KEY" }`.
`agentCapabilities`: `loadSession: true`; prompts `image: true` (the SDK's
`SDKUserMessage.images`), `embeddedContext: false`; `mcpCapabilities` http
and sse false (stdio servers are taken, as ACP asks, and not forwarded:
the first message says they are unreachable, Q5); `sessionCapabilities` `list`, `resume`, `close`;
`_meta.steering.supported: false` (cloud `steer()` always reverts to a
follow-up). No `session/fork`, no `session/delete`.

`authenticate` answers an error naming the `login` command: the owner put
sign-in in that command and chose against ACP sign-in.

### `session/new`

In order, each step refusing with its own words:

1. **Git**, local and first, so a refusal needs no key, no keychain and no
   network. `git` through `node:child_process` (`stdin` ignored,
   `GIT_TERMINAL_PROMPT=0`, 10 s each), in the session's cwd: not a work
   tree → refuse; detached HEAD → refuse; the branch's push remote missing
   or `.` → refuse "no remote"; **pushed** when the local remote-tracking
   ref of the same branch on its push remote contains HEAD (`git merge-base
   --is-ancestor`), with no network (Q4): a ref fetched before a force-push
   or deletion on the remote passes, and Cursor's own refusal then has the
   last word; the repository URL
   is the push remote's, turned into Cursor's form by `hosted-git-info`
   (npm's maintained parser: GitHub, GitLab, Bitbucket, sourcehut to
   `https://host/owner/repo`; other hosts passed as git has them, for Cursor
   to accept or refuse).
2. **Key** (see "Credentials"). None → `authRequired`. Then `Cursor.me({
   apiKey })`; `AuthenticationError` → `authRequired` with the SDK's message.
3. **Create** `Agent.create({ apiKey, mode, model?, cloud: { repos: [{ url,
   startingRef: <branch> }], workOnCurrentBranch: false, autoCreatePR: false
   } })`: the agent pushes a branch of its own and opens no PR unasked; the
   person tells it otherwise (decision 7).
4. **Answer** `{ sessionId: agent.agentId, configOptions }`. The session id
   *is* the cloud agent's `bc-…` id: the adapter keeps no mapping or state,
   and a session reopens from any machine.
5. **The first message**, after the answer (below, "Ordering").

### `session/prompt`

One cloud agent per session, one `agent.send()` per prompt, with
`SendOptions` `{ mode, model?, idempotencyKey, onDelta }`. `mode` is sent on
every send, so what the status line shows is what runs, including after a
resume (the SDK cannot read a resumed agent's mode back). The answer follows
`run.wait()`: `finished` → `end_turn`, `cancelled` → `cancelled`, `error` →
a JSON-RPC error with `RunResult.error.message`. `usage` from
`RunResult.usage` (`TokenUsage` → ACP `Usage`). No `usage_update`: the SDK
gives no context size, which ACP requires.

### The stream

Content comes from `SendOptions.onDelta`, the SDK's documented
token-by-token `InteractionUpdate`s ("text streams in token-by-token"), not
from `run.stream()`'s `assistant` events, whose types do not say whether
each is a piece or the message so far. Each awaited, so the SDK's own
backpressure holds:

| `InteractionUpdate` | ACP `session/update` |
| --- | --- |
| `text-delta` | `agent_message_chunk` |
| `thinking-delta` | `agent_thought_chunk` |
| `tool-call-started` | `tool_call`, `in_progress` |
| `tool-call-delta`, `partial-tool-call` | `tool_call_update` |
| `tool-call-completed` | `tool_call_update`, `completed` or `failed` |
| `shell-output-delta` | not drawn in v1 |
| `turn-ended`, `step-*`, `token-delta`, `summary*` | not drawn |

`run.stream()` is read beside it for what only `SDKMessage` carries:
`status` (`CREATING` → one line; others none; a terminal one with a
`message` → that line), `task` (its text as a line), `request` (the line
above), `usage`. A kind neither knows (a later SDK) is passed over. Every
adapter line has its own `messageId`, so chord does not join it to the
agent's text.

**Tool calls.** `toolCallId` is the `callId`. `kind` from the tool's name in
the SDK's `ToolCall` union only: `shell` → `execute`, `read` → `read`,
`edit`/`write` → `edit`, `delete` → `delete`, `grep`/`glob`/`ls`/`semSearch`
→ `search`, `webFetch` → `fetch`, anything else `other`. `title` is the
name, plus `: <value>` when the one field the SDK's own type names for that
tool (`command`, `path`, `pattern`, `globPattern`, `description`) is a
string; otherwise the bare name, never empty. `rawInput`/`rawOutput` as they
come. No `locations` (VM paths would draw as local files) and no `diff`
content (the SDK gives a `diffString`, not old and new text). An
`updateTodos` call also sends a `plan` from its todos, cancelled ones left
out (ACP has no such status).

**The run's end.** One line from `RunResult.git.branches[]` (branch, PR
link) and `agent.listArtifacts()` paths. Nothing is downloaded.

### Cancel, one turn, one run

`turn.ts` holds one run per prompt, captured by identity:

- cancel before `send()` returns a `Run` is held and applied when it does;
- cancel during a run calls `run.cancel()` bounded at 10 s, keeps
  forwarding what arrives until the run ends or the bound passes, then
  answers `cancelled`, exactly once; an unconfirmed stop adds the line in
  "Cancel" above;
- anything late from a run whose prompt has answered is dropped, so turn A
  never ends or cancels turn B;
- a second cancel, or one after the answer, does nothing.

**Stream loss.** `NetworkError` from the run's stream ends the turn as an
error: "Lost the connection to Cursor; the agent keeps running there:
<link>. Reopen the session to see where it got to." No reattach: a second
stream may replay events, and nothing in them lets the adapter drop the
ones already drawn. The adapter's hold on a run ends with its prompt's
answer.

### Ordering

- `session/new` and `session/resume`: answer, then the first message. The
  adapter writes it after the answer through what `@agentclientprotocol/sdk`'s
  agent side offers for work after a response; no timer. If the SDK offers
  nothing for it, ship stops and brings the question to the owner.
- `session/load`: replay, then the first message, then the answer.
- A prompt sent at once after the answer comes after the first message.

### `session/list`, `resume`, `load`, `close`

- **list**: `Agent.list({ runtime: "cloud", apiKey, cursor, limit })`, not
  archived, kept where `SDKAgentInfo.repos` holds the cwd's repository
  (both sides through `hosted-git-info`): every cloud agent on the account
  for this repository, whoever started it. `title` the agent's name,
  `updatedAt` its `lastModified`. chord's own `/resume` does not call it;
  `chord acp` clients and chord's MCP tools may.
- **resume**: `Agent.resume(id, { apiKey })`, the latest run from
  `Agent.listRuns`, answer, then the first message with that run's state.
- **load**: as resume, plus the replay: each run oldest first, its
  `run.conversation()` where `run.supports("conversation")`, steps mapped as
  the live updates are; a run that cannot give one gets a line saying so,
  never a guess.
- **close**: `agent.close()`; the cloud agent goes on.

### Modes and models: config options

- **mode**: ids `default` (name `Agent`, sent as the SDK's `agent`) and
  `plan`, so chord's status words apply as they do for other agents. A
  change applies from the next send.
- **model**: from `Cursor.models.list()`, one option per `ModelVariant`
  (its `displayName`, value its `ModelSelection` as JSON), one per model
  without variants. While `agent.model` is unset, a `Cursor's default`
  option stands for leaving `model` out. The SDK has no way back to the
  default once a model is set ("per-run model overrides are sticky"), so
  that option leaves the list then. A `RunResult.model` not in the list is
  added under its own id. A failed list leaves the current model alone.
- Env vars and artifact downloads are not served: ACP has no field for
  either.

### Errors

| Case | ACP | Words |
| --- | --- | --- |
| no key; key refused (`AuthenticationError`) | `-32000` | "Not signed in to Cursor." / the SDK's message |
| not a work tree, no remote, detached HEAD, not pushed | `-32602` | the adapter's, each with its way on |
| `IntegrationNotConnectedError` | `-32603` at start, prompt error later | the SDK's message and `helpUrl` |
| `RateLimitError` | prompt error | the SDK's message; no retry |
| `AgentBusyError` | prompt error | the SDK's message and the link |
| `AgentNotFoundError` | `-32002` | the SDK's message |
| archived (`ConfigurationError` `agent_archived`) | `-32602` | the SDK's message |
| `NetworkError` mid-run | prompt error | "Lost the connection…" above |
| other `CursorSdkError` | `-32603` | the SDK's message; `code`, `requestId` in `data` |

Errors are told apart by SDK class and `code` in `cursor.ts`, which turns
them into the adapter's own kinds; nothing reads a message's words.

## Credentials

`keyring.ts` is the `SdkCredentialStore` passed to
`Cursor.auth.login/logout/status`: one entry, service
`@chorded/cursor-cloud-acp`, account `cursor-api-key`, the password the JSON
of `StoredSdkCredentials`; an entry of another shape loads as signed out, so
the format holds across versions. On Linux the entry is pinned to the
Secret Service.

The store reaches only `login`, `logout` and `status`; every other SDK call
takes `apiKey` or resolves `CURSOR_API_KEY`, then the SDK's own login file.
`credentials.ts` therefore resolves one key per `session/new`, never cached
across sessions: `CURSOR_API_KEY` when set, else the keychain entry when
unexpired, else none (signed out). The result is always passed as `apiKey`,
the SDK's documented option, so a login another SDK program left in its own
file is not used (Q3). A key minted for another backend is passed as it is:
it fails at Cursor's first call, `Cursor.me`, with `AuthenticationError`, and
shows as the sign-in block with the SDK's message (Q10).

Every keychain call is bounded at 10 s: macOS asks with a dialog when a
different `node` reads an item another wrote, and the start then fails
naming the keychain instead of hanging.

Where no keychain is there (Linux without a Secret Service, a headless box),
`login` refuses, naming the keychain's error and pointing to
`CURSOR_API_KEY`; no key is written to disk (Q2).

## Process and failure

One Node process per agent start, under `npx`, in the process group chord
makes; it may serve several sessions. chord stops it as `src/acp/process.ts`
does.

| Case | Outcome |
| --- | --- |
| Node below 22.13 | `bin.ts`, parseable by old Node, writes one line to stderr and exits 1 before importing anything |
| first `npx` start | npm's download; chord's splash shows its slow line; nothing in the adapter |
| stdin ends, SIGTERM, SIGINT, SIGHUP | stop forwarding, `agent.close()` each, **no** `run.cancel()`, exit within 1.5 s |
| signed in while chord is open | the next `session/new` finds the key |
| keychain dialog | 10 s, then a refusal naming the keychain |
| git asks for a passphrase | it cannot reach a terminal; git fails, the start is refused with git's message |
| events faster than chord reads | each update awaited; the SDK's `onDelta` backpressure holds the rest |

Only ACP writes stdout; the adapter's own lines go to stderr. The SDK
documents only stderr (the login URL; Node 22's `node:sqlite` warning). No
`console` is redirected. A test fails on any stdout line that is not
JSON-RPC; if the real SDK ever writes stdout, that is the owner's question.
Cloud agents keep their state on Cursor's side; the adapter always passes
`runtime: "cloud"` and opens neither of the SDK's local stores.

## The package in the repository

- **Workspace.** `"workspaces": ["packages/*"]` in the root `package.json`;
  one `bun install`, one `bun.lock`. Installing `@cursor/sdk` at the root is
  not bundling it: chord's binary takes only what `src/` imports.
- **Node, not Bun.** The package's `tsconfig.json` has Node's types and not
  Bun's. ESLint forbids `Bun` and `bun:*` in `packages/*/src/**`, and
  `serve.ts` and what it imports may import the SDK for types only.
- **Its tests live in it.** `packages/cursor-cloud-acp/tests/` mirrors its
  `src/`, as `tests/` mirrors chord's; its fixture is
  `packages/cursor-cloud-acp/tests/fixtures/`. Nothing of the package is
  under chord's `tests/`.

### Its steps, checks and release

How `bun dev` checks, builds and releases a package is CHD-623's
(`docs/design/CHD-623.md`): each package defines its steps in a `steps.ts`
at its root, `bun dev quality <package>` runs its checks and nothing else,
and `bun dev release <package>` runs its release stages. What this package
puts there:

- **Checks** (`bun dev quality cursor-cloud-acp [--static]`): types (its
  Node project), tooling types (`tsconfig.tools.json`, Bun's types, for
  `steps.ts` and `scripts/`), covered, ESLint with its own
  `eslint.config.ts` (chord's shared rules plus the Node-only block),
  format, and when not `--static` its tests, its build and the Node smoke.
- **Release stages** (`bun dev release cursor-cloud-acp [--bump …]`):
  install, quality, build, pack (installed by Node 22.13+ and run), publish
  (`@chorded/cursor-cloud-acp`, tag `cursor-cloud-acp-v<version>`, no
  GitHub release). Versions, channels, guards and a stopped run are the
  release's, as CHD-623 sets them.
- **Its tooling** (`steps.ts`, `scripts/tools.ts`: build, pack, smoke) is
  dev tooling: outside its `files` and its Node project, checked by its own
  tooling project, never by chord's.
- **CI.** A required `node` job, on Node 22 only (Q8), setup-node at
  `22.13`, runs `bun dev quality cursor-cloud-acp`. chord's jobs run
  chord's checks only.

chord's checks leave `packages/` out (CHD-623); chord's tests never import
the package, and its window tests use `tests/fixtures/fake_agent/`
scenarios. chord keeps three boundary checks: ESLint forbids `src/**` to
import `packages/`, `@cursor/sdk` or `@napi-rs/keyring`; `compile_test.ts`
checks the binary holds no file of either; `tests/privacy_test.ts` reads
every tracked file.

### The build

`bun build src/bin.ts --target=node --packages=external` into `dist/`:
JavaScript (Node 22.13 runs no TypeScript), packages left as imports. The
build checks Bun's metafile lists only the package's own `src/` files, so the
SDK and the keyring are never bundled. `package.json`: `type: module`, one
`bin` (`cursor-cloud-acp`, so `npx @chorded/cursor-cloud-acp login` finds
it), `files: ["dist", "README.md", "LICENSE"]`, `engines.node >=22.13`, MIT,
`repository.directory`, public access. Dependencies: `@cursor/sdk` exact at
`1.3.1`, the owner's exception to AGENTS.md's caret rule (Q7): bun.lock
does not reach a person's `npx`, and the SDK marks tool shapes unstable;
`@agentclientprotocol/sdk` and `@napi-rs/keyring` with carets, `zod` in the
range both accept.

### chord's pin

`src/chorded.ts` holds chord's own npx agents in the registry's shape, with
`mcpServers: false` (a cloud VM cannot reach chord's or the person's local
servers, so chord says they are held back rather than the agent dropping
them). `src/agents.ts` merges it into the npx agents by name. The version is
a literal, bumped by a chord commit after a package release, so main never
pins a version that is not on npm. chord's release preflight (its `steps.ts`,
CHD-623) asks `npm view` for each pin and stops on a miss. 0.70.0's order:
CHD-623, this package's 0.1.0, then chord.

## Before ship builds the stream

The types and docs leave four facts open. Ship checks them in one
authorized live run with a tiny prompt (Q9) before the parts that depend on
them land:

1. `onDelta` fires for cloud runs (the docs list it with no runtime limit).
   If it does not, the stream mapping goes back to the owner: `run.stream()`'s
   `assistant` events cannot be drawn without knowing whether they are
   pieces or snapshots.
2. Whether `Agent.create` reaches Cursor before the first `send()` (if not,
   the link answers 404 until the first prompt, and an unreachable
   repository is refused at the first prompt).
3. `Agent.listRuns`' order and `run.conversation()` on finished cloud runs.
4. How many model variants `Cursor.models.list()` gives.

## Why

- **A package of its own on Node**, not riff-style inside chord: the owner's
  decisions 1 and 2; the SDK must never enter the binary.
- **A workspace** over a separate install: one lockfile, one CI install, and
  the root's tests reach its source.
- **`onDelta` for content**: the SDK's documented token stream; the
  alternative needs a guess the one rule forbids.
- **The session id is the cloud agent's id**: no adapter state, nothing to
  lose, reopenable anywhere.
- **Git before key**: refusals cost nothing, and the smoke stays off the
  keychain and the network.
- **Always `apiKey`**: one answer to "which key pays", the SDK's own option.
- **No reattach, no following runs live**: no event ids to deduplicate by,
  and chord would draw a turn nobody started.
- **Its tooling in CHD-623**: one way for every package to define and run
  its checks and release, so chord's release machinery is not written
  twice.
