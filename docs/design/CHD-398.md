# CHD-398: the @ finder matches without blocking the window

The owner (2026-10-17, Q4 on CHD-398): the `@` finder's match moves to
fzf's `AsyncFzf`, so a key typed after `@` no longer blocks the window.
ship-7 measured 45–106 ms per key on vscode's 20,657 files after the memo
(PR #19). AsyncFzf scores in chunks and yields: it measured stalls of
6–13 ms, with the result about 90–105 ms later. The owner also asks about
matching only from the second character after `@`. What the list shows
before that is the owner's choice; the options are below, not settled.

Evidence, on a small git tree of 20 files in a `mktemp -d` directory:

- `evidence/CHD-398/today/`: chord on the fake agent, run with
  `bun dev chord --fake -C`, after `@`, `@s` and `@sr`, at 80×24 and
  120×40.
- `evidence/CHD-398/claude-code/`: Claude Code 2.1.302 on the same tree
  after `@`, `@s` and `@sr`, typed and never sent. No prompt was spent.
- `evidence/CHD-398/mock/`: this design at both sizes.

## Today

`matchFiles` (`src/ui/prompt/mentions.ts`) gives the walk's first 100
files, in walk order and unscored, for an empty query. For any other
query it runs fzf, synchronously, in render. The list
(`src/ui/prompt/Prompt.tsx`) shows 6 rows under the prompt box at 80×24
and 10 at 120×40, with the highlighted row in `permission`. With no match
the finder closes, and Enter sends the draft (`fileFinder`, "None when
nothing matches").

```
╭──────────────────────────────────────────────────────────────────────────────╮
│ › @                                                                          │
╰──────────────────────────────────────────────────────────────────────────────╯
  package.json
  README.md
  tsconfig.json
  docs/decisions.md
  docs/FEATURES.md
  docs/guide.md
```

Claude Code, for a bare `@`, lists the tree's top level, five rows,
directories first: `+ tests/`, `+ docs/`, `+ README.md`, … From the first
character on it matches, directories and agents included (`@s` lists
`+ src/` and four `* … (agent)` rows; `@sr` lists `+ src/`, `+ src/ui/`, …).
So Claude Code matches from the first character.

## (1) Zero characters after `@`

**As today, settled:** the walk's first files in walk order. No match runs
for an empty query, so it costs nothing, and the list is there at once.
It reads the same as now: the files near the top of the tree first.

## (1) One character after `@`: the owner's choice

If matching starts at the second character, the list needs something to
show for `@s`. These are the options. The mocks are
`mock/one-char-*-80x24.txt` and `-120x40.txt`.

**A. A plain prefix filter, no fzf.** Files with a path segment that
starts with the character, case-insensitive, shortest path first. That is
one pass over the list with no scoring: about a millisecond at 20k files.
fzf takes over from the second character.

```
│ › @s                                                                         │
╰──────────────────────────────────────────────────────────────────────────────╯
  src/files.ts
  src/main.tsx
  src/settings.ts
  scripts/compile.ts
  src/ui/app/App.tsx
  src/ui/app/keys.ts
```

The list reacts to the first key. Its order differs from fzf's, so the
list reorders at the second key.

**B. The zero-character list, and a dim hint.** The list stays as it was
for `@`, and its last row becomes a dim `type 2 characters to search`.

```
│ › @s                                                                         │
╰──────────────────────────────────────────────────────────────────────────────╯
  package.json
  README.md
  tsconfig.json
  docs/decisions.md
  docs/FEATURES.md
  type 2 characters to search
```

This costs nothing, but the typed `s` changes nothing on screen, and
Enter would pick `package.json` for `@s`.

**C. Match from the first character, with AsyncFzf.** This is today's
list for `@s` (`mock/one-char-C-fzf-*`, the same as `today/at-s-*`). With
the match async, the first character no longer blocks. A one-character
query matches nearly everything, so it is the slowest to score (ship-7:
`s` 23 ms synchronous). Async, it only delays the list, and the previous
list shows meanwhile (below).

**Recommendation: C.** With AsyncFzf, the second-character rule no longer
has a freeze to prevent, and a list that ignores the typed character
(B) or reorders under the second (A) reads worse. Claude Code matches
from the first character too. If the owner still wants matching to start
at the second, A is the better of the other two, because the list still
answers the key.

## (2) While a match runs

- **The previous list stays**, rows and highlight as they were, so the
  list never blinks empty between keys. The typed characters show in the
  prompt box at once.
- **A dim `searching…` marker** replaces the list's last row, but only
  when the match has run longer than **150 ms**. Most keys on most trees
  come back sooner, and a marker for 100 ms would only flicker. The list
  does not grow by a row for it (`mock/pending-*`):

  ```
  │ › @sr                                                                        │
  ╰──────────────────────────────────────────────────────────────────────────────╯
    src/files.ts
    src/main.tsx
    src/settings.ts
    scripts/compile.ts
    src/ui/app/App.tsx
    searching…
  ```

- **A result for an older query is dropped.** A result is drawn only if
  its query is still the mention's query and the file list is the one it
  matched. AsyncFzf cancels the older search when a newer one starts, and
  anything that still arrives late is ignored. A result is never drawn
  over a newer key's list.
- **When it arrives**, the list is replaced and the highlight goes to its
  first row, as typing does today. An empty result closes the finder, as
  today.
- **No previous list** (the last result was empty, so the finder was
  closed): the finder opens with just the `searching…` row once 150 ms
  have passed, and stays closed until then.

## (3) Keys while a match is pending

- **↑ ↓** (and the other `finder_up` / `finder_down` keys) move the
  highlight in the list on screen, as today.
- **Enter and Tab** depend on the highlight:
  - If the person **moved the highlight** since the list on screen
    arrived, Enter and Tab pick that row at once. It is a row they chose
    by looking at it.
  - If they did not, Enter and Tab **wait for the pending match** and pick
    its first row. Someone who types `@mentions.ts` and presses Enter
    before the match is back gets `src/ui/prompt/mentions.ts`, not the
    first row of the list for `@mentions.t`. The wait is the match's own,
    about 100 ms on 20k files. Keys typed during it are applied after it,
    in order.
  - If the awaited result is empty, Enter sends the draft as typed and
    Tab does nothing, as when nothing matches today.
- **Esc** puts the finder away, as today. The pending result is dropped
  when it arrives.

No key is new, so the shortcuts panel does not change: its `tab enter to
add a file`, `↑ ↓ to pick a command or file` and `esc to close commands
or files` lines still say what the keys do.

## Colour roles

Nothing new from `src/ui/theme/theme.ts`. The highlighted row stays in
`permission`. The `searching…` marker, and option B's hint if chosen,
are dim.

## How it is checked

On the fake agent, a tree of thousands of files makes the match slow
enough to see the marker. A test with a held AsyncFzf result can show,
with no large tree: the previous list while pending, the marker after
150 ms, a stale result dropped, and Enter waiting.
