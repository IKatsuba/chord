# CHD-638: a website that is a terminal

The site is one chord_tui program compiled with `dart compile wasm` and drawn
full-window by wterm (`@wterm/dom`). Everything a visitor sees is drawn by
chord_tui; the page is a host for the terminal and nothing else. It covers
chord (the app) and chord_tui (the framework), lives in `site/`, and builds
to a static folder that any static host can serve. There is no server process
per visitor.

This is a design for the owner. The open questions are at the end, each with
options and one recommendation; nothing in them is decided here.

## What the probes found

Spike CHD-637 (commit 9cd77b053) left six items open. Each was probed against
wterm 0.6.0 (the current npm release) in headless Chrome 157, on a probe app
built from the spike's framework tree. The probe page served wterm from its
npm tarballs, not a CDN. The captures are in
[`evidence/CHD-638/`](evidence/CHD-638/).

Any failure runApp tries to print would be lost the same way. | `build-error-120x40.png` |

Four more facts the design rests on:

- **Size.** The probe (six framework examples plus the probe app) is
  2,197,475 bytes of Wasm: 624,699 gzip -9 and 493,032 brotli -q 11.
  wterm's core is 55 KB of Wasm, also shipped inlined as a 74 KB JS chunk.
  Start (compile and instantiate) took 23 ms.
- **Resize.** With `autoResize` on, a 1400x900 viewport gives 163x51 cells;
  resizing to 700x500 gives 80x28, and chord_tui redraws at the new size.
- **Phone.** An iPhone 15 viewport (390x844) gives 43x37 cells
  (`phone-390x844.png`). A tap focuses wterm's textarea, which opens the soft
  keyboard. Tap-as-mouse-report with tracking on was not probed.
- **The chord app does not compile to Wasm yet.** `bin/chord.dart`,
  `tool/start.dart` and `tool/steering.dart` all stop at `dart:ffi` in
  `lib/platform/process.dart`, `lib/platform/group_exec.dart` and
  `lib/platform/resource_executable.dart`. Any page that runs chord's own
  widgets needs those three behind conditional imports, as the spike did for
  the framework. What fails at runtime after that (processes, records,
  settings files) is unknown until it is tried.

**wterm carries everything the site needs.** Nothing here forces xterm.js.
The one visible defect is the seam on horizontal box lines at ratio 2
(question 8). xterm.js stays an option for the owner, not a recommendation:
the spike drew the same examples in it without seams, at the cost of a
larger dependency (about 300 KB of JS before addons) and a canvas that
browser find and screen readers do not read.

## The slice and its units

In build order. Framework units come before the site units that use them.
"Screen" marks a unit that changes what is drawn; designer looks at those
in a browser at 120x40 and 80x24 before review.

### Framework

**F1. Wasm-safe terminal and runApp.** Not on screen.
`packages/chord_tui/lib/`:

- Take the spike's split: `settle_input_ffi.dart` and
  `settle_input_stub.dart` behind `if (dart.library.ffi)`.
- runApp's exit path stops touching `stderr`, `exit`, `Process.killPid` and
  `Platform.environment` where they do not exist. One small
  conditionally-imported module (`process_io.dart` / `process_web.dart`)
  holds `reportFailure(Object)`, `exitWith(int)` and the environment. On the
  web, `reportFailure` goes to `console.error` and exiting is a no-op. On
  native, behaviour is byte-for-byte as today.
- Under Wasm, a clean quit returns from runApp and a failure completes its
  future with the error. It no longer throws `Unsupported operation`.

Tests: the existing run_app and signal suites unchanged; one VM test that the
failure report goes through the seam; one `compile`-tagged test that
`dart compile wasm example/main.dart` succeeds, so a new `dart:ffi` import
fails CI.

**F2. The web terminal.** Not on screen by itself. In two layers, so that
most of it is testable on the VM:

- `HostTerminal`, plain Dart: a `Terminal` over a host given as Dart
  functions (`write`, an input stream, a size and a resize stream). It owns
  the escape sequences that `StdioTerminal._acquire` writes today (alt
  screen, hidden cursor, bracketed paste, and with `mouse: true` the
  1000/1002/1006 modes), and undoes them on `leave`. It refuses `suspend`
  and `runEditor` with a clear error, because there is no process to lend
  the terminal to.
- `WebTerminal`, over `dart:js_interop`: binds a page object with `cols`,
  `rows`, `write`, `onData` and `onResize` (the spike's `_Host`) to a
  `HostTerminal`. It overrides `copyToClipboard`
  (`navigator.clipboard.writeText`), `openUrl` (`window.open` with
  `noopener`), `setTitle` (`document.title`) and `bell` (ignored). The page
  object is not wterm-specific, so the same binding drives xterm.js.

The call site reads like any chord_tui app:

```dart
import 'package:chord_tui/chord_tui.dart';
import 'package:chord_tui/web.dart';

void main() => runApp(
  const Site(),
  terminal: WebTerminal(mouse: true), // reads globalThis.chordTerminal
  exitProcess: false,
  handleSignals: false,
);
```

Where `WebTerminal` lives (a public `package:chord_tui/web.dart`, or
`site/` only) is question 3. The shape above is the same either way.

Tests: `HostTerminal` on the VM through a fake host (modes written on enter
and undone on leave, input and resizes delivered, suspend refused).
`WebTerminal` in headless Chrome (see "How done is checked").

### The site

**S1. The site's Dart package.** Not on screen. `site/pubspec.yaml`
(`chord_site`, `publish_to: none`, chord_tui by path), `site/lib/`,
`site/test/`, `site/web/main.dart` as above. Its own `analysis_options.yaml`
includes the root one. It is not part of the shared version.

**S2. Pages and navigation.** Screen. A pure router reducer
(`site/lib/router.dart`: the current page, history, and the URL fragment it
maps to) and the shell widget. The shell has a header with the name and the
links, the page in the middle, and a `KeyHelp` row at the bottom. Each page
is a widget. Every action has a key bound through `Actions`, and the
shortcuts panel lists it. The shape depends on question 1. The mocks below
are the recommended option.

**S3. Framework pages.** Screen. Pages about chord_tui, each built on live
widgets: what it is, `README`'s example running, then the gallery. The
gallery runs the framework's examples in place: `demo`, `markdown`,
`picker`, `form`, `text_area`, `diff`, `dialog`, `layers` and `mouse`. They
are imported from `packages/chord_tui/example/`, not copied.

**S4. chord pages.** Screen. What chord is, its screens, install. How its
screens are shown is question 2. That choice can add a unit to `lib/`: the
three-file ffi split (P1), and for the live option, an in-browser fake.

**S5. The page and the build.** Screen (fonts, colours, full-window
geometry). `site/web/index.html`: wterm full-window, the host object, the
Wasm loader, a `<noscript>` line, and an `aria-label` on the terminal. Then
`site/tool/build.dart`: `dart compile wasm -O4` into `site/build/` with
`index.html`, `main.wasm`, `main.mjs`, wterm's files and fonts, all URLs
relative. The output is a plain static folder with no host-specific files.
How wterm's JS gets into the build is question 7.

**S6. CI.** Not on screen. As question 6 decides.

## How done is checked

Without a browser (most of it):

- The router reducer, `HostTerminal`, and every page through
  `package:chord_tui/testing.dart` at 120x40, 80x24 and 43x37: render,
  press keys, check the screen. A page's text and layout are tested like
  any widget's. This runs on the VM with `dart test` in `site/`.
- F1's VM test and its `compile`-tagged Wasm build.
- The build tool's output: the expected files, relative URLs only, and the
  Wasm size against the budget (question 9).

Needs headless Chrome (one tag, `browser`, skipped by default, as `compile`
is):

- `WebTerminal` against a tiny host page: input, resize, clipboard, title,
  and the clean-quit path finishing without an error.
- A smoke test of `site/build/` served on loopback. It loads, the home page
  draws, Enter on item 3 opens the gallery, a click on a picker row changes
  the selection (SGR mouse), Shift+Enter reaches a text area (kitty), the
  console has no errors, and start time is reported.
- Driven from Dart. `package:puppeteer` (pub.dev, maintained, drives an
  installed Chrome over CDP) is the first package to try, per AGENTS.md; if
  it does not fit, the question goes to the lead before anything else.

Screen checks: designer captures the built site as whole-window colour PNGs
at 120x40 and 80x24 (and 43x37 for a phone), with the same headless driver
at device pixel ratio 2. Captures go under `docs/design/evidence/CHD-638/`.
The cell grid is fixed by `cols`/`rows` on the page for captures, and
auto-sized otherwise.

## Open questions for the owner

### 1. What the pages are and how a visitor moves between them

- **A. One app with a home menu and URL fragments.** A numbered home menu
  (as in the mock), pages as routes, Esc back, digits to jump, `?` for keys.
  The route is mirrored in `location.hash` (`#/chord_tui/gallery/markdown`),
  so links can be shared and the browser's Back works. One Wasm download.
  Cost: a small router and `hashchange` binding in S2.
- **B. One app, no URLs.** As A, but the address never changes. Cheapest;
  nothing can be linked and Back leaves the site.
- **C. One long scrolling document.** One page with sections and a contents
  jump list, read with the wheel and PgUp/PgDn, like a README in a pager.
  Simple to write; the gallery examples then have to live inside a scroll,
  where they fight it for keys.
- **D. A separate Wasm per page,** each with its own HTML file. Real URLs
  without a router, but every page change reloads, and the shared code
  downloads again for each page.

Recommendation: **A**.

### 2. Whether chord's pages show the real app or recorded screens

- **A. Recorded screens.** `tool/screenshots.dart` already drives the Dart
  fake through real flows. Add an ANSI-frame recording next to its PNGs, and
  a chord_tui `Playback` widget that plays frames with pause and step keys.
  No change to `lib/`. It looks exactly like chord, but it is a film, not
  chord.
- **B. chord's own screens, live, no agent.** Compile chord's screen
  fixtures (`tool/start.dart`, `tool/prompt.dart`, `tool/permission.dart`,
  `tool/plan.dart`...) into the site: the visitor types in the real prompt
  and answers a real permission box. Cost: the ffi split in three
  `lib/platform/` files (P1), plus whatever those fixtures touch at runtime
  (files, records), which is unknown until tried. It changes the port.
- **C. The whole app against an in-browser fake.** `bin/chord.dart`'s window
  with the Dart fake over in-memory ACP: a real session with canned
  replies. The strongest demonstration and much the largest cost: P1, the
  fake agent running in-process, and records, settings and processes all
  faked or made wasm-safe in `lib/`. A larger download too. A task for the
  architects team, not this slice.
- **D. A for this slice, then B as a follow-up task.**

Recommendation: **D**.

### 3. Where the web terminal lives

- **A. Public in chord_tui, as a separate library** `package:chord_tui/web.dart`
  (`WebTerminal`, `HostTerminal`). Any chord_tui app can ship to a browser,
  and the site proves the framework through the same API others get. Cost:
  it is published API to keep, needs `///` docs, a README section and a
  pana check for web support. `chord_tui.dart` stays free of `js_interop`.
- **B. `HostTerminal` public in `chord_tui.dart`, the `js_interop` binding in
  `site/`.** A plain-Dart seam others can bind to anything; the JS glue
  stays with the site. Smaller public surface, no web library to support.
- **C. Everything in `site/` only.** No API commitment. The framework gets
  only F1. A second web user would copy the code.

Recommendation: **A**.

### 4. What a visitor's quit or Ctrl+C does

The probes show both reach the app. With text selected in wterm, Ctrl+C and
Cmd+C copy instead.

- **A. Quit means "home".** Ctrl+Q and Ctrl+C go to the home page, and on the
  home page they do nothing; runApp never ends. Nothing on the site can
  leave the visitor at a dead screen.
- **B. Quit ends the program, and the page offers a restart.** runApp
  returns, the terminal is cleared, and a one-line notice (written to the
  terminal by the page, not by chord_tui) says "press any key to start
  again". Truthful to a terminal; a dead end for the visitor who pressed it
  by habit.
- **C. Quit keys are not bound.** Ctrl+Q and Ctrl+C do nothing anywhere. The
  simplest; a visitor trying to leave gets no response.

Recommendation: **A**.

### 5. Mobile and touch

- **A. The same app, sized to the phone, driven by tapping.** At 43 columns,
  the shell turns mouse tracking on and every list row and link is tappable;
  keys still work with a hardware keyboard. Cost: each page checked at
  43x37, and tap-to-SGR on iOS and Android verified (not probed yet).
- **B. As A, plus a chord_tui-drawn key row** (Esc, Tab, arrows, Enter) at
  the bottom on narrow screens, for the examples that need keys. Keeps
  "everything drawn by chord_tui". Costs one widget and some rows.
- **C. A fallback page for phones:** plain HTML with the README's text and
  links, no terminal. Cheap and readable, and it breaks "the site is a
  terminal".
- **D. Desktop only.** Phones get the same app with no tap support beyond
  focusing; the soft keyboard is the only input.

Recommendation: **B**.

### 6. How site/ joins CI

- **A. A `site` job,** required by `check`: `dart analyze` and the format
  check for `site/`, `dart test` (VM), the Wasm build with the size budget,
  and the `browser`-tagged tests with Chrome (preinstalled on Ubuntu
  runners). F1's Wasm compile test goes in the existing `compile` job.
  About 2–3 minutes added in parallel.
- **B. Fold into the existing jobs:** `static` analyzes `site/`, `tests`
  shards include it, `compile` builds the Wasm. No new job; the browser
  tests are not run.
- **C. Analyze and VM tests only;** the build and the browser checks run
  locally before a deploy.

Recommendation: **A**.

### 7. How wterm gets into the build

- **A. Fetched by the Dart build tool from npm, pinned with a checksum,** as
  `tool/release/x64_sdk.dart` fetches the SDK: version and sha512 in the
  tool, tarball cached under `.dart_tool`, files copied into `site/build/`.
  No new package manager in the tree.
- **B. A Bun workspace member `site/`** with `@wterm/dom` in `package.json`
  and `bun.lock`. Standard npm tooling and update flow; AGENTS.md says Bun is
  for the adapter only, so this changes that rule.
- **C. A pinned CDN import** (`esm.sh/@wterm/dom@0.6.0` with subresource
  integrity). Nothing to build; the site then depends on a third-party CDN
  at runtime, and the output is no longer self-contained.

Recommendation: **A**.

### 8. Renderer, font and the box-line seams

- **A. WebGL renderer and one bundled font.** WebGL was clean at ratio 4 and
  falls back to DOM without WebGL2; selection, find and screen readers still
  read DOM text. Bundling one OFL monospace font (about 100 KB woff2)
  pins cell metrics on every machine, and likely removes the ratio-2 seams
  if its advance is a whole number of pixels (to be checked in S5).
- **B. DOM renderer, system font stack** (`ui-monospace, Menlo, Consolas`).
  No download; the seams stay, and cell width differs by machine.
- **C. As A, and report the ratio-2 seam to wterm upstream** with the
  captures. Reporting is an outward action, so it is the owner's to approve.
- **D. Switch to xterm.js** (see "What the probes found"). Not needed for
  any capability; only for the seam.

Recommendation: **A**, plus **C** if the bundled font does not remove the
seams.

### 9. Size budget

The probe app with six examples is 493 KB brotli (625 KB gzip). With the
full gallery and the chord pages, about 600–800 KB brotli is likely.

- **A. A budget checked in CI:** first load (Wasm, JS, wterm, font) at most
  1.5 MB brotli, failing the build above it.
- **B. Report the size in CI, no limit.**
- **C. No check.**

Recommendation: **A**.

## Out of this slice

- Deploy. The output is a static folder with relative URLs. Any host must
  serve `.wasm` as `application/wasm` (all common ones do) for streaming
  compile. Choosing a host, a domain and how deploys run is a later task.
- Option C of question 2 (the whole app in the browser).
- Search engines and link previews. The page has a `<title>`, a
  description and a `<noscript>` paragraph; the text drawn in the terminal
  is not indexed as page text. A question for the deploy task.
