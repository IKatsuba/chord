# CHD-565: the list of agents chord offers

The build's specification, on the owner's answers (Q322–Q326, 2026-10-30). With
the setting absent, chord behaves as it does now. The tool's confirmation is the
one thing still open; nobody builds the tool before it is answered.

## Decisions

```json
{ "offeredAgents": ["claude", "codex", "my-agent"] }
```

| Question | Decision |
| --- | --- |
| Where it is set | The user's settings file, and an MCP tool that edits it. No screen and no key |
| Shape | `offeredAgents`, an array of names; its order is the order on screen |
| Files | The user's file only. In a project's file it is reported and left out, as `theme` is |
| What it governs | The start screen and `/new`'s completion. Nothing is refused |
| A listed CLI PATH lacks | Shown as `cursor · Cursor · not on PATH`; picking it gives today's refusal |
| An unknown name | Dropped, and named on the page |
| `[]` | Invalid: reported, and counts as absent, so the whole catalog shows |
| Only unknown names | No fall back: `No agents available` and a sentence naming the setting |

Rejected, one line each:

- A screen inside chord (`/agents`, `e` on the page): a new tick-and-reorder widget for a list set once.
- A later file replacing the list, joining lists, or a flag on each agent: the list is about a person, not a project.
- Governing `list_agents` too, or an allowlist refusing names: a saved team on another runtime would break, for a setting meant to shorten a menu.
- The PATH filter on a listed agent, or a dim row that cannot be picked: a name the person wrote would vanish, or `PickerList` would need disabled rows.
- A settings problem alone for an unknown name, an unknown row, or ignoring the whole key: the page would say nothing, or a typo could be picked, or one typo would cost the list.

### What does not change

- `chord agents` stays whole: it is where the names come from.
- `list_agents`, `open_agent`, team files and `propose_team` read `runtimes`, which stays whole.
- `chord <agent>`, `/new <agent>`, `--agent-command` and `--resume` work for a name outside the list. `@@` lists open recipients, never the catalog.
- `agent` only sets the opening highlight; outside the list, the first row is highlighted, as today. `-p` and every route that skips the picker do not read the list.
- A list of one still asks: the page never picks for the person.

## The setting

**`src/settings.ts`.** `offeredAgents` joins `USER_ONLY` (`:54`), so `loadSettings`
reports it in a project's file and `saveSetting` takes it. `mergeSettings` (`:362`)
copies key by key, so it needs its own line.

**A wrong element must cost the key, not the file.** `parseSettings` drops the path of
each issue, and deleting an array's element leaves a hole that fails again: after eight
rounds the whole file is ignored, `theme` with it. (Seen with `[1, "x"]` in
`teamSelection.constraints.agents`, today's behaviour there.) So the schema checks the
array as one value, an array of one or more non-empty strings, with its issue at
`offeredAgents`. `[]`, `[1]` and `""` each give one problem line and count as absent. A
test holds that `theme` survives each.

**A repeated name is dropped silently, its first place kept.** The screen is right
either way, and a problem line would be noise. It is not an unknown name.

**A pure module, `src/offered.ts`,** with its tests in `tests/offered_test.ts`:

```ts
function offeredAgents(
  listed: readonly ListedAgent[],
  offered: readonly string[] | undefined,
): { agents: readonly ListedAgent[]; unknown: readonly string[]; set: boolean };
```

- Absent: `agents` is `listed` as it is and `set` is `false`, so today's path is untouched.
- Set: the names in the array's order, repeats dropped, each its `listed` row; `unknown` holds the names `listed` lacks, in order.

`listed` is `listedAgents(agentCommands(layers))`, so a name a settings file gives a
command is known, a project's too. Such a name is unknown in a directory without that
project's file; the note says so there, and the owner's user-only choice accepts this.

**Unknown names are settings problems too,** one each, in the user's file:
`"offeredAgents": no agent named cdex, left out`. They go through `report` to stderr
and into the window's `warnings`, which hold every name; the page's note is the short form.

### The words

| State | Row | Style |
| --- | --- | --- |
| Some names unknown | `Unknown in offeredAgents: cdex, codx` | dim, a gap below the hint |
| More than fit | `Unknown in offeredAgents: cdex, codx, +2 more` | dim |
| Only unknown names | `No agents available`, then `offeredAgents in settings.json names no agent chord knows.` | dim, both |

**The note is one row, never wrapped.** A page's rows should not grow with a typo, and
the problem lines hold every name. A pure `unknownNote(names, width)` fits whole names
at `column − 2`, in order, and counts the rest as `+N more`, reserving that word's room;
at least one name always shows, and `CUT` cuts what is still too wide. The sentence in
the only-unknown state does not list names, so it does not repeat the note: no note there.

### Rows, against `startLayout`

`startLayout` takes a new `noteRows`, 0 or 2 (the gap and the row). The step is still
decided without it, so **a note never moves a window to another step**, and a list stays
the last thing to give way:

```ts
// `fits` and `cap` as today, from `around` without the note.
const note = noteRows > 0 && step !== 'none' && lines <= Math.min(fits - noteRows, cap);
// pageRows gains noteRows only where `note` holds.
```

A note that would cost a list row is not drawn; the problem lines still say it. In the
only-unknown state `lines` is 2, and the sentence counts as the list's second row.

## The MCP tool: a draft, not to be built yet

`offered_agents`, one tool that reads and writes. chord writes the file; the agent never
does, as with `propose_team`.

| Input | Means | Answer |
| --- | --- | --- |
| `{}` | Read the list, no question asked | `{ offered, file }` |
| `{ agents: ["claude", "codex"] }` | Replace the list | `{ offered, before, file, saved }` |
| `{ agents: null }` | Remove the key: the whole catalog again | same, `offered: null` |

`offered` is `null` where the key is absent. `agents` is required to be an array of one
or more non-empty strings, or `null`; `[]` is refused by the schema, and its description
says `null` is how to offer every agent, which is how a person gets the catalog back.

**Validation, first problem refused, nothing written:**

| Case | Answer |
| --- | --- |
| A name `listed` lacks | Refused: `Not an agent chord knows: cdex. chord agents lists them.` |
| A repeated name | Dropped, first place kept; `offered` shows what was written |
| A listed CLI PATH lacks | Written; the answer's `notOnPath` names it |
| A name only this project's file defines | Written; the answer's `onlyHere` names it, as it is unknown elsewhere |
| The same list as now | Nothing asked or written; `saved: false`, `unchanged: true` |
| No home, so no user file | Refused: `No settings file to save to` |
| A fork | Refused with `FORK_REFUSED`, as `propose_team` |

**Unknown names are refused at the call,** unlike in the file. An agent can correct
itself at once, while a typo written would only surface on the next start's page.
`listed` is the check, not `runtimes`: a window's `--agent-command` name is in `runtimes`
and would be unknown at the next start.

**Reading is from the file, at each call,** as `readTeamSelection` (`src/settings.ts:501`)
does, not from the window's copy, so a hand edit shows and a write starts from it. The
current list reads through `parseSettings`, so `[]` reads as absent.

**The file.** `saveSetting` (`src/settings.ts:830`) already refuses to overwrite a file
that is not valid JSON or not a JSON object, which reaches the agent as
`~/.config/chord/settings.json was not saved: it is not valid JSON`. It does not validate
other keys: a wrong `theme` stays as it was and is reported at the next start, which is
right, as the tool is not asked about it. Writes are atomic, and two windows are last
write wins, as `theme` is. `saveSetting` only sets, so removing the key needs a small
addition, and `src/AGENTS.md:5` gains the new writer, `saveOfferedAgents`.

**Callers: main alone.** `toolsOf`'s `person` case and `toolNames('person')`, so `/mcp`
lists it, with the fork refusal. Long-lived children, leads, members and tasks do not get
it: a person's own setting is between them and main. `ChordTool`, `CHORD_TOOLS` and the
headline switch in `src/ui/transcript/tools/chord.ts` gain it; the fork list in
`docs/guide.md:530` too.

**The running window.** Settings are read once: `listed` and `runtimes` are props from
`src/main.tsx:612` and `:647`, and `/new`'s rows are put in the app state at
`src/ui/app/App.tsx:452`. Nothing watches the file. So a successful write dispatches the
new list to this window's state, and **`/new` sees it at once**: a tool that says saved
while the list stays long reads as a bug. The start screen sees it at the next start, by
its nature. Other open windows and hand edits take effect at the next start, as every
other setting does. The said text: `Saved to ~/.config/chord/settings.json. /new offers
them now; the start screen at the next start.`

**Under `-p` the tool does not exist:** chord's server starts only for a window
(`src/main.tsx:589`), after `-p` has gone its own way.

### How a call is confirmed: the owner's choice

A read never asks. For a write:

| Option | What happens | Under `-p` | Under a runtime's auto or bypass mode | Trade-off |
| --- | --- | --- | --- | --- |
| **chord's box, every write** | `askPerson`, as `propose_team` | No tool | Still asks: `Conversation.ask` (`src/session/conversation.ts:2454`) reads no mode | The person always decides a change to their own file. One key more, on a rare action; on a runtime that also asks for MCP tools, two questions, as `propose_team` has today |
| **The runtime's tool permission alone** | Written with no box of chord's; a transcript row shows before and after | No tool | Written, nobody asked | One question at most, none under auto. Behaviour differs per runtime. A model, or text it read, can change a person's global setting unseen until it is done; the harm is bounded, as the list starts nothing and refuses nothing |
| **The box, with "don't ask again in this window"** | The box, plus an `allow_always` choice held in memory | No tool | Asks until the person picks it | Fewer questions for a person editing repeatedly, which is rare. New state and a new sentence, for little |

`--dangerously-skip-permissions` works only with `-p` (`src/main.tsx:122`), and its
`allowAll` answers the agent's requests in `src/session/oneshot.ts:110`, so it never
reaches a box of chord's.

**Recommendation: chord's box, every write.** It is the rule `propose_team` set for the
one other chord tool that writes a person's config: chord writes the file on the person's
yes. A runtime's mode says what the agent may do in a project, not what it may change in
the person's own settings. The cost is one key on something done rarely.

**What the box shows.** As `propose_team`: the call is served `pending` with the change
drawn on it, directly above an unchanged `SaveBox`, so before and after are in the
transcript and survive the answer. `SaveBoxQuestion` does not change.

```text
 ⏺ Offered agents · change
   ⎿  Now    every agent chord knows
      After  claude · codex · my-agent

 ✶ Waiting for you… (4s)

╭──────────────────────────────────────────────────────────────────────────────╮
│ Change the agents chord offers?                                              │
│                                                                              │
│ ❯ 1. Yes, in ~/.config/chord/settings.json                                   │
│   2. No, tell fake what to change                                            │
│                                                                              │
│ Esc to tell fake what to change                                              │
╰──────────────────────────────────────────────────────────────────────────────╯
```

- `{ agents: null }` shows `After  every agent chord knows`. A long list wraps under itself and is never cut, as what is being approved.
- Answered: `Saved to ~/.config/chord/settings.json`, or `Not saved; the person will say what to change`, with the agent told to end its turn and wait, as `proposeText` says.
- Withdrawn, by an interrupt or the turn's end: refused, `The person was not asked to the end; nothing was saved`.
- The box's keys are the permission box's; there is no new action.
