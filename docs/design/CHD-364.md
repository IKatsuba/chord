# CHD-364: a message steered into a running turn

Part of CHD-363. The owner decided that a message from another agent goes
into the receiver's running turn as it arrives (ACP's `_session/steering`),
automatically, and after the person's answer when the receiver waits on a
permission, a form or a link. A monitor's events and the person's own queued
prompts still wait for the turn's end. This is how that reads on screen. It
waits for the owner's approval before CHD-365 starts.

The captures are in `evidence/CHD-364/`. The `before-*` files are today's
chord on the fake agent's `agents` scenario: main opens `parser` and `docs`,
messages `parser` twice, and `parser` messages back twice while main's turn
runs. The `after-*` files are mocks built from those same captures, so only
what this design changes differs between them.

## The rule in one line

**A steered message is drawn where it went in, as today's `←` row, and
nothing else about it is new.** The queue then holds only what really waits:
the person's prompts, a monitor's events, and a message held behind an open
question.

## 1. The queue under the working line

Today (`80x24-before-parser-turn.txt`), main's message to a busy `parser`
waits under the working line until the turn ends:

```
 ⏺ Bash(deno task test tests/parse)
   ⎿  Running…

 ✸ Working… (10s · esc to interrupt)
 ← @main: I changed how a string at the...ests now and tell me only what fails.
```

**After:** the message never sits in the queue. It goes into the turn the
moment it arrives, so its queue row would show only for the steering
request's round trip. chord does not draw it for that round trip: a row that
blinks for a few milliseconds reads as a glitch. The message moves straight
to the transcript (part 2), and the working line stands alone
(`80x24-after-parser-turn.txt`):

```
 ⏺ Bash(deno task test tests/parse)
   ⎿  Running…

 ← @main
   ⎿  I changed how a string at the end of a line is read. Run the parser
      tests now and tell me only what fails.

 ✸ Working… (10s · esc to interrupt)
```

The queue's `←` row, as today, remains for:

- a message to a runtime that does not advertise steering (everything as
  today, owner's decision);
- a message held behind an open permission, form or link (part 4);
- a message whose steering request failed, which waits for the turn's end
  as today (part 5).

## 2. In the transcript: where the agent got it

The row is today's `←` row, header and body unchanged: `← @main`, or
`← @parser · fake` on main's side, with the text under `⎿`, folded after 6
lines. It is drawn **where chord handed it to the agent**: after whatever the
transcript holds at that moment, in the turn that is still running.

Main's side, mid-turn (`120x40-after-main-turn.txt`, against
`120x40-before-main-turn.txt` where both answers sat in the queue):

```
 → @parser
   ⎿  I changed how a string at the end of a line is read. Run the parser tests now and tell me only what fails.

 ← @parser · fake
   ⎿  Ran deno task test tests/parse: 2 failures, both in tests/parse/printer_test.ts.

 → @parser
   ⎿  The printer is fixed too; run the whole parser suite once more.

 ← @parser · fake
   ⎿  All 214 parser tests pass now.

 ✷ Working… (15s · esc to interrupt)
```

Against today's row after a turn (`120x40-before-main-end.txt`):

```
 ⏺ Waiting on parser.

 ← @parser · fake
   ⎿  Ran deno task test tests/parse: 2 failures, both in tests/parse/printer_test.ts.

 ⏺ Received the message from parser · fake.
```

- **No mark tells mid-turn from after-turn, and that is the point.** The
  position already says it: an after-turn row follows the agent's last
  reply and starts a new turn, while a mid-turn row sits among the turn's
  calls with the working line still going below it. Claude Code draws its
  own mid-turn messages the same way, as a plain prompt row where they went
  in. A tag such as `· mid-turn` would be one more word on every row in a
  busy team, and it would tell the person nothing they need to act on.
- **Where chord handed it over, not where the agent read it.** The agent
  reads it at its next step, which chord cannot see. So a call that was
  running when the message went in finishes above the row, and the agent's
  next step comes below it:

  ```
   ⏺ Bash(deno task test tests/parse)
     ⎿  214 passed, 0 failed

   ← @main
     ⎿  I changed how a string at the end of a line is read. Run the parser tests now and tell me only what fails.

   ⏺ Bash(deno task test tests/parse)
     ⎿  Running…
  ```

  That is honest: the row says when the message was given, and the call
  above it was already underway. If an adapter ever echoes the message back
  as a `user_message_chunk` at the step where it read it, that is the better
  place, and the row moves there with no change of shape.
- **The sender's `→` row loses `· queued`** when the message went straight
  into a turn: it did not wait (`→ @parser` above, against today's
  `→ @parser · queued`). `· queued` stays for a message that did wait,
  behind a turn or behind an open question.

## 3. The receiver's row in the agent list

**Unchanged.** A message that came in since the person last looked marks the
receiver's row `← message from @main`, as today, whether it started a turn
or went into one. The ranking stays CHD-167's: `● permission` first, then
`✗`, `←`, `✓`, `✻`. The person needs to know a message arrived that they
have not read; the list already says exactly that, and picking the agent
clears it.

`120x40-after-parser-turn.txt`, on `parser` while main works:

```
    main    fake · Fake Large with a 1M context window  ← message from @parser
    parser  fake · Fake Small                           ✻ working 9s
    docs    fake · Fake Large with a 1M context window  ● permission 9s
```

That is today's capture too: parser's messages to main were already marking
main's row while main's turn ran. A working receiver whose `←` hides its
`✻ working 41s` loses its timer until the person looks. I keep it that way:
the message is the more urgent news, and a second mark on the row would
crowd the narrow layout, where the row already fills 78 of 80 columns.

## 4. While the receiver waits on the person

A message to an agent that waits on a permission, a form or a link is held
until the person answers. It is the one case where a steered message sits
in the queue. Its row says why, with a dim `· after your answer` in the
header (`120x40-after-docs-held.txt`, against
`120x40-before-docs-permission.txt`):

```
 ✹ Waiting for permission… (6s)
 ← @main · after your answer: When the README section is done, add the new flag to docs/FEATURES.md.

╭──────────────────────────────────────────────────────────────────────────────────────────────────────────────────────╮
│ docs asks                                                                                                            │
│ Write notes.txt                                                                                                      │
```

At 80 columns the row is cut as every queue row is, and the tag survives the
cut because it is in the header (`80x24-after-docs-held.txt`):

```
 ✹ Waiting for permission… (6s)
 ← @main · after your answer: When the ...dd the new flag to docs/FEATURES.md.
```

- **Why the tag.** Without it, the row reads as today's queue: "this waits
  for the turn to end". With it, the person sees that their own answer is
  what holds a teammate's message, which is a reason to answer now. It is
  dim like the rest of the row: the permission box is what asks for
  attention, not the queue.
- **The same words for a form and a link.** Each is a question the person
  answers.
- **Answered:** the row leaves the queue and goes into the turn, drawn after
  the call the question was about (`120x40-after-docs-answered.txt`):

  ```
   ⏺ Write(notes.txt)
     ⎿  Allowed Write notes.txt · Allow

   ← @main
     ⎿  When the README section is done, add the new flag to docs/FEATURES.md.

   ✶ Working… (8s · esc to interrupt)
  ```

- **Rejected with Esc** is an answer too: the message goes in at once,
  after the rejected call.
- **Esc that interrupts the turn** with a message still held: it goes as the
  next turn once the interrupted one ends, as any message left in the queue
  does since CHD-360. Esc never puts it in the person's draft.
- **The list and the status line** are today's: the receiver's row keeps
  `● permission 12s`, which outranks `←`, and the status line keeps
  `● docs needs your permission · ctrl+x a to go`. When the person is not on
  the receiver, the held message is visible only after `ctrl+x a`, which is
  where they go to answer anyway.

## 5. The other states

- **Empty:** nothing new. A session with no other agents never steers.
- **A runtime without steering:** today's queue row and today's after-turn
  `←` row. Nothing marks the difference; the person sees the message wait,
  as now.
- **The steering request fails** (the turn ended just before it arrived, so
  Claude answers `promptRequired`, or the adapter errs): the message drops
  back into the queue and goes as the next turn, as today. No error is
  shown: nothing was lost, it only went the old way.
- **The receiver's agent exits** with a message in flight: today's
  `✗ exited`; the message is not delivered, as for any message to an
  exited agent.
- **Narrow (80×24):** shown above for each part. Nothing new is wider than
  today's rows.
- **Light and dark:** no new colour. The tag is dim, as the queue row is.

## Keys

None new. Steering is automatic (owner's decision 2). Esc, `ctrl+x a`, ↓
into the list and ctrl+o on a folded message work as today.

## For the owner to approve

1. A steered message has no queue row of its own; it appears straight in
   the transcript.
2. Its transcript row is today's `←` row, unmarked, drawn where chord handed
   it over (not where the agent read it).
3. The sender's `→` row drops `· queued` when the message went straight in.
4. The receiver's list row is unchanged (`← message from …` until seen).
5. A message held behind a permission, form or link waits in the queue with
   a dim `· after your answer` in its header, and goes in right after the
   answer.
