# CHD-610: riff's MCP calls, skills, elicitation and teams on screen

This draws the screen parts of riff part 8 from
[CHD-485](CHD-485.md#mcp-chords-own-tools-skills-and-instructions). Nothing
here is a new widget: every state below is drawn by a renderer or prompt
chord already has for other agents (owner's rule: riff's calls are drawn
from ACP `kind`, `title`, `rawInput`, `content` and `locations`, as every
agent's are). riff's job is to send the fields those renderers already
read. Colour roles are the existing ones from `src/ui/theme/theme.ts`:
`permission` for the ask box and its selection, `error` for a failed
result, `warning`/`error` for review text as in [CHD-608](CHD-608.md).
No new keys.

Today's screens on the plain fake agent, the baseline every unit is held
to, are under `evidence/CHD-610/main-*` (`mcpnote`, `mcpask`, `form`, at
120x40 and 80x24).

## U2: the `skill` tool call

ACP fields: `kind: read`, title `Skill <name>`, no `locations` (the
SKILL.md path is not the point of the row). The existing headline reader
turns a verb-first title into `Skill(<name>)`, as Claude Code draws its own
skill loads. The result is one line of `content`, not the skill's text:
the body would otherwise open with the SKILL.md front matter (`---`,
`name: …`), which reads as noise. ctrl+o shows `rawOutput` as for any call.

```text
 ⏺ Skill(release-notes)
   ⎿  Loaded skill release-notes (84 lines)
```

A later page, asked by offset:

```text
 ⏺ Skill(release-notes)
   ⎿  Loaded skill release-notes, lines 201–400 of 512
```

A resource of the skill names its file after the skill:

```text
 ⏺ Skill(release-notes)
   ⎿  Loaded skill release-notes, long.md, lines 201–210 of 210
```

Running: `⎿  Waiting…` as any call. An unknown name is the normal failed
call, in `error`:

```text
 ⏺ Skill(relase-notes)
   ⎿  Error: no skill named relase-notes
```

80x24 needs nothing different: the row is short.

## U3: an MCP server riff did not start

When riff skips a server (it fails to connect, listing its tools fails, or
a tool name libfx would rename), the window shows one agent message ahead
of the first prompt's reply, drawn as any agent text:

```text
 › list my notes

 ⏺ MCP server notes was not started: listing its tools failed (spawn
   notes-mcp ENOENT)

 ⏺ Here are your notes: …
```

One message per skipped server, plain text, the server's own name. A
stdio server's stderr tail, when the reason carries it, follows on its
own lines rather than run into the sentence, and is cut to its last few
lines so it never fills the screen.

An SSE server is not riff's to skip: riff takes no SSE (the MCP SDK
cannot bound an SSE connect), so chord holds it back before riff starts,
with the notice it shows for any agent that does not take a transport
(`N MCP server was not passed to riff, which takes them over … only: …`).
No `was not started` note is drawn for it.

## MCP calls in the transcript

riff titles an MCP call `mcp__<server>__<tool>` with the server's own
(original, unprefixed) name and the arguments in `rawInput`, as
claude-agent-acp does. The existing renderer then draws it as Claude Code
does, `<server> - <tool> (MCP)(key: value, …)`, with the result under `⎿`
(see `main-mcpnote-*`). A call to chord's own server is drawn as chord's
own call (`Monitor(…)`, `→ to @lead`, `Agent(name) · codex`) by the
`chordServer` match, so the title must carry the server name chord gave
riff, not libfx's sanitized prefix (`_2`, `_3` never reach the screen).

## U4: the permission prompt for an MCP call

The box is the existing permission box (`main-mcpask-*`): the raw title
`mcp__<server>__<tool>` on the first line, then the arguments as
`key: value` rows read from `rawInput`, then the options. riff's options
follow its ask mode as for shell (CHD-485 "Permission prompts"): `Allow`,
a session grant, `Deny`. The transcript row above it reads
`<server> - <tool> (MCP)(…)` with `⎿  Waiting…`. 80x24, the whole window:

```text
 › save a deploy checklist note

 ⏺ notes - save_note (MCP)(title: "Deploy checklist", tags: ["ops"])
   ⎿  Waiting…

 ››› Waiting for permission… (3s)

╭──────────────────────────────────────────────────────────────────────────────╮
│ mcp__notes__save_note                                                        │
│   title: Deploy checklist                                                    │
│   tags: ["ops"]                                                              │
│                                                                              │
│ Do you want to proceed?                                                      │
│ ❯ 1. Allow                                                                   │
│   2. Allow notes - save_note for this session                                │
│   3. Deny                                                                    │
│                                                                              │
│ Esc to reject                                                                │
╰──────────────────────────────────────────────────────────────────────────────╯

╭──────────────────────────────────────────────────────────────────────────────╮
│ ›                                                                            │
╰──────────────────────────────────────────────────────────────────────────────╯
  ? for shortcuts                                       fake · default · 1% used
```

The session grant covers that one tool of that one server with any
arguments, as Claude Code's `Yes, and don't ask again for <server> -
<tool> commands` (lead, settled with main): option 2 reads
`Allow <server> - <tool> for this session`, the server's original name.
In auto, an MCP call is `idempotent: false`, so one the admission rules do
not admit goes to the review and, on caution, incomplete or failure, asks
in CHD-608's reviewed box: the same title and argument rows, the review
text, `Allow once` / `Deny`, the countdown. Nothing MCP-specific.

A long argument (a file's content in a write) scrolls in the box as
`bigask` does today.

## U5: an MCP elicitation

Relayed into chord's existing form (`main-form-*`): the box in the prompt's
place, the message, the fields from `requestedSchema`, `Accept` /
`Decline`, `Esc to cancel`; a URL elicitation as the existing link prompt.
The header today reads `<agent> asks for input`, so riff's reads
`riff asks for input`, with ` · <title>` when the server's schema has one.
The answer row after it is the existing `riff asked: …` summary.

```text
 ››› Waiting for your input… (2s)

╭──────────────────────────────────────────────────────────────────────────────╮
│ riff asks for input                                                          │
│ Set up the deploy target                                                     │
│                                                                              │
│ ❯ * Project name                                                             │
│ …                                                                            │
│   Accept   Decline                                                           │
│                                                                              │
│ Type to fill in · ↑↓ to move · Esc to cancel                                 │
╰──────────────────────────────────────────────────────────────────────────────╯
```

The form never names the MCP server that asked. Naming it would change
the window for every agent and is left out of this slice (lead).

## U6: riff in a team

Nothing new on screen. riff as lead or member is one more runtime in the
existing team screens: the header reads `riff · ChatGPT · <model>`, the
agents list and `Agent(name) · riff` rows name it by runtime as they name
`codex` or `claude`, and its calls to chord's own server (`send_message`,
`spawn_task`, `list_agents`) draw as chord's own calls. Checked through a
fixture under `tests/fixtures/teams/fake/` at both sizes: lead and member
rows, a message each way, a member's ask reaching the lead's window.
