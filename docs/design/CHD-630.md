# CHD-630 — `@chorded/cursor-cloud-acp` 0.2.0: more of what `@cursor/sdk` allows

The owner, 2026-11-15 (task comment): the package serves everything
`@cursor/sdk` 1.3.1 allows that maps onto ACP; MCP servers a client sends are
**not** forwarded to the cloud agent and stay accepted and named unreachable,
as today (CHD-622, Q5). The version goes to 0.2.0 and chord's pin follows;
the owner publishes the package before chord's next release.

This file fixes the mapping, what chord already reads of it, and what a
person sees. The package's own design is `docs/design/CHD-622.md`; the
survey behind the task is `docs/design/evidence/CHD-624/survey.md` §2.4.
Captures of today's screens are in `docs/design/evidence/CHD-630/`.

Four points are open for the owner, marked **(Q1)** to **(Q4)**, collected
at the end. Units that depend on one wait for its answer.

## The mapping

it would back, whether chord reads that method, and what the package does.

"chord sends none": `src/acp/connection.ts` requests only `initialize`,
`auth/status` and `session/new`, `load`, `resume`, `list`, `fork`, `prompt`,
`set_config_option`, `set_mode`, `set_model` and `set_title`; `chord acp`
(`src/acp_agent.ts`, `src/acp/agent_app.ts`) reads none of the left-out

come back when chord grows a reader (archive from `/resume` is the
survey's F9 idea, not this task).

`initialize` gains `agentCapabilities.auth: { status: {} }` and nothing
else: no `sessionCapabilities.title`. `authMethods` and `authenticate`'s

## The account: `auth/status` and `auth/status_update`

### What is answered

The package resolves the key as it does for a session (CHD-622,
"Credentials"): nonempty `CURSOR_API_KEY`, else an unexpired keychain entry,
else none. With a key, `Cursor.me({ apiKey })` gives the account
(`SDKUser`). Nothing is cached across resolutions but the last answer, below.

| Resolution | `state` | `accounts` |
| --- | --- | --- |
| a key, and `Cursor.me` answers | `authenticated` | one account, below |
| no key | `unauthenticated` | none |
| a key `Cursor.me` refuses (`AuthenticationError`, a key for another backend among them) | `unauthenticated` | none |
| the keychain fails or does not answer in 10 s, or `Cursor.me` fails otherwise (network, rate limit) | `unknown` | none |

The one account, `active: true`:

| Field | Value |
| --- | --- |
| `label` | `Cursor` |
| `description` | where the key came from: `CURSOR_API_KEY`, or `keychain, expires <YYYY-MM-DD>` from the entry's `apiKeyExpiresAtMs` (`keychain` alone when it has none) |
| `name` | `userFirstName` and `userLastName`, joined by a space, each only when sent; left out when neither is |
| `email` | `userEmail`, when sent |
| `organization` | left out: the SDK gives a team id, never a team name |

`apiKeyName` is left out: it is the key's name in Cursor's dashboard, not the
person, and on a key `login` minted it is the SDK's default. A team or
service key has no user, so its account reads `Cursor · CURSOR_API_KEY`.
No field carries the key or any part of it.

`credentials.ts` then gives the source and expiry beside the key; that is
the package's own change, not chord's.

### When a push goes out

The package keeps the last status it answered or pushed. Every resolution —
`auth/status` itself, and the one `session/new`, `session/list`,
`session/resume` and `session/load` already make (`serve.ts:146`, which
calls `Cursor.me`, so no request is added) — computes the status again; when
it differs from the kept one, `auth/status_update` carries the new one,
before that request's answer or error. No push before the first
`auth/status` has been answered: there is nothing yet to update.

The package never polls. `login` and `logout` run in another process, a
terminal of the person's, so the serving process learns of them at its next
resolution: in chord, the next `/new cursor-cloud`, resume or reopen. A
signed-out start (`signedOut()`, -32000) pushes `unauthenticated` first when
the kept status said otherwise. `authenticate` keeps refusing with the
`login` command (`serve.ts:331`): the owner put sign-in in the package's
own command.

## The title: `session_info_update`

The cloud agent's `SDKAgentInfo.name` is the session's title; `summary` is
not used (a paragraph, not a title). Cursor names an agent from its first
prompt when `Agent.create` is given no `name`, as the package creates them;
the SDK cannot rename one afterwards.

The package sends `session_info_update { title, updatedAt }` — `title` the
name trimmed, `updatedAt` `lastModified` as RFC 3339 — whenever the name
differs from the last it sent for that session in this process, and never an
empty name or `null`:

- **resume and load**: from the `Agent.get` `reopen` already makes
  (`serve.ts:283`), after the session is held and before the replay and the
  resumed line, so the title is there with the first row **(Q4)**;
- **after a run ends**: `Agent.get` beside the `listArtifacts` the turn
  already asks for, raced with a cancel the same way, before the answer
  (late updates are dropped, `turn.ts`); a failed `get` sends nothing and
  says nothing;
- **`session/new`**: nothing; the agent has no name before its first
  prompt.

`session/list` already gives `title` and `updatedAt` (`serve.ts:510`),
unchanged.

### `/rename` against cursor-cloud

No `sessionCapabilities.title`, so chord's `/rename` keeps the title in
chord alone (`src/session/conversation.ts:2794`, `takesTitles` at
`src/session/session.ts:941`): `Renamed to <title> in chord only`. That is
chord's behaviour today; nothing in chord changes. chord keeps the later of
a rename and an agent title (`src/session/sessions.ts:262`), so:

- a rename before the first run ends is replaced by Cursor's name at its end;
- a rename after it stays for the rest of the process;
- every resume or reopen brings Cursor's name back, under (Q4)'s drawn
  answer.

The title shows where CHD-629 put it: `/status`'s `Title` row (mock above;
`not given` until the first run ends), the terminal title (OSC 7501) and the
next `/resume` picker. The header keeps what it opened with.

## Cost: `usage_update`

`agent.getUsage()` (or `Agent.getUsage(agentId)`) gives `AgentUsage`: the
whole agent's `usage` and `cost`, and each run's (`RunUsage`, by
`run-<uuid>`). `UsageCost` has `rawCostCents` (the undiscounted token cost)
and `chargedCents` (what was billed; 0 on plan-included, BYOK and credit
use). The SDK says cost is eventually consistent: it "can lag briefly after a
run ends", and is absent when not yet reported.

ACP's `usage_update` requires `used` (tokens in context) and `size` (the
context window). **The SDK backs neither**: its types have no context window
anywhere (`ModelListItem` is id, name, description, aliases, parameters,
variants), and `TokenUsage` is per run, many model calls added up, not what
is in context. So a cost can only reach chord with values for `used` and
`size` the SDK does not give. That is the open point.

### What chord does with it today

- The package answers each prompt with the run's tokens
  (`PromptResponse.usage`, `turn.ts:153`).
- `costFromTokens` (`src/session/enrichers.ts:63`) prices that answer at the
  model's price when chord's price data knows the model, and sends chord's own
  `usage_update` with `used` from the tokens and `size: 0`, marked filled.
  Most of Cursor's model ids are not in that data, so most turns get no cost.
- Once an agent sends a `usage_update` with a cost of its own,
  `agentCost` (`src/session/enrich.ts:452`) stops chord's estimate for the
  session; the package's update goes out before the answer, so the turn it
  prices is never also estimated. A turn before the first cost the package
  sends can still be estimated, and `/cost` then says `(part chord's
  estimate)`.
- A cost is a sum so far. chord turns it into each turn's share by what
  `src/cost_counts.ts:19` says the agent counts from: `opening` or `session`.
  cursor-cloud is not listed, so the first figure after a resume is the
  turn's own only by chance.
- A `size` of 0 is chord's own "no window known": chord keeps a size it
  filled as 0 (`src/session/enrich.ts:445`), and the status line draws no
  context part for it (`src/ui/status/status.ts:330`).

### (Q1) What the update carries

- **C1. No `usage_update`.** Tokens in the answer only, as today. `/cost`
  shows tokens, and a cost only where chord's price data knows the model.
  No chord change.
- **C2. `usage_update` after each run, before the answer: `cost` the whole
  agent's (`AgentUsage.cost`), `used: 0`, `size: 0`.** The figure is
  Cursor's, across every run the agent has had, wherever started; a cost
  that lagged at one run's end is in the next run's total. `used: 0` is not
  true (ACP calls it the tokens in context); chord shows no context part for
  `size: 0`, so the screen shows nothing false, but `chord acp` passes the
  zero on. Needs (Q3).
- **C3. As C2, `used` the run's input plus output tokens** (chord's own
  guess, `contextFrom`): the same number chord fills in today for agents that
  give only tokens, but sent as the agent's, unmarked. A cloud run's input
  counts every model call, so it reads fuller than the context is.
- **C4. As C2, but the cost counted from this opening**: the runs started
  since the session was opened, from `RunUsage.cost`. A cost still missing at
  the opening's last run is lost.

When `cost` is absent from `getUsage` at a run's end, the update is not
sent (an omitted cost leaves chord's last one; there would be nothing else
in it).

### (Q2) Which figure

`rawCostCents` — the tokens' price, what Claude's adapter's
`total_cost_usd` and chord's own estimate mean — or `chargedCents`, the bill,
0 for use a plan includes. Either goes as `{ amount: cents / 100, currency:
"USD" }`.

### (Q3) chord's one line

C2 and C3 need `cursor-cloud: 'session'` in `COST_COUNTS`
(`src/cost_counts.ts:19`), C4 needs `'opening'`: a change in chord beyond the
pin, small, but chord's. Without it chord still adds turns within one
opening; the first figure after a resume is then taken as that turn's alone
(`src/session/turn_costs.ts`), which under C2 counts every earlier run
again.

## Left out, and why

- `session/status`, `session/archive`, `unarchive`, `delete`, `logout`: chord
  sends none of them and `chord acp` reads none (above).
- Rename (`session/set_title`), system prompt, fork: the SDK cannot, for
  cloud agents.
- MCP: unchanged, by the owner's answer.
- Run status in `session/list`: ACP's list item has no status field; a
  `_meta` key nobody reads is not added.
