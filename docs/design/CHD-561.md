# CHD-561: Claude's session messages as rows in the parent

From claude-agent-acp 0.95 (0.99.1 is what chord pins), a client that declares
subagents no longer gets the Agent/Task call, nor a SendMessage call that
reached an announced child, as tool calls in the parent. It gets
`session_message`s, which chord's root reducer ignores, so those rows and a
foreground child's reply would vanish. The owner's answer to Q335 is to draw
them as rows in the parent, keeping what a person sees today.

Read from the adapter's source (`src/native-subagents.ts`,
`src/subagent-replay.ts`, PRs #1405, #1424, #1479) and its scenario snapshots,
not seen live. Today's screens replay the old wire by hand on origin/main.

```

| | Old wire, in the parent | New wire, in the parent |
| --- | --- | --- |
| Launch | `tool_call`, title the short task, content the prompt | `subagent_update`, then `session_message` (id: the launch's tool id, sender: this session, recipient: the child) |
| Foreground answer | The call's result, replacing the prompt | `session_message`, id `<launch id>:reply`, sender: the child, recipient: this session |
| Hand-back mode | The call's result | `session_message`, id: the hand-back's tool id, sender: the child, recipient: this session, and no `:reply` |
| Background launch | Result `Async agent launched successfully.` | Nothing after the launch |
| SendMessage that resumed a child | `tool_call`, title `SendMessage`, result JSON | `session_message`, id: the call's, sender: this session, recipient: the child |
| SendMessage that resumed no announced child | As above | The same `tool_call`, once, with its final status |
| A call a permission request showed | `tool_call` | Still a `tool_call` with its updates |
| A failure or a stop | The call's status and text | Nothing but the child's `idle` state, with `error.message` when the SDK gives one |
| Title and description | Role, short task | Name, else short task, else role; the role, unless it is the title |

## The rows

Two rows, both CHD-387's message rows, with no shape of their own: the
headline, the `⎿`, the same body, the owner's whole-and-wrapped rule.

```
 → to Agent(<title>)
   ⎿  <what was sent, dim>

 ← from Agent(<title>)
   ⎿  <what came back, dim>
```

**Why these and not a copy of today's row.** Today's `Find(the session layer)`
is the short task cut at its first word by the tool headline, and a named child
has no short task any more. Since the block's headline now says that task
itself, a copy would read `Find(the session layer)` over `Agent(Find the
session layer)`. Arrows say what the row is and who it is with, in a shape the
person already reads for chord's own agents.

**Direction comes from the wire, never from the id's shape.** A message is
outgoing when its sender is the session it arrived on, and incoming when its
recipient is. `:reply` means nothing to the screen; a hand-back draws the same
way with no such suffix.

### The launch

The `→` row stands above the child's block, where today's row stands, though
it arrives after the `subagent_update`:

- It goes directly before its child's block, or, when that block stands in a
  run of back-to-back subagents, before the first of the run. Rows of a
  parallel launch come in arrival order, and **the blocks stay one group**. A
  row between them would break `Running 2 agents…` into two blocks.
- It folds after `MESSAGE_LINES` (six) rows with `… +N lines (ctrl+o to
  expand)`, as a `spawn_task` prompt does: **a launch prompt is a task's prompt,
  often pages long**, not the short words CHD-387's rule was made for.

### The reply

The `←` row is appended where it arrives, under the block, and the `→` row stays:
asked, worked, answered, in that order. Today the reply replaces the prompt
above the block, so this is the one move in the geometry. Its text is whole, as
markdown, by the owner's 2026-10-17 rule for message bodies (settled below). Each message is upserted by its id, as `messaged` already does for a
child: content left out keeps the text, `null` or none clears the row.

120x40 and 80x24 alike (`rows/reply-120x40.png`, `rows/reply-80x24.png`):

```
 → to Agent(Find the session layer)
   ⎿  Find where chord hands each session/update to its listeners.

      Report the file that owns the routing, with line numbers.

 ⏺ Agent(Find the session layer)
   ⎿  Done (2 tool uses · 1s)

 ← from Agent(Find the session layer)
   ⎿  Routing lives in src/acp/connection.ts, in the relay at line 412.

      The listeners are kept in src/session/conversation.ts.

 ⏺ It is the relay in connection.ts.
```

### A message to a child

- **It resumes a finished child:** a `→` row where it arrives, whole, as CHD-387
  says for a sent message. The block stays where it stood and goes back to
  running, as it does today. This row shows more than today's: who it went to
  and what it said, in place of the JSON.
- **The child is still running, live:** the adapter sees no resume, so it sends
  the `tool_call` after all, and **today's `SendMessage` row stands unchanged**.
  A resumed session may draw that same message as a `→` row (below).
- **It reached no announced child,** or a permission request showed the call:
  today's `SendMessage` row too. A permission-shown launch keeps its tool row
  and gets a `→` row as well, because the adapter sends both; it is rare, and
  chord does not guess one away.

`rows/message-120x40.png`, `rows/message-80x24.png`:

```
 ⏺ Now I will ask it for the tests.

 → to Agent(Find the session layer)
   ⎿  Now find the tests that cover it.

 ››› Working… (3s · esc to interrupt)
```

### A background child

A `→` row and the block, with no `←`: the wire has no reply for it. Its ending
is the block's and CHD-479's `item_ended` line, as today. A background child that
hands a report back gets a `←` row where it arrives, between turns too.

`rows/background-120x40.png`, `rows/background-80x24.png`.

### The child fails or is stopped

No `←` row. The `→` row stays, so the person still reads what was asked, and the
block says how it ended. Today the folded view shows the failure's text in the
call row, so **a block with a `→` row draws `endNote`'s failure text folded as
well**, under `Failed`, in `error`, wrapped. Blocks without one, Codex's among
them, stay as they are. With no `error.message` it reads `Failed (…)` alone, and
a stop reads `Cancelled (…)`.

`rows/failed-80x24.png`, `rows/stopped-80x24.png`:

```
 → to Agent(Run the test suite)
   ⎿  Run bun test and report what fails.

 ⏺ Agent(Run the test suite)
   ⎿  Failed (3 tool uses · 12s)
      The build still fails.
```

### Folded and ctrl+o

The rows stand outside the block, so **folding the block touches neither**. In
ctrl+o's view the launch prompt unfolds, and the block opens as it does today:
its task, its work with `← from <agent>` for a message it got, its ending.
A prompt and a sent message therefore read twice in this view, once as sent and
once as the child's own history; that is the view's purpose, and today's
already repeats the prompt while the child runs.

`rows/open-120x40.png`, `rows/open-80x24.png`.

### Inside a child

A child's own launch and message rows draw in its work in ctrl+o's view, by the
same rules; its folded block still shows only calls. A child's outgoing view of
a hand-back, on its own session, sender itself and recipient its parent, draws
nothing there: the parent's `←` row says it. `messaged` must not fold either kind
as a message the child received, and its first message must stay its prompt.

A nested launch no longer arrives as a call, so a parent's `N tool uses` counts
the nested child once rather than twice.

### A resumed session

- **chord's own record:** replayed through the same reducer, so a new session
  reads as it did live. `session_message` at the root must stay in the record.
  **An old record keeps its tool calls and draws today's rows,** beside blocks
  titled by role, and needs no migration.
- **The adapter's replay,** should chord show one: the same messages, upserted by
  id, in the adapter's order. A launch's child history comes right after its
  launch, so a SendMessage's `→` row can land after the work it caused, and a
  message that reached a running child draws as a `→` row, not the live tool row.
  chord does not reorder them.

## What the data cannot give

## Colour roles

No new role, from `src/ui/theme/theme.ts`, as CHD-387:

- `→`, plain: a `session_message` is already delivered, so it is never the dim
  or `error` arrow.
- `←`, plain; `to` and `from` dim; the name bold, in whatever colour
  `useAgentColour` gives `Agent(<title>)`.
- Bodies dim, markdown's styling on top; the fold line dim.
- The failure's text `error`, as under `Failed` in ctrl+o's view.

## Keys

No new action and no new key. `ctrl+o` (`app:toggleTranscript`) unfolds a launch
prompt as it does every fold, read from the binding. Selection and copy treat
the rows as they do any message row. The background view's `Enter to go to its
call` goes to the block, which has not moved.

## Settled

The lead's decisions on what this page left open:

1. **The background view's name: title first, for Claude only.** On the new wire
   `description ?? title` would make the role the name, `Explore` where it says
   `Find the session layer` today, in the view and in `item_ended`. The wire
   cannot tell the two apart, as Codex's standard `subagent_update` and the draft
   shape both put the task in `description`. So a Claude child's name reads title
   first, and **no other agent's name moves**.
2. **The role stays out:** `Agent(Find the session layer)`, with no `· Explore`
   note. The title tells siblings apart, and the note would be right for Claude
   only, as other agents' description is a whole task.
3. **A long reply stays whole,** under the owner's 2026-10-17 rule for message
   bodies, though today's folds at three rows and a subagent's report can be
   long. The lead states this in the report so the owner can object; the
   alternative is six rows with ctrl+o, as the launch prompt.

## Checked on the unit

fe440ac2 through 10decf74 on OpenTUI 0.8.1, on the fake, at 120x40, 80x24 and
50x20, captured in `evidence/CHD-561/rows/unit/`. Where it differs from this
page, the unit is right:

- A failure's text also shows in a group's row, not only under a lone block: it
  is the same case.
- A launch is the first `→` to a child. Every later one stays whole and goes
  where it came, and breaks a group if it lands between blocks.
- **A launch prompt is clipped by layout at six rows,** drawn whole and counted
  in laid-out rows, so a box the clip cuts has no closing edge above the fold
  line. **While clipped, no code block in it has a key or a button,** not even one
  wholly above the fold: `┌─ sh ───┐`, and `ctrl+x b` says `No code block to
  pick`, so a person can never copy or run lines they have not seen. `ctrl+o`
  brings them all back, and a prompt that fits keeps them.
- A Claude child's name reads title first by its adapter's name, from
  `initialize`'s `agentInfo.name`, not from its first message.
- Not run: a resume through the adapter's own replay. A resume from chord's
  record draws as live did.
